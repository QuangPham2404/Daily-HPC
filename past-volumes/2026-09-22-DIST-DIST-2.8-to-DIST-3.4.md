## 0. Concise Summary

Today's volume sits at a hinge point in the curriculum. The point-to-point module ends with its characteristic failure mode — **deadlock** (DIST-2.8) — and the MPI Foundations module begins with the system whose careful semantics we have been studying from the inside: **what MPI actually is** (DIST-3.1), **communicators** (DIST-3.2), **ranks** (DIST-3.3), and **datatypes** (DIST-3.4).

The deadlock lesson formalizes what last week's blocking-semantics and protocol material implied: a distributed program hangs permanently when its wait dependencies form a cycle — every rank in some set blocked, each waiting for a message only another member of that set will send. The canonical trap is a ring exchange where every rank does a standard blocking `MPI_Send` *before* its `MPI_Recv`. Whether that program deadlocks is deliberately implementation-dependent, because the standard-mode send may complete either eagerly (after an internal copy) or via rendezvous (only after the receiver posts its match). Code that "works on my laptop" can deadlock on the cluster — and the fix ladder (reordering, `MPI_Sendrecv`, non-blocking `MPI_Isend`/`MPI_Irecv`, buffered mode) teaches the general principle: never let communication dependencies form a cycle, and never write code whose correctness depends on which side of an implementation choice you land.

That is the perfect motivation for asking what MPI is: a *specification*, not a piece of software — a consensus API and semantics contract (MPI Forum, since 1994) that many independent implementations (Open MPI, MPICH and its derivatives, vendor stacks) realize with different internals. Communicators add the safety machinery we hinted at during message matching: every communication is namespaced by a *context*, so independently written software layers cannot cross-match each other's messages. Ranks give each process a logical identity that is deliberately decoupled from physical placement — the seed of Module 12's rank-placement material. Datatypes let you describe non-contiguous memory (ghost columns, matrix tiles, arrays of structs) once and hand the layout to the library, which either packs it or drives the NIC's scatter-gather engine directly.

The developments section covers the biggest change to "what MPI is" in two decades: **MPI 5.0 (June 5, 2025) standardized an Application Binary Interface**, so a binary compiled against one MPI implementation can run against another's `libmpi_abi.so`. **MPICH 5.0.0 (February 2026)** is the first stable implementation release with full MPI-5 including the ABI, and **Open MPI 6.0.x (currently in pre-release)** adds the Forum ABI for C applications. Together they turn today's "API standard, not a binary standard" lesson into live 2025–2026 engineering news.

## 1. Learn the Concepts

### 1.1 Deadlock (DIST-2.8)

**The problem.** Last week we built a precise model of what a blocking send and receive wait for (DIST-2.2), how messages are matched (DIST-2.4), which transfer protocol the library picks (DIST-2.5), where bytes physically sit in the meantime (DIST-2.6), and who advances a non-blocking operation (DIST-2.7). Deadlock is the failure mode that emerges when those waits are composed: a distributed program is **deadlocked** when a set of processes is blocked such that each is waiting for an event that only another process *in that set* can produce — and none of them can proceed to produce it. No timeout, no error message, no crash: the job simply stops making progress, usually at 100% CPU (spinning on internal polling) or 0% (blocked in the OS).

**A reasoning tool: the wait-for graph.** Draw one node per process, and an edge P → Q when P is blocked waiting for something only Q can provide. Under a fixed set of dependencies, the program is permanently stuck exactly when this graph contains a **cycle**. This is the same cycle-detection idea used for deadlock in operating systems (processes and resources) — here the "resources" are matching receives, eager buffer space, and internal handles. The graph is a *thinking tool*, not a library feature: MPI defines no portable runtime deadlock detection, so the discipline of predicting cycles before you write the code is the real defense.

**The canonical trap.** Every HPC programmer eventually writes a neighbor exchange in a ring:

```c
/* each rank: send to the right neighbor, receive from the left */
MPI_Send(buf, N, MPI_DOUBLE, right, 0, MPI_COMM_WORLD);
MPI_Recv(buf, N, MPI_DOUBLE, left,  0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
```

Every rank enters `MPI_Send` first. What happens next depends on the *standard-mode send semantics* from DIST-2.2: `MPI_Send` may complete as soon as the send buffer can be reused — which happens either **eagerly** (the library copies the message into an internal buffer and returns) or via **rendezvous** (the call blocks until the receiver has posted the matching receive). The MPI standard states this explicitly and even warns about the consequence (MPI 1.1, §3.5, *Semantics of point-to-point communication*): when standard-mode sends are used, "a deadlock situation may occur where both processes are blocked because buffer space is not available."

So the ring above is:

- **Working code** on a configuration where N is small enough for the eager protocol: each send copies out, returns, and the receives then match — no deadlock, *by luck*.
- **Deadlocked** where the message size crosses the eager/rendezvous threshold (last week we estimated why real thresholds sit in the tens of kilobytes): every rank blocks inside `MPI_Send` waiting for a receive that the rank to its left will never post, because *it* is stuck in its own send. The wait-for graph is a full cycle around the ring.

The deep lesson is the one MPI has been teaching all week: **the standard deliberately leaves this behavior implementation-dependent, so correct code must be correct under both behaviors.** A program whose correctness depends on the send returning eagerly is not a correct MPI program — it is a program that has not been caught yet. The deterministic debugging trick that follows: substitute `MPI_Ssend` (synchronous send, completes only when the receiver has posted its match) in tests to force the rendezvous-like path and expose latent ordering bugs in a small run instead of a 4,000-node hang.

**The fix ladder.** From crudest to most general:

1. **Reorder (odd/even).** Even ranks send first, odd ranks receive first. At every instant, half the pairs can make progress, so no cycle forms. Works, but pattern-specific and easy to break when the topology changes.
2. **`MPI_Sendrecv` / `MPI_Sendrecv_replace`.** One call performs a blocking send and a blocking receive *as if concurrent*: the implementation launches both directions and completes when both are done. For neighbor-exchange patterns this is guaranteed to make progress, because the library is free to post the receive internally while the send is outstanding. This is exactly what the call was designed for.
3. **Non-blocking communication (the canonical modern answer).** Post the receive first (or both operations together), do useful work, then complete:

   ```c
   MPI_Request req[2];
   MPI_Irecv(rbuf, N, MPI_DOUBLE, left,  0, MPI_COMM_WORLD, &req[0]);
   MPI_Isend(sbuf, N, MPI_DOUBLE, right, 0, MPI_COMM_WORLD, &req[1]);
   /* ... compute on interior cells while the transfer runs ... */
   MPI_Waitall(2, req, MPI_STATUSES_IGNORE);
   ```

   Since MPI-4.0, `MPI_Isendrecv` combines the pair in one call. Recall the DIST-2.3 rule that keeps this correct: touch neither buffer until completion. This pattern does double duty — it removes the deadlock *and* buys communication/computation overlap, which is why Module 11 exists.

4. **Buffered mode: `MPI_Bsend` + `MPI_Buffer_attach`.** The sender completes once the message is copied into a user-attached buffer, decoupling it from the receiver entirely. The costs are explicit memory and a hard failure mode: if the attached buffer is too small, the call raises an error rather than silently blocking — a visible failure, which is honestly better than a hang. Usually worse than option 3, but useful when restructuring around non-blocking calls is impractical.

**The second family: resource deadlocks.** Cycles in "who waits for whose message" are the famous case, but blocking dependencies also run through *internal* resources:

- **Eager-buffer / unexpected-message exhaustion.** If many ranks eagerly spray a rank that has not yet posted receives, the receiver's unexpected-message queue fills; senders then block waiting for buffer space or a rendezvous handshake. The wait-for cycle now passes through internal buffer state — invisible in the source code. This class typically appears only at scale, which is what makes it nasty.
- **Outstanding-request limits.** Every non-blocking operation consumes an entry in the implementation's request machinery; internal limits exist and are implementation-defined.
- **Communicator/context exhaustion.** `MPI_Comm_dup` in a loop without `MPI_Comm_free` consumes a finite, implementation-defined context-ID space; long-running coupled codes have hit this in practice. (Communicators are the next topic — this is one of the reasons they must be freed.)
- **Collective mismatch.** If some ranks call `MPI_Bcast` and others call `MPI_Reduce` on the *same communicator*, the program is erroneous, and the usual symptom is a hang: collectives match by order within the communicator's context, not by tag, so a mismatched sequence leaves every rank waiting at a collective that never completes. This is a *correctness* bug that *looks* like deadlock — and it is exactly the failure mode communicators were designed to prevent from happening accidentally between independent software layers.

**Diagnostics.** When a job hangs: attach a debugger to one stuck rank, read its backtrace, and ask the wait-for-graph questions — *who is this rank waiting for, and what is that rank waiting for?* Follow the cycle; note whether the edges pass through messages or internal resources (a rank blocked in `MPI_Send` to a rank that is computing happily is a matching bug, not a cycle). Runtime verification tools such as Jülich's MUST automate this class of checking (mismatched collectives, unsafe buffer use) for small runs. And keep in mind that MPI itself will not tell you — the standard defines the semantics, not a watchdog.

**HPL connection (brief).** HPL's look-ahead panel factorization and its chunked panel broadcasts exist precisely to keep the dependency graph acyclic and busy: ranks deep-copy panel pieces early and immediately return to trailing-update GEMMs instead of sitting in blocking broadcasts whose data they will not need for thousands of FLOPs yet. We will dissect that machinery in Module 15; for now, read it as "a production code engineered around everything in this section."

### 1.2 What MPI is (DIST-3.1)

**The problem it solved.** Before 1992, nearly every parallel machine shipped its own communication library — Intel's NX, IBM's EUI, portable systems like PVM, vendor message-passing layers — and each had different calls, semantics, and idioms. Parallel codes were written against one library and could not move to another machine without rewrites. The community response was the **MPI Forum**, formed after a 1992 workshop at Williamsburg: a consortium of vendors, national laboratories, and universities (over 40 organizations) working by consensus. The result, **MPI 1.0, was ratified in May 1994** — a 228-page specification. The versions since: MPI-2.0 (1997; dynamic processes, one-sided RMA, parallel I/O), MPI-3.0 (2012; non-blocking collectives, new RMA, Fortran 2008 bindings), MPI-4.0 (June 2021; persistent collectives, partitioned communication, sessions, large-count interfaces), MPI-4.1 (2023; corrections), and **MPI-5.0 (June 5, 2025)** — by now a ~1,200-page document, as Martin Schulz's "State of MPI" talk documents in its version-growth chart.

**What MPI is, precisely.** MPI is a **specification**: an application programming interface, language bindings, and — critically — a *semantics contract*. It is not software. An MPI *implementation* is a separate product that provides the specified functions and honors the specified semantics: **MPICH** (Argonne) and its derivative family (Intel MPI, Cray MPICH, MVAPICH2 from Ohio State), **Open MPI** (the open consortium), and vendor stacks. The implementations differ enormously inside — network devices, shared-memory transports, protocol thresholds, collective algorithms, tunables — and everything we studied in Modules 1–2 (eager versus rendezvous, buffering, progress engines) lives *inside* implementations of this one standard. The standard's job is to specify behavior tightly enough for portability while leaving exactly the right freedom for optimization; the standard-mode send's "may or may not block" is not sloppiness — it is that philosophy in one sentence.

**The programming model.** MPI prescribes SPMD, distributed-memory execution: your single program is launched as N processes, each with a private address space. There are no shared variables between processes; all interaction happens through library calls — point-to-point, collectives, one-sided, and I/O. The non-overtaking matching rule (DIST-2.4) is part of the contract, which is why deterministic reasoning about asynchronous code is possible at all.

**API standard ≠ ABI standard — the distinction that drives today's news.** MPI standardized the *source* interface. At the binary level, nothing was standardized: an executable compiled against Open MPI could not run against MPICH, because symbol sets, type sizes, calling conventions, and above all **handle representations** differed. A concrete example from the ABI literature: MPICH provides *compile-time constant* predefined handles (so `MPI_COMM_WORLD` is a literal integer in the header), while Open MPI's predefined handles in C are not compile-time constants. Either approach is fine at the API level; they are irreconcilable at the binary level. Every MPI application therefore had to be recompiled — for each implementation, and often per major version. For thirty years this was simply a law of nature: MPI is an API standard, not a binary standard. In June 2025 that sentence stopped being true — see the developments section.

**Why this design won.** Message passing maps onto any hardware: within a node, implementations route messages over shared memory; across nodes, over whatever fabric exists — TCP, InfiniBand, libfabric/UCX. A standard with careful semantics let a huge software ecosystem (ScaLAPACK, PETSc, HPL itself, and thousands of application codes) become portable across machines that did not exist when the code was written. That longevity is the payoff the 1994 designers were aiming at.

### 1.3 MPI communicators (DIST-3.2)

**The problem.** Suppose your code calls a parallel math library (a BLACS/ScaLAPACK-style linear algebra layer, or PETSc) while also doing its own point-to-point messaging. Both layers use integer tags. If all messages lived in one flat namespace, a library-internal message with tag 7 could match *your* receive with tag 7, and the program would silently corrupt itself. Distributed-memory codes need **namespaces for communication**.

**The mechanism.** An MPI **communicator** is two things bound together: an ordered **group** of processes, and a **context** (an internal context ID). Every communication call — point-to-point or collective — names a communicator, and message matching (DIST-2.4) actually uses the key **(context, source, tag)**. Context IDs are generated by the implementation and are never visible to you, which is the point: two independently developed software layers using two different communicators *cannot* see each other's messages, no matter what tags they pick. This is the machinery that makes layered parallel software possible at all.

**The core operations.**

- `MPI_Comm_size(comm, &n)` and `MPI_Comm_rank(comm, &myrank)` — the queries every MPI program starts with. On `MPI_COMM_WORLD`, the initial communicator spanning the whole job, this is the process count and your global ID.
- `MPI_Comm_dup(comm, &newcomm)` — same group, **fresh context**. This is the standard courtesy contract: a well-behaved library duplicates the communicator it is handed and uses the duplicate internally, so its traffic is invisible to the caller. Now you know *why* that convention exists.
- `MPI_Comm_split(comm, color, key, &newcomm)` — partition the ranks by `color` (one new communicator per color) and order the ranks within each by `key`. The workhorse for building sub-teams: solver components, node-local groups, topology-aware pieces.
- `MPI_Comm_group` / `MPI_Group_incl` / `MPI_Comm_create` — explicit group construction when split-by-color is not expressive enough (collective over the parent communicator).
- `MPI_Comm_free(&comm)` — release the group binding and its context. Ties directly back to §1.1: contexts are a finite internal resource, so a communicator created per iteration and never freed will eventually exhaust them.
- **Inter-communicators** — a communicator spanning *two* groups, for manager/worker and coupled multiphysics patterns (mention only; they appear later in practice).
- `MPI_Comm_split_type(comm, MPI_COMM_TYPE_SHARED, ...)` — MPI-3's way to get "all ranks on this node," which we use in the next section.

**Virtual topologies.** `MPI_Cart_create` overlays an N-dimensional grid on a communicator (with periodic flags), and `MPI_Cart_coords`/`MPI_Cart_rank` translate between rank and coordinates. Two details matter conceptually. First, `MPI_Cart_sub` splits a Cartesian communicator into lower-dimensional sub-communicators — the rows and columns of a 2-D grid. Second, the `reorder` flag *permits* the implementation to renumber ranks for communication locality — the first appearance of topology-aware placement in the API, and a signpost toward Module 12.

**The HPL connection.** HPL arranges its ranks into a **P × Q process grid** (chosen roughly square, P·Q = number of ranks) and works with row- and column-communicators derived from it: the panel factorization broadcasts travel along one axis, trailing updates along the other (full treatment in DIST-15). The entire structure is `Comm_split`-style machinery — when you read HPL tuning papers that talk about process grids, this section is the machinery underneath the words.

**Cost model.** Creating a communicator is a collective operation with nonzero cost — context allocation, internal setup, and typically synchronization. The engineering rule: build your communicator hierarchy **once** at startup, reuse it for the program's lifetime, and free what you do not need. Creating communicators inside a per-timestep loop is both slow and a context leak.

### 1.4 MPI ranks (DIST-3.3)

**The definition.** A **rank** is the index of a process in a communicator's group: an integer from 0 to N−1, stable for the lifetime of that communicator. Your rank in `MPI_COMM_WORLD` is assigned by the launcher; ranks in derived communicators are renumbered by the split/create logic. The same physical process is rank 42 in the world, rank 3 in its node-local communicator, and rank 0 in its row communicator — **rank identity is always relative to a communicator**, and every rank-based argument in MPI (a reduction root, a broadcast source) is interpreted in the communicator named in the call.

**The central discipline: ranks are logical, placement is physical.** The MPI standard says *nothing* about where rank k executes. Rank 1 and rank 2 might be two threads of one core, processes on opposite NUMA domains of one node, or processes on nodes separated by three switches. Two consequences, one for correctness and one for performance:

1. **Correctness:** an MPI program must be valid for *any* legal mapping of ranks to hardware — exactly parallel to the send-semantics rule from §1.1. Code that only works when ranks 0 and 1 share a node is not correct MPI code.
2. **Performance:** communication cost between rank i and rank j depends entirely on their physical relationship — shared memory (same node), PCIe or NVLink hops (same node's GPUs), or network hops and possible congestion (different switches). The *cost matrix* is physical; the *numbering* is logical. Misalignment between them is one of the most common silent performance bugs in HPC — Module 12 (rank placement, affinity, topology) exists entirely to close that gap.

**The local-rank idiom on GPU clusters.** The standard pattern for one-process-per-GPU applications shows how rank logic and physical binding meet:

```c
MPI_Comm shm, shm_is_not_used;          /* node-local communicator */
MPI_Comm_split_type(MPI_COMM_WORLD, MPI_COMM_TYPE_SHARED, 0, &shm);
int local_rank;
MPI_Comm_rank(shm, &local_rank);
/* typical binding: each rank claims its node's local_rank-th GPU */
cudaSetDevice(local_rank);
```

`MPI_COMM_TYPE_SHARED` (MPI-3) gives you the ranks sharing your node without any out-of-band scheduler information; the local rank then selects the GPU. Variants of this idiom appear in essentially every MPI+CUDA application, including HPL-MxP-style benchmarks.

**Rank order shapes collective algorithms.** Collectives organize their internal trees and rings over the group's rank sequence — a reduction flows "toward rank 0" by convention of the call's root argument, not because rank 0 has privileges. The tree/ring geometry implied by rank order is why renumbering ranks can change collective performance even when the physical placement is unchanged — a Module 4 and DIST-12.6 topic, filed now as a reminder that rank order is a performance variable, not just a naming scheme.

**What you control (preview).** Launchers expose placement controls (Open MPI's `--map-by`/`--bind-to`, Slurm's `--distribution`, and equivalents in other stacks), and Modules 12–13 turn them into a systematic method. The rule at this stage: **before interpreting any scaling measurement, know what each rank physically owns** — which core, which NUMA domain, which GPU, which NIC. A code that looks communication-bound is sometimes simply a mis-mapped one.

### 1.5 MPI datatypes (DIST-3.4)

**The problem.** Real scientific data is rarely contiguous in memory: a matrix row is contiguous but a *column* is strided; a stencil halo is a border strip; particle arrays are arrays of heterogeneous structs. Without a description mechanism you have two bad options: many tiny messages (each paying the latency tax from DIST-1.6/1.7) or manual packing into a scratch buffer (an extra copy, plus code you maintain). MPI's answer: **describe the memory layout once as a datatype, and let the library do the work**.

**The formalism: the type map.** Every MPI datatype is ultimately a **type map**: a sequence of pairs

```
Typemap = { (type0, disp0), (type1, disp1), ..., (typen-1, dispn-1) }
```

where `typei` is a basic type and `dispi` is a byte displacement from the start of the buffer. A predefined datatype is the trivial case: `MPI_INT` is `{(int, 0)}`. From a type map the standard derives the **lower bound** (minimum displacement), the **upper bound** (maximum displacement + size, with an alignment epsilon), and the **extent** (ub − lb) — the stride between successive copies of the datatype when a message contains more than one. Extent is where nearly all datatype bugs live, as we will see.

**The constructor ladder**, from least to most general:

| Constructor | Layout described |
|---|---|
| `MPI_Type_contiguous(count, old)` | `count` copies of `old` back-to-back |
| `MPI_Type_vector(count, blocklength, stride, old)` | `count` equal blocks, `stride` elements apart |
| `MPI_Type_indexed[_block]` | blocks at arbitrary displacements |
| `MPI_Type_create_struct` | per-block (blocklength, displacement, type) triples |
| `MPI_Type_create_subarray` | an N-dimensional sub-box of an N-D array |
| `MPI_Type_create_resized` | same type map, overridden lb/ub (fixes the extent) |

**Worked example — a halo column.** Take a 2-D stencil solver with local grid `u[ny+2][nx+2]` in row-major C layout (one ghost cell on each side). The west halo column is `u[i][0]` for `i = 1..ny` — `ny` doubles, each `nx+2` doubles apart. One derived datatype replaces `ny` individual sends:

```c
MPI_Datatype col;
MPI_Type_vector(ny, 1, nx+2, MPI_DOUBLE, &col);
MPI_Type_commit(&col);
/* send the whole west border in one call */
MPI_Send(&u[1][0], 1, col, left, TAG_HALO, comm);
```

**The extent gotcha, concretely.** The extent of `col` is `(ny−1)·(nx+2) + 1` doubles — the span from the first to the last selected element. If you send *two* of these datatypes (count = 2), MPI tiles them `extent` apart, which for a column type is *not* what you want for two adjacent columns (they should advance by one element). The fix is `MPI_Type_create_resized(col, 0, 1*sizeof(double), &col_adj)` — same type map, extent forced to one element — after which count = 2 sends two side-by-side columns correctly. This is the single most common derived-datatype bug: **the extent is a stride, and the default stride is the type's span, not your intent.**

**A struct example.** For `struct Partstruct { char c; double d[6]; char b[7]; }`, `MPI_Type_create_struct` takes blocklengths `{1, 6, 7}`, types `{MPI_CHAR, MPI_DOUBLE, MPI_CHAR}`, and displacements obtained with `MPI_Get_address` (never `offsetof` alone across compilers — the MPI-provided address arithmetic is the portable path). One send of 1,000 particles is then one call with count 1000 and the struct type — versus packing loops or a thousand byte-count calls.

**Lifecycle.** Create (local, cheap) → `MPI_Type_commit` (a local operation that finalizes the datatype for communication) → use in *any* communication call, including collectives → `MPI_Type_free`. As with communicators: commit once at setup, reuse for the run; constructing and committing inside a hot loop is wasted work.

**What the implementation actually does** — this is where datatypes reconnect to Module 2. The datatype engine flattens the type map into a list of (offset, length) segments. Then one of two things happens:

1. **Pack path:** segments are copied into a contiguous bounce buffer, transmitted, and unpacked at the receiver — extra copies on both sides, exactly the DIST-2.6 taxonomy.
2. **Scatter-gather path:** the segment list is handed to the transport as a scatter-gather descriptor — an RDMA write with a gather list, or a series of shared-memory copies — so no intermediate buffer exists on the fast path.

So derived datatypes are not just sugar: on a modern RDMA transport they can drive the NIC directly. The trade-off is CPU cost in the pack/flatten engine for deep or complex type maps — extremely irregular layouts can still be faster with explicit packing (or, on GPUs, with a packing kernel — see below).

**Large counts (MPI-4).** The classic MPI interfaces take the element `count` as a C `int`, capping a single message at 2³¹−1 elements. For 8-byte doubles that is 16 GiB — but for 4-byte integers or short types it is 8 GiB or less, and modern GPU-scale buffers cross it. MPI-4.0's answer was a parallel set of `_c`-suffixed interfaces taking a 64-bit `MPI_Count` (e.g., `MPI_Type_create_struct_c`), rather than changing existing signatures — a compatibility decision the Forum discussed at length, as Schulz's State-of-MPI slides recount. The takeaway for daily work: know both spellings exist; new code that might carry huge buffers should use the `_c` forms.

**GPU note (preview of Module 6).** When buffers live in GPU memory, non-contiguous layouts get expensive: CUDA-aware MPI implementations commonly process derived datatypes by staging data through host memory or packing on the host, so the "free" strided send you enjoyed on CPUs can silently become two extra device-to-host copies. A common high-performance pattern is to reshape communication into contiguous chunks with a small GPU packing kernel. File this as a reason Module 6 exists; we will quantify it there.

**ABI note (bridge to the developments).** The MPI-5 ABI standardizes handle representation — `MPI_Datatype`, like all MPI handles, becomes a fixed-width integer with values *fixed by the standard* (its Appendix A), rather than an implementation-chosen value. Datatypes are a concrete place where "API standard" and "binary standard" meet.

## 2. Key Developments / News

### 2.1 MPI 5.0 (June 5, 2025): the standard grows a binary interface

**What happened.** The MPI Forum released MPI 5.0 on June 5, 2025 — a major revision whose headline change, per the standard's own preface, is "the addition of a standard Application Binary Interface (ABI) to allow interoperability of different implementations."

**What technically changed.** The ABI (version 1.0) fixes the binary layer of the C bindings: a specified `mpi.h` and a shared library named `libmpi_abi` (`libmpi_abi.so` on Linux). An application compiled against one conforming implementation — via the `mpicc_abi` wrapper convention — can be *run* against another conforming implementation's `libmpi_abi.so` without recompiling. Predefined handles become fixed integer values defined by the standard (its Appendix A), resolving the MPICH-versus-Open-MPI handle-representation divergence from §1.2. The rules are strict and worth knowing exactly: the application must be dynamically linked; the launcher (`mpiexec`) must match the runtime library — you cannot mix one implementation's launcher with another's library; an application must use exactly one ABI (a forum-ABI binary cannot be mixed in one job with binaries using an implementation's native ABI); and features deprecated in MPI-3.1 or earlier are excluded from the ABI header, cleaning the binary surface.

**Why it matters.** This dissolves the thirty-year "recompile for every MPI" law from §1.2. Binary-distributed HPC software — Spack packages, container images, Python wheels for mpi4py — can be built once and run against whatever MPI the center provides, including the center's vendor-tuned stack. The Forum's ABI working group had prototyped the design both inside MPICH and as the external Mukautuva translation layer, documenting use cases (binary packaging, non-C languages, implementation-agnostic tools) in its 2023 paper.

**Connection to today's curriculum.** This is DIST-3.1 materialized: the entire development is about the precise boundary between "API standard" and "binary standard" that defines what MPI *is*.

**What to watch.** Adoption breadth: each implementation ships the ABI on its own schedule (see below), and early releases have ABI bugs — the Open MPI documentation explicitly advises testing with current releases of both sides when interoperating. Also watch whether Fortran lands on the Forum ABI (Open MPI's position: wait-and-see, possibly via external Fortran bindings).

### 2.2 MPICH 5.0.0 (February 4, 2026): first stable full-MPI-5 release

**What happened.** Argonne's MPICH team released MPICH 5.0.0 on February 4, 2026 — the first stable release of the 5.0.x series and the first stable open-source implementation release claiming full MPI-5 support, including the new ABI specification (`MPI_VERSION`/`MPI_SUBVERSION` now 5/0). A 5.0.1 point release followed within weeks.

**What technically changed.** Beyond the ABI (available in source builds via `--enable-mpi-abi`), the release notes list more robust **MPI sessions** support, and — directly relevant to last week's DIST-2.5 material — a **native rendezvous mode for the CH4:OFI netmod**: rendezvous implemented natively over libfabric rather than layered on generic operations. It also adds the MPI-5 Fortran `LOGICAL1/2/4/8/16` datatype kinds and software reduction support for `bfloat16` (the latter via the `MPIX_` extension prefix — an implementation extension, not standard). The 5.0.1 fixes are a useful reality check on young ABI code: among them a big-endian collective data-loss bug and an ABI-build breakage accidentally introduced in a 5.0.1 release candidate.

**Why it matters.** MPICH is the root of a large implementation family — Intel MPI, Cray MPICH, and MVAPICH2 all descend from it, and the earlier MPICH ABI Initiative already made that family mutually binary-compatible. MPICH adopting the Forum ABI early puts the standard ABI on the mainline path for that whole lineage.

**Connection.** DIST-3.1 (the implementation ecosystem) and DIST-2.5 (rendezvous as a live implementation concern, not just a textbook mechanism).

**What to watch.** Whether vendor derivatives (Intel MPI, Cray MPICH, MVAPICH2) pick up the Forum ABI in their 2026–2027 releases — that is the test of whether `libmpi_abi` becomes the default binary layer of HPC.

### 2.3 Open MPI 6.0.x (pre-release, September 2026): the Forum ABI arrives in the other major stack

**What happened.** The Open MPI project's v6.0.x series — in pre-release as of this writing, with the project's front page announcing "v6.0.0 release coming soon" — adds support for building C MPI applications against the MPI-5.0 standard ABI.

**What technically changed.** Per the v6.0.x changelog and new documentation: a single Open MPI installation provides **both** its own long-standing ABI (`libmpi`, via `mpicc`) **and** the Forum ABI (`libmpi_abi`, via `mpicc_abi`), built by default. The constraints from §2.1 apply verbatim — dynamic linking required, matching launcher required, and no mixing the two ABIs within one job. Two deliberate limitations stand out: **C only** (no `mpifort_abi` / Fortran Forum-ABI wrapper — a documented wait-and-see position while no other implementation ships the Fortran ABI, possibly to be served by external Fortran bindings projects), and **Open MPI's non-standard extensions are absent** from `libmpi_abi` by design, since no other implementation provides them. The SC25 "State of the Union" BoF slides add an elegant engineering detail: the ABI `mpi.h` is generated from the MPI standard's machine-readable definition via the Forum's `pympistandard` tooling, and mpi4py's author contributed testing and fixes.

**Why it matters.** With both MPICH and Open MPI shipping `libmpi_abi`, the compile-once/run-anywhere-MPI story is no longer a standardization hope — it is two mainstream runtimes. One nuance to keep straight: ABI support and full MPI-5 *API* conformance are separate tracks (Open MPI 5.0.x conformance, for reference, is MPI-3.1 plus partial MPI-4.0), so check the release notes for exactly what a given version implements.

**Connection.** DIST-3.1's API/ABI distinction, and DIST-3.8 (MPI implementations — two modules ahead) where this ecosystem gets its own dedicated volume.

**What to watch.** The final v6.0.0 release notes: its exact MPI-5 API conformance level, and whether Fortran Forum-ABI support materializes via external bindings.
