## 0. Concise Summary

Yesterday's topic (GPU-8.1) established *why* PCIe is no longer sufficient as the only interconnect for tightly coupled multi-GPU systems. Today we study what actually replaces it, in five steps.

First, **peer-to-peer (P2P) memory access**: the mechanism by which one GPU dereferences a pointer that lives in another GPU's memory, with no staging through host RAM. This is the semantic primitive — every dedicated GPU fabric, from NVLink to xGMI, ultimately presents itself to software as "you can load/store your peer's memory, quickly."

Second, **NVIDIA NVLink**, the dominant proprietary scale-up interconnect: its link anatomy, its bandwidth accounting (a place where marketing numbers and per-direction numbers routinely get confused), and its five-then-six generation trajectory from 160 GB/s on Pascal to 3 TB/s per GPU on the Vera Rubin generation announced this year.

Third, **NVSwitch**, the switch ASIC that turns point-to-point NVLink into an all-to-all fabric. Direct links scale as n(n−1)/2 and die at eight GPUs; a switched fabric is what makes a 72-GPU rack behave as one accelerator with 130–216 TB/s of aggregate communication.

Fourth, **AMD's Infinity Fabric / xGMI**, a different philosophy: instead of a switch, a fully connected mesh of seven links per GPU, giving hardware-enforced coherence across the whole 8-GPU baseboard.

Fifth, **the rest of the ecosystem** — Intel's Xe Link (built for Aurora, now without a merchant successor after the Falcon Shores cancellation), the OCP OAM module standard that AMD, Intel, and others share, CXL on the host side, and the new open UALink specification that wants to be the vendor-neutral equivalent of NVSwitch.

In the developments section we cover three events with direct bearing on these topics: NVIDIA's **NVLink Fusion** opening the NVLink ecosystem to third-party silicon (May 2025), the **Vera Rubin / NVLink 6** platform entering full production (March 2026), and the **UALink 1.0** specification ratification (April 2025) as the open counterweight.

The through-line: at modern GPU scale, the interconnect *is* the computer. Compute per die roughly doubles per generation, but model and problem sizes grow faster, so the fabric — its bandwidth, its topology, and its memory semantics — increasingly determines what is efficient and what is merely possible.

## 1. Learn the Concepts

### 1.1 GPU peer-to-peer memory access (GPU-8.2)

**The problem.** In the classic CUDA model, each GPU owns a private memory space, and the host is the only entity that can address all of them. If GPU 1 needs data that resides on GPU 0, the naive path is: GPU 0 → PCIe → host pinned buffer → PCIe → GPU 1. Every byte crosses the PCIe root complex twice, consumes host memory bandwidth, adds latency, and burns CPU cycles on staging. On a PCIe 4.0 x16 link (~32 GB/s per direction), a 1 GB halo exchange between two GPUs becomes two serialized 31 ms transfers instead of one 31 ms transfer — and on top of that you pay kernel-driver overhead and cache pollution.

**The mechanism.** Peer-to-peer access removes the staging hop. Under CUDA's Unified Virtual Addressing (UVA), all device memories and host memory share one 64-bit virtual address space, so a pointer is globally meaningful — the question is only whether the hardware can route a transaction for that address to the right physical memory. P2P support means the driver programs each GPU's page tables (and the PCIe/interconnect address-decode windows) so that a virtual page allocated on GPU 0 maps to GPU 0's physical HBM even when the access originates from GPU 1's SMs.

The API contract is small and worth knowing by heart because it appears in every multi-GPU codebase:

```cpp
int ok;
cudaDeviceCanAccessPeer(&ok, 0, 1);      // query: can 0 reach 1 directly?
cudaSetDevice(1);
cudaDeviceEnablePeerAccess(0, 0);        // 1 now maps 0's allocations
cudaSetDevice(0);
cudaDeviceEnablePeerAccess(1, 0);        // and vice versa (it is asymmetric!)
```

Three properties matter:

- **Enabling is directional and explicit.** GPU A mapping GPU B's memory does not give B access to A. Both sides must opt in. Once enabled, *all* current and future allocations on the peer become visible, which is why the CUDA documentation warns that subsequent `cudaMalloc` calls on the peer get more expensive — every allocation must be mapped into every enabled peer's page tables, an overhead that grows multiplicatively with the number of peers. Modern code can avoid this with the Virtual Memory Management APIs, allocating peer-visible regions explicitly rather than globally.
- **There is a fan-out limit.** Per the CUDA Programming Guide, on non-NVSwitch systems each device supports a system-wide maximum of eight peer connections. Switched fabrics lift this limit — a first hint of why NVSwitch (topic 8.4) is not just "more bandwidth" but a qualitative change.
- **The platform can silently break it.** On Linux, bare-metal PCIe P2P is unsupported when the IOMMU is enabled (risking silent device-memory corruption), and PCIe Access Control Services (ACS) — which redirects point-to-point traffic through the CPU root complex — can quietly destroy P2P performance even when the feature "works." Anyone who has debugged a multi-GPU box where `cudaDeviceCanAccessPeer` returns true but bandwidth is 3 GB/s has met ACS.

**Two communication styles over the same mapping.** Once P2P is enabled you get, essentially, two modes:

1. **Bulk copy (DMA):** `cudaMemcpy(dst_on_1, src_on_0, ...)` with `cudaMemcpyDefault`. UVA lets the runtime see both pointers are device pointers on *different* devices, and it issues a peer DMA — the copy engines of the GPUs move data directly across the interconnect with no host staging. If P2P is unavailable, the same call transparently falls back to a staged copy through host memory; the API never lies to you, it just gets slow.
2. **Direct load/store:** a kernel running on GPU 1 simply dereferences `p0`. Each such access becomes a remote memory transaction — one interconnect traversal plus one fetch in GPU 0's memory system. Data that the remote GPU's L2 has already cached can be served from that L2, which is why fine-grained P2P can beat bulk copies for small, reused structures (halo cells, reduction partials, locks and flags).

**Measured reality.** NVIDIA's `p2pBandwidthLatencyTest` sample (in cuda-samples) prints bandwidth and latency matrices for every GPU pair. A representative run on a 6× A100-PCIe host, where adjacent pairs carry NVLink bridges and the rest are PCIe-only, shows the stakes:

| Path | Unidirectional bandwidth | Round-trip latency |
|---|---|---|
| NVLink-bridged pair, P2P enabled | ~190–275 GB/s | ~2.2–2.5 µs |
| Same pair, P2P disabled (host staged) | ~15–19 GB/s | ~19–21 µs |
| PCIe-only pair, P2P enabled | ~9–11 GB/s | ~2.2 µs |
| PCIe-only pair, P2P disabled | ~10–16 GB/s | ~20 µs |

Read the columns carefully: enabling P2P on a *PCIe-only* pair barely helps bandwidth (PCIe is the ceiling either way) but still cuts latency roughly 8×, because even a host-staged copy requires two interconnect traversals plus a CPU detour. And the ~19 GB/s ceiling for host-staged traffic on this host shows the extra tax of crossing the root complex. This is exactly the gap that dedicated interconnects (next topic) attack.

**Why an HPC engineer cares.** Nearly every multi-GPU communication library is built on P2P as its fast path: NCCL uses CUDA P2P between same-node GPUs and selects ring or tree algorithms based on the P2P topology it discovers; AMD's RCCL does the same over xGMI; HPL-MxP and distributed HPL implementations broadcast pivot panels and reduce partial results over these paths; HPCG's SpMV exchanges halo rows through them. When someone says a workload "doesn't scale past one node," the first question to ask is whether the per-GPU communication volume exceeds what the P2P fabric can absorb — a theme we will quantify when we reach bisection bandwidth (GPU-8.8).

### 1.2 NVIDIA NVLink (GPU-8.3)

**Why a new protocol, not just faster PCIe.** PCIe is a general-purpose, host-centric I/O fabric. Three of its properties clash with GPU-to-GPU traffic: (1) topology — GPUs normally hang off a root complex owned by the CPU, so peer traffic may traverse it (the ACS problem above); (2) semantics — PCIe is a bus-style transaction protocol without cache-coherent or fine-grained remote-atomic operations between peers; (3) economics — PCIe lane counts and per-lane rates are set by a broad standards body whose cadence lags GPU memory-bandwidth growth by years. NVLink is NVIDIA's answer: a purpose-built, GPU-centric interconnect that treats GPU-to-GPU traffic as the primary case, with the host connection as one among several peers.

**Link anatomy.** An NVLink "link" is a bundle of differential-pair sublinks — effectively 16 lanes organized as two unidirectional 8-lane groups (one per direction). Each generation raises the per-lane signaling rate and/or the number of links per package. The numbers that matter are easily double-counted, so let us fix the accounting convention once: **NVIDIA's headline "NVLink bandwidth per GPU" is the sum over all links of the per-link rate counting both directions.** Equivalently, the sustained per-direction throughput is half the headline number.

| Generation | Architecture (year) | Links per GPU | Per link, per direction | Headline per-GPU bidirectional total |
|---|---|---|---|---|
| NVLink 1 | Pascal P100 (2016) | 4 | 20 GB/s | 160 GB/s |
| NVLink 2 | Volta V100 (2017) | 6 | 25 GB/s | 300 GB/s |
| NVLink 3 | Ampere A100 (2020) | 12 | 25 GB/s | 600 GB/s |
| NVLink 4 | Hopper H100 (2022) | 18 | 25 GB/s | 900 GB/s |
| NVLink 5 | Blackwell B200 (2024) | 18 | 50 GB/s | 1,800 GB/s |
| NVLink 6 | Vera Rubin (announced 2026) | 36 | — | 3,000 GB/s |

Two observations from this table. First, NVLink 3→4 (A100→H100) gained nothing per link; the 1.5× improvement came purely from 12→18 links. Second, NVLink 5 doubled the per-direction per-link rate to 50 GB/s, which is where Blackwell's 2× comes from — 18 links × 50 GB/s × 2 directions = 1,800 GB/s. For context, a PCIe 5.0 x16 slot moves 64 GB/s per direction (128 GB/s bidirectional), so NVLink 5 per GPU is roughly 14× PCIe 5.0 x16 on the headline number, per NVIDIA's own comparison.

**Link aggregation.** A single GPU's links do not have to go to distinct peers. Between exactly two GPUs (for example, a dual-GPU workstation with an NVLink bridge), all links can bond into one fatter pipe: two A100s with a 12-link bridge get the full 600 GB/s between them. On an 8-GPU HGX board, by contrast, each GPU's 18 links fan out across the fabric — which is where the switch, topic 8.4, becomes unavoidable.

**Semantics beyond bandwidth.** NVLink is not merely "fast PCIe." It carries cache-coherent traffic, remote memory operations, and (in recent generations) remote atomics, which let a kernel on GPU A perform an atomic add on a word in GPU B's memory without a round trip through software. This is the substrate that CUDA's P2P API (previous topic) presents to you, and it is also what lets a GB200 superchip present Grace CPU DRAM and Blackwell HBM as one address space over NVLink-C2C (the on-package sibling of NVLink, 900 GB/s between Grace and its two Blackwell dies).

**A note on honesty in comparisons.** When you read interconnect comparisons — NVLink vs. xGMI vs. UALink — always check three things: (1) bidirectional-sum vs. per-direction convention, (2) per-GPU aggregate vs. per-link rate, (3) theoretical SerDes rate vs. realized application bandwidth. Vendors do not exactly lie, but they do choose the convention that flatters them, and a factor of 2 or 7 hides in each choice. We will see a concrete example of theoretical-vs-realized in the xGMI numbers below.

### 1.3 NVSwitch and switched GPU fabrics (GPU-8.4)

**The full-mesh wall.** With direct links only, a system in which every GPU has a dedicated link to every other GPU needs n(n−1)/2 pairwise links, and each GPU must spend n−1 of its own link budget on its peers. At n=8 that is 28 links and 7 per GPU — feasible, and exactly what AMD does (next topic). At n=16 it is 120 links and 15 per GPU; the SerDes count, package pins, board routing, and power scale quadratically while the benefit per added GPU scales linearly. Full mesh dies somewhere between 8 and 16 GPUs, permanently.

**What a switch changes.** A switch ASIC terminates every GPU's links on one side and provides non-blocking any-to-any forwarding on the other. Each GPU needs only enough links to reach *the switch*, not every peer; the switch's radix (port count) and its internal forwarding capacity determine the domain size. Two consequences:

1. **Topology becomes uniform.** With direct links, GPU pairs that happen to share a bridge see peak bandwidth and others see PCIe — software had to care *which* pair it was. With a switch, every pair sees the same path through the same fabric. The CUDA eight-peer limit disappears; every GPU in the domain can P2P-access every other.
2. **The fabric becomes a shared resource.** Aggregate capacity now depends on switch bisection, not just link counts — the seed of GPU-8.8.

**Generations.** The first NVSwitch (2018, Volta era) exposed 18 NVLink ports per chip; twelve of them stitched the DGX-2's sixteen V100s into the first single-domain 16-GPU system. The second and third generations (Ampere, Hopper) grew port counts and per-port rates — an HGX H100 board places four third-generation NVSwitches between its eight GPUs, absorbing all 144 links (8 GPUs × 18). The qualitative jump came with Blackwell: the NVLink 5-generation switch chip exposes 144 NVLink ports with 14.4 TB/s of non-blocking switching capacity, supports domains of up to 576 GPUs, and — critically — moved out of the baseboard and into the rack.

**Anatomy of GB200 NVL72.** The GB200 NVL72 rack is the canonical switched-fabric system and worth memorizing as a picture:

```
  18 compute trays                     9 NVLink switch trays
  (each: 1 Grace CPU +                 (each: 2 NVSwitch ASICs,
   2 Blackwell GPUs,                    144 NVLink ports each)
   NVLink-C2C 900 GB/s)
      72 GPUs × 18 links = 1,296 links  →  9 trays × 144 ports = 1,296 ports
        copper backplane connects every GPU to every switch tray,
        2 links per GPU per tray
```

Every Blackwell GPU sends 2 of its 18 links to each of the 9 switch trays. Any GPU pair communicates at the full per-GPU rate (1.8 TB/s class) regardless of location in the rack; the aggregate all-to-all bandwidth is 130 TB/s. A liquid-cooled NVL72 draws on the order of 120 kW (the GB300 variant up to ~142 kW) — the interconnect is a first-class consumer of that power, and the copper backplane (flat cables tens of centimeters long) is a deliberate choice to avoid optical transceivers' power and cost at in-rack distances.

**In-switch computation: SHARP.** Since the Hopper generation, NVSwitch also performs *in-network reductions*: when a collective (an all-reduce, a reduce-scatter) flows through the switch, the switch ASIC itself adds the operands instead of merely forwarding them, collapsing O(n) forwarded traffic into a single result stream. NVIDIA reports ~4× bandwidth efficiency for FP8 reductions with the Blackwell-generation SHARP support. For an HPL-MxP-style workload whose time is dominated by FP16/BF16 all-reduces after each distributed GEMM, in-switch reduction changes the arithmetic of scaling: the reduction cost grows with the *result* size rather than the *input* size times the fan-in.

**What to watch next.** A switched fabric converts the question "which GPU is my neighbor?" into "what is the bisection bandwidth of my fabric?" — which is precisely GPU-8.8. And the moment the domain exceeds one rack (NVLink Fusion systems, Rubin Ultra's NVL576 class), the switched fabric starts to look suspiciously like a network, with hops, contention, and routing — the subject of GPU-8.7.

### 1.4 AMD Infinity Fabric / xGMI (GPU-8.5)

**Lineage.** AMD's scale-up story starts not with GPUs but with CPUs: Infinity Fabric is the coherent fabric that glued the chiplets of Zen processors together from 2017, evolving the coherent link role that HyperTransport played in pre-Zen Opterons. When AMD re-entered the accelerator market with the Instinct line, the same fabric technology was extended off-package: **xGMI** (External Global Memory Interconnect) is the GPU-to-GPU face of Infinity Fabric. The MI200 series (2021) brought xGMI to Instinct; MI300 and MI350 refined it.

**Topology: mesh, not switch.** AMD's flagship platforms (MI300X, MI350-series) put eight OAM modules on a Universal Baseboard (UBB) with **seven xGMI links per GPU — one to each peer — forming a fully connected mesh**: 8×7/2 = 28 physical pairwise links. Where NVIDIA spends its per-GPU link budget reaching a switch, AMD spends it reaching every peer directly. There is no switch ASIC, no hop, no shared forwarding resource: pairwise bandwidth is guaranteed by construction, and the aggregate per-GPU injection bandwidth is simply 7 × (per-link rate).

**Numbers, with the honesty checklist applied.** On MI300X, each xGMI link is rated 64 GB/s (aggregate bidirectional; 32 Gbps signaling over 16 lanes), so each GPU has 7 × 64 = 448 GB/s of theoretical injection bandwidth, and AMD quotes 896 GB/s of aggregate fabric bandwidth for the 8-GPU ring. Now the realized numbers, from AMD's own RCCL/xGMI engineering blog: sustained point-to-point unidirectional bandwidth per link is **45–48 GB/s, about 75% of the 64 GB/s theoretical**, with CRC and protocol overhead eating the rest. A rule of thumb you can carry across vendors: dedicated interconnects deliver roughly 70–80% of theoretical in well-tuned collective libraries; if you see 40%, suspect topology or configuration, not physics.

**Coherence: the differentiator.** xGMI is a *coherent* fabric — it bridges the coherent domains of the individual GPU packages into one. The practical consequence: the eight GPUs' HBM stacks form a single hardware-coherent memory space (8 × 192 GB = 1.5 TB on MI300X; 2.3 TB on MI355X), and a kernel on any GPU can load from any peer's memory with hardware keeping the views consistent. `amd-smi topology` exposes this — its link-type matrix should show XGMI (not PCIE) for every off-diagonal GPU pair, and its access matrix ENABLED, on a correctly cabled system. A mis-cabled baseboard shows up instantly as PCIE entries — a five-minute diagnostic that saves days.

**The current generation.** The MI350 series (MI355X launched June 12, 2025 at AMD's Advancing AI event) keeps the same 8-GPU fully connected design but raises the fabric: Infinity Fabric links run at 38.4 Gbps (vs. 32 on MI300X), each link carries 153.6 GB/s, and per-GPU P2P ring aggregate bandwidth rises to 1,075.2 GB/s (~20% over MI300X). Each MI355X packs 288 GB of HBM3E at 8 TB/s and up to 1,400 W TBP — and note the balance: 8 TB/s of local memory bandwidth against ~1.1 TB/s of fabric injection bandwidth. The ratio (~7:1) is a design statement about how much of a workload's data movement stays local; NVIDIA's NVL72 ratio is similar (8 TB/s HBM3E per Blackwell Ultra vs. 1.8 TB/s NVLink).

**Mesh vs. switch, honestly compared.**

| Dimension | AMD mesh (MI300X/MI355X) | NVIDIA switched (NVL72) |
|---|---|---|
| Max domain | 8 GPUs (per UBB) | 72+ GPUs (576 with switch chips) |
| Per-pair latency | One hop, fixed | Through switch, still µs-class |
| Pairwise bandwidth guarantee | By construction (dedicated links) | Statistical (shared switch bisection) |
| Link budget per GPU | n−1 = 7 | 18 to the switch, reused for all peers |
| Failure domain | A bad cable kills one pair | A bad switch tray touches everyone |
| Scale-up path | Scale-out beyond 8 (PCIe/network) | Scale the fabric itself |

Both are correct answers to the same physics. AMD bets that at n=8, a mesh's simplicity, determinism, and coherence win; NVIDIA bets that model parallelism wants domains far larger than 8 and pays the switch to get there. The workload decides: a tightly coupled HPL-MxP run on 8 GPUs is at home on a UBB; a mixture-of-experts model with expert-parallel all-to-all over 72 GPUs needs the rack-scale domain.

### 1.5 Other accelerator scale-up fabrics (GPU-8.6)

**The common substrate: OAM/OAI.** Before the vendor specifics, one piece of infrastructure almost everyone shares. In 2019, OCP's Open Accelerator Infrastructure (OAI) workstream — driven initially by Microsoft, Facebook, and the hyperscalers — defined the **OCP Accelerator Module (OAM)**: a mezzanine module (~102×165 mm, up to ~1000 W, two high-density mezz connectors) carrying an accelerator die stack with **up to eight x16 high-speed links — one or two to the host, up to seven module-to-module**. A Universal Baseboard (UBB) hosts eight OAMs and wires the inter-module links into the vendor's chosen topology (fully connected, ring, or almost-fully-connected). OAM exists because a PCIe card form factor cannot support dense inter-ASIC topologies: card-edge connectors and slot spacing do not provide enough high-speed, low-loss lanes between adjacent accelerators. AMD's Instinct OAMs, and Intel's Ponte Vecchio OAMs, are both instances of this standard — which is why "the same baseboard, different fabric" was ever possible.

**Intel Xe Link — built for one machine.** Intel's entry was Xe Link, deployed on Ponte Vecchio (PVC), the GPU built for the Aurora supercomputer at Argonne. The engineering is instructive: Ponte Vecchio is a 47-tile, >100-billion-transistor package in which connectivity got its own dedicated die — the **Xe Link tile, built on TSMC N7, with up to 90 Gbps SerDes and an embedded 8-port switch**, 16 Xe Links total per package. The embedded per-tile switch means a PVC package could route between its own links without an external switch — an early answer to the mesh-vs-switch question, embedded in the package. Aurora's scale: 10,624 blades, each with 2 Xeon Max CPUs and 6 PVC GPUs; 63,744 GPUs in total, connected in x4 OAM subsystems with all-to-all Xe Links, plus x8 UBB variants. The final blade was installed in June 2023; Aurora debuted on TOP500 with 585 PFLOPs on a partial system in November 2023 and subsequently crossed the exaflop line in 2024 — the Xe Link fabric carried what was briefly the largest GPU count ever fielded in one machine.

**Intel's retreat.** The follow-on story is a lesson in interconnect economics. In January 2025, on its Q4 earnings call, Intel announced that **Falcon Shores — the planned successor GPU — would not be brought to market**, becoming an internal test chip, with resources redirected to **Jaguar Shores, a rack-scale, system-level solution**. The stated reasoning is directly relevant to today's topics: "it's not enough to just deliver the silicon" — customers now buy coherent rack-scale domains (the NVL72 lesson), and a standalone GPU with a good interconnect but no switch ecosystem and no rack story is not competitive. As of today there is no Intel merchant successor to Xe Link's GPU scale-up role; Intel's coherent play has moved to CXL on the host side and to participation in the open UALink ecosystem below.

**CXL: the host-side coherent path.** Compute Express Link is PCIe's coherent sibling: it runs over the standard PCIe electrical layer (from PCIe 5.0 onward, CXL 2.0/3.x ride the same SerDes) but adds cache-coherent memory semantics with three protocols (CXL.io for I/O, CXL.cache for coherent caching, CXL.mem for memory access). Its role in scale-up is real but different: CXL is how CPUs attach to each other, to memory expanders, and to some accelerators coherently at PCIe-class speeds — 4th-gen Xeon (Sapphire Rapids) was the first mainstream server CPU with CXL 1.1 devices. What CXL does not (yet) provide is GPU-class bandwidth: a CXL x16 link is 64 GB/s per direction on PCIe 5.0, versus NVLink 5's 900 GB/s per direction per GPU. Think of CXL as the coherent *control and data plumbing* plane and the dedicated fabrics as the *bulk traffic* plane.

**UALink: the open answer.** The most consequential recent entry is **Ultra Accelerator Link**. The UALink Consortium (incorporated October 2024; board includes AMD, Intel, Broadcom, Alibaba, AWS, Cisco, Google, Meta, Microsoft, Apple, Astera Labs, HPE, Synopsys) ratified **UALink 200G 1.0 in April 2025**. Its design point reads like a wish list compiled from everything above:

- **200 Gbit/s per lane** (212.5 GT/s signaling to carry FEC overhead), links of x1/x2/x4, so a full x4 "station" is 800 Gbit/s;
- **a switched pod of up to 1,024 accelerators**, routed by 10-bit accelerator IDs — NVSwitch-class domains at NVLink-5-class per-lane rates, as an open spec;
- **memory semantics**: direct load/store and atomic transactions between accelerators — the P2P primitive of topic 8.2, promoted to an industry standard — deliberately *excluding* host CPUs from remote-node access, to keep the latency and power budget lean;
- **<4 m cable reach with sub-µs round-trip latency** targets for 64–640 byte payloads, i.e., in-pod, rack-adjacent distances, with Ethernet (not UALink) handling scale-out beyond the pod.

Whether UALink silicon ships in volume on schedule is an open question — consortium specs do not manufacture themselves — but its existence confirms the thesis of this whole module: scale-up interconnect has become the defining component of accelerator systems, to the point that a dozen competitors will standardize rather than concede the category to one vendor.

**The unifying ideas** across NVLink, NVSwitch, xGMI, Xe Link, and UALink:

| Idea | Why it recurs |
|---|---|
| High-rate SerDes lanes, aggregated in bundles | Bandwidth scales by adding lanes/links, not by magic per-wire speed |
| Memory semantics (load/store/atomics), not message semantics | P2P pointer access is what makes multi-GPU memory "just work" in software |
| Bidirectional-sum marketing numbers | Always halve the headline to get per-direction; always derate ~25% for realized bandwidth |
| Mesh for small n, switch for large n | n(n−1)/2 link growth vs. switch radix — pure counting |
| Standardized modules (OAM/UBB) | Nobody can route hundreds of 100G-class lanes through card slots |

### 1.6 System view: what this means for real workloads

Pull the five topics together on one workload. Take HPL-MxP (mixed-precision HPL) on 8 GPUs. After each distributed GEMM iteration the partial results must be combined; the communication volume per GPU scales with the surface of its block, and the efficiency of that all-reduce is decided entirely by today's topics:

- whether the library can issue **P2P loads/stores at all** (8.2) — else every reduction stages through host memory at ~15 GB/s;
- whether the **fabric** moves data at 450–900 GB/s per direction or 64 GB/s (8.3, 8.5);
- whether the reduction is done **in-switch** with SHARP or by forwarding through peers (8.4);
- whether the **topology** gives every pair equal bandwidth or bottlenecks through a hub (8.5 vs. 8.4 — and quantified in 8.7/8.8, where bisection bandwidth finally gets its own treatment).

The same reasoning, with different communication patterns, governs HPCG's sparse halos, CFD stencil exchanges, and MoE expert routing. The interconnect does not merely connect the GPUs; it decides the algorithmic strategies that are affordable.

## 2. Key Developments / News

### 2.1 NVIDIA opens NVLink to third-party silicon: NVLink Fusion (May 2025)

**What happened.** At Computex (Taipei, May 18, 2025), NVIDIA announced **NVLink Fusion**, licensing NVLink connectivity to third parties building semi-custom AI infrastructure. MediaTek, Marvell, Alchip, Astera Labs, Synopsys, and Cadence are building custom AI compute that plugs into NVLink scale-up fabrics; Fujitsu and Qualcomm plan custom CPUs that couple with NVIDIA GPUs over NVLink, paired with Spectrum-X scale-out.

**What technically changed.** Until this point, NVLink/NVSwitch domains were closed: only NVIDIA silicon could attach. NVLink Fusion makes the fabric an open (though NVIDIA-controlled) attachment ecosystem — an accelerator from a third party can, in principle, join the same 72-GPU (and larger) domains and speak the same load/store, coherent memory-semantic protocol that topics 8.2–8.4 describe.

**Why it matters and how it connects.** This is the interconnect-as-platform play: if the scale-up fabric is where the value concentrates (today's lesson), then opening it selectively converts competitors' silicon into ecosystem participants while keeping fabric governance — and rack design, and the software stack — at NVIDIA. It is also a direct answer to UALink (below): rather than face a single open standard alone, NVIDIA positions its mature, shipping fabric as the pragmatic open choice. Watch: which silicon actually ships with Fusion PHYs, and whether Fusion domains match native NVLink bandwidth.

### 2.2 Vera Rubin and NVLink 6 enter full production (March 2026)

**What happened.** At GTC on March 16, 2026, NVIDIA announced the **Vera Rubin platform** with seven chips in full production: Vera CPU, Rubin GPU, NVLink 6 Switch, ConnectX-9 SuperNIC, BlueField-4 DPU, Spectrum-6 Ethernet switch, and — notably — the newly integrated NVIDIA Groq 3 LPU. Partner systems ship in the second half of 2026.

**What technically changed.** Sixth-generation NVLink raises per-GPU bandwidth to **3 TB/s across 36 links** (vs. 1.8 TB/s / 18 links on Blackwell), and **Vera Rubin NVL72 connects 72 GPUs all-to-all for 216 TB/s aggregate** — up from 130 TB/s on GB200/GB300 NVL72. NVIDIA claims MoE training with one-fourth the GPUs versus Blackwell and up to 10× inference throughput per watt (vendor claims, not yet independently verified). The platform is explicitly **pod-scale**: GPU racks, CPU racks, inference-accelerator racks, storage racks, and Ethernet racks designed to operate as one system.

**Why it matters and how it connects.** The three-generation trajectory — 900 GB/s (Hopper, 2022) → 1,800 (Blackwell, 2024) → 3,000 GB/s (Rubin, 2026) per GPU — is the quantification of today's thesis: interconnect bandwidth is growing on the same cadence as compute, because at trillion-parameter scale the fabric is the bottleneck. The Groq LPU's appearance inside an NVLink platform is the NVLink Fusion concept made real — heterogeneous silicon in one coherent domain. For curriculum purposes, note the rack power (100+ kW class) and the copper-backplane-at-in-rack-distance engineering from topic 8.4 repeated at higher rates.

### 2.3 UALink 1.0: the open scale-up standard is ratified (April 2025)

**What happened.** On April 8, 2025, the UALink Consortium released the **UALink 200G 1.0 Specification**: 200 Gbit/s per lane, up to x4 links (800 Gbit/s per station), switched pods of **up to 1,024 accelerators**, routed by 10-bit IDs, with direct load/store and atomic transactions between accelerators. Cable reach is optimized for <4 m with sub-µs round-trip latency targets; the design goal is ~93% effective bandwidth. The consortium's board spans AMD, Intel, Broadcom, Google, Meta, Microsoft, AWS, Cisco, Apple, Alibaba, Astera Labs, HPE, and Synopsys.

**What technically changed.** Before UALink, every vendor's scale-up fabric was proprietary; there was no open way to build a switched, memory-semantic accelerator pod. UALink 1.0 is precisely that: an open NVSwitch-class alternative with the P2P semantics of topic 8.2 as the native protocol, deliberately scoped to accelerator-to-accelerator traffic (host CPUs are excluded from cross-node access) to keep latency and power low.

**Why it matters and how it connects.** Combined with NVLink Fusion on one side and Intel's Jaguar Shores rack-scale pivot (topic 8.5) on the other, 2025 marked the moment the industry converged on the same architectural conclusion this module teaches: scale-up domains of dozens-to-hundreds of accelerators with load/store semantics are the unit of AI and HPC computing. What to watch: first UALink silicon and switch products, and whether the promised 93% effective bandwidth materializes in real pods — apply the honesty checklist of topic 8.3 to every announcement.
