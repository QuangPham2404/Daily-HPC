## 0. Concise Summary

Yesterday's volume closed out the foundations module with latency versus throughput. Today we cross into the GPU execution model proper, and the through-line is a single question: **what actually happens between writing a kernel function in host code and arithmetic executing on a Streaming Multiprocessor?**

We start with the measuring sticks — clock frequency, operations per cycle, execution width, FLOP/s, bandwidth, latency, and utilization (GPU-1.6) — because every claim about GPU performance reduces to these quantities multiplied together. We then follow the life of a piece of work: the host–device split and the kernel launch (GPU-2.1), the three-level decomposition of a problem into threads, blocks, and grids (GPU-2.2), the hardware's regrouping of threads into 32-wide warps — or 64-wide wavefronts, or 16/32-wide subgroups, depending on the vendor (GPU-2.3) — and finally the physical destination of all of it: the SM, Compute Unit, or Xe-core (GPU-2.4).

The key connection: the thread hierarchy is a *software* contract designed around a *hardware* reality. Blocks exist because SMs have finite, private resources (registers, shared memory, a fixed number of resident warps); warps exist because SMs execute instructions on fixed-width SIMD lanes. The whole programming model is an abstraction placed over the machine so that the same kernel runs on 15 SMs (a 2012 Tesla K20X) or 224 SMs (a 2026 NVIDIA Rubin GPU).

In developments: NVIDIA's Vera Rubin platform entered full production with a 224-SM Rubin GPU; a peer-review-track microbenchmarking study gave the first systematic public characterization of Blackwell's 148-SM dual-die design; and AMD's MI350 series scaled the Compute Unit model to 256 CUs via chiplets. All three are, at bottom, stories about today's curriculum: replication and feeding of the compute building block.

## 1. Learn the Concepts

### 1.1 The measuring sticks: basic hardware performance quantities (GPU-1.6)

Before following work through a GPU, we need the vocabulary for saying precisely how fast any of it is. Every performance number you will ever see for a processor decomposes into a small set of primitive quantities:

- **Clock frequency** $f$ — how many cycles per second the logic advances, in Hz. GPU boost clocks are typically 1–2.5 GHz, far below CPU clocks (3–6 GHz), and for a good reason we will see below.
- **Operations per cycle** — how many useful operations one execution unit completes each cycle. An FMA (fused multiply-add) unit completes one FMA per cycle, which counts as **2 FLOPs** (one multiply + one add). This convention — an FMA is two floating-point operations — is universal in HPL and in every vendor datasheet, and forgetting it is the most common source of factor-of-two confusion.
- **Execution width** — how many parallel lanes a unit has. A "512-bit vector engine" has 16 lanes of 32-bit data (512/32).
- **FLOP/s (rate)** — aggregate floating-point operations per second. Theoretical peak is:

$$\text{Peak FLOP/s} = (\#\text{units}) \times (\text{ops/cycle/unit}) \times f$$

- **Bandwidth** — bytes per second that a memory system or link can move: GB/s or TB/s.
- **Latency** — the *time* for one request to complete, in ns or cycles. Bandwidth and latency are independent limits; a system can have enormous bandwidth while individual accesses take 400–800 cycles of DRAM latency.
- **Utilization** — the fraction of theoretical peak actually achieved: $\text{utilization} = \text{achieved} / \text{peak}$. When the TOP500 lists an HPL efficiency of, say, 75%, that is precisely this quantity: $R_{\max}/R_{\peak}$ for the LINPACK benchmark. Utilization is also the honest way to report benchmark results — a speedup without knowing against what peak is a half-truth.

**A worked example that will recur all day.** The NVIDIA H100 SXM datasheet lists 67 TFLOP/s FP32 and 34 TFLOP/s FP64. Where do those numbers come from? The GPU has 132 SMs; each SM contains 128 FP32 lanes and 64 FP64 lanes; the boost clock is ≈1.98 GHz. Then:

$$\text{FP32 peak} = 132 \times 128 \times 2 \times 1.98\,\text{GHz} \approx 66.9\ \text{TFLOP/s}$$
$$\text{FP64 peak} = 132 \times 64 \times 2 \times 1.98\,\text{GHz} \approx 33.4\ \text{TFLOP/s}$$

which matches the datasheet. Nothing in a datasheet is magic — every peak is units × ops/cycle × clock, and by the end of this volume you will be able to derive all of them yourself from architectural facts. (Note the datasheet's tensor-core numbers are quoted "with sparsity," i.e., assuming 2:4 structured sparsity in the operands, which halves the dense figure. Always read the footnote.)

One more distinction to lock in: **latency vs. throughput vs. bandwidth.** A single HBM3 access on an H100 takes on the order of several hundred nanoseconds — thousands of cycles when queued behind other traffic. Yet the memory system sustains 3.35 TB/s. The resolution of this apparent paradox is pipelining: many requests are in flight simultaneously, and *aggregate* delivery rate is high even though *each* request is slow. This is exactly the latency-hiding idea from GPU-1.5, and in a few sections we will see the hardware mechanism (massive hardware multithreading) that makes it work.

### 1.2 Host, device, and kernels (GPU-2.1)

A GPU does not run your program. It runs *your kernel* — a function you compile separately and *launch* from CPU code. This host/device split is the foundational fact of heterogeneous computing:

- The **host** is the CPU and its system memory. Host code does everything a GPU is bad at: control flow, file I/O, operating-system interaction, launching work.
- The **device** is the GPU with its own memory (HBM on a modern accelerator). Device code executes only when the host launches it.
- A **kernel** is the function that runs on the device, executed by *many threads simultaneously* — typically thousands to millions.

In CUDA, the syntax makes the launch explicit:

```c
// host code
__global__ void vecAdd(const float* A, const float* B, float* C, int N);

int main() {
    // ... allocate A, B, C in device memory, copy inputs host->device ...
    vecAdd<<<numBlocks, blockSize>>>(dA, dB, dC, N);
    // host continues immediately — the launch is asynchronous
    cudaDeviceSynchronize();   // wait for the device to finish
    // ... copy result device->host ...
}
```

The `__global__` qualifier marks a kernel; the `<<<numBlocks, blockSize>>>` configuration is the *launch configuration*, and those two parameters are the subject of the next section. The equivalent in other stacks: HIP uses the same triple-chevron syntax on AMD hardware; OpenCL/SYCL phrase it as enqueuing a kernel into a command queue with an `nd_range`; but the semantics — host enqueues, device executes, host may wait — are the same everywhere.

Three behaviors of this model matter for everything downstream:

1. **Launches are asynchronous.** `vecAdd<<<...>>>` returns control to the host immediately. The kernel executes while the host marches on. This is not an optimization; it is the contract, and it is what allows overlapping compute with communication (Theme 2 territory).
2. **The host must explicitly manage device memory.** Data lives in one of two address spaces (we will study the discrete memory model in Module 7). Copies are explicit API calls, and their cost is real — a point every GPU programmer relearns the first time a "GPU-accelerated" loop runs slower than the CPU version because of transfer overhead.
3. **The kernel body is written as if for one thread.** Inside the kernel there is no "element loop." Instead, each of the thousands of launched threads executes the same function once, distinguished only by its index. The kernel below computes exactly one output element per thread:

```c
__global__ void vecAdd(const float* A, const float* B, float* C, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // which element is "mine"?
    if (i < N) C[i] = A[i] + B[i];
}
```

That single line of index arithmetic — `blockIdx.x * blockDim.x + threadIdx.x` — is the bridge between the logical problem ("add N-element vectors") and the physical machine, and understanding why it looks like that requires the full hierarchy, which we cover next.

### 1.3 Threads, blocks, and grids: hierarchical work decomposition (GPU-2.2)

How does one function call become a million threads? Through a fixed, three-level hierarchy:

```
Grid  (the whole kernel launch — all work)
 │
 ├── Thread block 0     … up to 1024 threads each
 ├── Thread block 1        (CUDA name: block; OpenCL/HIP: work-group)
 ├── Thread block 2
 └── …  (thousands to millions of blocks)
       │
       └── Threads  (each executes the kernel body once;
                     CUDA: thread; OpenCL: work-item)
```

Each level exists for a reason, and the reasons are hardware reasons:

**Threads are the unit of program state.** A thread owns its program counter and its registers. When you write kernel code, you write the code of one thread.

**Blocks are the unit of cooperation and of scheduling.** Threads within a block can synchronize with each other (`__syncthreads()`) and share data through fast on-chip shared memory. A block is assigned to exactly one SM (streaming multiprocessor), and all its threads execute there; multiple blocks can be resident on one SM concurrently. Crucially, **different blocks are independent**: a kernel cannot assume any ordering between blocks, and (with modern exceptions like cooperative groups) blocks cannot synchronize with each other. As blocks finish, the hardware launches new blocks onto vacated SMs.

**Grids are the unit of scale.** The grid — all blocks of one launch — is sized to the problem, not to the hardware. The same kernel launched with a million blocks runs correctly on a 15-SM Tesla K20X from 2012 and on a 224-SM Rubin GPU in 2026; the only difference is how many blocks run at once. This *scalable* decomposition is the founding idea of the CUDA programming model: express enough parallelism, and the hardware fills itself.

Each thread is identified by built-in variables: `threadIdx` (which thread within its block), `blockIdx` (which block), `blockDim` (threads per block), and `gridDim` (blocks in the grid). All can be 1-, 2-, or 3-dimensional, which maps naturally onto data: a 2-D matrix is covered by a 2-D grid of 2-D blocks, with

```c
col = blockIdx.x * blockDim.x + threadIdx.x;
row = blockIdx.y * blockDim.y + threadIdx.y;
```

and the same pattern extends to a 3-D CFD stencil. The global thread ID formula in one dimension — `blockIdx.x * blockDim.x + threadIdx.x` — is just "which block am I in, times how big each block is, plus where am I within it."

**A worked example.** Vector addition with $N = 2^{26} = 67{,}108{,}864$ elements and 256 threads per block:

$$\text{blocks needed} = \left\lceil \frac{N}{256} \right\rceil = \left\lceil \frac{2^{26}}{2^8} \right\rceil = 2^{18} = 262{,}144\ \text{blocks}$$

The GPU has 132 SMs. If each SM can host, say, 8 of these 256-thread blocks at once (a limit we will learn to compute in Section 1.5), the whole grid still runs in waves: $\lceil 262144 / (132 \times 8) \rceil = 249$ waves of blocks sweep through the machine, and the machine stays busy as long as there are blocks left to launch. This "grid larger than the hardware" property is what makes GPU code portable across generations.

Why cap blocks at 1024 threads (the limit on current NVIDIA GPUs; 1024 work-items per work-group in OpenCL and on AMD/Intel too)? Because a block's threads must be able to share the block's private resources — shared memory and a common barrier — and the barrier must be fast. Hardware barrier networks scale poorly with participant count; 1024 is the largest group the SM can rendezvous at full speed. Cooperation *beyond* 1024 threads historically required separate kernel launches or global-memory spin loops — until Hopper added thread-block clusters (compute capability 9.0), an optional extra level between block and grid in which blocks placed on the same GPC can address each other's shared memory ("distributed shared memory"). Clusters preview Module 10; file them away as "the hierarchy grew a level to feed bigger tiles to tensor cores."

One more asymmetry worth internalizing now: **synchronization cost grows with scope.** Threads in a warp are synchronized essentially for free (next section). Threads in a block synchronize with `__syncthreads()` — cheap, but it stalls the whole block. Blocks in a grid synchronize only at kernel boundaries (or with cooperative launch) — expensive. The further up the hierarchy you coordinate, the more it costs, which is why high-performance kernels push as much cooperation as possible *down* into the cheapest scopes.

### 1.4 Warps, wavefronts, and subgroups (GPU-2.3)

So far "threads" have been an abstraction. At the hardware level, no GPU schedules individual threads. The SM's front end creates, manages, schedules, and executes threads in **fixed-size groups**:

- **NVIDIA: the warp — 32 consecutive threads.** The partitioning rule is deterministic: each warp contains threads of consecutive, increasing thread IDs, with the first warp containing thread 0. A block of 256 threads is exactly 8 warps; a block of 1000 threads is 32 warps, the last one only half full (wasted lanes — one reason block sizes are usually multiples of 32).
- **AMD CDNA: the wavefront — 64 work-items** (often shortened to "wave"). CDNA Compute Units have 4 SIMD units of 16 lanes each; a full wave64 instruction is executed by one SIMD unit over four cycles. AMD's RDNA gaming architecture (and its wave-programming model visible to HIP programmers via sub-group intrinsics) went the other way: native **wave32**, with wave64 supported via dual issue, to reduce divergence cost and per-wavefront register pressure.
- **Intel: the sub-group — 8, 16, or 32 work-items** (Xe-HPC supports 16 and 32). Intel's execution units are 512-bit SIMD machines, i.e., 16 FP32 lanes; a 16-wide sub-group instruction retires in one cycle, a 32-wide one in two.

Different names and widths — same purpose. Why do all three vendors execute threads in lockstep groups? Because it buys **SIMD economics with a scalar-thread programming model**. The instruction fetch, decode, and issue hardware — program counter, instruction buffer, register operands — is shared across the group, and only the arithmetic lanes are replicated. One instruction issue serves 32 (or 64, or 16) threads. If each thread had its own front end, the chip would be mostly control logic and not much arithmetic; this is the same area-spending argument as GPU-1.2, now seen from inside the machine.

The cost of the group is that **the warp executes one common instruction at a time.** Full efficiency is realized only when all 32 threads agree on their execution path. If threads in the same warp take different sides of a data-dependent branch, the warp executes each path taken, disabling the threads not on that path — *branch divergence*, the subject of a full topic later (GPU-2.7). Different warps always execute independently, so divergence is strictly a within-warp phenomenon. And because the threads of a warp have a single instruction stream, code that assumes lockstep (old "warp-synchronous" tricks) has been unsafe since Volta introduced independent thread scheduling with per-thread program counters; today, correctness inside a warp requires explicit `__syncwarp()` or the `_sync` intrinsics.

Two practical consequences of warp granularity that HPC engineers hit constantly:

1. **The last warp of a block can waste half the machine.** A grid-stride or 33-thread block leaves lanes idle. Choose block sizes as multiples of the warp/wave size.
2. **Warp-level primitives exist because the hardware group is real.** Shuffles (`__shfl_sync`), ballot, and warp reductions exchange data between lanes *without touching memory* — the topic of a later volume, but the reason they are fast is that the 32 lanes live on the same SM partition and share a register-file bypass network.

A quick numerical example of the efficiency math. Suppose each thread of a warp loads one FP32 value and adds it to an accumulator: the warp executes one load instruction and one add instruction. If half the warp is inactive because of divergence, the same two issues serve only 16 threads — effective utilization of the issue slots halves. Now extrapolate to a stencil kernel where every iteration has a boundary branch: on the boundary warps, the FP32 peak you computed in Section 1.1 is unreachable *by construction*, no matter how good your code is. The performance quantities of GPU-1.6 are always per-lane peaks; the group structure of this section decides how many lanes you can actually keep active.

Finally, the term **SIMT** — Single-Instruction, Multiple-Thread — is NVIDIA's name for this arrangement: a programming model of independent scalar threads implemented on hardware that issues one instruction per group of 32. Per the CUDA Programming Guide, GPU instructions are issued in order, without branch prediction or speculative execution — the SM spends its transistors on lanes and resident contexts instead of control speculation. That is the architectural bet of the whole machine, and everything in the next section is what the bet bought.

### 1.5 The SM, the Compute Unit, the Xe-core (GPU-2.4)

Where does a warp physically execute? On the GPU's replicated compute building block — and here the vendors' names differ but the anatomy is strikingly similar:

| | NVIDIA (Hopper H100) | AMD (CDNA 2, MI250X) | Intel (Xe-HPC, PVC Max 1550) |
|---|---|---|---|
| Building block | Streaming Multiprocessor (SM) | Compute Unit (CU) | Xe-core |
| Per GPU | 132 SMs (SXM5) | 110 CUs per GCD × 2 GCDs | 64 Xe-cores per tile × 2 tiles |
| Internal partitioning | 4 processing blocks, each: 32 FP32 + 16 INT32 + 16 FP64 + 1 tensor core, own warp scheduler + 16K registers | 4 SIMD16 units (= 64 vector lanes) + 4 matrix core units | 8 vector engines (XVE, 512-bit) + 8 matrix engines (XMX, 4096-bit) |
| Scheduling group | warp (32) | wavefront (64) | sub-group (16/32); 8 HW threads per XVE |
| On-chip shared memory | up to 228 KB shared/L1 per SM | 64 KB LDS per CU | 128 KB SLM (+ 512 KB L1/SLM combined) per Xe-core |
| Resident threads | 2048 (64 warps) per SM | ~2560 work-items (40 waves) per CU buffer | 8 threads per XVE slot |

**The NVIDIA SM.** The Hopper SM is organized as **four processing blocks** (NVIDIA's diagrams call them SM sub-partitions), each a nearly self-sufficient machine: its own warp scheduler and dispatch unit, its own 16K × 32-bit register file partition, and its own execution units — 32 FP32 lanes, 16 INT32 lanes, 16 FP64 lanes, load/store units, an SFU (special function unit for transcendentals and rarer ops), and one fourth-generation tensor core. Per SM that totals 128 FP32 + 64 INT32 + 64 FP64 lanes and 4 tensor cores, with 256 KB of combined L1/shared memory. Each scheduler picks one ready warp and issues one instruction per cycle; with four partitions, an SM can retire up to four warp instructions per cycle. The register file — 64K 32-bit registers per SM, 255 usable per thread — is *partitioned among resident warps*, which is the mechanism behind occupancy limits: a kernel using 64 registers per thread with 512-thread blocks needs 64 × 512 = 32K registers per block, so exactly two such blocks (64 warps) fit — and one extra register per thread would halve that. Resident-warp capacity is capped at 64 warps / 2048 threads per SM on Hopper.

**The AMD Compute Unit.** CDNA 2's CU likewise has a scheduler front end (buffering up to 40 wavefronts), four 16-wide SIMD units — so a full wave64 FP32 vector instruction occupies one SIMD for four cycles — plus four Matrix Core units for the MFMA path, a 64 KB Local Data Share (the AMD name for shared memory) with improved FP64 atomics, and scalar/vector register files. AMD's peak figures follow the same multiplication: 110 CUs/GCD × 128 FP64 FLOPs/cycle/CU × 2 GCDs × 1.7 GHz ≈ 47.9 TFLOP/s FP64 vector on MI250X, with the matrix cores doubling that to 95.7 TFLOP/s FP64.

**The Intel Xe-core.** Intel's building block swaps the "four partitions" motif for eight 512-bit vector engines, each multithreaded with 8 hardware threads, plus eight 4096-bit XMX matrix engines. A full Ponte Vecchio package (Data Center GPU Max 1550) is a tour de force of packaging: 128 Xe-cores on two compute tiles (plus RAMBO cache tiles, HBM2e tiles, and SerDes tiles — 47 tiles on five process nodes, 3-D stacked with Foveros and EMIB), with up to 408 MB of L2 and Xe Link scale-up ports. Packaging is Module 9's subject; today's point is that under the packaging, the building block is the same familiar shape: scheduler + registers + vector lanes + matrix engines + local shared memory.

**What the block must guarantee.** Whatever the vendor, the compute block is defined by a set of architectural contracts:

1. **Block placement**: a thread block / work-group is assigned to exactly one SM/CU (in cluster mode, a group of blocks to one GPC), and cannot migrate. Its threads' registers and shared memory live there.
2. **Residency limits**: finitely many warps and blocks can be *resident* (occupying resources) simultaneously — 64 warps per SM on Hopper. Resident warps are the hardware's pool of ready work.
3. **Independence**: blocks require no inter-block communication to run, which is precisely what lets the GPU's block scheduler fire new blocks at vacated SMs without global coordination.

Why is the building block replicated to such an extreme — 132 copies on H100, 220 CUs on an MI250X, 128 Xe-cores on a PVC? Because replication of a small, self-sufficient block is the cheapest way to convert transistors into throughput, and because the block's private resources (registers, shared memory, schedulers) scale *with* the lane count. The SM is deliberately sized so that its 2048 resident threads can cover the latency of the memory system it feeds — the quantitative treatment of that balance (occupancy, latency hiding) is Module 5, but you can already see the shape of the argument: the SM is a latency-hiding container with just enough fast local state to keep its lanes fed.

### 1.6 Closing the loop: deriving a datasheet from a building block

Run the full chain once, end to end, because it ties all five topics together:

1. Host code allocates device memory and launches `kernel<<<262144, 256>>>` (GPU-2.1) — 67M elements, 262,144 blocks of 256 threads (GPU-2.2).
2. Each 256-thread block is cut into 8 warps of 32 consecutive threads (GPU-2.3).
3. The block scheduler places each block on one SM; its 8 warps join the up-to-64-resident-warps pool of that SM (GPU-2.4). With 4 blocks of 256 threads resident per SM, an H100 holds 132 × 2048 = 270,336 threads in flight simultaneously.
4. Each SM's four warp schedulers issue ready warps into their partitions' lanes. If every issued FP32 FMA has all lanes active, the machine sustains (GPU-1.6):

$$132\ \text{SMs} \times 128\ \text{lanes} \times 2\ \text{FLOP/FMA} \times 1.98\ \text{GHz} \approx 67\ \text{TFLOP/s}$$

That number — the datasheet's FP32 peak — is not a property of the GPU "as a whole." It is 67,896 lanes switching coherently at 1.98 GHz, and every abstraction above it (threads, blocks, grids, kernel launches) exists to keep those lanes issued with useful work. When HPL-MxP runs at 70% of peak, the missing 30% is accounted for in exactly these terms: waves with ragged tails, divergent boundary warps, memory stalls that resident warps did not fully cover, launch and synchronization gaps. There is no other place for performance to hide — which is why an HPC engineer reads a GPU not as a "black box with TFLOPs" but as *N copies of a known container*.

## 2. Key Developments / News

### 2.1 NVIDIA Vera Rubin enters full production — 224 SMs, HBM4, NVLink 6

**What happened.** NVIDIA's Vera Rubin platform — the successor to Blackwell — was detailed at CES 2026 and declared in full production at GTC in March 2026. The Rubin GPU integrates **224 Streaming Multiprocessors** with fifth-generation Tensor Cores optimized for NVFP4 and FP8, **288 GB of HBM4** per GPU, and a new Transformer Engine; the platform pairs it with the Vera CPU (88 custom "Olympus" Arm cores with spatial multithreading) and the NVLink 6 switch, delivering 3.6 TB/s GPU-to-GPU. The rack-scale DGX Vera Rubin NVL72 integrates 72 Rubin GPUs and 36 Vera CPUs into one NVLink domain rated at 3,600 PFLOPS NVFP4 inference.

**What technically changed.** Through today's lens: the building block count grew from 132 (H100) and 148 (B200) to 224, the memory system moved to HBM4, and the scale-up fabric doubled again — while the *shape* of the machine (SMs, warps, thread-block hierarchy, clusters) is unchanged. This is the curriculum's central thesis made physical: generational change is mostly replication + feeding, not re-architecture of the execution model.

**Why it matters / what to watch.** A kernel you write today with the hierarchy of Section 1.3 runs on Rubin unchanged — but to *tune* for it you will reason exactly as in Section 1.6, with new unit counts. Watch for full SM-level disclosures (partition structure, resident-warp limits) in the architecture whitepaper as systems deploy through H2 2026.

### 2.2 First systematic microbenchmarking of Blackwell's architecture

**What happened.** A December 2025 arXiv study (v3, March 2026) by Jarmusch and Chandrasekaran contributed an open-source microbenchmark suite characterizing the B200 against the H200: memory subsystem, tensor-core pipeline, and precisions from FP32 down to FP4.

**What was demonstrated.** The paper's architecture summary confirms the B200's dual-die design — two GPU dies totaling 208 billion transistors, 148 SMs across eight GPCs, four L2 partitions (double Hopper's), eight HBM3e stacks, unified by the NV-HBI die-to-die link into a single device — plus Blackwell-specific units: Tensor Memory (TMEM, a dedicated on-chip memory for tensor-core data movement that offloads shared memory and register file), a hardware decompression engine, and fifth-generation tensor cores with FP4/FP6. Notably, the authors report that Blackwell's tensor-core path "breaks from the warp-synchronous paradigm characterizing earlier architectures (Volta, Ampere, Hopper)." Measured (paper claim, not vendor number): tensor-core enhancements deliver 1.85× ResNet-50 and 1.55× GPT-1.3B mixed-precision training throughput versus H200, with 32% better energy efficiency.

**Connection to today.** This is precisely the kind of paper today's curriculum lets you read critically: "148 SMs" means Section 1.6's arithmetic with new counts; "TMEM" is a new stage in the SM's data path (Module 10 will cover it); "breaking warp-synchronous execution" is a statement about Section 1.4's group contract. Watch: independent replications as Blackwell fleets grow, and how programming models absorb the new memory stage.

### 2.3 AMD MI350: the Compute Unit model scaled by chiplets

**What happened.** AMD launched the Instinct MI350 series (June 2025) on the CDNA 4 architecture: MI350X/MI355X with **256 Compute Units** — eight XCD compute chiplets of 32 CUs each, fabbed on TSMC N3P — 288 GB HBM3E at 8 TB/s, and MI355X peaks of 78.6 TFLOP/s FP64, 5 PFLOP/s dense FP16 matrix, and 10.1 PFLOP/s FP8, with new MXFP6/MXFP4 datatype support.

**Technical significance.** Compare with Section 1.5's MI250X (2 GCDs × 110 CUs): AMD scaled the same building block from 220 to 256 CUs not by making one giant die but by adding chiplets — the packaging route Intel took to 128 Xe-cores on Ponte Vecchio. For HPC, note what *didn't* change: the wavefront model, the LDS, the matrix-core-per-CU structure. Chiplet integration (and its bandwidth implications) is Module 9's topic; today's takeaway is that the CU remains the atom of AMD's architecture, and peak FP64 still derives as CUs × FLOPs/cycle/CU × clock — 256 CUs × 256 FP64 FLOPs/cycle (matrix) × ~1.2 GHz ≈ 78.6 TF.

**What to watch.** ROCm 7's maturity on the new datatypes, and MI350 systems appearing in TOP500 HPL runs — where utilization (Section 1.1) can be compared directly against NVIDIA parts.
