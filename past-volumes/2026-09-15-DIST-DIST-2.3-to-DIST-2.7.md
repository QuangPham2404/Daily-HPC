## 0. Concise Summary

Last week's volume ended with blocking communication: a send or receive that does not return until some completion condition is met. Today we follow one logical thread through the rest of the point-to-point module — **what happens between initiation and completion, and who does the work.**

We start with **non-blocking communication** (DIST-2.3): the split of every transfer into an *initiation* call (`MPI_Isend`/`MPI_Irecv`, returning a request handle) and a separate *completion* call (`MPI_Wait`/`MPI_Test`). This split is the entire mechanism behind communication/computation overlap — the topic of Module 11 — so getting the semantics exactly right now pays off repeatedly.

But once sends and receives are decoupled in time, a new problem appears: the receiver may not know which incoming message belongs to which buffer. **Message matching** (DIST-2.4) is the envelope-and-queue machinery — source, tag, communicator, posted-receive list, unexpected-message list — that steers arriving bytes to the right application buffer, and its non-overtaking ordering rule is what makes asynchronous message-passing code deterministic.

Then we descend into the transport: **eager versus rendezvous protocols** (DIST-2.5), the implementation's size-dependent choice between "send everything immediately and hope the receiver has a buffer" and "negotiate first, then let the receiver pull data directly into its final buffer." A back-of-envelope calculation shows why real thresholds sit in the tens of kilobytes. This forces the question of **where the bytes physically sit in the meantime** (DIST-2.6): application buffers, eager/bounce buffers, RDMA-registered staging memory, and the copies between them.

Finally, **progress** (DIST-2.7) asks the question that ties the whole module together: after `MPI_Isend` returns, *who actually advances the transfer?* The answer — hardware queues, MPI-internal polling, a progress thread, or (increasingly) the GPU itself — determines whether the overlap you wrote on paper actually happens.

The developments section covers exactly this frontier: **UCX 1.20–1.22** moving the progress engine into the NIC and GPU with its Direct NIC / device-initiated communication APIs, the quiet **sunset of hardware MPI tag-matching offload** on ConnectX-8+ (a real-world lesson in which parts of matching are worth putting in silicon), and an **August 2025 paper** measuring persistent and partitioned MPI on stencil codes — the standardized descendants of today's `MPI_Isend`/`MPI_Wait` pattern.

## 1. Learn the Concepts

### 1.1 Non-blocking communication (DIST-2.3)

**The problem.** In DIST-2.2 we established precisely what a blocking send and receive wait for. The problem is what happens *while* they wait: nothing. If rank 0 posts a blocking receive for a message rank 1 will send only after finishing a 40 ms computation, rank 0's core sits idle for 40 ms even though it has perfectly useful local work it could be doing. Blocking point-to-point operations therefore serialize communication and computation into alternating phases — the bulk-synchronous pattern we will meet as BSP in Module 14. For latency-critical codes (and for every strong-scaling regime, where communication grows relative to computation) this alternation is unaffordable.

**The mechanism.** MPI's answer is to split every transfer into two calls:

```
initiation                          completion
MPI_Isend(buf, n, dtype, dest,      MPI_Wait(&request, &status)
          tag, comm, &request)      MPI_Test(&request, &flag, &status)
                                    MPI_Waitall / MPI_Waitany / MPI_Testany ...
```

`MPI_Isend`/`MPI_Irecv` (the *I* is for *immediate*) are **local**: they validate arguments, set up internal state, hand what they can to the transport, and return — typically in tens to hundreds of nanoseconds, not microseconds. All the actual work — matching, copying, DMA, acknowledgment — happens between initiation and completion, ideally concurrent with your computation. Completion is a separate call that blocks (`MPI_Wait`) or polls (`MPI_Test`) until the operation is done, where "done" has the same two meanings we pinned down for blocking operations in DIST-2.2:

- a **send is complete** when the send buffer is safe to overwrite (the library is done reading it);
- a **receive is complete** when the data has landed in the receive buffer and is safe to read.

The `MPI_Request` handle returned by the initiation call is your ticket for the completion call. It names an *operation in progress*, not a message — a detail that matters when you keep arrays of requests, as real codes do.

**A concrete example: the halo exchange.** Every stencil code (CFD, weather, lattice QCD) has the same shape. With blocking calls:

```c
/* blocking version — serialized, deadlock-prone if ordered badly */
MPI_Send(ghost_out[EAST],  ..., east,  TAG_E, comm);
MPI_Recv(ghost_in [WEST],  ..., west,  TAG_W, comm);
```

Every rank first sends east, then receives from west. Whether this deadlocks depends on eager-protocol buffering (Section 1.3) — a fragile way to write code. The non-blocking version separates concerns:

```c
/* non-blocking version — safe, and overlap-capable */
for (d = 0; d < NDIRS; d++)
    MPI_Isend (ghost_out[d], ..., nbr[d],  TAG(d), comm, &sreq[d]);
for (d = 0; d < NDIRS; d++)
    MPI_Irecv (ghost_in [d], ..., nbr[d],  TAG(d), comm, &rreq[d]);
compute_interior();                 /* work that needs no ghost data */
MPI_Waitall(2*NDIRS, reqs, statuses); /* now finish the exchange */
compute_boundary();                 /* work that needs ghost data */
```

Two things changed. First, deadlock is structurally impossible: no rank ever *waits* before every operation in the pattern has been initiated, so there is no cyclic wait-for graph (we will formalize deadlock in DIST-2.8). Second, `compute_interior()` now overlaps with the network transfer — the exposed communication time shrinks from the full exchange time to whatever part of it is still unfinished when the interior work runs out. That distinction — total versus *exposed* communication — is so important that Module 11 dedicates DIST-11.1 to it.

A timeline makes the gain visible:

```
blocking:      [send/recv exchange][---- interior compute ----][boundary]
non-blocking:  [init][---- interior compute ----][wait][boundary]
                      [==== network transfer, in flight ===...==]
```

**System behavior.** Overlap is only real if something below the MPI layer can advance the transfer while your code computes. On InfiniBand-class fabrics, the NIC processes its send/receive queues autonomously once work has been posted — that is what makes the pattern above genuinely concurrent. But not every stage of every protocol is hardware-driven; rendezvous sends, matching of unexpected messages, and data movement into application buffers often need *someone* to run code. Who that someone is — and when it runs — is the progress question of DIST-2.7, and the honest answer is "it depends," which is why overlap claims must always be measured, not assumed.

**A classic application pattern.** A common server/worker idiom, worth memorizing because it recurs in every I/O-heavy code (it is also the fix for the "unexpected message storm" failure we will meet in 1.6): pre-post a *window* of receives, then service completions as they occur with `MPI_Waitany`, immediately re-posting the freed slot:

```c
for (i = 0; i < WINDOW; i++)
    MPI_Irecv(buf[i], ..., MPI_ANY_SOURCE, tag, comm, &req[i]);
for (;;) {
    MPI_Waitany(WINDOW, req, &idx, &st);   /* blocks for ONE completion */
    process(buf[idx], &st);
    MPI_Irecv(buf[idx], ..., MPI_ANY_SOURCE, tag, comm, &req[idx]);
}
```

`MPI_Waitany`/`MPI_Testany` complete exactly one operation (the first available); `MPI_Waitall` completes a whole set; `MPI_Waitsome` completes a batch. Choosing among them is a performance decision, not just a convenience: `Waitany` lets you start processing message *k* while messages *k+1..n* are still arriving — a pipelined consumer.

**One semantic anchor from the standard.** Non-blocking does not weaken the ordering guarantees: messages between the same pair of processes, in the same communicator, with the same tag, are still **non-overtaking** — a send posted first is matched by a receive first. Only the *timing* is relaxed, never the ordering. (MPI 5.0, Chapter 3, formalizes these semantics; the same chapter defines persistent requests — communication arguments bound once, started many times — which we meet again in the developments section.)

### 1.2 Matching messages (DIST-2.4)

**The problem.** Once senders and receivers are decoupled in time — and once a single pair of processes runs many concurrent operations — the receiving MPI library faces a continuous stream of incoming messages and a set of application-posted receive buffers. Which incoming message belongs in which buffer? The bytes on the wire carry no pointers; the application named buffers by *communication call*, which happened at some other time, possibly on another process. Message matching is the bookkeeping system that resolves this.

**The mechanism: the message envelope.** Every message carries, alongside its payload, an envelope of four fields:

```
(communicator, source/destination rank, tag, size+datatype info)
```

- the **communicator** provides the *context*: messages in different communicators never match each other. This is why a profiling library or a numerical library using its own `MPI_Comm` cannot accidentally swallow the application's messages — each communicator is an isolated matching space.
- the **source and destination ranks** identify the endpoints *within* that communicator.
- the **tag** (an integer, with an implementation-defined upper bound `MPI_TAG_UB`, typically at least 2³¹−1 on modern stacks) lets the same pair of processes run many parallel conversations: one tag per logical data stream.
- the receiver may use wildcards — `MPI_ANY_SOURCE` and/or `MPI_ANY_TAG` — to accept "any message of this communicator" and learn the actual source and tag afterwards from the returned `MPI_Status` (with `MPI_Get_count` giving the received length).

**Matching as two queues.** How does an implementation actually implement this? The Linux kernel's InfiniBand documentation, describing how UCX and MPI stacks offload matching onto NVIDIA NICs, states the data model plainly, and it is the universal picture across MPI implementations:

- the **posted-receive list**: receives the application has already initiated but that have not yet matched anything;
- the **unexpected-message list**: messages that have already arrived for which no matching receive has been posted yet.

An arriving message first scans the posted-receive list; on a hit, delivery proceeds immediately. On a miss, it is parked on the unexpected-message list — and, as we will see in 1.3 and 1.6, *someone must store its payload* in the meantime. Symmetrically, a newly posted receive first scans the unexpected list (a hit delivers immediately from stored data); on a miss it joins the posted-receive list. Every message and every receive passes through exactly one of these two rendezvous-with-bookkeeping paths, and the lists are the reason an MPI library's memory footprint can grow unexpectedly — the "261,895 unexpected messages queued" failure quoted in 1.6 is literally this list overflowing available eager-buffer memory.

**The ordering rule.** Matching must be deterministic, so MPI imposes **non-overtaking order**: among messages from the same sender, in the same communicator, with the same tag, an earlier send always matches an earlier receive. Generalizing: when several (message, receive) pairs could legally match, the pair using the *earliest posted send and the earliest posted receive* wins — but, as the kernel documentation carefully notes, that does not mean tags are consumed in posting order; a later tag can match first if earlier ones cannot satisfy the rules. Non-overtaking is what makes the halo-exchange code of 1.1 safe across iterations: iteration *k*'s east-tagged message cannot be consumed by iteration *k+1*'s receive, provided you tag by iteration or complete (`Waitall`) before re-initiating — and if you use one tag for all iterations *and* keep requests outstanding across iterations, matching order is exactly what stands between correct data and stale ghosts.

**A concrete failure.** Suppose in the worker-server pattern of 1.1 the server posts receives with a specific source rank instead of `MPI_ANY_SOURCE`, but the workers send *both* work-requests and heartbeat messages with the same tag. The heartbeat can match the work-request slot: the server gets the wrong data with no error, because the message *did* legally match the envelope. Wildcards plus a tag *namespace* (e.g., tag 100+type) are the standard defense. Matching bugs rarely announce themselves; they return plausible data.

**Connection forward.** Tags are pure *metadata* overhead — they exist so the receiver can sort traffic that would otherwise be ambiguous. Keep that framing: when a future architecture (NCCL, NVSHMEM) replaces "post a receive and hope" with "operate on an explicitly addressed remote buffer," tags largely disappear, because the ambiguity they resolve was created by the send/receive abstraction itself. That trade — implicit matching versus explicit addressing — is one of the deepest forks in communication-stack design, and we will walk both branches (Modules 9 and 10).

### 1.3 Eager versus rendezvous protocols (DIST-2.5)

**The problem.** The matching machinery of 1.2 tells an arriving message *where* it should go. But *how* the bytes travel is a separate, size-dependent decision made by the communication library, before any of that matching may have happened. The core tension: the sender wants to hand data off immediately and return; the receiver wants data delivered straight into the final application buffer with no intermediate copies — and the receiver's matching receive may not even be posted yet.

**Eager protocol.** The sender transmits the *entire message* immediately, unconditionally:

```
sender                                receiver
  | ---- eager message (header+data) -->  no posted receive yet?
  |                                      => copy data into internal buffer,
  |                                         park on unexpected list
  | <--------- (ack / CQE) ------------   send buffer now reusable
```

The receiver, if the matching receive is already posted, can DMA the payload directly into the application buffer. If not — an *unexpected* message — the library must swallow the payload into its own storage and deliver it later, with a second copy, when the receive is finally posted (the kernel's tag-matching documentation describes exactly this split, and the rendezvous-triggered `RDMA READ` alternative, for the hardware-offload case).

**Rendezvous protocol.** For large messages, the sender first sends only a small *header* (envelope, maybe a memory key). The receiver, once it has matched a receive and knows the destination buffer, *pulls* the data itself with a remote read directly into the final buffer, then acknowledges:

```
sender                                receiver
  | ---- small header (envelope+rkey) -->
  |                                     match against posted receive
  | <-- RDMA READ (receiver pulls) -----  data lands in app buffer
  | <------------ fin/ack --------------  "data consumed"
  |    send buffer reusable at fin        receive completes at fin
```

No intermediate copy of the payload ever exists; the receiver's NIC writes straight into the application buffer using RDMA (the mechanism behind RDMA is Module 7's subject — here it appears as a black box that reads remote registered memory).

**Why size decides.** Each protocol pays a cost the other avoids:

| dimension | eager | rendezvous |
|---|---|---|
| sender-side latency | minimal — post and go | must wait for handshake |
| receiver memory risk | must buffer unexpected data | none — data goes only to the final buffer |
| copies of payload | 0 (expected) or 1–2 (unexpected) | 0 — RDMA READ into final buffer |
| extra round trips | 0 | 1 (header out, pull/fin back) |
| receiver CPU/NIC work | copy or direct delivery | issue RDMA READ, process fin |

A back-of-envelope crossover: rendezvous buys the elimination of one payload copy at the receiver, at the price of one extra round trip, roughly 2α (plus handshake processing). Eager's copy costs m/B_copy, where B_copy is the effective copy bandwidth through host memory — say 10 GB/s for a memcpy through caches. Setting m/B_copy = 2α with α = 1 µs gives m* ≈ 20 KB: exactly the tens-of-kilobytes range where real implementations put their thresholds. MPICH's CH3 layer has always selected eager versus rendezvous by a per-transport threshold (its source explicitly branches on `eager_threshold`; historical MPICH documented ~20 KB for shared memory and ~100 KB for TCP); UCX exposes `UCX_RNDV_THRESH` for the same purpose. The precise number is a tuning parameter — but the *existence* and rough magnitude of the crossover follow from the model, which is the useful skill: given α, B, and copy costs, you can predict which regime a message size falls into before running anything.

**Interaction with non-blocking semantics.** Eager and rendezvous also change what `MPI_Isend` completion *means* operationally. For an eager send, the transfer can complete as soon as the wire has accepted the data (or, on RDMA transports, the NIC has read the buffer) — completion is largely a local event. For a rendezvous send, the fin/ack makes send completion partly *remote*: the sender's buffer is not guaranteed reusable until the receiver has actually pulled the data. This is why a large `MPI_Isend` followed immediately by overwriting the buffer is illegal — `MPI_Wait` must intervene — and why the standard's "buffer may be reused after completion" rule from DIST-2.2 is not vacuous: for rendezvous messages it encodes a real cross-process dependency.

**Hardware angle.** Modern NVIDIA ConnectX-7-class NICs ship dedicated offload engines for exactly these two mechanisms — "MPI tag matching" and "Rendezvous protocol offload" are listed as in-network-computing accelerators on the ConnectX-7 datasheet — and UCX's hardware tag-matching support constrains the protocol itself: with matching offloaded, the effective rendezvous threshold becomes `min(segment size, UCX_RNDV_THRESH)` because the NIC's posted-receive entries and bounce-buffer sizes bound what the hardware path can express. Implementation reality shapes protocol thresholds from both sides.

### 1.4 Buffering and copying (DIST-2.6)

**The problem.** Sections 1.1–1.3 kept saying "the library stores it," "a copy occurs," "staging buffer." Time to be systematic: between the application buffer you named in the MPI call and the wire, there is a *hierarchy* of buffers, and every extra buffer is a potential copy — and every copy is bandwidth, cache pollution, and latency you did not ask for. At modern speeds this is not a rounding error: a 400 Gb/s (50 GB/s) link is already close to what a host's memory system sustains for a *single* streaming copy, and a GPU-resident buffer connected without GPUDirect pays far more.

**The buffer hierarchy.**

```
application buffer (user memory, maybe GPU memory)
      ↕  copy #n — where it all goes wrong
library staging buffers:
    • eager buffers / unexpected-message storage (heap)
    • bounce buffers (small pre-registered, reusable)
    • RDMA-registered staging regions (pinned host memory)
      ↕  DMA (zero-copy if registered)
NIC / transport
```

Where copies actually occur, case by case:

1. **Eager + expected receive**: NIC DMAs payload directly into the application buffer. Zero copies — the best case. This requires the receive to be posted before the message arrives, which is precisely why the pre-posted-receive-window pattern of 1.1 exists: *pre-posting converts an unexpected message into an expected one, eliminating a copy.*
2. **Eager + unexpected receive**: payload is copied into internal storage when it arrives, then copied again into the application buffer when the receive is posted. Two traversals of the payload through host memory.
3. **Rendezvous**: receiver's NIC writes directly into the application buffer (registered for RDMA). Zero copies of the payload — the entire point of the extra round trip.
4. **GPU-resident buffers without GPUDirect** (previewing Module 6): GPU memory → copied to pinned host staging → NIC; on arrival, host staging → GPU memory. Two extra full-payload copies *plus* PCIe crossings, all done by the CPU or copy engines. This is the "host staging" path that Modules 6–7 replace with GPUDirect RDMA.

**The rules MPI gives you for managing buffering.** The standard offers *send modes* precisely because buffering policy is an application decision:

- `MPI_Send` (standard mode): implementation chooses eager or rendezvous — the behavior we analyzed in 1.3.
- `MPI_Bsend` (buffered mode): *you* guarantee buffering by attaching your own buffer (`MPI_Buffer_attach`); the send is then locally completable the moment the payload is in *your* buffer, no receiver involvement needed. Cost: your memory, your copy — but predictable, deadlock-free behavior (the buffer turns any send into an effectively eager one).
- `MPI_Ssend` (synchronous mode): the opposite promise — completion requires the receiver's matching receive; no hidden buffering on the send side at all.

Choosing a mode is choosing *who owns the copy*: the implementation (standard), you (buffered), or nobody (synchronous).

**UCX's concrete knobs.** Because UCX fronts most modern InfiniBand MPI stacks, its tuning variables are a good map of where copies live in a production stack: `UCX_TM_THRESH` (default 1024 bytes — messages below this are candidates for the hardware tag-matching path), `UCX_TM_MAX_BB_SIZE` (bounce-buffer size for hardware matching: the NIC matches against small pre-registered *bounce* buffers rather than arbitrary user buffers, trading an internal copy for offloaded matching), and `UCX_RNDV_THRESH` (the eager/rendezvous crossover of 1.3, further clamped by transport segment sizes). The lesson from the knobs: *every* buffer boundary in the hierarchy is a tunable, because every one is a performance trade-off.

**A worked cost comparison.** Sending a 4 MB GPU-resident array between nodes, host-staged versus (future) GPUDirect:

```
host-staged:  GPU -- PCIe copy --> pinned host buf --NIC--> wire
              ~ 4MB / 25GB/s = 160 µs per PCIe crossing (each way)
              + 2 host-memory traversals + CPU/GPU engine involvement
GPUDirect:    GPU memory --NIC DMA--> wire     (Module 7 territory)
```

The host-staged path pays roughly 320 µs of pure PCIe copy time *per direction* before a single byte crosses the network — larger than the wire time of the message itself on a 400 Gb/s link (4 MB / 50 GB/s = 80 µs). Buffering is not a detail; it can be the dominant term.

### 1.5 Progress (DIST-2.7)

**The problem.** Everything so far described operations as if they advance by themselves. They do not. `MPI_Isend` posted some work; *something* must now execute that work — drive the NIC, process completions, walk matching lists, copy unexpected payloads, issue rendezvous pulls. The question "who, and when?" is the **progress** question, and its answer determines whether the overlap you wrote is real.

**Who can advance an operation?**

1. **The hardware.** NICs with kernel-bypass transports process posted work autonomously: once a send descriptor sits in a queue, the NIC DMAs, frames, transmits, and produces completion events with no CPU involvement. Pure hardware progress is why simple eager transfers genuinely overlap with computation.
2. **You, the application, whenever you call MPI.** Most MPI implementations make progress *opportunistically inside MPI calls*: every `MPI_Wait`, `MPI_Test`, even `MPI_Send` first polls for network events, advances matching, retires completions. If your code calls no MPI function for 10 ms, *nothing* progresses for 10 ms — even transfers the hardware could have finished — because the software half of the protocol (matching, buffer delivery, rendezvous handshakes) is frozen.
3. **A dedicated progress thread.** Implementations can run a background thread that polls continuously (at cost: a core, cache interference, and locking against the main thread — this is also where `MPI_THREAD_MULTIPLE` and thread-support levels become relevant). UCX and the major MPIs support asynchronous-progress modes of exactly this kind.
4. **The accelerator itself — increasingly.** The newest answer: GPU kernels issue communication work directly, so progress happens on the device timeline with no CPU in the loop (UCX's device APIs, and NVSHMEM's device-initiated model in Module 10). This is the direction the whole field is moving, as the developments section shows.

**Why progress failure looks like mysterious stalls.** Consider a rendezvous receive: the header arrives; the receiver-side library must issue the RDMA READ that pulls the payload. If the receiving rank is deep inside a 50 ms compute kernel making no MPI calls, that RDMA READ is not issued until the kernel ends — the sender's data sits in its buffer, the sender's `MPI_Isend` stays incomplete, and if the sender then loops on `MPI_Wait`, both ranks appear "hung" on a perfectly correct program. The code is deadlock-free by the DIST-2.8 definition yet stalls on *progress*. The same mechanism explains why pre-posted receive windows (1.1) fix more than matching: they give the library standing work that hardware can progress immediately.

**The unexpected-message storm, revisited with full machinery.** Now every piece of today's volume clicks together on a real failure mode, documented in MPICH's mailing-list archives: 63 processes all sending results to one receiver. The receiver processes each message slower than senders produce them (it must *do something* with each payload). The senders' eager sends complete locally — buffer reusable once the wire took the data — so senders experience no backpressure and keep sending. Arriving messages find no posted receives (the receiver is busy), so each payload is copied into internal unexpected-message storage — until the library dies with *"Failed to allocate memory for an unexpected message. 261,895 unexpected messages queued."* Eager protocol (1.3) + unbounded unexpected buffering (1.6's queues from 1.2) + a receiver that cannot make progress fast enough (1.5): the failure is a *systems* failure, not a bug in any one layer. The fixes follow from the analysis: pre-post a bounded receive window (turn unexpected into expected), throttle senders with synchronous sends or credit-based flow control, or restructure with collectives — each fix attacks a different layer of the same stall.

**Progress and fairness.** One more subtlety: when an implementation polls opportunistically, it typically progresses *all* pending work on every call — but which completions get processed in which order is unspecified. Codes that assume `MPI_Test` on request A will somehow progress (but never complete) request B are relying on implementation behavior the standard does not promise. Rule of thumb: never reason about *partial* progress; reason about completion guarantees only.

**Where this lands.** Progress is the bridge from today's module to everything modern: asynchronous progress threads (Module 11's overlap engineering), hardware progress (RDMA, Module 7), and device-initiated progress (NVSHMEM, Module 10). The one-sentence summary of the entire point-to-point module: *a message is a state machine — initiated, matched, transported, buffered, completed — and the art of distributed performance is knowing which agent advances each state transition, and paying only for the transitions that are actually on your critical path.*

## 2. Key Developments / News

### 2.1 UCX 1.20–1.22: the progress engine moves into the NIC and the GPU

**What happened.** The UCX project — the communication framework underneath HPC-X, Open MPI's primary high-performance transport on InfiniBand, and much of the GPU-cluster MPI ecosystem — has shipped three major releases in the past year: 1.20.0 (December 2, 2025), 1.21.0 (June 24, 2026), and 1.22.0 (August 2, 2026). The headline theme across all three is *device-initiated communication*: a new GPU device API for direct GPU-to-GPU communication, host APIs for GPU device management, a device signaling API, the `rc_gda` transport and the GDAKI transport "with endpoint export to GPU," and — most significantly for scale-out — support for a **Direct NIC (DPU) data path with CUDA, enabled by default for the IB transport**, plus `nvidia_peermem` driver checks, DMA-BUF mapping over PCIe for the Direct NIC path, and ConnectX-9 device support. The 1.22 release continues the arc (GET/PUT rendezvous protocols for RMA, multi-lane support for device operations, four-rail defaults for "Vera"-class platforms).

**What technically changed.** Until now, even "GPU-aware" MPI stacks kept the CPU as the coordinator: host threads posted NIC work on behalf of GPU data. The Direct NIC / GDAKI path lets GPU-side operations reference NIC resources directly — the GPU initiates, the NIC executes, and the host is off the data path and largely off the control path. In today's vocabulary: progress (DIST-2.7) moves from "the application thread when it calls MPI" and "a progress thread" to "the device itself," which is exactly the category NVSHMEM was built to exploit (Module 10) and the direction DIST-17.5 names as GPU-initiated networking.

**Why it matters.** This is the software-stack response to a hardware reality from earlier volumes: at 800 Gb/s per port with multiple rails per GPU, a CPU core shepherding every transfer becomes the bottleneck — host-mediated progress cannot keep up with injection bandwidth. Offloading initiation to the device is the same latency-regime fix we identified in the Quantum-X800 discussion (reduce the number of host-side events, since α on the host path cannot shrink), applied to software.

**Connection to today's curriculum.** Every piece of today's lesson reappears with new actors: the "who advances the operation" question of DIST-2.7 now has a fourth answer; the buffer hierarchy of DIST-2.6 gains device-visible lanes and rkeys (remote memory keys packed for device use); and the protocol machinery of DIST-2.5 (eager/rendezvous, now extended with GET/PUT rendezvous for RMA in 1.22) is being re-expressed on paths that bypass the host entirely.

**What to watch.** Whether MPI applications transparently benefit (device-initiated paths first serve NVSHMEM-style runtimes and libraries like NCCL), how GDAKI's peer-failure handling matures (fault tolerance is a 1.22 "foundation" item, meaning the hard parts are still ahead), and whether ConnectX-9's device capabilities widen the gap between GPUDirect-capable stacks and everything else.

### 2.2 Hardware MPI tag matching heads to maintenance — a lesson in what is worth putting in silicon

**What happened.** NVIDIA's HPC-X documentation now states that hardware tag matching — offloading MPI's matching lists to the NIC, supported since ConnectX-5 — "is in maintenance support mode for adapter cards from ConnectX-5 through ConnectX-7 and is unsupported on ConnectX-8 NICs and newer." The ConnectX-7 datasheet, by contrast, still advertises MPI tag matching and rendezvous-protocol offload as headline in-network-computing engines. A feature that was once a flagship capability of the InfiniBand MPI stack is being retired as the hardware generation that carried the GPU-direct era arrives.

**What technically changed.** Hardware tag matching moves the receiver's posted-receive list into the NIC: the hardware scans arriving messages against posted receives (tag, source, communicator), delivers eager messages straight into application buffers, and hands off only what it cannot match. The Linux kernel's InfiniBand documentation describes the resulting design in detail — the hardware-maintained posted-receive list shadowed in software, the unexpected-message list staying in software, and the rendezvous path where the NIC "uses the information from the header to initiate an RDMA READ operation directly to the matching buffer." The costs were real too: bounce buffers for messages matched in hardware (`UCX_TM_MAX_BB_SIZE`), a matching-size threshold (default `UCX_TM_THRESH` = 1024 bytes), and a rendezvous threshold clamped by hardware segment sizes — the buffering and protocol knobs of DIST-2.6 as hard constraints.

**Why it matters, and why it is being sunset.** Hardware matching is a *latency-regime* optimization: it removes per-message CPU work from the receive path so small, latency-sensitive messages can be consumed while the CPU computes. That matters for CPU-driven MPI message streams. But the workloads driving the newest hardware (collective-heavy LLM/HPL-MxP-class GPU computing) increasingly avoid MPI matching altogether — NCCL, asked about this on NVIDIA's own forums, "does not use the MPI tag matching semantics or the hardware tag matching offload": its channels are pre-negotiated, point-to-point, and explicitly addressed. When the dominant traffic stops matching, silicon that only accelerates matching is dead weight — and the transistor budget goes instead to the device-initiated data paths of 2.1.

**Connection to today's curriculum.** This development is DIST-2.4 (matching) and DIST-2.7 (progress) rendered as a product decision: NVIDIA effectively bet that *implicit matching* — the receiver-side bookkeeping of send/receive semantics — is not where future progress should happen, while *explicitly addressed, device-initiated data movement* is. When you reach Module 10, notice that NVSHMEM's symmetric-heap, put/get model is exactly the "no matching needed" design that made hardware tag matching unnecessary.

**What to watch.** Whether the Ultra Ethernet ecosystem reopens the question (its transport semantics were designed around explicitly addressed, packet-sprayed data paths rather than matching), and whether any successor offload (in-network collectives, SHARP-class aggregation) fares better against the same economics.

### 2.3 Paper: persistent and partitioned MPI for stencil communication (arXiv:2508.13370)

**What happened.** A 2025 paper (arXiv:2508.13370, cs.DC, submitted August 2025) adds persistent and partitioned MPI communication optimizations to the Comb stencil benchmarking suite and measures their effect on halo-exchange-dominated communication at various scales — reporting speedups of up to **37%** for persistent communication and up to **68%** for partitioned communication over the baseline non-blocking implementation.

**What technically changed.** The baseline is precisely the pattern from Section 1.1: per iteration, pack halo buffers, `MPI_Isend`/`MPI_Irecv` every face, `MPI_Waitall`, unpack. The persistent variant (an MPI-1-era idea, standardized in MPI-4 with generalized requests) binds the *arguments* of each communication once via `MPI_Send_init`/`MPI_Recv_init` — the standard's own metaphor is a "half-channel" — and then each iteration reduces to `MPI_Startall` + `MPI_Waitall`. The partitioned variant (MPI-4) goes further: a single message is split into partitions, and *threads* fill/communicate partitions concurrently — overlapping pack, transfer, and unpack at sub-message granularity. The paper also analyzes how process count, thread count, and message size modulate the gains.

**Why it matters.** Persistent communication attacks exactly the per-call overheads we catalogued today: argument validation, request setup, matching-list maintenance, and the repeated re-expression of an *unchanging* communication pattern (same buffers, same neighbors, same tags — every stencil iteration of every timestep). Partitioned communication additionally attacks the serialization *inside* the communication: the pack→send→wait→unpack chain that a single thread otherwise executes sequentially. These are measured, reproducible wins on the single most common communication pattern in scientific computing (halo exchange, Module 14's DIST-14.2).

**Research claim versus independent fact.** The 37%/68% figures are the authors' measurements on their systems, for stencil codes with specific message sizes and process/thread counts — the paper itself analyzes how the benefit varies with those parameters, and the speedups should be read as "up to," not "always." The *mechanism* (amortized setup, sub-message overlap), however, is solidly grounded in the semantics we studied today.

**Connection to today's curriculum.** Persistent requests are the standard's answer to "I keep issuing the identical non-blocking operation" — a direct optimization of DIST-2.3's initiation path that also relieves DIST-2.4's matching machinery (envelopes can be bound once). Partitioned communication is a first taste of fine-grained overlap, which Module 11 develops fully (double buffering, pipelining, chunk sizing). The paper is, in effect, today's lesson with benchmarks attached.

**What to watch.** Adoption of MPI-4 partitioned communication in production codes (it requires restructuring around partition-ready buffers); how these optimizations compose with the device-initiated paths of 2.1 (persistent, explicitly addressed channels are exactly what GPU-side runtimes want); and whether future MPI standards deepen this direction (MPI 5.0 already generalized persistent collectives).
