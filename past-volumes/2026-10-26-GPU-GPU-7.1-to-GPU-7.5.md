## 0. Concise Summary

Today we cross the border between the two halves of an accelerated node: the CPU's DRAM and the GPU's HBM. The **discrete memory model** (GPU-7.1) says these are two separate physical memories with two separate address spaces, joined by one wire — and that single fact explains most of the structure of GPU programming: why `cudaMalloc` exists, why `cudaMemcpy` exists, and why data movement is a first-class cost you budget for rather than an implementation detail.

That wire is **PCI Express** (GPU-7.2). We work through lanes, generations, packet structure, and the encoding evolution (8b/10b → 128b/130b → PAM4 with flit-based encoding), and derive the key engineering inequality: the arithmetic intensity needed to keep a GPU fed across a PCIe link is hundreds of flops per byte — for an A100 on Gen4, about 780 FP64 flops per byte, which for HPL means problem sizes below N ≈ 10,000 spend as much time on the upload as on the factorization itself.

Section GPU-7.3 follows a transfer end to end — API call, driver, DMA copy engine, TLPs across the root complex — including the direction-dependent synchronization semantics of `cudaMemcpy` and the double-buffering math for overlapping copies with kernels. GPU-7.4 explains the single biggest practical transfer optimization, **pinned (page-locked) host memory**: why DMA cannot safely read pageable memory, how the driver's hidden staging copy silently halves your bandwidth, and what pinning costs in return. GPU-7.5 introduces **Unified Virtual Addressing (UVA)** — one virtual address space spanning host and all GPUs — and draws the crucial line between virtual unification (pointer plumbing, which CUDA has had since CUDA 4.0) and physical unification (shared or coherent memory, which is a hardware property).

In developments: PCI-SIG shipped the **PCIe 7.0 specification** (128 GT/s, up to 512 GB/s bi-directional per x16) in June 2025; a three-way demo at the **2026 OCP Global Summit** pushed PCIe over optics to rack scale, attacking the reach limit rather than the rate limit; and an **ISMM 2026 paper** gave the first systematic empirical validation of the Grace-Hopper superchip's CPU-GPU cache coherence — the exact boundary today's curriculum draws, seen from the other side.

## 1. Learn the Concepts

### GPU-7.1 — The discrete CPU-GPU memory model: two computers, one wire

**Why the model exists.** A server GPU is not a device with a fast port; it is a second computer. It has its own memory (HBM or GDDR, soldered on-package or on-board), its own memory controllers, its own page tables managed by the device driver, and its own execution engines. The host CPU's DRAM is a different physical memory, built on different technology (DDR DIMMs, optimized for capacity and cost per gigabyte) than GPU memory (HBM stacks, optimized for bandwidth: multi-TB/s today versus a few hundred GB/s for the best DDR5 systems).

This separation is not an accident or a temporary inconvenience — it exists because it lets each memory system scale with the processor it serves. GPU compute throughput has grown roughly in step with HBM bandwidth (both ride the same packaging and process advances), while host DRAM capacity grows independently. If GPU and CPU shared one physical memory, that memory would have to compromise between the two roles, or the interconnect would have to carry every GPU load and store — which no link in existence can do at HBM rates.

**The consequences.** The discrete model means:

1. **Two address spaces.** A pointer obtained from `malloc` is meaningful to the CPU; a pointer from `cudaMalloc` is meaningful to the GPU. Dereferencing the wrong one in the wrong place is not a type error the compiler catches — on the device it is a runtime illegal-memory-access, and on the host it is a segfault, because each side's MMU simply has no mapping for the other's addresses.
2. **Explicit data movement.** Data crosses between the spaces only because you asked it to, with `cudaMemcpy` / `cudaMemcpyAsync` (or a peer-to-peer transfer). There is no hardware path by which a normal GPU load instruction reaches host DRAM on a classic discrete system — the load goes to the GPU's MMU, finds no translation, and faults.
3. **Data movement is a budgeted cost.** Because the link (PCIe today's topic) is 1–2 orders of magnitude slower than either memory, the amount of data moved per unit of work — the arithmetic intensity — decides whether offloading pays at all.

**A concrete lifecycle.** The canonical accelerated program has this shape:

```c
float *h_A = (float*)malloc(bytes);        // host address space
float *d_A;
cudaMalloc(&d_A, bytes);                   // device address space
cudaMemcpy(d_A, h_A, bytes, cudaMemcpyHostToDevice);   // cross the wire
myKernel<<<grid, block>>>(d_A, n);         // runs on the GPU only
cudaMemcpy(h_A, d_A, bytes, cudaMemcpyDeviceToHost);   // cross back
```

Four of the five lines exist purely because of the discrete model. On an integrated GPU (or a cache-coherent superchip, see §2.3), the same computation can be expressed without the copies — which is precisely why vendors are attacking this boundary.

**When does offloading pay? Quantify it.** Suppose a computation does `F` flops over `M` bytes of input that must cross the link at effective bandwidth `B`, and the GPU computes at rate `r_gpu`. Even with perfect overlap of copy and compute (GPU-7.3), the input upload costs `M/B` seconds and cannot be hidden below the compute time `F/r_gpu`. The copy fully hides only if

```
M / B  ≤  F / r_gpu        ⟺        I = F/M  ≥  r_gpu / B
```

i.e., the algorithm's arithmetic intensity `I` (flops per byte moved) must exceed the ratio of GPU compute rate to link bandwidth. For an A100 80GB on a PCIe Gen4 x16 link: `r_gpu` ≈ 19.5 TF/s FP64 (tensor cores), `B` ≈ 25 GB/s achieved — so `I` must be at least **~780 FP64 flops per byte**. That is an enormous intensity; very few kernels sustain it, which is why the CUDA Best Practices Guide's first data-transfer rule is simply: *minimize transfers, and keep intermediate results on the device* [2].

**Connection to HPL.** In HPL (dense LU factorization, `F = 2N³/3` flops over an `N×N` matrix of `8N²` bytes), the intensity of the initial upload is `I = N/12` flop/byte. Setting `N/12 = 780` gives **N ≈ 9,400**: for problem sizes below that, uploading the matrix to an A100 over PCIe Gen4 takes about as long as factorizing it. At N = 100,000 the upload is ~9% of runtime — still visible, which is why serious runs generate the matrix directly on the device (or read it from storage via GPUDirect) and let all subsequent traffic flow GPU-to-GPU over faster fabrics. The host link is a loading dock, not a highway.

**What this topic is not.** The discrete model is the *default*, not the law. Unified Memory (GPU-7.6, next volume) and coherent superchips (§2.3) change who moves the data and whether the two sides share page tables — but the physics of "two memories, one wire" still governs performance in all of them. Everything below is about that wire.

### GPU-7.2 — PCI Express: the wire itself

**Structure: lanes, links, packets.** PCIe is a *point-to-point, packet-switched, full-duplex* interconnect. A **lane** is one differential pair in each direction. Links scale by width — x1, x4, x8, x16 — with a GPU typically getting x16 and NVMe drives x4. Data moves as **TLPs (transaction layer packets)**: a header (address, type, routing) plus a payload (up to 256–4,096 bytes depending on negotiated max payload size), protected by CRC at the data-link layer. Flow control is credit-based: the receiver advertises buffer credits per TLP class, and a transmitter may not send what it cannot pay for — this is why a PCIe link never drops data under congestion, it simply stalls.

Topology is a tree rooted at the CPU's **root complex** (GPU-6.5), which converts PCIe transactions into memory transactions on the host side. **PCIe switches** fan out the tree — on multi-GPU boards and appliances, a switch typically sits between the host link and several GPUs, and (importantly) also enables **peer-to-peer** traffic between devices hanging off the same switch without round-tripping through host DRAM.

**Generations and the encoding story.** Each generation doubles the per-lane rate; what changed is *how* the doubling is achieved:

| Generation | Raw rate/lane | Encoding | Usable/lane/direction | x16 per direction |
|---|---|---|---|---|
| PCIe 3.0 (2010) | 8 GT/s | 128b/130b NRZ | ~0.985 GB/s | ~15.8 GB/s |
| PCIe 4.0 (2017) | 16 GT/s | 128b/130b NRZ | ~1.97 GB/s | ~31.5 GB/s |
| PCIe 5.0 (2019) | 32 GT/s | 128b/130b NRZ | ~3.94 GB/s | ~63 GB/s |
| PCIe 6.0 (2022) | 64 GT/s | PAM4 + flit | ~7.88 GB/s | ~126 GB/s |
| PCIe 7.0 (2025) | 128 GT/s | PAM4 + flit | ~15.8 GB/s | ~252 GB/s |

Two mechanisms did the work. First, encoding efficiency: Gen1/2 spent 20% of the wire on 8b/10b balancing; Gen3 moved to 128b/130b (~1.5%), which is where the "8 GT/s but 0.985 GB/s" numbers come from. Second, and more fundamental: at Gen5, classic NRZ signaling (two voltage levels, one bit per symbol) hit a wall — 32 Gbaud is already at the limit of what cheap FR-4 boards and copper cables can carry. Gen6's answer was **PAM4**: four voltage levels, two bits per symbol, so 64 GT/s arrives at a 32-Gbaud symbol rate — the same baud as Gen5. The price is signal integrity: four levels shrink the vertical eye opening to roughly a third, costing on the order of 9 dB of noise margin, which is why Gen6+ also adopted **flit-based encoding** with CRC and forward error correction — small, fixed-size flits that make FEC practical at low overhead. PCIe 7.0 (§2.1) continues this scheme at 64 Gbaud PAM4 to reach 128 GT/s [5].

**Latency.** Per-hop link latency is hundreds of nanoseconds, but a complete host-initiated transfer — API call, driver validation, descriptor handoff to a DMA engine, TLPs across the root complex, completion — lands in the microseconds. Order-of-magnitude, this is 10–100× a local HBM access (~few hundred ns) and 10–100× cheaper than an inter-node network message. PCIe sits in the middle of the latency hierarchy, which is exactly its architectural role.

**Why PCIe becomes the bottleneck.** Put the numbers side by side: an H100 SXM carries ~3.35 TB/s of HBM3 bandwidth; its host link (Gen5 x16) carries ~63 GB/s per direction usable — a **~53:1 ratio**. A kernel that streams its working set from host memory across PCIe runs at roughly 2% of the speed the same silicon could achieve from HBM. This ratio is the entire reason the ecosystem looks the way it does:

- GPUs carry large local memories so that working sets *stay* on the device (7.1's intensity condition);
- scale-up fabrics (NVLink, soon §2.2's optical variants) exist because PCIe could not serve GPU-to-GPU traffic at those rates;
- and entire software disciplines — pipelining, prefetch, GPUDirect — exist to make sure the slow link is never on the critical path.

The link's *reach* is also a bottleneck: Gen5-class NRZ signaling works over roughly half a meter of board copper, which bounds how large a single PCIe domain can be. Hold that thought for §2.2.

### GPU-7.3 — Host-to-device and device-to-host transfers: the path of a copy

**Who actually moves the data.** When you call `cudaMemcpy(d_A, h_A, bytes, cudaMemcpyHostToDevice)`, the CPU does not copy anything byte-by-byte. The runtime validates the arguments, splits the request into chunks, and posts descriptors to the GPU's **copy engines** — the DMA engines we met as GPU-5.7's asynchronous hardware queues. For an H2D copy, the copy engine issues PCIe *memory-read* TLPs toward the root complex; the host memory controller returns the data in completion TLPs; the engine writes it into HBM. For D2H, the engine reads HBM and issues memory-*write* TLPs toward the host. The CPU's involvement ends at posting the descriptor (and, for synchronous calls, waiting).

```
   Host side                                Device side
 ┌───────────────┐  x16 lanes   ┌─────────────────────────────┐
 │ DDR5 DRAM     │◄────────────►│ copy engine (DMA)           │
 │  ┲ (pinned or │  TLPs both   │  ┃ posts reads/writes        │
 │  ┃ pageable)  │  directions  │  ▼                          │
 │ CPU cores ────┤              │ HBM3e (frame buffer)        │
 │ root complex  │              │ SMs (compute)               │
 └───────────────┘              └─────────────────────────────┘
```

**Synchronization semantics — subtler than the API names suggest.** The CUDA Runtime API documentation is refreshingly blunt that "synchronous" and "asynchronous" in the function names describe the *intent*, while the actual behavior depends on the memory type and direction [3]:

| Transfer | Sync `cudaMemcpy` returns… | Notes |
|---|---|---|
| Pageable → device | …after the pageable buffer has been copied to driver staging memory | A *hidden extra copy* through pinned staging buffers (§7.4); the DMA to the device may still be in flight |
| Pinned → device | …only when the whole transfer is done | Synchronous with respect to the host |
| Device → host (any) | …only when the copy has fully completed | The host buffer is safe to read on return |
| Device → device | immediately, no host sync | Executed on-device |

The same document notes that the "Async" variants *may* behave synchronously when pageable memory forces the driver to stage through pinned buffers [3] — the single most common reason a "non-blocking" copy secretly blocks.

**Asynchronous transfers and streams.** `cudaMemcpyAsync(..., stream)` enqueues a copy on a stream — an ordered queue of device operations. Operations in different streams can overlap, and on any modern GPU the copy engines and the SMs are independent resources, so a copy in stream A genuinely proceeds while kernels run in stream B. The `asyncEngineCount` device property reports how many copy engines exist (typically at least one per direction).

**The correctness trap.** Async means *the function returns early*, not *the data has moved*. After `cudaMemcpyAsync(d, h, …)` returns, `h` must not be modified until the copy completes — enforce with `cudaStreamSynchronize` or an event. The classic bug: reuse of the host buffer in a loop overwrites data that the DMA engine has not fetched yet.

**Overlap math: double buffering.** Suppose a workload splits into `C` chunks, each needing copy time `c` and kernel time `k`. Serial execution costs `C·(c+k)`. With two buffers alternating copy and compute:

```
T_pipelined ≈ c + (C−1)·max(c, k)
```

The first chunk's copy is exposed; after that, the slower of the two stages dominates and the faster one hides entirely. Numeric example: `c = 0.8 s`, `k = 2.0 s`, `C = 10`. Serial: 28 s. Pipelined: `0.8 + 9×2.0 = 18.8 s` — a 33% saving, within 6% of the compute-only floor of 20 s. If `c > k`, the same formula tells you the link, not the GPU, is the pace-setter — which is exactly the situation GPU-7.4 exists to fix.

This pattern — copy chunk *i+1* while computing chunk *i* — is the backbone of out-of-core HPC: streaming LU solvers, batched distributed linear algebra, and every GPU pipeline that processes more data than fits in VRAM.

### GPU-7.4 — Pinned versus pageable transfers: why pinning changes everything

**The backstory: virtual memory.** Host memory as the CPU sees it is virtual. The OS maps virtual pages onto physical frames through per-process page tables, and it retains the right to change that mapping at any time — migrating a page between DRAM and swap, compacting memory, or reusing the frame after `free`. Pageable (ordinary `malloc`'d) memory lives under this regime.

**Why DMA can't touch it.** A DMA engine works with *physical* addresses: the device drives addresses onto the memory bus. If the OS migrated a page between the moment the driver translated "virtual page → physical frame" and the moment the DMA engine read that frame, the engine would silently receive the wrong data — no error, just corruption. The OS cannot revoke a translation it has handed to a device. Hence the rule: **DMA requires page-locked (pinned) memory** — pages the OS promises never to move or swap out.

**What the driver does when you don't pin.** If you pass pageable memory to a transfer, the CUDA driver cannot DMA from it directly, so it copies your buffer into its own pinned staging buffers first and DMAs from there [3]. Your transfer becomes: CPU memcpy into staging (at host DRAM bandwidth, single-threaded) + DMA across PCIe. The staging copy is why pageable transfers typically land well under half of link bandwidth, while pinned transfers on the same system approach it. NVIDIA's Best Practices Guide quantifies the target: on PCIe Gen3 x16, pinned transfers attain roughly 12 GB/s against ~15.8 GB/s usable — about three-quarters of the wire [2]. The table in §7.3 already showed the semantic consequences: pageable H2D returns after staging (the DMA may still run), pinned H2D is synchronous, and pageable "async" calls degrade toward synchronous [3].

**How to pin.** Three entry points [1]: `cudaMallocHost` (allocate fresh pinned memory), `cudaHostAlloc` (same, with flags for portability/mapping), and `cudaHostRegister` (pin an *existing* buffer — invaluable when the memory comes from a third-party library you don't control). Note the interplay with topology (GPU-6.5/6.6): the physical frames behind a pinned allocation are placed by the allocation/first-touch policy of the calling thread, so on a dual-socket server, pinning from a thread on the far socket from the GPU silently adds an inter-socket hop to every transfer. Pin on the NUMA node that owns the GPU's root complex.

**The costs — pinning is not free.** The Best Practices Guide is explicit: pinning is a *heavyweight* operation (it locks pages, updates kernel page tables, and can require global TLB shootdowns), and pinned memory is a scarce resource — it is unswappable, so every pinned gigabyte reduces what the OS can schedule flexibly; over-pinning degrades whole-system behavior in ways that are hard to predict in advance [2]. Practical discipline: pin the buffers that actually cross the link, size them honestly (double-buffer pools, not whole datasets), and reuse them rather than pinning per-iteration.

**Where this is heading.** Pinning exists because PCIe systems have no shared translation between CPU and GPU. On Grace-Hopper-class coherent systems with NVLink-C2C, hardware coherence plus huge pages removes the need to pin for performance [4] — and with CUDA's HMM on x86 Linux, ordinary malloc'd memory gains software coherence [1]. GPU-7.8 will pick up that thread properly; for now, the takeaway is: **on every discrete-PCIe system you will actually use this decade, pinned staging buffers plus async copies are the difference between ~50% and ~75–90% of link bandwidth.**

### GPU-7.5 — Unified Virtual Addressing: one address space, still two memories

**What UVA is.** Since CUDA 4.0, all memory in a process — host memory and the global memory of *every* GPU in the system, however allocated (`cudaMalloc`, `cudaMallocHost`, `malloc`, `mmap`) — lives in a **single virtual address space**, with the CPU and each GPU occupying disjoint ranges [1]. UVA is plumbing, not magic: no data moves because UVA exists. What it buys:

1. **Pointer introspection.** The *value* of a pointer now tells the runtime where the memory lives: `cudaPointerGetAttributes()` answers "host, GPU 0, GPU 1, managed…?" for any address.
2. **Direction-free copies.** `cudaMemcpyDefault` lets the runtime infer H2D/D2H/D2D from the pointers — the direction argument stops being a foot-gun.
3. **Peer access with real pointers.** When peer access is enabled between two GPUs, UVA is what allows a kernel running on GPU 0 to dereference a pointer allocated on GPU 1 directly: the address itself identifies the owning device, and the traffic flows over the P2P path (PCIe or NVLink) without staging through host DRAM.

**What UVA is not — the critical distinction.** UVA unifies the *virtual* address space only. The underlying memories remain physically separate, and a host pointer still cannot be dereferenced by device code on a classic discrete system (that requires *mapped* memory — GPU-7.7, next volume — or Unified Memory's migration machinery — GPU-7.6). Conflating the two is the most common conceptual error in this area, so state it precisely:

> UVA: one *numbering scheme* for addresses. Unified Memory: a *data-placement and migration* feature. Coherent systems: a *hardware* guarantee that CPU and GPU views of memory agree. Three different layers, three different topics.

**Why UVA still matters for performance-minded code.** Because a virtual address no longer implies a physical location, libraries can accept "a pointer" and internally dispatch on where it lives — cuBLAS taking device pointers, NCCL resolving peer addresses, profilers attributing transfers. UVA is also the substrate that made later features expressible: managed memory (7.6) hands the *migration* of UVA-space allocations to the runtime; Grace-Hopper's **ATS** (Address Translation Services) makes CPU and GPU literally share one per-process page table, so every system allocation is visible to both processors without any driver mediation [4] — the hardware-era fulfillment of what UVA approximated in software.

**The mental model to keep.** Think of the process as owning one enormous virtual address space, over which two computers each hold partial maps. The CPU's map covers host memory densely and device memory only at the driver's discretion; each GPU's map covers its own HBM plus whatever host memory has been explicitly mapped or pinned-registered for it. Every performance question in this module — Is the data on the right side of the wire? Was the staging copy needed? Can the pointer even be dereferenced from here? — reduces to asking *which maps contain which address, and where the physical bytes actually are*.

**Connections.** UVA ties together everything today: the two-address-spaces problem of 7.1 is *represented* in the unified numbering; the copies of 7.3 are what still move the physical bytes; the pinning of 7.4 registers host ranges into the device's map so DMA can address them; and the peer-to-peer and coherence questions of 7.6–7.9 are all about how much of each other's maps CPU and GPUs can see and at what consistency. Next volume: managed memory and how the runtime decides where the bytes live.

## 2. Key Developments / News

### 2.1 PCIe 7.0 ships: 128 GT/s over PAM4, doubling the host-link ceiling

**What happened.** In June 2025, PCI-SIG officially released the PCIe 7.0 specification to members: 128.0 GT/s raw rate per lane — up to 512 GB/s bi-directional on an x16 link — using PAM4 signaling and flit-based encoding, with improved power efficiency and full backwards compatibility; PCIe 8.0 pathfinding is already in progress [5].

**What technically changed.** Gen7 is the second generation to rely on PAM4: 128 GT/s at a 64-Gbaud symbol rate with two bits per symbol, carried in FEC-protected flits. The significance for system builders is less the rate itself than the *feasibility mechanics*: NRZ at 128 GT/s would demand channels an order of magnitude better than anything affordable; PAM4 plus FEC extends the "double every three years" cadence on realistic boards — at the cost of eating into link-layer budget with error correction and tighter equalization requirements.

**Why it matters for this curriculum.** The host-device link of GPU-7.2 typically lags the spec edge by one to two generations — today's accelerator platforms attach at Gen5 (~63 GB/s per direction usable on x16). Even at Gen7 rates, the arithmetic-intensity condition from §7.1 only relaxes by ~4×: keeping a modern GPU fed across the wire still demands hundreds of flops per byte. PCIe 7.0's real near-term customers are scale-out NICs, CXL memory expanders, and storage — links whose traffic is *streaming* rather than *random access*. Watch: Gen6 endpoints entering volume in the 2026–2027 platform generation, and the first silicon PHYs at Gen7 rates.

### 2.2 PCIe goes optical at rack scale — the reach limit, answered

**What happened.** At the 2026 OCP Global Summit (San Jose, October 12–15, 2026), Lumentum, Astera Labs, and Corning demonstrated a rack-scale PCIe-over-optics link: Lumentum's 1060 nm VCSEL-based optical engine (2D VCSEL/photodetector arrays with backside lens technology) over Corning multimode fiber, switched by an Astera Labs Scorpio Smart Fabric Switch. The proof-of-concept ran multiple 32 Gb/s NRZ optical channels and an error-free PCIe 5 link in a rack-representative arrangement [6].

**What technically changed.** Note the rate: 32 Gb/s NRZ per channel is PCIe-5-class signaling. This demo attacks *reach and density*, not bandwidth per lane. Electrical Gen5-class signaling is practical over roughly half a meter of board copper; beyond that, retimers and thick cables burn power and obstruct airflow. Converting to optics costs a fixed electrical↔optical conversion penalty per end, but after that, distance is nearly free — which is how a PCIe domain can be stretched across a rack of trays and switches while preserving load/store transaction semantics (the TLP machinery of GPU-7.2 rides unchanged on top).

**Why it matters.** §7.2 identified two PCIe bottlenecks: bandwidth ratio and *reach*. The industry fixed the first by inventing NVLink for GPU-to-GPU scale-up; the second is now being fixed by putting the same class of optical links under the PCIe/CXL fabric itself. The parallel move is visible at the top of the stack too: NVIDIA's Vera Rubin Ultra NVL576 plans combine copper in-rack with direct optical rack-to-rack NVLink across eight racks — per NVIDIA's March 2026 materials as reported at OCP 2026 — and co-packaged optics switch trays [7]. The pattern to internalize: *electrical for centimeters, optics for meters*, at every layer of the fabric. Watch: whether PCIe-over-optics gets standardized (today it is vendor demos plus switch ecosystems), and the power-per-bit crossover where optics beats copper inside a single rack.

### 2.3 Grace-Hopper's cache coherence, empirically validated (ISMM 2026)

**What happened.** "Consistency and Coherence of the NVIDIA Grace-Hopper Superchip" (Bagchi, Srivastava, Levine, Nagarajan — presented at ISMM 2026, Boulder, June 2026) reports the first systematic empirical study of the memory consistency and coherence of a shipping cache-coherent CPU-GPU system. Using a heterogeneous litmus-testing methodology spanning 1,960 test variants, the authors validate that Grace-Hopper enforces the Compound Memory Consistency Model (CMCM) — the theoretical contract required for *independently compiled* CPU and GPU code to interact safely through shared memory — and introduce "value propagation" tests that reverse-engineer the underlying coherence machinery: internal GPU coherence relies on write-throughs and self-invalidations rather than classical writer-initiated invalidations, while global CPU-GPU coherence is maintained by directory-based invalidations consistent with an AMBA CHI-like protocol [8].

**Why it matters.** Grace-Hopper is the standing counterexample to today's curriculum topic — the discrete model of GPU-7.1 deliberately *not* applies: NVLink-C2C connects Grace CPU and Hopper GPU with 900 GB/s of bidirectional, memory-coherent bandwidth (NVIDIA states ~7× an x16 Gen5 link) and, with ATS, a single shared per-process page table, so CPU and GPU threads transparently access both LPDDR5X and HBM; the OS simply sees two NUMA nodes [4]. But "cache-coherent" in a datasheet is a marketing summary. Whether independently compiled CPU and GPU binaries can share memory correctly depends on the precise consistency model — a property no vendor datasheet specifies rigorously. This paper converts the datasheet claim into a measured protocol-level characterization, which is exactly the kind of ground truth a performance engineer needs before building, say, fine-grained CPU-GPU synchronization on atomics (which NVLink-C2C accelerates natively [4]).

**Connection and watch-next.** This development sits precisely at the boundary today's topics draw: UVA (7.5) unified *numbering*; ATS unifies *translation*; coherence unifies *contents*. The remaining curriculum topics in this module — managed memory (7.6), zero-copy (7.7), coherence itself (7.8), and the IOMMU (7.9) — walk this same spectrum from discrete to unified, and we will use this paper's findings (self-invalidation, directory-based CPU-GPU coherence) when we get there. Caveat for rigor: this is a research claim from a single group's methodology, published but young; treat the CMCM validation as strong evidence, not settled law.
