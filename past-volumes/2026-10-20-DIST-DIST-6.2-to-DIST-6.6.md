## 0. Concise Summary

Yesterday's DIST volume ended with the *host-staging path*: to send GPU-resident data between nodes, the classic route runs GPU → host memory → NIC → network → NIC → host memory → GPU. Today's five topics form a single causal chain that explains how modern GPU clusters eliminated most of that detour.

We start by **quantifying why host staging is expensive** (DIST-6.2): it adds device↔host copies, doubles PCIe traversals, pushes four passes of data through host DRAM, and — worst of all — puts the CPU and two synchronization points on the critical path of every message. The answer is **GPU-aware communication** (DIST-6.3): let the communication library accept device pointers directly and decide internally how to move them. **CUDA-aware MPI** (DIST-6.4) is the concrete realization: you pass a `cudaMalloc` pointer straight into `MPI_Send`, and the library detects the pointer type via CUDA's Unified Virtual Addressing and selects a transport — CUDA IPC inside a node, GPUDirect RDMA zero-copy for large inter-node messages, staged copies as fallback. The enabler hiding underneath is **GPU memory registration** (DIST-6.5): a NIC's DMA engine needs stable physical addresses, so GPU memory must be pinned and mapped into the PCIe Base Address Registers before the NIC can touch it — an operation that costs up to milliseconds. That cost is tamed by **registration caches** (DIST-6.6), the pin-down caches that keep buffers registered across messages and use lazy deregistration, LRU eviction, and allocation interception to stay correct when applications free and reuse buffers.

Three developments anchor this in the real world: the MPI 5.0 standard (ratified June 2025) with its new ABI, now fully implemented by MPICH 5.0.x; the ongoing kernel-side migration from the `nv_peer_mem`/`nvidia-peermem` peer-memory modules toward the Linux `dma-buf` framework, which quietly re-plumbs the very registration mechanism we study today; and the 2013 ICPP paper by Potluri et al. that first measured the host-staging penalty and the first-generation GPUDirect RDMA fix in MVAPICH2.

The practical payoff: understanding this block is what lets you look at a multi-GPU benchmark result and ask the right question — not "is the network slow?" but "which path did these bytes actually take, and was the buffer registered?"

## 1. Learn the Concepts

### 1.1 Where we left off: the staged path, recalled

From DIST-6.1, the traditional inter-node path for GPU-resident data is:

```
 Sender node                                Receiver node
 ┌─────────┐  cudaMemcpy   ┌──────────┐  NIC DMA  ┌─────┐   network   ┌─────┐  NIC DMA  ┌──────────┐ cudaMemcpy  ┌─────────┐
 │ GPU HBM │ ────────────▶ │ host DRAM│ ────────▶ │ NIC │ ═════════▶ │ NIC │ ────────▶ │ host DRAM│ ──────────▶ │ GPU HBM │
 └─────────┘   (D2H)       └──────────┘           └─────┘            └─────┘           └──────────┘   (H2D)      └─────────┘
      ▲                                                        │                                    ▲
      └────────────────── the GPU never talks to the NIC ───────┘──────────────────────────────────────┘
```

Every byte crosses the host twice, and the application (or the MPI library emulating this pattern internally) must orchestrate each hop. Today we dissect exactly why that is expensive, and how the modern stack removes it.

### 1.2 DIST-6.2 — Why host staging is expensive

"Expensive" is not a vague adjective here — host staging fails in four distinct, individually measurable ways. Separating them matters because each one bites a different workload regime.

**Cost 1: extra copies.** The staged path inserts at least one device-to-host copy on the sender and one host-to-device copy on the receiver — copies that produce no useful arithmetic. Worse, if the application stages through a *pageable* host buffer (a plain `malloc`), the CUDA driver cannot DMA from it directly and silently inserts an additional internal copy through a driver-owned pinned buffer. This is why communication libraries insist on pinned host buffers (`cudaHostAlloc`/`cudaMallocHost`) for staging, and it is also the first hint of a theme that runs through this whole volume: *DMA-capable devices can only touch memory whose physical location is pinned and known.* Keep that phrase; it returns in §1.5.

**Cost 2: doubled PCIe traffic and host memory pressure.** A direct path moves N bytes across the PCIe fabric once on the way out of the GPU and once into the remote GPU. The staged path instead forces, per side: one GPU↔host crossing plus one host↔NIC crossing. The same payload therefore traverses roughly twice as many PCIe links, and it makes four passes through host DRAM (write + read on the sender, write + read on the receiver) instead of zero. On a server where host DRAM bandwidth is shared with the MPI ranks actually computing, a dense all-to-all phase can saturate memory controllers with pure relay traffic.

A small numerical picture makes it concrete. Take a 1 GB GPU buffer on a PCIe 4.0 x16 system (~32 GB/s raw, realistically ~25 GB/s of achievable copy bandwidth):

| | Staged (sender side) | Direct (GPUDirect RDMA) |
|---|---|---|
| GPU↔host PCIe traffic | 1 GB (D2H copy) | 0 |
| host↔NIC PCIe traffic | 1 GB (NIC DMA read) | 0 |
| NIC↔GPU traffic | 0 | 1 GB (P2P DMA via BAR) |
| Host DRAM traffic | 2 GB (write + read) | 0 |
| Serialized link time (≈25 GB/s) | ~40 ms copy, then ~40 ms DMA | ~40 ms total |

Even with perfect chunked pipelining — which real libraries implemented precisely to hide this — the sender must still move 2 GB across two links and through DRAM for 1 GB of payload, and the CPU must feed the pipeline. The direct path is one crossing and no host involvement.

**Cost 3: CPU on the critical path.** In the staged scheme the CPU must, per message: launch the copy, wait for it to complete (a `cudaMemcpy` blocks; an async copy needs a stream synchronization before the buffer is safe to hand to MPI), then post the send. The receiver mirrors this. That is two CPU round-trips with hard ordering points per message per side. For large messages this wastes cycles; for *small* messages it is catastrophic, because the per-call overheads (kernel/driver launch, sync, MPI posting) dominate the actual wire time. A 64-byte message that should cost a few microseconds of network latency instead pays two copy launches and two synchronization points, each costing more than the transfer itself.

**Cost 4: serialization of the GPU pipeline.** The staging copies occupy copy engines and impose ordering: compute kernel → copy to host → network → copy to device → compute kernel. Each arrow is a place where a GPU can go idle while the *data* is the only thing working. Async copy engines can overlap with SM work in principle, but the application must be structured carefully to exploit that, and the ordering point before the MPI send remains.

Historically, MPI libraries fought these costs with **pipelined staging** — chunking the buffer so that copy, DMA, and network transfer overlap — which recovers much of the bandwidth for large messages but cannot remove the copies, the DRAM traffic, or the small-message latency floor. Pipelined staging still exists today as the *fallback* path when direct transport is unavailable; we will meet it again in DIST-7.8. The decisive fix was architectural: stop routing through the host at all.

### 1.3 DIST-6.3 — GPU-aware communication

The core idea is a division of responsibility:

> A communication stack is **GPU-aware** when its API accepts buffers that live in accelerator memory directly, and the *library* — not the application — decides how to move them, choosing between a direct path (device-to-network) and a staged path based on transport availability, message size, and topology.

This single sentence hides three engineering problems the library must now own:

**1. Pointer-type detection.** When `MPI_Send` (or its UCX equivalent) receives a `void*`, is it host memory, device memory, managed memory, or (on AMD systems) HIP memory? CUDA's **Unified Virtual Addressing (UVA)**, enabled by default since CUDA 4.0 on 64-bit processes, makes this answerable: the process's virtual address space is partitioned so that all CUDA-managed pointers fall inside a known VA range (within the first 40 bits of the address space), and `cuPointerGetAttribute()` reports the memory type and metadata for any pointer. The catch: that query costs on the order of a fraction of a microsecond — small, but a per-message tax. UCX therefore maintains a **memory-type cache**, intercepting `cudaMalloc`/`cudaFree` calls via memory hooks so pointer types are known without a driver round-trip (the cache can be disabled with `UCX_MEMTYPE_CACHE=n` when the hooks misbehave, e.g., with statically linked CUDA runtimes). Note this is a cache of *pointer types*, which is different from the registration cache of §1.6 — the two are frequently confused.

**2. Capability and topology discovery.** Can the NIC DMA to GPU memory at all (is the peer-memory/dma-buf support loaded, §1.5)? Are the two GPUs under the same PCIe root complex, enabling intra-node peer-to-peer? Is CUDA IPC available? The same logical "send" may take a completely different physical path on two clusters, and the library must discover this at communicator/window setup time, not per message.

**3. Fallback correctness.** GPU-awareness must degrade gracefully: if GPUDirect RDMA is unavailable (older driver, missing kernel module, GPU and NIC on separate root complexes in some configurations), the library silently reverts to staged transfer and the program still runs — just slower. This fallback asymmetry is exactly why DIST-16.2 later teaches you to *verify which path you actually got* instead of trusting the API name.

The architectural point worth internalizing: **GPU-awareness is a property of the software stack, not of the network.** The identical InfiniBand fabric carries a staged or a direct transfer depending entirely on whether the library detected, registered, and used GPU memory. When a benchmark shows a 2× bandwidth difference between "the same code, different MPI build," this is almost always the layer that differs.

### 1.4 DIST-6.4 — CUDA-aware MPI and equivalent models

CUDA-aware MPI is the most widespread realization of GPU-aware communication, and the programming change is deliberately minimal:

```c
float *d_buf;
cudaMalloc(&d_buf, N * sizeof(float));
/* ... kernels write into d_buf ... */
MPI_Send(d_buf, N, MPI_FLOAT, peer, tag, MPI_COMM_WORLD);   /* device pointer, directly */
```

No `cudaMemcpy`, no host staging buffer, no changed call signature. Everything interesting happens *inside* the library. Following the pointer through a modern stack (Open MPI over UCX is the canonical open-source example), the library must:

1. **Detect** the buffer is device memory via UVA (§1.3).
2. **Select a transport.** Open MPI v5.0 exposes several CUDA-capable paths: the UCX PML (the preferred route), the `smcuda` shared-memory BTL for intra-node transfers, the OFI MTL (GPU support via libfabric's *hmem* abstraction), and PSM2 on Omni-Path. UCX itself classifies GPU traffic into three CUDA transports — `cuda_copy` (staging through host memory), `gdr_copy` (low-latency host access to GPU memory via BAR mappings, used for small messages), and `cuda_ipc` (intra-node peer-to-peer via CUDA inter-process handles) — alongside GPUDirect RDMA zero-copy for large inter-node messages.
3. **Pick a protocol by message size.** For *small* inter-node messages, zero-copy RDMA does not pay: registration and rendezvous overheads exceed the wire time, so the library reads the device buffer out via a BAR mapping (gdrcopy-style) or a copy and injects it eagerly. For *large* messages, it registers the buffer and lets the NIC RDMA directly into or out of GPU memory — true zero-copy. This eager/rendezvous split is the same regime logic from DIST-2.5, now applied to device buffers.
4. **Register the memory** with the NIC before any of the direct paths work — the mechanism of §1.5.

Two practical caveats keep "CUDA-aware" from being a single yes/no bit:

- **Support is per-operation.** Open MPI documents exactly which MPI calls accept device buffers — point-to-point, `MPI_Bcast`, `MPI_Allreduce`, gather/scatter families and more are supported, but (depending on version and transport) some operations are not: under UCX, the one-sided operations (`MPI_Put`, `MPI_Get`, RMA windows) do not accept CUDA buffers, and several non-blocking collectives gained support only gradually. Passing a device pointer to an unsupported operation is an error, not a silent slowdown.
- **Query, don't assume.** Open MPI provides `MPIX_Query_cuda_support()` and the `ompi_info` build flags to check at compile/run time; equivalent queries exist in other stacks.

Beyond NVIDIA, the same model appears as **ROCm-aware MPI** (Open MPI v5.0 introduced a generic *accelerator framework* so CUDA-specific code became one component alongside ROCm), and in MPICH, whose GPU support runs through libfabric's hmem interfaces and the Yaksa datatype engine (now maintained inside the MPICH tree), which handles pack/unpack of non-contiguous GPU-resident data. The ecosystem detail worth remembering: for years, device buffers in MPI were an *implementation extension*. The standard itself caught up gradually — MPI 4.1 (November 2023) introduced the `mpi_memory_alloc_kinds` info keys so an application can negotiate with the library about which memory kinds ("mpi", "system", "cuda", "rocm", ...) it intends to use, and MPI 5.0 (June 2025) continued the consolidation (see §2.1). What you write today as "pass the device pointer" is on its way from convention to guaranteed contract.

### 1.5 DIST-6.5 — GPU memory registration

Why does a NIC need memory *registered* at all? Go back to the phrase from §1.2: DMA-capable devices can only touch memory whose physical location is pinned and known. A NIC's DMA engine operates on **physical addresses**. The OS's virtual memory machinery — page tables, demand paging, migration, swap — is invisible to it. If the NIC were handed a virtual address that the OS later remaps mid-transfer, the DMA would land in the wrong physical page, silently corrupting whatever moved in there. Registration closes this gap in three steps, per the NVIDIA GPUDirect RDMA design document:

1. **Pin** the pages: translate the virtual range to a list of physical pages and lock them so the mapping cannot change.
2. **Describe** the region to the device: build the scatter-gather list / page table the DMA engine will walk.
3. **Protect** it: the NIC (in InfiniBand terms) gets a memory region with local and remote keys authorizing exactly that range for exactly that operation set — the full verbs-level story is DIST-7.3; here we only need the concept.

For **host memory**, pinning uses standard kernel facilities (`get_user_pages()`/`put_page()`). For **GPU memory**, the situation is structurally different: GPU memory is not in the host's page tables at all. It lives behind the GPU's PCIe **Base Address Registers (BARs)** — windows in the physical address space that the GPU backs with its own memory. The NIC performs *peer-to-peer DMA* through these BAR windows exactly as it would read system memory. To make this work, pinning must go through the NVIDIA kernel driver: `nvidia_p2p_get_pages()` returns a page table of GPU pages to the third-party driver, along with a callback the NVIDIA driver can invoke to revoke the mapping. GPU pages here are large — on Kepler-class parts 64 KB versus the host's 4 KB — and BAR mappings are managed in 64 KB chunks, so registrations are aligned to 64 KB boundaries. A glue layer ties this to the RDMA stack: the `nvidia-peermem` kernel module (which replaced the older off-tree `nv_peer_mem`) registers the NVIDIA driver as a *peer memory client* with the InfiniBand core, so that a standard `ibv_reg_mr` call can cover a GPU virtual-address range (see §2.2 for where this is heading).

**Registration is expensive.** The NVIDIA documentation is blunt: pinning GPU memory into BAR "is an expensive operation, taking up to milliseconds." That is kernel-mode transitions, page-table construction, and BAR mapping — per buffer, before a single byte moves. Compare with the transfer it enables: a 64 KB message on a 400 Gbit/s link takes about 1.3 µs on the wire. Registering per message would make registration the *dominant* cost by two to three orders of magnitude. Hold that ratio; it is the entire motivation for §1.6.

One correctness subtlety deserves mention because it bites real codes: **memory ordering**. The GPU has a relaxed memory model, and CUDA APIs may return before the work they queue is globally visible. If a `cuMemcpyDtoD` returns asynchronously (a normal optimization) while a NIC is about to read the destination buffer through its BAR mapping, the NIC can read stale data — corruption, not a crash. The fix is `cuPointerSetAttribute(..., CU_POINTER_ATTRIBUTE_SYNC_MEMOPS, ptr)`, which opts that specific allocation into more conservative, synchronous API behavior. The GPUDirect documentation notes this disables optimizations and can cost performance — safety purchased with serialization, applied at per-allocation granularity so only the buffers that are actually RDMA-exposed pay for it.

### 1.6 DIST-6.6 — Registration caches

Since registration costs milliseconds and transfers cost microseconds, the only viable design is to **register once, transfer many times**. That is the registration cache (historically "pin-down cache"), and its anatomy is a small masterclass in performance-engineering trade-offs.

**Hit path.** The cache is keyed by virtual-address range. On each communication call, the library looks up the buffer; a hit returns the existing memory region in sub-microsecond time; a miss triggers the millisecond registration. For long-running codes that reuse buffers — which is most scientific codes — the hit rate is essentially everything.

**Lazy deregistration.** The naive counterpart — unpin after each transfer — reintroduces the millisecond cost on every message, so caches keep regions registered after use. The NVIDIA design document explicitly identifies lazy unpinning as "key to a high performance RDMA implementation." Regions are only released under pressure:

- **Size limits with LRU eviction.** Open MPI's `smcuda` path exposes `mpool_rgpusm_rcache_size_limit` (bytes): when the cache exceeds it, least-recently-used entries are evicted. UCX's registration cache similarly gained configurable memory-usage limits. The pressure is real: pinned BAR address space is a finite resource (256 MB-class on the Kepler parts the original documents describe; larger but still bounded on modern GPUs), so an unbounded cache eventually fails to map new buffers.
- **Registration failure as a trigger.** When pinning a new region exhausts BAR space, the cache evicts (typically LRU) and retries.

**The invalidation problem — the hard part.** Caches keyed by virtual address live dangerously, because *virtual addresses get reused*. Free a buffer with `cudaFree` and the next `cudaMalloc` may return the same address for a different allocation. A stale cache entry would then hand the NIC a memory region pointing at the old physical pages — silent data corruption in someone else's buffer. The NVIDIA documentation illustrates the subtlety with tokens: the same virtual address can map to different contexts and even different GPUs over the program's lifetime. Two mitigation strategies exist:

1. **Intercept allocation events.** Hook `cudaMalloc`/`cudaFree` so the cache learns about deallocations the moment they happen and can unpin proactively. This is UCX's memory-hook approach (the same interception that feeds its memory-type cache). Cost: per-allocation overhead, and edge cases with statically linked runtimes or allocations made before the library initialized.
2. **Tag checking.** CUDA assigns each allocation a monotonically increasing **Buffer ID** (`CU_POINTER_ATTRIBUTE_BUFFER_ID`). On each cache use, re-query the buffer's current ID; if it differs from the one stored at registration time, the buffer was freed and reallocated — invalidate and re-register. This is correct without hooks but adds a driver query to the critical path, which is why the NVIDIA documentation recommends it *not* be used for latency-sensitive implementations, preferring event interception.

Note the echo of a familiar pattern: this is the same lookup-plus-validation structure as CPU caches and TLBs, with the same fundamental tension — validation on the fast path costs latency, validation off the fast path risks staleness.

**Two system-level consequences.** First, multi-library stacks (MPI + NCCL + a direct-verbs application) each keep their own registration cache over the same memory — duplicated pinning, duplicated BAR pressure, and one more reason DIST-6.8's path selection matters. Second, application behavior now has a hidden performance contract: *a loop that allocates a fresh GPU buffer per iteration defeats the registration cache and pays milliseconds per message*, while a pre-allocated buffer pool pays registration once. This is one of the most common real-world "my CUDA-aware MPI is mysteriously slow" causes.

### 1.7 Putting it together: one buffer, two regimes

Consolidate with a concrete scenario — a rank that must ship a GPU-resident array to a peer node, twice, at two sizes, on a system where GPUDirect RDMA is available and the buffer was registered on first use:

| | 64 B control message | 256 MB data block |
|---|---|---|
| Chosen path | eager: gdrcopy-style BAR read + network inject | rendezvous: RDMA zero-copy GPU→GPU |
| Registration cache | hit (sub-µs lookup) | hit (lookup; MR already programmed) |
| PCIe crossings (sender) | 1 (NIC reads via BAR) | 1 (NIC streams via BAR) |
| Host DRAM traffic | 0 | 0 |
| CPU on critical path | posts once | posts once |
| Wire time @ 400 Gb/s | ~1.3 ns× — effectively latency-bound (~2 µs) | ~5.2 ms |

And the same two messages through a *staged* fallback on an unregistered path: the 64 B message pays two copy launches and two sync points (tens of microseconds of pure orchestration); the 256 MB block pays ~2× the PCIe crossings, ~4 passes through host DRAM, and a CPU feeding the pipeline. Neither regime is exotic — a stencil code exchanges halo cells (small) every step; HPL-MxP broadcasts panel blocks (large) every panel step. Real codes live in both rows at once.

The HPL connection is worth stating precisely, since it is where these mechanisms meet your benchmarking experience: in HPL-MxP the panel factorization result lives in GPU memory and must reach every rank in the process grid. Every panel broadcast is a large GPU-resident collective — exactly the workload where zero-copy registration amortizes perfectly, because the same buffer pool is reused for the entire run. This is also why, when you profile distributed HPL and see time in broadcast, the fix is never "make the network faster"; it is "check which path the broadcast actually took" (CUDA-aware collective over GPUDirect vs. silently staged) — the diagnostic method DIST-16.2 will formalize.

## 2. Key Developments / News

### 2.1 MPI 5.0, the new ABI, and the first fully conforming implementation

**What happened.** The MPI Forum ratified MPI 5.0 on June 5, 2025 — the first major version since MPI 4.1 (November 2023), headlined by a standardized **MPI ABI** (binary interface), so an application compiled once can link against any conforming MPI library. In February 2026, Argonne released **MPICH 5.0.0**, described by the project as the first stable release with full MPI-5 support including the ABI, followed by **MPICH 5.0.1** (April 10, 2026), a fix release whose changes include a GPU-relevant CMA bug fix ("Fix bug in CMA code when GPU support is enabled") and a multi-NIC libfabric initialization crash fix.

**What technically changed.** Two threads matter for GPU communication. First, portability: since MPI 4.1 the standard defines the `mpi_memory_alloc_kinds` info keys, letting an application declare and query which memory kinds (host, `cuda`, `rocm`, ...) it will use, so GPU-aware behavior is negotiated through the standard rather than per-implementation extensions like `MPIX_Query_cuda_support`. Second, the ABI removes the historical fragmentation penalty of shipping binaries against N MPI builds — significant for accelerator software, where the GPU-aware support matrix (which transports, which operations, which CUDA versions) already varies enough.

**Why it matters and what to watch.** For today's curriculum: the "pass a device pointer to MPI" convention of DIST-6.4 is being promoted from implementation courtesy to portable, queryable contract, while the underlying mechanisms of DIST-6.5/6.6 stay implementation territory. One asymmetry to keep in mind when reading release notes: implementation maturity differs — MPICH 5.0.x claims full MPI-5, while the Open MPI v5.0.x series documents full MPI-3.1 with *partial* MPI-4.0 support (it reports `MPI_VERSION 3, MPI_SUBVERSION 1`). Neither is "better"; they are different points on the conformance/performance curve, and knowing which claims which is part of reading a cluster's software stack like an HPC engineer.

### 2.2 The peer-memory module era is ending: dma-buf takes over GPUDirect registration

**What happened.** The kernel plumbing that lets an InfiniBand NIC register GPU memory — the peer-memory mechanism behind §1.5 — is being replaced. The off-tree `nv_peer_mem` module was deprecated once the equivalent `nvidia-peermem` module shipped inside the GPU driver (branch R470+; CUDA 12.2's changelog notes customers needing persistent mappings must move to `nvidia-peermem`). Now the Linux kernel community has standardized on the **dma-buf** framework as the general mechanism for peer-to-peer DMA between RDMA NICs and device memory, and distributors are publishing migration guidance — Ubuntu's kernel team, for example, documents migration paths for NVIDIA GPUDirect over InfiniBand, noting recent kernels support dma-buf natively for GPU/NIC memory sharing. On the middleware side, UCX has supported the dma-buf route since v1.14.0 as an alternative to a peer-memory driver for GPU zero-copy RDMA.

**What technically changed.** `dma-buf` is a kernel-standard exporter/importer framework for sharing buffers across drivers: the GPU driver exports a buffer's scatter-gather table, the RDMA core imports it — no bespoke "peer memory client" API binding the InfiniBand subsystem to GPU-specific code, and no dependency on GPU memory having `struct page` backing. For the registration cache of DIST-6.6, the interesting part is what *doesn't* change: the cache logic — VA-keyed lookup, lazy deregistration, LRU, allocation interception — sits above the pinning mechanism, so a stack like UCX can swap the underlying registration path (peer-memory vs. dma-buf) while the caching strategy carries over.

**Why it matters.** This is today's curriculum lived in production: DIST-6.5's registration mechanism is not a frozen design but an actively migrating one, and cluster software stacks (MLNX_OFED, GPU drivers, UCX versions) must be upgraded *coherently* — an `nvidia-peermem`/kernel/UCX mismatch is a classic cause of "GPUDirect silently fell back to staging." When you inherit a cluster, checking which peer-memory path is loaded (`lsmod | grep -e nvidia_peermem -e nv_peer_mem`, and whether the UCX build uses dmabuf) is now part of the DIST-16.2 fast-path/fallback-path checklist.

### 2.3 Landmark paper: quantifying the host-staging penalty (ICPP 2013)

**What happened.** In the historical thread: Potluri, Hamidouche, Venkatesh, Bureddy, and Panda (Ohio State), "Efficient Inter-node MPI Communication Using GPUDirect RDMA for InfiniBand Clusters with NVIDIA GPUs," ICPP 2013 — to the authors' knowledge the first work demonstrating inter-node GPU-to-GPU MPI communication using the then-new GPUDirect RDMA (introduced with Kepler-class GPUs and CUDA 5.0), implemented in MVAPICH2.

**What was demonstrated.** The paper is the empirical version of §1.2: it measures what the host-staged path costs and what the first direct path recovered. Reported results: inter-node GPU-to-GPU `MPI_Send`/`MPI_Recv` latency improved by 69% for 4-byte and 32% for 128 KB messages; unidirectional bandwidth doubled (2×) at 4 KB and improved 35% at 64 KB; and two real applications — LBMGPU and AWP-ODC — saw communication-time reductions of up to 35% and 40% respectively. The paper also documents the limitations of first-generation hardware/software (e.g., small-message registration costs — precisely the problem registration caches were built to solve) and the hybrid designs MVAPICH2 used, including pipelined staging for the cases direct transfer did not win.

**Why it matters for today.** Treat these numbers as the *origin data* of this curriculum block, with two cautions the source rules of this project require: they are paper-reported measurements on 2013 hardware (FDR-era InfiniBand, Kepler GPUs), not current absolute values; and the 69%-latency/2×-bandwidth gains are against an *unoptimized* staged baseline — later, pipelined-staging baselines narrow the large-message gap. The durable lessons are structural, and they are exactly today's topics: the small-message regime is where staging's CPU/synchronization overhead dominates; the large-message regime is where its doubled crossings and DRAM relay dominate; and both are solved not by faster networks but by removing the host from the path — the design decision that every CUDA-aware MPI stack, UCX transport, and registration cache you will ever profile descends from.

### Further Reading

- **NVIDIA GPUDirect RDMA design documentation** (citation 1) — *Reference deep-dive, ~45 min.* The single best primary source for this entire block; read sections 2–4 closely and you will understand registration and caching better than most application programmers.
- **Open MPI "CUDA" documentation** (citation 2) — *Practical, ~20 min.* Read it as a checklist for the next cluster you touch: what to query, what can silently fall back.
- **Potluri et al., ICPP 2013** (citation 6) — *Historical deep dive.* Short by conference-paper standards and directly maps to today's concepts; pay attention to the limitations section, which is a preview of DIST-7.
- **MPI 4.1/5.0 standard, "Memory Allocation Info" chapter** — *Standards reading, ~15 min.* Where "GPU-aware" becomes a negotiated contract rather than an extension.
- **UCX FAQ, "Working with GPU"** (citation 3) — *Quick operational reference, ~10 min.* The `UCX_TLS` and troubleshooting notes are exactly what you will reach for during a debugging session.
