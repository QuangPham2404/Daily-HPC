## 0. Concise Summary

Themes 1–3 built the *objects*: GPU architectures, distributed communication, and the dense linear algebra that HPL is made of. Theme 4 changes the verb. Performance engineering is not about knowing what a GPU or an MPI broadcast is — it is a disciplined, empirical method for making a *specific* program run faster on *specific* hardware, and today we lay its foundations: what the discipline actually is, why correctness must come before speed, and the three raw metrics everything else is built on — wall-clock time, throughput, and latency.

The central idea of PERF-1.1 is that optimization is a **loop** — measure, model, hypothesize, intervene, validate — because modern machines are too layered for intuition: five levels of cache, out-of-order cores, DVFS, shared interconnects, and accelerators interact nonlinearly, and a mental model calibrated on single-threaded code fails silently. PERF-1.2 states the precondition: an incorrect result is worthless at any speed, and worse, every optimization step (reassociation, mixed precision, layout changes, parallelization) is itself a correctness risk that must be re-validated. PERF-1.3 through 1.5 then build the metric toolkit: wall time is the end-to-end truth that includes all waiting; throughput is work per unit time, the economics of expensive machines; latency is the duration of a single operation, what dependency chains and interactive users actually feel. These are **independent axes** — batching raises throughput while lengthening per-request latency, and the same hardware posts very different numbers depending on which one you constrain.

The developments today institutionalize exactly these ideas. SPEC released **CPU 2026** (May 2026) and began retiring CPU 2017 — and its four-suite structure (integer/floating-point × rate/speed) is literally throughput and latency measured as separate, non-interchangeable metrics. MLCommons' **MLPerf Inference v6.0** (April 2026) scores systems across offline (pure throughput), server (throughput under a 99th-percentile latency bound), and interactive (tighter latency) scenarios, with accuracy floors that must be met before any performance number counts — "correctness before performance" written into benchmark law. And NVIDIA's **Nsight Systems 2026.4.1** adds vClock, an unprivileged virtual clock for aligning timestamps across cluster nodes, plus an NCCL "straggler" recipe — measurement infrastructure that makes distributed wall time and tail latency attributable to a specific rank.

Why it matters: every HPL tuning session, every kernel optimization, and every procurement argument you will ever take part in is an argument about these three metrics under a correctness constraint. Getting their definitions exactly right is the difference between engineering and folklore.

## 1. Learn the Concepts

### 1.1 What performance engineering is (PERF-1.1)

Suppose you have a program that works: it factorizes a matrix, runs a CFD timestep, or trains a model, and it produces the right answer. It is, however, too slow. The question performance engineering answers is: **by what method do you make it faster?**

The naive answer is "optimize it" — apply known tricks: unroll loops, increase block sizes, add more nodes, turn on compiler flags copied from a forum post. This folklore-driven approach occasionally works, and that is precisely its danger: it produces unexplainable wins and losses, teaches nothing transferable, and frequently makes things slower, because on modern hardware the effect of an optimization depends on which resource is currently limiting the program.

Why does intuition fail? Because a modern HPC node is a stack of interacting systems: out-of-order superscalar cores with deep pipelines, four or five levels of cache with hardware prefetchers, TLBs, DVFS that changes clock speed under thermal and power limits, shared memory controllers, network interfaces with their own processors, and GPUs whose performance depends on occupancy, memory coalescing, and instruction mix. You met this stack in Theme 1 (GPU architecture) and Theme 2 (communication). No mental model tracks all of it simultaneously, and the interactions are nonlinear. A concrete example you already know from HPL work: the block size NB is not "bigger is better" or "smaller is better." Small NB makes panel factorization (a small, dependency-heavy, poorly parallelizable phase) run more often relative to the big GEMM updates; large NB makes each GEMM more efficient but increases communication granularity and can overflow cache residency. Measured performance versus NB is non-monotone and machine-specific — nobody can predict the optimum for your particular cluster from first principles. It has to be measured.

The discipline that replaces folklore is a **loop**:

```text
        ┌────────────────────────────────────────────┐
        ▼                                            │
  1. MEASURE     define the metric and region;      │
                 collect data on the real system    │
        ▼                                            │
  2. MODEL       compare against a performance      │
                 model (Roofline, Amdahl, scaling)  │
        ▼                                            │
  3. HYPOTHESIZE state a mechanism-level,           │
                 falsifiable explanation            │
        ▼                                            │
  4. INTERVENE   change one conceptual mechanism    │
        ▼                                            │
  5. VALIDATE    re-verify correctness AND          │
                 re-measure end-to-end ─────────────┘
```

Each stage has a specific job. **Measurement** (today's PERF-1.3–1.5, deepened in Modules 2–3) produces ground truth; its output is only as good as the definitions of the metric and the boundaries of the measured region. **Modeling** uses cheap analytical tools — the Roofline model (Module 5) and Amdahl's law (Module 6) — to predict what is *achievable* and to sanity-check what was measured; a measurement that beats a theoretical peak is not a miracle, it is a measurement bug. **Hypothesis** converts "it's slow" into a mechanism: not "make the GEMM faster" but "the GEMM runs at 60% of peak because the trailing-update blocks are too small to saturate the tensor cores." A good hypothesis is falsifiable (Module 22): it predicts what you should observe if it is true, and what you should observe if it is false. **Intervention** changes exactly one conceptual mechanism at a time — if you change block size, process grid, and compiler flags simultaneously, a 10% improvement teaches you nothing about which change caused it. **Validation** has two halves that must never be separated: the result must still be *correct* (PERF-1.2, below), and the *end-to-end* runtime must actually improve — a 2× speedup of a phase that occupies 5% of wall time is invisible in the total (we quantify this with Amdahl's law in Module 6).

Two habits distinguish an engineer from a tinkerer. First, **measurement is ground truth and models are compressions**: when a model and a careful measurement disagree, the model (or the measurement's assumptions) is wrong — but you must know which. Second, **carry mechanisms, not settings**: "larger messages amortize per-message latency" is a mechanism that transfers to every machine you will ever use; "NB=232 was fastest on cluster X" is a number that means nothing on cluster Y (Module 25 formalizes this as performance portability).

One illustrative thread we will reuse all day: imagine a small cluster — three nodes, one GPU each, 50 TFLOP/s of FP64 peak per GPU, 150 TFLOP/s aggregate — running HPL on an n = 100,000 matrix (about 80 GB in FP64, distributed across the three nodes; the operation count is ⅔n³ − ½n² ≈ 6.67 × 10¹⁴ FLOP). Every concept today will attach to this one run.

### 1.2 Correctness before performance (PERF-1.2)

It seems almost too obvious to state: a program that produces wrong answers has zero value at any speed. But the point is sharper than it looks, for three reasons.

**First, incorrectness can masquerade as speed.** The fastest way to "optimize" any program is to skip work — drop an iteration, ignore a boundary condition, let a race condition elide an expensive update. If you do not verify correctness, some of your "optimizations" will be doing exactly this, silently. Correctness checking is what keeps the whole optimization loop honest: it is the control experiment that ensures your speedup came from doing the same work faster, not from doing less work.

**Second, every optimization step is itself a correctness risk.** Consider what the interventions in §1.1 actually do to a numerical program. Reassociating a floating-point sum (so it can be parallelized) changes the rounding behavior and therefore the result — bitwise different, but usually within tolerance. Switching precision (FP64 → FP32/BF16 operands, as in HPL-MxP) changes error bounds and is only acceptable if the algorithm compensates — in HPL-MxP's case, iterative refinement keeps the final solution at FP64-quality while the bulk arithmetic runs in low precision. Changing data layout (padding, transposing, blocking) invites indexing bugs that corrupt values silently. Parallelization introduces races and non-deterministic reduction orders. Each turn of the optimization loop must therefore re-validate, and the validation must be part of the loop, not an afterthought.

**Third, "correct" for floating-point code is a defined property, not a feeling.** Exact reproducibility and acceptable accuracy are different targets. The standard tool for linear algebra is the **scaled residual**: for a solved system Ax = b, check ‖Ax − b‖ against a bound scaled by the problem's magnitudes and machine precision (e.g., ‖A‖·‖x‖·ε·n), so the test is meaningful across scales. HPL itself works this way: the benchmark's output includes a residual check on the computed solution, and a run that fails it is not a valid HPL result no matter how fast it was — the timing is only meaningful for runs that pass. (This is documented in the HPL materials at Netlib, cited below.) Mixed-precision variants inherit the same philosophy: the answer must land within the acceptance tolerance before the timer's number means anything.

The benchmark world has absorbed this lesson institutionally. MLPerf Inference — which we meet again in the news section — requires every submission to first meet an **accuracy floor** (for example, retaining ≥ 99% of a reference model's accuracy) before its performance numbers are valid. The rule exists because without it, vendors would win benchmarks by quantizing aggressively and quietly degrading quality: throughput purchased with correctness. The same logic applies to your own work: an HPL-MxP run that beats the cluster record but fails the residual test is not a result, it is a bug report.

Practical rules that follow:

- **Verify before you time, and after every change** — make the residual/accuracy check a scripted part of the loop, not a manual step you perform once.
- **Keep verification outside the timed region** — checking the answer costs time too, and it must not contaminate the performance measurement (we treat timing hygiene in Module 2).
- **Test at more than one problem size** — layout and precision bugs often hide at sizes where padding or remainders behave differently.
- **Decide your tolerance deliberately** — "close enough" must be a number derived from the downstream use of the result, and it should be written down.
- **Treat bitwise reproducibility as a separate, stronger property** — deterministic reductions and fixed execution orders cost performance; require them only when the application truly needs run-to-run identity.

There is a fourth, subtler point: **the measurement itself can be incorrect**. A timer that measures the wrong region, a missing GPU synchronization that reports launch time instead of execution time (§1.3), a clock that jumps due to NTP — these are correctness bugs in your *performance data*. An engineer who optimizes based on wrong measurements is doing folklore with extra steps. That is why the next three topics are about getting the metrics exactly right.

### 1.3 Wall-clock time (PERF-1.3)

**Wall-clock time** is elapsed real time between two points in a program's execution, measured on a clock that advances whether or not the program is doing anything useful. It is the simplest and most honest metric: it is what the user experiences, what the job scheduler bills, and what every other performance number is derived from.

The first thing to get exactly right is that **wall time is defined by its boundaries** — where you start and stop the clock — and different legitimate choices give different numbers for the same program. For our three-node HPL run, at least four wall times exist:

1. **Timed-region wall time**: from just before factorization starts to just after the last update completes — the region HPL's own timer brackets. Call it T.
2. **Process wall time**: from `MPI_Init` to `MPI_Finalize` — includes generating/reading the matrix, distributing it, and the residual check.
3. **Job wall time**: from job start to job end — includes loading modules, allocating nodes, staging input files, writing results.
4. **Queued time**: how long the job waited — which is real to the user but measures the *scheduler*, not the program.

None of these is "the" runtime; each answers a different question. Two engineers can report "runtime" for the same code and differ by 2× by choosing different boundaries, so a performance report that does not state its boundaries is incomplete. In what follows, T is the timed-region wall time; suppose for our run T = 9.0 s.

The second thing to get right is the **clock itself**. On Linux, use `CLOCK_MONOTONIC` (e.g., `clock_gettime`) for intervals: it advances uniformly and cannot be adjusted backward or forward by NTP, whereas wall-of-day clocks (`gettimeofday`, `CLOCK_REALTIME`) can jump when the system corrects time — a interval measured across a jump is simply wrong. Modern counters give nanosecond resolution, though resolution and accuracy are different things (timer overhead and resolution get their own topic in Module 2, PERF-2.8).

The third thing — the one that bites GPU programmers immediately — is **asynchrony**. CUDA kernel launches are asynchronous: the host call returns before the GPU finishes the work. Host-side timing around a launch therefore measures *submission*, not *execution*. To measure GPU work you must either synchronize (`cudaDeviceSynchronize`/`cudaStreamSynchronize`) before reading the end time, or use device-side events (`cudaEventRecord`/`cudaEventElapsedTime`) that timestamp on the GPU itself. Unsynchronized timing is one of the most common measurement bugs in GPU performance work — it is a correctness bug in your data, exactly as §1.2 warned. (MPI has the same trap in a milder form: timing a non-blocking operation without the completing `MPI_Wait` measures posting, not communication.)

Why is wall time so central for *parallel* programs? Because **it includes all waiting**. In our 9.0 s HPL run, each GPU spends only about 4.4 s actually executing kernels if the run were perfectly compute-bound (6.67 × 10¹⁴ FLOP ÷ 150 × 10¹² FLOP/s ≈ 4.44 s). The remaining ~4.6 s — broadcasts, barrier waits, dependency stalls, straggler effects — is time the program *spends* without any GPU doing useful work, and wall time honestly charges every second of it to you. Metrics that average utilization across resources can hide this; the elapsed clock cannot. That is also why wall time is the natural denominator for derived metrics: the HPL score is

```text
GFLOP/s = (2/3·n³ − 1/2·n²) / T
        = 6.67 × 10¹⁴ FLOP / 9.0 s
        ≈ 74.1 TFLOP/s
```

The numerator is fixed by the problem size, so for a fixed n, minimizing wall time *is* maximizing the score — the two views carry identical information (Module 2, PERF-2.2, makes this "time per operation vs. operations per second" duality explicit).

Finally, wall time disciplines local optimization: an optimization is real only if it reduces the end-to-end clock. Speeding up a phase that occupies 10% of T by 2× shortens T by only 5%. Local metrics that improve while T stands still (better cache hit rate in a kernel that was never on the critical path) are the mirages of performance work — Module 2 (PERF-2.5) and Module 19 return to this with the concept of the critical path.

### 1.4 Throughput (PERF-1.4)

**Throughput** is completed units of work per unit of time: FLOP/s, samples/s, tokens/s, timesteps/s, jobs/day. Where wall time describes one run, throughput describes a *rate of production* — and it is the metric of anyone who owns an expensive machine, because the economics of HPC are expressed in cost and energy per unit of work, not per run. TOP500 is, literally, a throughput ranking: Rmax is FLOP/s.

Defining throughput requires choosing the **unit of work** (this gets its own topic in PERF-2.1), and the choice embeds a claim about what is useful. In HPL the unit is the FLOP of the factorization operation count; in an inference service it might be a completed request or a generated token; in a weather code it might be a simulated day of model time. "Useful" matters: counting FLOPs the program performed *because of a wasteful algorithm* inflates throughput without producing value — an O(n³) method that does 2× the necessary FLOPs of a better method can post high FLOP/s and still be the slower program. Throughput measures production rate, not efficiency of production (that is §PERF-1.7's cousin, efficiency, next volume).

For our HPL run, the aggregate throughput is 74.1 TFLOP/s, or about 24.7 TFLOP/s per GPU. Whether that is good depends on the reference you divide by — exactly the question of *efficiency*, which we will formalize in the next PERF volume. What throughput alone already tells you: the machine completed 6.67 × 10¹⁴ units of work in 9 s.

Throughput improves through a small set of mechanisms, worth naming now because the rest of this theme is largely about them:

- **More hardware** — more nodes, more GPUs (parallelism; its limits are Module 6's subject).
- **Better per-unit efficiency** — improving kernels, memory access, overlap (Modules 5, 11–14).
- **Batching** — amortizing fixed per-operation overheads (launch cost, per-message latency, per-request setup) over more units. Sending one 8 KB message instead of eight 1 KB messages moves the same data with one-eighth the per-message cost — you met this as the large-message regime in the DIST volume's latency/bandwidth model.
- **Pipelining/overlap** — keeping all stages of a multi-stage process busy simultaneously (Module 14).

Batching deserves emphasis because it exposes the trade this volume keeps returning to: batching *raises throughput* by amortizing overheads, but it usually *lengthens the latency of each individual unit* — a request may wait for a batch to fill; a message waits for coalescing. This is not a defect; it is the fundamental dial between our next two topics.

Institutionally, the throughput/latency split appears in the oldest CPU benchmark family on earth. SPEC's suites come in paired flavors: **SPECrate** runs multiple copies of each benchmark simultaneously on a machine and scores aggregate jobs-completed-per-day — a machine *throughput* metric aimed at servers handling many independent jobs. **SPECspeed** runs a single copy and scores the elapsed time of that one job — a *latency* (per-job time) metric aimed at interactive or single-task systems. Same hardware, two official numbers, neither convertible into the other; a 128-core server wins SPECrate by a huge margin while posting an unremarkable SPECspeed, because per-core clock and memory latency — not core count — dominate a single job. When SPEC released CPU 2026 this May, it kept and sharpened exactly this structure, and added more internal parallelism to the speed suites — we examine that in the news section, because it is a live demonstration of throughput and latency diverging on real hardware.

One more property to internalize: throughput is a **steady-state** concept (formalized in Module 2). During warm-up — JIT compilation, first-touch page allocation, cache population — instantaneous throughput is lower and unrepresentative; a measurement window that includes startup underestimates the machine's productive rate. Our HPL example is mostly steady GEMM work, but a job that processes only three timesteps measures mostly startup. Report the window you measured, and whether it excludes warm-up.

### 1.5 Latency (PERF-1.5)

**Latency** is the time required to complete *one* operation, stage, request, or dependency — one memory access, one kernel launch, one message, one HTTP request, one token's generation. Throughput asks "how much per second?"; latency asks "how long does this one take?" They are independent axes: a system can have enormous throughput and terrible latency (a batch-oriented pipeline), or low latency and modest throughput (a small responsive server). Neither is "better"; they answer different questions, and every real system sits somewhere on a trade-off curve between them.

Latency is easiest to feel through the **hierarchy of latencies** inside a machine. Approximate, order-of-magnitude figures for current server-class hardware (exact values vary by generation and configuration — treat these as powers of ten, not specifications):

```text
register access                      ~0        (in the same clock domain)
L1 cache hit                         ~1 ns     (a few cycles)
L2 cache hit                         ~4 ns
L3 / last-level cache hit            ~15–40 ns
DRAM / HBM access                    ~100 ns
MPI small-message latency (node-node,
  InfiniBand, software stack incl.)  ~1–3 µs
CUDA kernel launch overhead          ~3–10 µs
collective at full-machine scale     ~ms
time-to-first-token, LLM inference   ~seconds
```

Two facts about this table organize most of performance engineering. First, each level is roughly an order of magnitude slower than the one above it, which is why *where* data lives (Theme 1's cache hierarchy) and *how many times* you cross levels dominates kernel behavior. Second, the gaps are so large that **hiding latency behind independent work is often the only viable strategy**: a dependent chain of DRAM accesses at ~100 ns each moves at ~10 × 10⁷ accesses/s per thread regardless of the core's clock — the memory latency, not the FLOP rate, sets the pace. You met this in Theme 1 as why GPUs need thousands of resident threads: with a ~500-cycle memory latency, an SM must have other warps to issue while one waits. Latency *hiding* (overlap) and latency *reduction* (fewer, larger, more local operations) are the two families of remedies — Module 4 classifies "latency-limited" behavior and Module 14 develops overlap.

**Latency sums along dependency chains.** If operation B needs A's result, and C needs B's, the chain's completion time is the sum of the three latencies no matter how much parallel hardware surrounds it. This is why a parallel machine can be slow: the *critical path* — the longest dependency chain through the computation — sets a floor on wall time that no amount of idle hardware can lower (Module 19 develops this fully). In HPL, the panel factorization is exactly such a chain of small dependent operations, which is why it starves big GPUs despite the machine's enormous aggregate throughput.

**Latency is a distribution, and its tail is what hurts.** Reporting "average latency" hides the tail; a request stream where 99% complete in 10 ms and 1% complete in 2 s has a fine mean and unusable behavior for anything interactive. Hence tail metrics — p99, p99.9 — and hence the nastiest tail effect in distributed computing: in a collective operation, *every* participating rank waits for the slowest one. One straggler node — thermally throttled, on a congested link, or simply given more work — injects its latency into the entire machine. Our 9.0 s HPL run contains ~4.6 s of non-compute time; some of it is exactly this: ranks arriving at the next broadcast at different times and paying the maximum as the price of synchronization (Module 18 treats load imbalance and stragglers in depth).

The measurement discipline follows from the definition: to measure latency, instrument *individual* operations (not aggregates), repeat many times, and report percentiles — a single sample of a noisy quantity is anecdote, not data (Module 3 supplies the statistics). And because latency and throughput trade off, any serious benchmark must say which one it constrains. MLPerf Inference does this explicitly — its scenarios are different points on the trade-off curve, and the numbers are not comparable across them: the *offline* scenario fires all queries at once and reports pure throughput; the *server* scenario drives requests with Poisson arrivals and binary-searches for the highest throughput that still meets a 99th-percentile latency bound; the *interactive* scenario tightens the bounds further. For the DeepSeek-R1 benchmark in the current v6.0 round, server submissions must hold p99 time-to-first-token ≤ 2 s and per-output-token interval ≤ 80 ms, while the new interactive scenario tightens these to ≤ 1.5 s and ≤ 15 ms. Identical hardware, different constraint, different achievable throughput — the benchmark makes the frontier auditable instead of letting vendors pick whichever point flatters them.

Synthesizing the day: our HPL example now has all its numbers. The run is *valid* only because the residual check passes (§1.2). Its timed-region wall time is 9.0 s, honestly including ~4.6 s of waiting (§1.3). Its throughput is 74.1 TFLOP/s (§1.4). And its slack time decomposes into latency phenomena — dependency chains in the panel, per-message startup costs, and straggler waits at collectives (§1.5). The obvious next questions — *is 74 TFLOP/s good against the 150 TFLOP/s peak? which resource is actually limiting us?* — are precisely the topics of the next PERF volume: utilization, efficiency, and bottleneck analysis (PERF-1.6–1.8), where the raw metrics defined today become diagnostic tools.

## 2. Key Developments / News

### 2.1 SPEC releases CPU 2026 and begins retiring CPU 2017 — throughput and latency as separate, official metrics

**What happened.** On May 5, 2026, the Standard Performance Evaluation Corporation released the SPEC CPU 2026 benchmark suites, presented by the SPEC CPU committee at ICPE 2026 in Florence. It is the first full generation since SPEC CPU 2017 and comprises 52 benchmarks built from 38 real applications across four suites — integer and floating-point, each in **rate** (throughput) and **speed** (single-job latency) variants. Concurrently, SPEC published the retirement schedule for CPU 2017: since August 11, 2026, new CPU 2017 publications on SPEC's site require a simultaneous CPU 2026 result on the same configuration; SPEC stops accepting CPU 2017 results on November 3, 2026, and fully retires the suite on November 17, 2026.

**What technically changed.** The 2026 suites respond to nine years of hardware drift: much higher core counts, changed memory hierarchies, and the migration of production software to open source. Compared to 2017, the workloads are larger and more diverse, memory benchmarking is expanded, the speed suites contain more internal parallelism (multi-threading and multi-processing, so a single "job" itself uses a parallel machine), the suite integrates widely used open-source applications, a new open-source-compiler reporting category encourages publication with community toolchains, and optional energy/power measurement accompanies performance — the familiar SPEC methodology extended to efficiency.

**Why it matters.** Two design decisions connect directly to today's curriculum. First, the rate/speed pairing is throughput and latency institutionalized: SPECrate measures aggregate jobs/day (procurement question: "how many builds/simulations per night?"), SPECspeed measures one job's elapsed time (user question: "how long is my interactive run?"). As core counts grow, these numbers diverge — a many-core server can dominate rate while posting ordinary speed — so a vendor quoting "SPEC" without saying which suite is answering a question you didn't ask. Second, SPEC states plainly in its FAQ that there is **no conversion formula** between CPU 2017 and CPU 2026 scores: different code, data sets, hardware stress, metric calculations, and run rules mean the correlation will be "far from perfect." That is a formal admission of a theme running through today's lesson: performance numbers are bound to their methodology — boundaries, units, rules — and are not physical constants that survive a change of context. The retirement schedule exists precisely so that old-methodology numbers stop accumulating next to new ones on procurement tables.

**What to watch.** The first wave of vendor CPU 2026 publications (allowed since June 2026); whether the open-source-compiler column changes what vendors must disclose about tuning; and, closer to November 3, how quickly the industry's comparison baselines migrate. For your own work, the habit to copy: state the suite, the metric, and the rules alongside any number you quote.

### 2.2 MLPerf Inference v6.0 — a benchmark suite built on the throughput/latency frontier and accuracy floors

**What happened.** On April 1, 2026, MLCommons published results for MLPerf Inference v6.0, describing it as the most significant revision in the suite's history. Five of eleven datacenter tests are new or updated: an open-weight GPT-OSS 120B benchmark for math/reasoning/coding; an expanded DeepSeek-R1 benchmark adding an *interactive* scenario that permits speculative decoding; DLRMv3 (a sequential recommendation benchmark co-engineered with Meta); the suite's first text-to-video generation benchmark; a vision-language benchmark built on Shopify product data; and a YOLO11-based edge object-detection test. A new harness, LoadGen++, lets LLMs run under a serving-style stack. Multi-node participation hit a record: 30% more multi-node submissions than the previous round, 10% of submitted systems exceeding ten nodes (versus 2%), and the largest system at 72 nodes and 288 accelerators.

**What technically changed.** The scenario structure is the curriculum connection. Each scenario is a point on the throughput/latency curve, with the LoadGen load generator defining it precisely: *offline* sends all queries in a single batch and measures raw throughput; *server* injects requests with Poisson arrivals and finds the maximum throughput that still satisfies a tail-latency bound (for GPT-OSS: p99 time-to-first-token ≤ 3 s and per-output-token interval ≤ 80 ms); *interactive* tightens the bounds (DeepSeek-R1: p99 TTFT ≤ 1.5 s, TPOT ≤ 15 ms), and explicitly allows speculative decoding — a technique that trades extra compute for lower token latency. Separately, every submission must first meet an accuracy floor relative to a reference (e.g., ≥ 99% of reference accuracy) before any performance number is valid.

**Why it matters.** This is today's lesson rendered as benchmark law. The accuracy floor is "correctness before performance" (PERF-1.2) enforced at submission time — throughput purchased with degraded quality is disqualified, not merely footnoted. The scenario split is the throughput/latency trade-off (PERF-1.4/1.5) made auditable: the same hardware posts different numbers per scenario, and a serious comparison must say which point on the frontier it is buying. And the multi-node trend shows AI inference becoming a distributed-systems problem in the HPC sense — network topology, collective communication, and straggler behavior now dominate at 72-node scale, which is Theme 2's territory applied to a new workload.

**What to watch.** How speculative-decoding submissions distribute their TTFT/TPOT results (does the extra compute pay for itself at the interactive bounds?); LoadGen++ adoption as the standard harness; and the next round's multi-node scale records — at some point "inference cluster" and "HPC system" become the same procurement.

### 2.3 Nsight Systems 2026.4.1 — measurement infrastructure for distributed wall time and stragglers

**What happened.** NVIDIA's current Nsight Systems release (2026.4.1) adds tooling squarely aimed at distributed performance measurement: **vClock**, an unprivileged virtual clock that aligns timestamps across cluster nodes so traces collected on different machines can be laid on one timeline; an improved NCCL recipe set including a **straggler analysis** recipe that pinpoints the slow MPI rank delaying collectives; high-frequency NIC metrics collected through the DOCA Telemetry Service without root privileges; Arm Topdown-based single-pass CPU metric sets; and extended uncore-event profiling on the Vera CPU and Thor platforms. The companion kernel profiler, Nsight Compute (2026.2), continues the discipline of *reproducible measurement* by defaulting to clock control — `--clock-control=base` locks GPU clocks during profiling, because a floating clock makes kernel timings vary with thermal state rather than with your code.

**Why it matters.** You cannot diagnose what you cannot attribute. The straggler problem from §1.5 — one slow rank taxing the whole machine at every collective — is invisible in per-node averages and only visible when per-rank timelines are aligned to a common clock; vClock is the plumbing that makes that alignment possible without privileged access. The straggler recipe then operationalizes the diagnosis: convert "the job is slow" into "rank 17 enters every Allreduce 40 ms late." This is PERF-1.1's loop given better instruments — measurement first, hypothesis second. The clock-control default is the same philosophy applied to the *validity* of measurements (§1.2): a kernel timing collected on a boost-clocked, thermally drifting GPU is not a stable fact about your code. The release notes' long-standing guidance that profiling sessions beyond ~5 minutes are not officially supported is the same point from the other side: tracing at high fidelity perturbs and floods the very system being measured, so profile narrow regions, not whole jobs.

**What to watch.** vClock-based multi-node timelines becoming routine in cluster profiling workflows; NCCL straggler detection feeding into scheduler-level remedies; and on the CPU side, single-pass topdown metric sets reducing the multiplexing artifacts that complicate counter interpretation (a topic we take up with performance counters in Module 7).
