## 0. Concise Summary

Today's issue closes out the GPU memory-hierarchy module (GPU-4.9 through GPU-4.12) and opens the resource-residency and scheduling module with GPU-5.1 — five topics that together answer one question: **how does an SM keep the memory system fed, and what must physically fit on the SM to do so?**

We start with cache locality (GPU-4.9): why the *pattern* of addresses a warp generates — not the number of bytes — determines how many memory transactions the hardware must issue. We then separate the two limits that are constantly confused (GPU-4.10): latency, the delay of a single request, and bandwidth, the sustained byte rate once many requests are in flight. Little's law ties them together and explains why GPUs bet on thousands of threads rather than out-of-order cores. GPU-4.11 covers atomics and memory ordering: where read-modify-write operations actually execute (the L2 for global memory), why scopes exist (the coherence point differs per scope), and why a release–acquire pair is the minimal correct pattern for inter-block communication. GPU-4.12 makes bandwidth derivable from first principles — pins × data rate ÷ 8 — and works it through A100, H100, B200, GDDR7, and the incoming HBM4 generation. GPU-5.1 then inventories what can simultaneously reside on an SM/CU: warp slots, thread blocks, registers, shared memory (and, new on datacenter Blackwell, Tensor Memory), and shows with a worked example how the tightest of these caps resident work.

Two developments connect directly to this material: the HBM4 volume ramp (12-high stacks in mass production, 16-high in customer qualification — the 2048-pin-per-stack generation that arithmetic alone predicts delivers >2 TB/s per stack), and Blackwell's Tensor Memory (TMEM), the first genuinely new *resident SM resource* in over a decade, which turns accumulator capacity into a first-class occupancy constraint.

## 1. Learn the Concepts

### 1.1 GPU-4.9 — Cache locality and access patterns

**The problem.** In GPU-4.7 you saw how a warp's accesses are merged into hardware memory transactions. What determines the *number* of transactions is not how many bytes your kernel logically touches, but the **access pattern**: the sequence of addresses as seen by the memory system. Two kernels reading exactly the same total number of bytes can differ in effective memory traffic by more than an order of magnitude. The vocabulary for this is cache locality:

- **Spatial locality** — consecutive accesses land near each other in address space (ideally within the same cache line).
- **Temporal locality** — the same address is re-accessed soon after its first use, while it may still be cached.
- **Reuse** — a value loaded once is used many times (by many threads, or across loop iterations). Reuse that is *exploited* becomes temporal locality; reuse that is *squandered* becomes repeated DRAM traffic.
- **Stride** — the address delta between successive accesses of a given thread (or the warp as a whole). Stride 1 in the innermost dimension is the happy case; large strides are the pathology.

**The mechanism: lines and sectors.** On modern NVIDIA GPUs, the L1/L2 hierarchy moves data in **128-byte cache lines split into four 32-byte sectors**; the natural unit of a global-memory transaction is a 32-byte sector (the CUDA C++ Programming Guide describes global-memory coalescing in these terms, and the behavior is inherited by compute capability 9.x/10.x from the CC 5.x rules). AMD CDNA GPUs use **64-byte cache lines**. A perfectly coalesced warp load — 32 threads each reading a consecutive 4-byte float — touches 128 contiguous bytes: one line, four sectors, one transaction group. The same warp reading with stride 32 (each thread 128 bytes apart) touches 32 *different* lines: 32 sectors fetched, 4 bytes used from each — 12.5% efficiency on NVIDIA, 6.25% on a 64-byte-line AMD part.

**A worked example: the column walk.** Take a 4096×4096 matrix of `float` stored row-major (16 KB per row). A kernel where each thread walks **down a column** (`i`, `j+1`, `j+2`, …) advances its address by 16 KB per step. Every single load lands in a fresh cache line, and the line's other 124 bytes are dead weight unless another warp happens to want them *before eviction*. The fix is not more cache — it is changing the layout or the traversal: block the matrix into tiles that fit in shared memory (as in GPU-4.3), so each line loaded from DRAM is fully consumed; or store a transposed copy; or in the SoA-vs-AoS sense, reorder fields so that threads that execute together read the same array. This is why layout changes hardware behavior (the topic title): **the memory system does not see your algorithm, only your address stream.**

**Temporal locality and the L2 persistence mechanism.** GPUs have small, per-SM L1 and one large, chip-wide L2 (40 MB on A100, 50 MB on H100; 32 MiB per XCD plus a 256 MiB "L3" on MI300X, per AMD's specification tables). Temporal locality across the whole device is therefore an L2 property, and modern CUDA lets you *manage* it explicitly: since CUDA 11.0, devices of compute capability 8.0+ support **L2 access management**. You can set aside a portion of L2 (up to a device-specific cap, e.g. a fraction of `prop.persistingL2CacheMaxSize`) and attach an *access policy window* to a stream, marking a contiguous region of global memory as `cudaAccessPropertyPersisting` or `cudaAccessPropertyStreaming`. Persisting accesses get priority retention in the set-aside portion; streaming accesses are preferentially evicted. The canonical HPC use case is a data structure every block re-reads — in HPL terms, think of the current panel factorization being consumed by every trailing-matrix update: marking it persisting keeps it resident in L2 instead of letting streaming matrix body traffic evict it. This is explicit, software-controlled temporal locality — the hardware will not discover it for you if your reuse distance exceeds what default LRU retains.

**Conflict misses and padding.** A third locality failure is *conflicts*: when data you want to keep resident maps onto the same cache set (or, in shared memory, the same bank — GPU-4.8) as streaming data. The classic remedy of padding a leading dimension by one element (+4 bytes) shifts each row onto different sets and can restore near-linear cache behavior at the cost of a few percent of memory. Locality, in short, has three enemies — cold misses (inherent), capacity misses (working set > cache), and conflict misses (accidental) — and only the second and third respond to cleverness.

**Connections.** Coalescing (GPU-4.7) is spatial locality at transaction granularity; shared-memory tiling (GPU-4.3) is how you convert *temporal* reuse within a block into on-chip traffic; L2 persistence extends the same idea across blocks. In the next topic we meet the two currencies this whole machinery is denominated in.

### 1.2 GPU-4.10 — Memory latency versus memory bandwidth

**Why these are different limits.** Latency and bandwidth are constantly conflated. They are physically distinct:

- **Latency** is the time from issuing one memory request to its data returning: on the order of **hundreds of nanoseconds** for HBM on a modern datacenter GPU (request → cross-chip interconnect → memory controller → DRAM row activation (tRCD) → column access (CL) → data return, plus queueing). Latency is a *per-request* property.
- **Bandwidth** is the sustained rate at which the memory system can deliver bytes when **many requests are in flight simultaneously**: 3.35 TB/s on an H100 SXM, 8 TB/s on a B200. Bandwidth is a *pipeline-throughput* property of the interface: pins × data rate (Section 1.4).

A system can be idle at every instant (latency-bound, bandwidth unused) or saturated (bandwidth-bound, latency invisible). Which one you hit depends on a single quantity: **offered concurrency**.

**Little's law — the binding constraint.** For any pipelined system:

```
bytes in flight  =  bandwidth  ×  latency
```

This is Little's law from queueing theory, and it is the single most useful equation in GPU performance. Work it for an H100 (illustrative, order-of-magnitude numbers):

- Per-SM fair share of HBM bandwidth: 3.35 TB/s ÷ 132 SMs ≈ **25 GB/s per SM**.
- Memory round-trip: ~700 ns (a rule of thumb; the exact figure is not publicly specified and varies with bank conflicts and queueing).
- Required bytes in flight per SM: 25 GB/s × 700 ns ≈ **17.5 KB**.

Now count what an SM can hold: 2048 resident threads (GPU-5.1). If every thread has one outstanding 4-byte load, that is 2048 × 4 B = **8 KB in flight — not enough**. If each thread issues one 16-byte vectorized load (`float4`, the pattern the compiler generates for aligned, contiguous access), that is 32 KB — comfortably enough. Two conclusions fall out immediately: (1) **scalar per-thread loads cannot saturate HBM even at 100% occupancy** — vectorized, coalesced access is not optional; (2) occupancy is fundamentally a *latency-hiding* mechanism. This is the deep reason GPUs carry thousands of threads per SM where a CPU core carries a handful: the CPU hides latency with out-of-order execution, deep speculation, and large low-latency caches; the GPU hides it with **thread-level parallelism**, because transistors were spent on arithmetic lanes instead.

**The three regimes.** A kernel sits in one of three states:

| Regime | Cause | Symptom | Fix |
|---|---|---|---|
| Latency-bound | Not enough independent work in flight | Low bandwidth use, low compute use, stalls | More concurrency (occupancy, ILP), prefetch, cp.async/TMA |
| Bandwidth-bound | Arithmetic intensity too low for the machine's balance point | Time ∝ bytes moved | Move fewer bytes: reuse, tiling, precision, layout, L2 persistence |
| Compute-bound | Arithmetic intensity above the balance point | Time ∝ FLOPs | Fewer/better operations (this is where HPL lives) |

The pivot between the last two is the **arithmetic intensity** (FLOPs per byte moved from DRAM) versus the machine's **balance point** (peak FLOP/s ÷ peak byte/s). For a B200: roughly 2,250 dense FP16 TFLOP/s against 8 TB/s gives ≈ **280 FLOP/byte** in FP16 — a strikingly high ridge point, and the formal roofline treatment arrives later in the Performance Engineering theme. For now, note the *qualitative* use: HPL runs far above any such balance point (each panel byte funds O(n²) trailing updates), which is why it is compute-bound even on deeply bandwidth-starved parts, while HPCG's sparse mat-vec sits far *below* it (indirect indexing, little reuse per byte) and is bandwidth/latency-bound everywhere. Same hardware, opposite regimes — determined entirely by arithmetic intensity.

**Why the distinction matters for optimization.** The two regimes respond to *different* levers, and applying the wrong one wastes effort: adding occupancy to a bandwidth-bound kernel changes nothing (the pipe is already full); converting to lower precision helps a bandwidth-bound kernel (fewer bytes) but not a latency-bound one. The practical diagnostic is simple: if achieved bandwidth is far below peak *and* SM utilization is low, you are latency-bound; if bandwidth is near peak, further optimization means moving fewer bytes, not moving them faster.

### 1.3 GPU-4.11 — Atomics and memory ordering

**The problem.** When thousands of threads update the same location — a histogram bin, a global counter, a sparse-matrix entry — ordinary load/modify/store sequences interleave and lose updates. An **atomic** operation makes read-modify-write (RMW) indivisible: `atomicAdd`, `atomicCAS`, `fetch_min`/`fetch_max`, and the usual C++ memory-order flavors. Hardware guarantees the RMW is atomic at the **scope** it names, no matter which units execute it.

**Where atomics execute.** The scope's coherence point tells you the physical location (this is documented in the CUDA C++ memory-model material):

| Scope | PTX suffix | Point of coherency | Typical cost |
|---|---|---|---|
| Block (`thread_scope_block`) | `.cta` | L1 / shared memory | Cheapest |
| Cluster | `.cluster` | L2 (distributed) | Moderate |
| Device (`thread_scope_device`) | `.gpu` | L2 | Moderate — crosses SM boundary |
| System (`thread_scope_system`) | `.sys` | L2 + connected system caches | Most expensive |

Global-memory atomics on NVIDIA GPUs are performed **at the L2 cache**, the device coherence point — an atomic RMW on a line locks or arbitrates ownership of that line in L2. Shared-memory atomics execute in the SM's shared-memory/L1 hardware. The performance consequence: **same-address contention serializes**. One hundred warps atomically incrementing *distinct* addresses proceed in parallel (bank and L2-slice permitting); one hundred incrementing the *same* address form a hardware queue, one RMW per round-trip. Standard mitigations: per-block partial results in shared memory reduced once at the end, and **warp-aggregated atomics** — lanes of a warp contributing to the same index combine into a single atomic before leaving the SM (the compiler/runtime does this for some patterns; it is worth doing manually for histograms). AMD's guidance mirrors this: keep atomics in the LDS (workgroup scope) and reduce to global memory once.

**Memory ordering — why atomics alone are not enough.** An atomic makes *one* location's RMW indivisible; it says nothing about the order in which *other* memory operations around it become visible. GPUs are **weakly ordered** machines: writes may be buffered, L1 caches are not coherent across SMs (global stores go through to L2; per-SM caches need explicit invalidation to observe another SM's stores), and the compiler reorders freely. If block 0 writes a result and then sets a flag, block 1 spinning on that flag may observe the flag *before* the result — unless you impose ordering.

The C++-standard toolset, available in CUDA C++ via `cuda::atomic`/`cuda::atomic_ref<T, Scope>` and mapped to PTX (`st.release.gpu`, `ld.acquire.gpu`, `fence.acq_rel.gpu`, …), gives a minimal, efficient pattern:

```cpp
// Producer (block 0, device scope)
data = 42;
flag.store(1, cuda::memory_order_release);   // everything before is visible before the store

// Consumer (block 1, device scope)
while (flag.load(cuda::memory_order_acquire) != 1) ;   // nothing after is hoisted before the load
// assert(data == 42) now holds
```

**Release** orders prior writes before the flag store; **acquire** orders subsequent reads after the flag load. `relaxed` gives atomicity with no ordering (fine for pure counting); `seq_cst` adds a total order across all sequentially consistent operations and is rarely needed. The CUDA documentation's own worked example shows the failure mode: if the producer's store is declared `thread_scope_block` but the consumer reads at `thread_scope_device`, the operations do not become "morally strong" relative to each other — the pairing is invalid and the code has a **data race (undefined behavior)**, even though each operation is individually atomic. Scope mismatch is a real and common bug: the *scope of both sides* of a communication must include the communicating threads.

The classic pre-C++ intrinsics map onto the same machinery: `__threadfence_block()` / `__threadfence()` / `__threadfence_system()` are block/device/system-scope fences. Underneath it all sits the formally specified PTX memory consistency model (subject of the paper "A Formal Analysis of the NVIDIA PTX Memory Consistency Model", which the PTX documentation cites for the C++-to-PTX mappings) — GPUs are weakly ordered by *specification*, not by accident, which is what makes scoped atomics portable and provable rather than folklore.

**Practical rules.** Use the narrowest scope that includes everyone who touches the location; use `relaxed` unless you are publishing data; prefer shared-memory/LDS atomics plus one final global reduction; and remember that atomics are *serialization points* — every atomic that can be eliminated or aggregated is contention removed from L2.

### 1.4 GPU-4.12 — Deriving theoretical memory bandwidth

**The formula.** Peak memory bandwidth of any DRAM interface is derived, not looked up:

```
BW (bytes/s) = pins × data rate (transfers/s per pin) ÷ 8 bits/byte
```

where "data rate" already accounts for DDR (both clock edges) — it is the marketing number quoted in Gbps/pin. Everything else — stacks, channels, bus width — is bookkeeping for *how many pins*.

**HBM organization (recap from GPU-4.6, extended).** An HBM stack is a column of DRAM dies (4-Hi to 16-Hi) bonded with through-silicon vias onto a logic base die, presenting a wide, slow-ish interface: **1024 data pins per stack** through HBM3/HBM3e, **doubled to 2048 pins in HBM4**. The GPU package carries several stacks (5 on H100, 8 on B200), each hanging off its own memory controller slice; address bits are interleaved/hashed across channels and stacks so that sequential streams from many warps spread across the whole interface rather than saturating one controller.

**Worked derivations.**

| System | Interface | Data rate | Arithmetic | Peak BW |
|---|---|---|---|---|
| A100 SXM | 5 × HBM2e = 5120 bits | 3.2 Gb/s/pin | 640 B × 3.2 G/s | **2.05 TB/s** |
| H100 SXM | 5 × HBM3 = 5120 bits | ≈5.2 Gb/s/pin (inferred: 3.35 TB/s ÷ 640 B) | 640 B × 5.24 G/s | **3.35 TB/s** |
| B200 | 8 × HBM3e = 8192 bits | 8 Gb/s/pin (JEDEC HBM3e) | 1024 B × 8 G/s | **8.19 TB/s** |
| Rubin (target, per industry reporting) | 8 × HBM4 = 16384 bits | ~10.7 Gb/s/pin | 2048 B × 10.7 G/s | **~22 TB/s** |
| RTX 5090 (GDDR7, non-HBM example) | 512 bits | 28 Gb/s/pin (PAM3) | 64 B × 28 G/s | **1.79 TB/s** |

The B200 row is a clean sanity check: 8 stacks × 1024 pins × 8 Gbps ÷ 8 = 8192 GB/s, exactly the advertised 8 TB/s. The Rubin row shows the same arithmetic run *forward* as a feasibility check on reported targets: 22 TB/s over an 8-stack HBM4 interface demands ~10.7 Gb/s per pin — above the JEDEC 8 Gb/s baseline, consistent with reporting that NVIDIA pushed vendors past the standard speed grade (see Development 1). The GDDR7 row demonstrates the alternative philosophy: GDDR uses few pins at very high signal rate (PAM3 signaling) on a GPU-cost substrate; HBM uses many pins at moderate rate on silicon interposer — same formula, opposite corner of the design space, and the reason HBM wins by 4–5× per package in bandwidth but costs far more.

**Capacity runs on the same axis.** Stack capacity = die capacity × height: HBM4 dies are 24 Gb (3 GB) or 36 Gb (4 GB); a 12-Hi stack of 24 Gb dies is 36 GB, and a 16-Hi stack is 48 GB. Eight stacks give 288 GB (the Rubin-class configuration) — capacity, not just bandwidth, rides on stack height.

**What the theoretical number does not include.** The formula gives the *pin-limited* ceiling. Achievable bandwidth is lower because of: DRAM refresh and activation overhead (row misses cost tRCD), ECC, protocol and queueing overhead, load imbalance across controllers, and access patterns that break the interleave (e.g., a power-of-two stride that aliases onto one channel). Well-behaved streaming kernels reach a large fraction of peak; random and strided patterns can collapse it. That is why Section 1.1's access patterns and this section's ceiling are one topic split in two: the ceiling is arithmetic, the approach to it is program design. When a colleague quotes "8 TB/s," the correct mental tag is: *pin-limited, spread-evenly, refresh-paid-for* — everything else is your problem.

### 1.5 GPU-5.1 — What can reside on an SM/CU

**The problem this topic opens.** Module 5 is about a finite set of on-chip resources that must simultaneously hold a kernel's working context. An SM (NVIDIA) or CU (AMD) is not a blank execution engine that "runs threads"; it is a set of **fixed-size partitions** — warp slots, thread-block slots, registers, shared memory — and a kernel launch is a request to fill them. Residency — what is physically *on* the SM at one time — is the concept; occupancy (GPU-5.2, next time) is the metric built on it.

**The inventory (NVIDIA, datacenter parts, from the CUDA technical specifications):**

| Resource | A100 (CC 8.0) | H100 (CC 9.0) | B200 (CC 10.0) |
|---|---|---|---|
| Max threads per block | 1024 | 1024 | 1024 |
| Max resident threads per SM | 2048 | 2048 | 2048 |
| Max resident warps per SM | 64 | 64 | 64 |
| Max resident blocks per SM | 32 | 32 | 32 |
| 32-bit registers per SM | 65,536 | 65,536 | 65,536 |
| Max registers per thread | 255 | 255 | 255 |
| Shared memory per SM | 164 KB | 228 KB | 228 KB |
| Max shared memory per block | 163 KB | 227 KB | 227 KB |
| Unified L1 + shared per SM | 192 KB | 256 KB | 256 KB |

Two structural facts hide in this table. First, the **register file is exactly 64 Ki × 32-bit = 256 KiB per SM** — the same capacity as the entire unified L1/shared-memory partition, and (a coincidence worth savoring) the same as Blackwell's new Tensor Memory. Registers are allocated **per warp, statically, at launch** (in fixed granularities — 256 registers per warp on Volta-class and later), from a compile-time per-thread count; there is no runtime paging. Second, the per-block and per-SM shared-memory limits differ by 1 KB reserved for system use, and shared memory above 48 KB per block requires an explicit opt-in via `cudaFuncSetAttribute` — the unified cache is *partitioned per kernel* (the "carveout"), not a fixed split.

**The AMD picture (CDNA, e.g. MI300X / gfx942).** Same concepts, different names and proportions: a **wavefront** is 64 threads; a **workgroup** is up to 1024 threads = 16 wavefronts, and — like a CUDA block on an SM — a workgroup's wavefronts all reside on **one CU**. Per the ROCm/HIP documentation, a CDNA CU contains four SIMD units (each issuing 16 lanes per cycle, so one 64-thread wavefront instruction takes four cycles on one SIMD), 8–10 wavefront instruction buffers per SIMD, a 512 KiB **VGPR file** (vector registers, doubled from CDNA2's 256 KiB), scalar registers, and **64 KiB of LDS** (Local Data Share, the shared-memory analog: 32 banks × 4 bytes). The wavefront/VGPR/LDS triad plays exactly the roles of warp/registers/shared-memory, with the pleasant difference that AMD exposes the VGPR count per kernel explicitly to the programmer.

**A worked residency example.** Kernel K: 256 threads/block (8 warps), 40 registers/thread, 12 KB shared memory/block, on an A100.

- **Registers:** per warp, 32 × 40 = 1280 registers (already a multiple of the 256 granularity); per block, 8 × 1280 = 10,240. Blocks fitting in 65,536 registers: 65536 ÷ 10240 = **6** (7 would need 71,680). 
- **Threads:** 2048 ÷ 256 = **8** blocks.
- **Blocks:** hard cap 32.
- **Shared memory:** 164 KB ÷ 12 KB = **13** blocks.

The binding constraint is registers: only 6 blocks × 256 threads = 1536 resident threads = 48 of 64 warp slots. Note that *no single resource is exhausted* — threads and shared memory have headroom; the SM is register-starved. This is the everyday mechanics of GPU performance, and it is why `__launch_bounds__`, `-maxrregcount`, and register-pressure trade-offs (GPU-5.3) exist: they are levers on this arithmetic.

**Hardware meaning of "resides."** A resident warp owns: its share of the register file (fixed), a warp-context slot (the per-warp program counter and divergence state — one PC per *warp*, not per thread, as covered in the execution model), and its block's slice of shared memory. A resident block is *pinned* until all its warps finish — blocks never migrate between SMs, which is precisely what makes them the unit of scheduling independence (GPU-5.5). Blocks that do not fit wait in a queue; they are not partially resident. There is no oversubscription magic: if a block's static needs (e.g., 200 KB shared memory, or 1024 threads × 200 registers) exceed any single SM's capacity, the kernel simply cannot launch.

**Blackwell adds a resident resource class.** On datacenter Blackwell (SM100, compute capability 10.0), the SM carries a **256 KiB Tensor Memory (TMEM)** — 512 columns × 128 lanes × 32 bits — that exists *beside* registers and shared memory and is addressable only through the `tcgen05` instruction family. Accumulator and operand tiles of fifth-generation Tensor Core MMAs live there, allocated in 32-column units (powers of two, 32–512 columns) at kernel runtime, and a 256×128 FP32 accumulator tile (128 KB) consumes half of it. For the first time since shared memory, a kernel's *tensor-core working set* is a distinct, budgeted SM resource — with real occupancy consequences we develop in Section 2.2. Notably, workstation Blackwell (CC 12.0) has *no* TMEM and caps shared memory at 99 KB: within one GPU generation, the residency model itself now differs by market segment.

**Connections.** GPU-4.2/4.3 introduced registers and shared memory as *storage*; this topic makes them *capacity constraints that gate concurrency*. Little's law (Section 1.2) supplies the why: residency exists to hold in-flight work so latency is hidden. Next issue's GPU-5.2 (occupancy) turns today's arithmetic into a metric — and explains why 100% occupancy is often the wrong target.

## 2. Key Developments / News

### 2.1 HBM4 enters its volume ramp: 12-Hi in mass production, 16-Hi in qualification

**What happened.** At Hot Chips 2026 (August 23–24, Stanford), SK hynix VP of package engineering Lee Jae-sik stated that the company's 12-layer HBM4 is in **mass production**, while the 16-layer product has entered **customer qualification** — the first concrete confirmation of 16-Hi status. SK hynix's Q2 2026 earnings materials corroborate the trajectory: HBM4 mass-production shipments began in Q2 2026 with yields "approaching mature HBM3E levels," ramping through the second half of the year, with HBM4E samples already delivered for 2027 volume. This generation feeds NVIDIA's Rubin platform (industry reporting puts Rubin at 288 GB across eight HBM4 stacks).

**What technically changed.** HBM4's defining change is the doubling of the per-stack interface from 1024 to **2048 data pins**, with shipping speed grades above 10 Gb/s/pin against the JEDEC baseline of 8 — which Section 1.4's arithmetic turns into >2 TB/s per stack and ~20+ TB/s aggregate for an 8-stack GPU (reported Rubin targets of ~22 TB/s imply ≈10.7 Gb/s/pin; NVIDIA originally announced 13 TB/s before raising it, pushing vendors up the speed-grade curve). The 16-Hi path is a packaging story: HBM stacks are capped at 775 µm total height, so 16-Hi (48 GB/cube) requires ~50 µm-thin core dies and halved inter-die gaps, straining SK hynix's MR-MUF process; hybrid bonding — which would remove micro-bumps, allow thicker dies, and cut bump pitch below 18 µm — was pushed out to HBM5 at the earliest.

**Why it matters.** This is the supply side of Section 1.2's balance point: every doubling of bandwidth raises the arithmetic-intensity ridge that separates latency-tolerant, compute-bound workloads from the memory-bound regime — and for bandwidth-bound workloads (LLM decoding, sparse methods, most of HPCG's profile), memory generation *is* the performance generation.

**Connection to today's curriculum.** GPU-4.12 is literally this development's math: pins × rate ÷ 8. Watch stack counts (capacity), pin counts (bandwidth), and die thickness (yield/thermals) as the three independent variables.

### 2.2 Blackwell's Tensor Memory: a new resident SM resource

**What happened.** With datacenter Blackwell (compute capability 10.0), NVIDIA introduced **Tensor Memory (TMEM)** — a 256 KiB per-SM, per-SM-addressable memory class alongside registers and shared memory — reachable only through the new `tcgen05` PTX instruction family (PTX ISA 8.6+). Fifth-generation Tensor Core MMA operations read operands from shared-memory descriptors and accumulate **into TMEM** instead of into warp registers; `tcgen05.alloc`/`dealloc` manage column allocations (32-column granularity, powers of two, 32–512 columns), and the MMA is issued by a single thread with completion tracked by mbarrier — asynchronous to warp execution. NVIDIA's CUDA documentation recommends this feature set be used through CUTLASS and CUDA-X libraries rather than raw PTX.

**What technically changed.** The accumulator of a GEMM tile moved out of the register file into its own memory with its own ports. The register file (256 KiB, GPU-5.1) was structurally saturated as an accumulator store: a 256×128 FP32 accumulator tile is 128 KB — *half* the SM's entire register file — before a single address register or epilogue temporary. TMEM's capacity (256 KiB) matching the register file is the tell: the accumulator budget did not grow, it was *relocated* so registers can serve addressing, epilogue, and control flow while tensor cores stream results at their own rate.

**Why it matters.** Occupancy analysis (the module this week opens) now has a fourth resource axis on SM100-class parts: a kernel's TMEM column demand — accumulator tiles, their double buffers, operand/scale residency — competes for a 512-column budget the way registers compete for 64 Ki, and CUTLASS's sanctioned SM100 tile shapes are exactly the shapes that fit that budget. It also bifurcates the architecture family: workstation Blackwell (CC 12.0) ships without TMEM and with 99 KB shared-memory caps, so "Blackwell" kernels are not portable across the generation without restructuring.

**What to watch.** How quickly libraries (cuBLAS, CUTLASS epilogues) expose TMEM budgeting as a tunable, and whether TMEM-style dedicated accumulator memory appears in AMD's roadmap (CDNA's accumulator registers, AccVGPR on MI100+, solved the same problem differently).
