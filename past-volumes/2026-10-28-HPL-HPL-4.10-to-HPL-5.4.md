## 0. Concise Summary

Today closes out the BLAS foundations module and opens the Gaussian elimination module — and the two connect more deeply than the curriculum ordering might suggest.

The first topic, **HPL-4.10**, surveys the BLAS ecosystem as it actually ships: cuBLAS, rocBLAS, oneMKL, Arm Performance Libraries, OpenBLAS, and BLIS. The key idea is that BLAS is a *specification* of operations, not a piece of code — every hardware vendor and several open-source communities reimplement GEMM, TRSM, and friends from scratch for each architecture, because a tuned GEMM can extract an order of magnitude (or more) more performance than a naive triple loop on the same silicon. The GotoBLAS lineage — Goto's packing-and-microkernel design, formalized in his 2008 paper with van de Geijn — is the direct ancestor of OpenBLAS and the template for essentially every modern implementation. We also note a numerical subtlety that matters for reproducibility: two "correct" BLAS libraries can produce different last bits because they sum in different orders.

The remaining four topics build **Gaussian elimination** from first principles: the strategy of converting a general linear system into a triangular one (HPL-5.1), the mechanics of one elimination step — pivot row, multipliers, rank-1-style updates (HPL-5.2), the full forward-elimination sweep and its characteristic \(\tfrac{2}{3}n^3\) FLOP cost (HPL-5.3), and back substitution, the \(O(n^2)\) serial-then-parallel unwind of the triangular system (HPL-5.4). A fully worked 3×3 example threads through all four sections, with every number checkable by hand.

The key connection: elimination is where dense linear algebra *earns* its dependence on BLAS. Each elimination step is mathematically a rank-1 update; real LU codes block those updates so that the overwhelming majority of the \(\tfrac{2}{3}n^3\) FLOPs execute inside vendor GEMM kernels. The vendor-library story and the algorithm story are one story.

In developments: NVIDIA's cuBLAS now *emulates* FP64 matrix multiplication on Blackwell INT8 tensor cores with accuracy guarantees (up to ~13× faster than native FP64 on some shapes), collapsing the precision-versus-speed trade-off into library internals; OpenBLAS 0.3.34 (July 2026) fixed race conditions in level-3 BLAS and in GETRF — the LAPACK routine that implements exactly today's algorithm; and the current CUDA 13.4 cycle keeps extending cuBLAS for Blackwell/Rubin. Each development lands directly on today's curriculum.

## 1. Learn the Concepts

### 1.1 Vendor BLAS libraries (HPL-4.10)

Over the past two weeks we built up the BLAS hierarchy operationally: Level-1 vector kernels like AXPY (HPL-4.5), Level-2 GEMV (HPL-4.6), Level-3 GEMM and TRSM (HPL-4.7, HPL-4.8), and why Level-3 operations are the fast ones (HPL-4.9). The remaining question is pragmatic: **whose code do you actually call?**

The crucial mental model is that **BLAS is an interface, not an implementation**. The BLAS specification defines operation *semantics* — function signatures and the mathematical meaning of each routine, e.g. `dgemm` computes \(C \leftarrow \alpha A B + \beta C\) in double precision — but says nothing about how the work is organized in caches, registers, or threads. Anyone can implement it. Netlib hosts a *reference* implementation that is simple, portable, and slow. Production systems replace it with an implementation tuned for specific hardware, and that choice is one of the highest-leverage decisions in the entire HPC software stack, because dense linear algebra — and everything built on it, including LAPACK, ScaLAPACK, and HPL itself — spends most of its time inside BLAS calls.

Why can tuned implementations be so much faster? We derived the mechanism in HPL-2.5–HPL-2.8 and HPL-4.9: the naive triple loop over \(C = AB\) re-reads operands many times, so memory traffic scales like the FLOP count (\(O(n^3)\) words moved), while the arithmetic itself is only \(2n^3\) FLOPs. On any modern machine the floating-point units can consume data far faster than main memory can supply it, so the naive loop runs at a small fraction of peak. Blocking restores reuse: stage panels of \(A\) and \(B\) in cache, keep tiles of \(C\) in registers, and traffic drops toward \(O(n^2)\) — the surface-to-volume argument from HPL-2.8. The same two or three nested loops, reorganized around the memory hierarchy, differ in delivered performance by large factors, sometimes more than 10× between reference and tuned code on the same processor. This is not a marginal optimization; it is the difference between an HPL run that finishes this week and one that does not.

**The ecosystem.** The major implementations in practice:

| Library | Steward | Hardware focus | Notes |
|---|---|---|---|
| cuBLAS / cuBLASLt | NVIDIA | NVIDIA GPUs | Ships with the CUDA Toolkit; the newer cuBLASLt API exposes algorithm selection and heuristics |
| rocBLAS | AMD | AMD GPUs | Part of the ROCm/HIP stack, open source on GitHub |
| oneMKL | Intel | Intel CPUs and GPUs | Part of oneAPI; BLAS, LAPACK, sparse, FFTs |
| Arm Performance Libraries | Arm | Arm Neoverse | BLAS and LAPACK for Arm servers |
| Accelerate | Apple | Apple Silicon | The system BLAS/LAPACK on macOS |
| OpenBLAS | OpenMathLib community | x86-64, Arm, POWER, RISC-V, and more | Community continuation of GotoBLAS2, begun in 2011 |
| BLIS | UT Austin FLAME group + community | Portable framework | Not one library but a *framework* for instantiating them |

Two lineages deserve special mention because they shaped everything else. First, **GotoBLAS**: in the mid-2000s Kazushige Goto, working at UT Austin, produced a dense linear algebra library whose GEMM design — pack blocks of the operands into contiguous buffers laid out exactly as the microkernel wants, then run a small register-blocked kernel that keeps \(C\)-tiles resident in registers — came to define high-performance GEMM. His 2008 paper with Robert van de Geijn, *Anatomy of High-Performance Matrix Multiplication*, remains the canonical description. When GotoBLAS development stopped, the community forked it into **OpenBLAS**, which today is the default BLAS on most Linux distributions and supports a wide range of CPU architectures, with runtime CPU dispatch (`DYNAMIC_ARCH`) selecting per-architecture kernels. Second, **BLIS**: rather than hand-writing a new library per architecture, the FLAME group generalized the GotoBLAS design into a layered framework where porting to new hardware means writing one small microkernel; the rest of GEMM — packing, thread parallelism, the outer loop structure — is inherited. The BLIS design was formalized in a 2015 ACM TOMS paper by Van Zee and van de Geijn.

Why do hardware vendors maintain their own libraries at all? Because peak performance is architecture-specific. A kernel that maps well onto AVX-512 vector units on an Intel Xeon says nothing about what fits AMD's Zen cores, Arm NEON/SVE pipelines, or an NVIDIA GPU's SIMT execution and tensor cores. Vendor libraries encode, per architecture and per matrix shape, decisions we will study in module 9: tile sizes, packing layouts, loop orderings, and — on GPUs — thread-block shapes and kernel selection heuristics. cuBLASLt makes this explicit: rather than one hidden implementation, it lets (or requires) the caller to pick or query algorithms, with heuristics tuned per GPU architecture. This is why BLAS library releases track hardware releases so closely, a point the developments section makes concrete.

**A numerical subtlety worth internalizing.** The BLAS specification fixes the mathematics but not the summation order. GEMM implementations accumulate dot products in different orders — blocked, vectorized, with or without fused multiply-adds (HPL-3.9). Because floating-point addition is not associative (HPL-3.7), two compliant implementations can return slightly different results for the same inputs. Neither is "wrong"; both are correct to within their rounding behavior. Practical consequences: bitwise-reproducible dense linear algebra requires pinning the BLAS library and version (and often disabling thread-count variation), and when you compare a hand-written kernel against a vendor library, expect agreement to a few ulps, not to the last bit. This also connects to error accumulation (HPL-3.8): library reordering is one more source of small perturbations, which is why HPL's own validation is residual-based rather than bitwise (HPL-12.10, coming later in this theme).

**Why this sits at the start of today's lesson.** Everything we do in the next four topics — elimination, forward sweep, back substitution — is the algorithmic skeleton that real dense solvers wrap around BLAS. The pure algorithm below looks scalar and serial; production LU (LAPACK's `GETRF`, and HPL itself) blocks it so that the bulk of the FLOPs execute as GEMM calls into exactly the libraries above. When you run HPL and read its performance, you are reading a joint report on the *algorithm structure* (this module and the next two) and the *vendor kernel quality* (this section).

### 1.2 The elimination idea (HPL-5.1)

Setting aside libraries for the rest of the lesson, we ask the mathematical question: how do you actually solve \(Ax = b\) for a general dense \(n \times n\) matrix \(A\)?

First, what *not* to do: explicitly computing \(A^{-1}\) and then multiplying \(A^{-1}b\). It never helps — it costs more arithmetic than solving directly and adds rounding error without accuracy benefit. The standard advice in every numerical linear algebra text and in the LAPACK Users' Guide is the same: **solve, don't invert**. What makes direct solving tractable is that two classes of systems are already trivially solvable: triangular ones. If \(U\) is upper triangular, the last equation \(u_{nn}x_n = c_n\) contains exactly one unknown; solve it, substitute upward, and each equation in turn introduces exactly one new unknown. Lower-triangular systems unwind the same way from the top. Triangular solves cost only \(O(n^2)\) — quadratic, not cubic.

Elimination is the strategy for getting from "general" to "triangular": **systematically apply row operations that preserve the solution set, chosen to create zeros below the diagonal**, until what remains is upper triangular. The invariant is elementary but worth stating precisely, because the entire method's correctness rests on it: replacing row \(i\) by \((\text{row } i) - \ell \cdot (\text{row } k)\) is a reversible operation, so every system in the sequence is *equivalent* to the original — same solution set, different shape. We are not approximating; we are reshaping.

A 2×2 example shows the whole idea in four numbers. Solve

\[
\begin{bmatrix} 2 & 1 \\ 6 & 5 \end{bmatrix} x = \begin{bmatrix} 5 \\ 17 \end{bmatrix}.
\]

Subtract 3× row 1 from row 2 (the multiplier 3 is exactly what kills the 6: \(6 - 3\cdot 2 = 0\)):

\[
\begin{bmatrix} 2 & 1 \\ 0 & 2 \end{bmatrix} x = \begin{bmatrix} 5 \\ 2 \end{bmatrix}.
\]

The system is now upper triangular. Back substitution is immediate: \(2x_2 = 2 \Rightarrow x_2 = 1\), then \(2x_1 + 1 = 5 \Rightarrow x_1 = 2\). Check against the original system: \(2\cdot2 + 1 = 5\), \(6\cdot2 + 5\cdot1 = 17\). Solved — and the expensive part was *one* elimination step.

Two structural observations turn this from a trick into an algorithm family:

1. **The expensive transformation depends only on \(A\), not on \(b\).** All the row operations that triangularize \(A\) can be recorded and applied to any right-hand side. This is the factor-then-solve structure introduced in HPL-1.8: factor \(A\) once (\(O(n^3)\)), then solve for many right-hand sides (\(O(n^2)\) each). It is why LAPACK splits the work into `GETRF` (factor) and `GETRS` (solve), and why applications that solve repeatedly — implicit time-stepping, circuit simulation, many-query problems — are built on a single factorization.

2. **The multipliers are not garbage — they are data.** The numbers we computed to kill entries below the pivot (the 3 above) collectively form a lower-triangular matrix \(L\) such that \(A = LU\). That identification is the subject of module 6 (HPL-6.1–HPL-6.3); today we simply note that elimination *is* a factorization in disguise, and the famous \(\tfrac{2}{3}n^3\) cost of "Gaussian elimination" and of "LU factorization" is the same cost.

One caveat to flag now and settle in module 7: everything today assumes the pivots we encounter are usable. If a pivot is zero, the method stalls; if it is merely tiny, dividing by it amplifies rounding error destructively. Pivoting — row exchanges to select good pivots — is the fix, and it is why real codes interleave elimination with row swaps. The pure-algorithm view we build today is the engine; pivoting is the safety system wrapped around it.

### 1.3 One elimination step in detail (HPL-5.2)

Now the mechanics, precisely. Suppose after \(k-1\) steps the first \(k-1\) columns below the diagonal are already zero. Step \(k\) eliminates column \(k\):

- The **pivot row** is row \(k\); the **pivot** is the diagonal entry \(a_{kk}\) (assumed nonzero today).
- For each row \(i > k\), compute the **multiplier** \(\ell_{ik} = a_{ik}/a_{kk}\) — exactly the scalar that makes \(a_{ik} - \ell_{ik} a_{kk} = 0\).
- Replace row \(i\) by row \(i - \ell_{ik} \cdot\) row \(k\), across columns \(k+1 \dots n\) and in the right-hand side.

Three views of that update, in increasing order of hardware relevance:

**Row view.** Each updated row is an AXPY (HPL-4.5): \(r_i \leftarrow r_i - \ell_{ik}\, r_k\). One multiply and one subtract per element — or one FMA (HPL-3.9), which is how real hardware executes it.

**Matrix view.** Collect the multipliers into a vector \(\ell = (0,\dots,0,\ell_{k+1,k},\dots,\ell_{n,k})^T\). The update to the trailing submatrix (rows and columns \(>k\)) is a **rank-1 update**: \(A_{trailing} \leftarrow A_{trailing} - \ell\, r_k^T\). Elimination is a sequence of rank-1 updates — the outer-product view that module 6 will formalize (HPL-6.5) and that explains why blocked variants reformulate it as GEMM.

**Cost view.** The trailing submatrix is \((n-k)\times(n-k)\); each entry gets one FMA. So step \(k\) costs

\[
(n-k)^2 \ \text{FMAs} \;\approx\; 2(n-k)^2 \ \text{FLOPs}
\]

on the matrix, plus \(O(n-k)\) for the right-hand side. The work *shrinks* as elimination proceeds: step 1 updates nearly the whole matrix, the last step updates a single entry. That declining-work structure is exactly what load-balances poorly across ranks late in a distributed factorization — a theme we will meet in HPL-19.5 and HPL-11.8.

**Parallelism within a step.** The rows below the pivot are updated independently of each other — row \(i\)'s update never reads row \(j\)'s result. So within one step, the work parallelizes cleanly across rows (threads, SIMD lanes across columns). But *between* steps there is a hard dependency: step \(k+1\)'s pivot row is step \(k\)'s output. This serial-dependency, parallel-within-step structure is the seed of the panel bottleneck that dominates distributed LU (HPL-5.7 next volume, then HPL-7.7 and module 20).

**Worked step.** Carry the example we will use for the rest of the lesson:

\[
A = \begin{bmatrix} 2 & 1 & 1 \\ 6 & 4 & 5 \\ 2 & 3 & 6 \end{bmatrix}, \qquad b = \begin{bmatrix} 7 \\ 29 \\ 26 \end{bmatrix}.
\]

*Step 1 (pivot \(a_{11}=2\)):* multipliers \(\ell_{21} = 6/2 = 3\), \(\ell_{31} = 2/2 = 1\).

- Row 2 ← row 2 − 3·row 1 = \((6,4,5) - 3(2,1,1) = (0, 1, 2)\)
- Row 3 ← row 3 − 1·row 1 = \((2,3,6) - (2,1,1) = (0, 2, 5)\)
- RHS: \(c \leftarrow (7,\; 29-3\cdot7,\; 26-1\cdot7) = (7, 8, 19)\)

*Step 2 (pivot \(a_{22}=1\) in the reduced matrix):* multiplier \(\ell_{32} = 2/1 = 2\).

- Row 3 ← row 3 − 2·row 2 = \((0,2,5) - 2(0,1,2) = (0, 0, 1)\)
- RHS: \(c_3 \leftarrow 19 - 2\cdot 8 = 3\)

After two steps the matrix is upper triangular:

\[
U = \begin{bmatrix} 2 & 1 & 1 \\ 0 & 1 & 2 \\ 0 & 0 & 1 \end{bmatrix}, \qquad c = \begin{bmatrix} 7 \\ 8 \\ 3 \end{bmatrix}, \qquad
L = \begin{bmatrix} 1 & & \\ 3 & 1 & \\ 1 & 2 & 1 \end{bmatrix}.
\]

Everything here is checkable by hand: multiplying \(L U\) row by row reproduces \(A\) exactly (e.g. row 3: \(1\cdot(2,1,1) + 2\cdot(0,1,2) + 1\cdot(0,0,1) = (2,3,6)\)), and \(L c = b\) (row 3: \(1\cdot7 + 2\cdot8 + 1\cdot3 = 26\)). The multipliers were chosen as exact small integers so the example is rounding-free — in floating point they would generally not be exact, which is where module 7's stability analysis begins.

A final detail with big implementation consequences: we computed the zeros below the pivot, but we *knew* they would be zero — that is the whole point. Rather than storing zeros, real codes store the multiplier \(\ell_{ik}\) in the memory location of the entry it eliminated. The matrix \(A\) is thereby transformed, in place, into a packed array holding \(U\) above the diagonal and the multipliers below it — which is precisely the \(L\) and \(U\) of module 6 sharing one \(n^2\) storage (HPL-6.4). Nothing about the math changes; only the memory layout does.

### 1.4 Forward elimination: the full sweep (HPL-5.3)

The **forward sweep** is just the step of §1.3 iterated down the matrix:

```text
for k = 1 to n-1:                     # pivot row
    for i = k+1 to n:                 # rows to clean out below the pivot
        l_ik = a[i,k] / a[k,k]        # multiplier (stored in place of a[i,k])
        for j = k+1 to n:             # trailing columns
            a[i,j] = a[i,j] - l_ik * a[k,j]   # one FMA
        b[i]   = b[i]   - l_ik * b[k]
```

"Forward" refers to the direction of travel: we march from the top-left corner down, leaving zeros and finished rows behind us. The output is an upper-triangular system \(Ux = c\), plus the multipliers implicitly stored in the zeroed-out lower triangle.

**The cost, derived.** Step \(k\) costs \(2(n-k)^2\) FLOPs on the matrix (HPL-5.2's count). Summing over all steps, with the substitution \(j = n - k\):

\[
\sum_{k=1}^{n-1} 2(n-k)^2 = 2\sum_{j=1}^{n-1} j^2 = \frac{(n-1)\,n\,(2n-1)}{3} \;=\; \frac{2}{3}n^3 - n^2 + \frac{n}{3}.
\]

There it is: **forward elimination costs \(\tfrac{2}{3}n^3 + O(n^2)\) FLOPs** — the famous two-thirds cube that dominates dense direct solvers. (HPL-5.6 next volume revisits this derivation from the operation-count standpoint and connects it to HPL's own FLOP accounting, HPL-12.11.) The right-hand side contributes only \(\sum_k 2(n-k) = n^2 - n\) FLOPs, and back substitution another \(O(n^2)\) — both negligible at scale relative to the cubic term.

Small-\(n\) sanity check, exact numbers for a 4×4 system:

| Phase | Exact FLOP count | Formula |
|---|---|---|
| Matrix updates, forward elimination | 28 | \(\sum 2(n-k)^2 = 2(9+4+1)\) |
| RHS updates | 12 | \(\sum 2(n-k) = 2(3+2+1)\) |
| Back substitution (incl. divisions) | 16 | \(\sum_i (2(n-i)+1) = 7+5+3+1\) |
| **Total solve** | **56** | vs. asymptotic \(\tfrac{2}{3}n^3 \approx 42.7\) for the matrix part alone |

Note the exact count exceeds the asymptotic leading term at \(n=4\) — the \(-n^2 + n/3\) correction is still large at small sizes. This is a general pattern you will meet repeatedly in HPL parameter reasoning (module 13): asymptotic formulas guide, but finite-size corrections matter, especially near the small problem sizes where panels and edges live.

**System behavior — and an honest warning.** The loop nest above is the *mathematics* of elimination, not the *implementation*. Read literally, it re-streams the entire trailing matrix from memory at every step \(k\): the \((n-k)\times(n-k)\) trailing block is touched but only \((n-k)^2\) FMAs are done on it, giving arithmetic intensity of order 1 FLOP per word — memory-bound at every step, exactly the disease that makes Level-1/2 BLAS slow (HPL-4.2, HPL-4.3). A literal scalar implementation of forward elimination would run at a small fraction of peak on any modern processor.

Real dense LU codes therefore do not run this loop literally. They **block** it: eliminate a whole panel of \(NB\) columns at once (recursively, using the same mathematics at smaller scale), then apply the accumulated effect of the panel to the trailing matrix as one big **GEMM** — a rank-\(NB\) update instead of \(NB\) separate rank-1 updates. That reorganization converts the memory-bound rank-1 stream into compute-bound Level-3 work (HPL-4.9), which is the entire subject of module 8. Today's scalar sweep is the correct *semantic model* — what the algorithm computes and in what dependency order — and the blocked algorithm is the performance-preserving *schedule* of the same mathematics. Keeping the two levels distinct (math vs. schedule) will make modules 8–11 far easier to read: every blocked or distributed variant is the same elimination, re-tiled for a memory hierarchy or a process grid.

### 1.5 Back substitution (HPL-5.4)

After forward elimination we hold an upper-triangular system \(Ux = c\). Back substitution unwinds it from the bottom, where the information is most concentrated:

```text
for i = n down to 1:
    s = c[i]
    for j = i+1 to n:
        s = s - U[i,j] * x[j]        # dot product with the already-known tail
    x[i] = s / U[i,i]
```

Each row \(i\) consumes the *already computed* unknowns \(x_{i+1},\dots,x_n\), leaving exactly one unknown \(x_i\) in its equation. On our running example:

- \(i=3\): \(x_3 = 3/1 = 3\)
- \(i=2\): \(x_2 = (8 - 2\cdot3)/1 = 2\)
- \(i=1\): \(x_1 = (7 - 1\cdot2 - 1\cdot3)/2 = 1\)

So \(x = (1,2,3)\) — and substituting back into the *original* system confirms it exactly: row 1: \(2+2+3 = 7\); row 2: \(6+8+15 = 29\); row 3: \(2+6+18 = 26\). (End-to-end this 3×3 solve took 25 FLOPs: 10 on the matrix in forward elimination, 6 on the RHS, 9 in back substitution.)

**Cost and character.** Row \(i\) does \(n-i\) FMAs plus one division: \(\sum_i (2(n-i)+1) = n^2\) FLOPs total. Quadratic — for large \(n\), pure noise next to the \(\tfrac{2}{3}n^3\) elimination. But *character* matters more than count here. Back substitution touches \(\sim n^2/2\) words of \(U\) and performs \(\sim n^2\) FLOPs, so its arithmetic intensity is O(1) FLOPs per word — around 0.25 FLOP/byte in FP64 — *independent of problem size*. Contrast GEMM, whose blocked intensity grows with dimension (HPL-2.6, HPL-4.9): back substitution sits permanently in the memory-bound region of the roofline. It is a Level-2-BLAS-shaped operation (GEMV/TRSV-like), not a GEMM-shaped one, and no amount of tuning changes that — the operation fundamentally moves a matrix to perform only \(O(n^2)\) arithmetic on it.

**Parallelism: serial outside, parallel inside.** The outer loop is a strict serial dependency chain — \(x_i\) needs every later \(x_j\) — so back substitution cannot be parallelized across rows the way an elimination step can. Within a row, though, the inner dot product parallelizes (SIMD, or split across threads), and the whole solve becomes Level-3-izable when there are many right-hand sides: solving \(UX = C\) for a block of \(NB\) columns is TRSM (HPL-4.8), which is why the factor-then-solve structure of §1.2 matters so much — batched solves amortize into efficient kernels, one-at-a-time solves cannot. In distributed settings (HPL's actual execution of the solve phases), triangular solves also *lose work symmetry*: rows near the bottom of \(U\) carry long dot products while rows near the top are nearly empty, so ranks owning different parts of the matrix finish at different times — an early instance of the load-balance and rank-skew issues of HPL-19.5 and HPL-20.7.

One symmetry note: the same algorithm run top-down solves *lower*-triangular systems \(Ly = b\) (forward substitution — the inner loop runs over the already-computed earlier unknowns). Module 6 needs exactly that to complete the solve \(Ax = b \Rightarrow Ly = b \Rightarrow Ux = y\): elimination's triangular output pairs with *two* substitutions. The LAPACK naming makes the mapping concrete: `GETRF` ("GEneral TRiangular Factorization") performs the elimination/factorization of §1.2–1.4, `GETRS` ("... TRiangular Solve") performs the pair of substitutions, and `LASWP` applies the row interchanges that pivoting (module 7) interleaves into the sweep. These names are worth memorizing now — they are the units in which real libraries, and the OpenBLAS news below, talk about exactly today's algorithm.

### 1.6 The complete pipeline

Assembling the whole lesson into one dependency diagram:

```text
        A, b
         │
         ▼
  ┌──────────────────┐   O(2n³/3) FLOPs, O(n) steps, parallel within a step,
  │ forward          │   rank-1-updates math; blocked into GEMM by real codes
  │ elimination      │   (LAPACK: GETRF + pivot row swaps LASWP)
  └──────────────────┘
         │  U (upper triangular), L (multipliers), transformed RHS c
         ▼
  ┌──────────────────┐   O(n²) FLOPs, serial chain over rows, memory-bound,
  │ back substitution│   parallel inside each row; TRSM-izable for many RHS
  │ (and fwd. subst. │   (LAPACK: GETRS — two triangular solves)
  │  for L in mod. 6)│
         ▼
         x                verified by the residual ‖b − Ax‖ (HPL-12.10)
```

The cost hierarchy is stark and worth internalizing as a single table:

| Phase | FLOPs | Share at \(n = 10^5\) | Character |
|---|---|---|---|
| Forward elimination (matrix) | \(\tfrac{2}{3}n^3 + O(n^2)\) | ~100% | GEMM-izable, compute-bound when blocked |
| RHS updates + substitutions | \(\sim 3n^2\) | \(\sim 3\times10^{-5}\) | Memory-bound, latency-sensitive |

At HPL scale, the \(O(n^2)\) pieces are a rounding error on the FLOP budget — yet they still decide real outcomes. The benchmark runs one enormous factorization plus one solve and then *checks the residual*; and in HPL-MxP (module 16), when the GEMM engine is accelerated by low precision, the panel and solve phases — including these triangular sweeps — are exactly what stops shrinking, which is why the algorithmic bottleneck migrates there (HPL-16.6, HPL-20.8). Knowing *today* that substitutions are structurally memory-bound and serial-chained is the foundation for reading those later results correctly.

This also completes the arc that began at HPL-4.10: the algorithm we just built by hand is, line for line, what `GETRF`/`GETRS` compute — but wrapped in blocking that turns the rank-1 math into vendor-GEMM calls. Next volume finishes module 5 with the elimination-matrix formalism (HPL-5.5), the complete complexity analysis (HPL-5.6), and the dependency structure (HPL-5.7) — the bridge into module 6's LU factorization.

## 2. Key Developments / News

### 2.1 cuBLAS now emulates FP64 GEMM on tensor cores — the precision/speed trade-off moves inside the vendor library

**What happened.** In CUDA Toolkit 13.0 Update 2, NVIDIA's cuBLAS introduced *floating-point emulation* for matrix multiplication: FP32 matmuls can execute on BF16 tensor cores (the "BF16x9" scheme), and — the newer half — FP64 matmuls can execute on Blackwell's INT8 tensor cores, using a splitting technique from the Ozaki scheme (building on error-free-transformations work published by Ozaki et al. at IEEE ARITH 2019). An "automatic dynamic precision" (ADP) framework analyzes the inputs and selects emulation parameters intended to guarantee accuracy equal to or better than native FP64, falling back to native execution when emulation would not help.

**What technically changed.** The mechanism is operand splitting: decompose each high-precision operand into several low-precision components whose cross-products, summed, reconstruct the high-precision product. For FP32 on BF16 hardware, each FP32 operand splits into three BF16 pieces (24 mantissa bits ÷ 8 per piece), giving the nine products of BF16x9. The FP64-on-INT8 path uses a larger splitting in the same spirit. The point is architectural: on Blackwell-class GPUs, tensor-core throughput at low precision vastly exceeds the FP64 vector units, so paying several cheap low-precision products to buy one accurate high-precision product can still win overall — despite doing *more raw operations*.

**Why it matters.** Per NVIDIA's October 2025 technical blog, emulated FP64 with ADP reaches up to ~13× native FP64 GEMM speed on an RTX PRO 6000 Blackwell Server Edition (shape-dependent), with application results including ~1.5× end-to-end for Quantum ESPRESSO with default ADP (nearly 3× with a 39-mantissa-bit setting, outputs consistent to 12 significant digits), ~2.4× for matrix products in the ecTrans weather library via BF16x9 FP32 emulation, and significant ZGEMM gains in BerkeleyGW — all vendor-reported, on NVIDIA hardware, so treat the magnitudes as claims to reproduce rather than independent facts. The structural significance for this curriculum: HPL-3.10's precision-versus-speed trade-off and HPL-14's mixed-precision machinery are now being absorbed *inside the BLAS call itself* — the application asks for FP64 semantics and the library decides how to deliver them. That raises a genuinely open question worth watching: FP64 emulation is not "mixed-precision iterative refinement" (no correction solve — the split products reconstruct accuracy directly), so where it sits relative to benchmark rules that require 64-bit arithmetic (classic HPL) is a live discussion as tensor-core-to-FP64-unit ratios keep widening.

**Connection to today's topics.** Direct hit on HPL-4.10: the vendor-BLAS layer is where architecture-specific numerical strategy now lives, not just kernel tuning. It also pre-loads module 14–16: when we study HPL-MxP's low-precision factorization plus high-precision correction, contrast it with this *emulation* approach — refinement buys speed by tolerating error and correcting it; emulation buys speed by spending cheap FLOPs to avoid error in the first place.

### 2.2 OpenBLAS 0.3.34 (July 2026): thread-safety fixes land in GETRF — today's algorithm, in the wild

**What happened.** OpenBLAS 0.3.34, released 16 July 2026, fixed potential race conditions between concurrent calls to level-3 BLAS functions (inadvertent use of non-unified locks) and a separate potential race condition in **GETRF** — the LU factorization routine implementing exactly the forward elimination of §1.3–1.4. The release also added or improved multithreading thresholds in a batch of routines including **GETRS** and **LASWP** (the solve and row-interchange routines of §1.5), shipped a significantly faster SGEMM kernel for 32-bit Arm, and realigned its LAPACK contents with the upcoming Reference-LAPACK 3.13.0.

**What technically changed, and why it matters.** Two threads of substance. First, thread *safety*: OpenBLAS uses internal buffers (notably the GEMM packing buffers central to the GotoBLAS design of §1.1) that must be shared carefully when multiple application threads call BLAS simultaneously — which HPC applications absolutely do, e.g. task-based solvers, or threaded applications where each thread runs its own linear algebra. A race in GETRF means two concurrent LU factorizations can corrupt each other's scratch state: a correctness bug, not a performance bug, and precisely the class of defect that a residual check (HPL-12.10, HPL-21.8) exists to catch. Second, multithreading *thresholds* for the O(n²) routines: deciding when GETRS/LASWP work is large enough to justify spawning threads is a live instance of §1.5's lesson — substitutions are memory-bound with a serial dependency chain, so naive parallelism can easily cost more than it earns; the library encodes cutoffs below which it stays serial. Both changes are the curriculum's "system behavior" column made real: the same mathematics we wrote by hand, with its concurrency structure and cost hierarchy, shaping engineering decisions in the most widely deployed open BLAS.

**Connection to today's topics.** GETRF, GETRS, and LASWP are §1.3–1.5's algorithm under their LAPACK names; the OpenBLAS→Reference-LAPACK 3.13.0 alignment also previews how BLAS and LAPACK co-evolve as one stack. **Watch next:** whether the Reference-LAPACK 3.13.0 release itself lands further changes in the LU path, and the ongoing OpenBLAS per-architecture kernel work (the faster Arm SGEMM is the GotoBLAS-lineage story of §1.1 continuing, architecture by architecture).

### 2.3 CUDA 13.4 cycle: cuBLAS keeps re-targeting Blackwell and Rubin

The current CUDA 13.4 release notes show the vendor-BLAS treadmill of §1.1 at full speed: support added for the NVIDIA Rubin architecture (compute capability 10.7), cuBLASLt grouped-GEMM performance improvements on Blackwell — up to ~20% for large problem sizes where matrices exceed L2 cache capacity, via dynamic scheduling of matrix tiles — and the experimental grouped-GEMM API extended to MXFP8 inputs on compute capability 10.x and 11.0 GPUs. Grouped GEMM exists to amortize the launch/scheduling overhead of *many small* matrix multiplications — the same small-GEMM inefficiency we will meet formally in HPL-19.3, and visible already in today's elimination context: the per-step rank-1 updates of §1.3 are the extreme small-GEMM case that blocking exists to eliminate. One caution flag from the same release notes: grouped-GEMM operations shipped with a wrong-results bug on Blackwell/Rubin (introduced in cuBLAS 13.7.0, per NVIDIA fixed in patch 13.8.1) — a useful reminder that vendor libraries are software too, and that validating *delivered* numerics (residuals, not vendor claims) is a permanent part of the HPC engineer's job.
