## 0. Concise Summary

The previous PERF volume established *what* to count (units of work) and the two reciprocal views of a measurement (time per operation vs. operations per second). Today's five topics are the first hard wall every practical measurer hits: the fact that a raw timer reading is not yet a fact about the program. Before a number can support an optimization decision, you must know **which regime of the program's life it came from** (warm-up or steady state), **which boundary it spans** (a kernel, a phase, or the entire run), **which accounting convention produced it** (inclusive or exclusive), and **whether the act of observing and synchronizing changed what was observed**.

Warm-up effects (PERF-2.3) are the one-time costs that contaminate the first iterations of any timed region: JIT compilation, page faults and TLB misses as memory is first touched, cache population, CUDA context and module loading (lazy or eager), memory allocation, and file-system metadata caching. Steady-state measurement (PERF-2.4) is the deliberate separation of setup time from repeated compute behavior — the part of the run whose properties you actually want to characterize — and it is why HPCG's official rules require a 1800-second minimum run and a problem size of at least a quarter of memory, and why Google Benchmark supports an explicit warm-up interval whose samples are discarded. End-to-end versus kernel-only timing (PERF-2.5) is the gap between local and global truth: a kernel that got 20% faster may shorten total runtime by 0.3% because it was 1.5% of the run, hidden behind other work, or not on the critical path at all — Amdahl arithmetic, applied before you optimize rather than after. Inclusive versus exclusive time (PERF-2.6) is the call-graph accounting problem: profilers like `perf report --children` and gprof report *self* time (samples landing in the function itself) and *children/inclusive* time (self plus everything called beneath), and the two columns answer different questions — "what is hot?" vs. "what is expensive to *reach*?". Synchronization and timing (PERF-2.7) closes the loop: on an asynchronous machine, a timing is only meaningful if the timed work is guaranteed to have executed *between* the two timer reads; CUDA events inserted in a stream measure GPU-side time without stalling the pipeline, `MPI_Wtime` on the calling processor is a per-process clock with no guarantee that clocks across ranks are synchronized, and profiling itself serializes — Nsight Compute serializes kernel launches it profiles, changing the very concurrency you wanted to measure.

The developments section revisits a landmark that codifies today's entire lesson into twelve rules — Hoefler and Belli's SC'15 paper *Scientific Benchmarking of Parallel Computing Systems: Twelve Ways to Tell the Masses when Reporting Performance Results* — and then looks at two concrete current practices: the warm-up and iteration discipline built into Google Benchmark v1.9.5, and CUDA lazy module loading, which moved first-launch costs into measured windows and made warm-up non-optional in GPU benchmarking.

Why this matters: almost every wrong performance conclusion you will ever draw — or be sold — is a warm-up artifact, a scope mismatch, or an unsynchronized timer away. These five topics are the immune system.

## 1. Learn the Concepts

### 1.1 Warm-up effects: the first iteration lies (PERF-2.3)

Time the first invocation of anything and you will measure a different program than the one production runs. A *warm-up effect* is any one-time (or early-phase) cost that decays as the program repeats its work. The main families:

```text
1. Translation and loading   — JIT compilation (Java, Julia, Numba, PyTorch/TensorFlow
                               graph modes), CUDA module loading (context creation,
                               kernel image load; lazy since CUDA 12.x by default),
                               dynamic linker symbol resolution, page faults on first
                               touch of new memory (demand paging, zero-fill).
2. Cache population          — instruction cache, data cache, TLB (page-table walks),
                               GPU L2 and instruction cache. The first pass reads from
                               DRAM; later passes may hit cache.
3. Allocation and placement  — malloc growth, cudaMalloc, NUMA first-touch page
                               placement; lazy allocator pools in frameworks.
4. System caches             — file-system metadata and page cache (first read of an
                               input file touches disk; later ones may not), network
                               connections, MPI eager-buffer setup, library init.
5. Hardware state            — frequency ramping (DVFS/turbo), GPU clocks rising from
                               idle P-state, thermal state.
```

Two of these deserve mechanism-level detail because they dominate GPU benchmarking.

**Lazy module loading.** A CUDA "module" is the compiled code container for kernels; loading it means copying the kernel image into device memory and fixing up its metadata. Historically the runtime loaded all modules of a context eagerly at the first CUDA call — a large, mostly wasted startup cost when an application links big libraries but launches few kernels. Since CUDA 11.7 (opt-in) and later releases (on by default on Linux from the 12.2 timeframe), `CUDA_MODULE_LOADING=LAZY` defers loading until a kernel is first launched. The trade-off, stated in NVIDIA's own documentation, is exactly a warm-up hazard: "Lazy loading may skew performance measurements by moving CUDA module initialization into the measured execution window. To avoid this: do at least one warmup iteration prior to measurement [or] preload the benchmarked kernel." The first launch of each kernel now carries its own load cost — so a naive timing harness that starts its clock before the first launch of kernel *K* measures *K* plus a module load, while the tenth launch measures *K*.

**First-touch and demand paging.** On Linux, a freshly `malloc`ed page is not yet mapped. The first write to each 4 KiB page triggers a page fault; the kernel allocates a physical frame (zero-filled for anonymous memory), updates the page table, and only then does the store complete. On a NUMA system *the faulting core's local node claims the page* — the first-touch policy that Theme 4 will revisit in detail later. In a timed loop this means the first iteration pays one fault per page plus a TLB-miss walk per page, and every later iteration reuses warm mappings. For an array of 1 GiB that is 262,144 page faults stacked onto iteration one. The classic symptom is a first iteration 2–50× slower than the second, with a monotone decay until a floor.

The practical rule is not "always discard the first iteration." It is: **know which one-time costs are part of the thing you want to measure, and move the rest outside the timed region deliberately.** If you are characterizing a sparse solver's per-iteration cost, page faults and JIT are contamination; discard warm-up. If you are measuring an application whose production pattern is "start, run once, exit" (a batch job, a CLI tool, a cold-start inference server), first-run costs *are* the performance, and discarding them is a category error — you would then need to time from process start (see PERF-2.5).

A compact diagnostic habit: plot iteration time versus iteration index for the first few dozen iterations. Warm-up shows up as a decay curve. If the curve never flattens, you are not looking at warm-up but at a *drift* (thermal throttling, clock decay, memory fragmentation) — a steady-state problem, not a setup problem.

### 1.2 Steady-state measurement: separate setup from repeated behavior (PERF-2.4)

*Steady state* is the regime in which per-iteration cost has stopped drifting — the program is repeating its work with stable state: caches populated, memory mapped, code compiled, clocks settled. The distinction from setup is a definitional choice you must make explicit:

```text
Total wall time = setup time + N × (steady-state per-iteration time) + teardown
                  └── one-time: allocate, initialize, compile, load, connect ──┘
```

You measure steady state when the quantity you want to reason about is the *repeated* behavior — because that is what scaling, roofline, and optimization arguments are built on. You measure setup separately (or end-to-end) when the deployment pattern is one-shot.

Production benchmark suites legislate this split, and their rules are worth reading as case law:

- **HPCG** requires official runs of at least **1800 seconds** — the stated reason being that short runs measure mostly setup and transient effects rather than the sustained memory-system behavior the benchmark exists to expose; it additionally requires the problem to occupy at least a quarter of memory so that cache-friendly small runs cannot masquerade as solver performance.
- **Google Benchmark** (the C++ microbenchmark library, used across HPC and systems software) has a dedicated `--benchmark_min_warmup_time` flag, separate from `--benchmark_min_time`: warm-up samples are *discarded*, then the timed samples are collected and the iteration count is chosen adaptively so the timed region is long enough for stable statistics. The library also reports mean and standard deviation across `--benchmark_repetitions` runs — the warm-up/discard/repeat discipline as software.
- **HPL**, at the other extreme, has no warm-up phase *inside* the benchmark: the reported Time/Gflops is a single end-to-end measurement of one factorization. But experienced tuners run small-N sweeps first (the "warm-up" of the tuning process, warming page cache, MPI connections, and our knowledge of the machine), then the record run.

Three rules of thumb for your own harnesses:

1. **Decide the window by decay, not by fixed count.** Discard iterations until the running median of the last *k* iterations changes by less than your noise threshold. A fixed "skip 3 iterations" works until it doesn't.
2. **Keep the steady-state window long enough to beat timer resolution** (PERF-2.8's subject, next volume) — if one iteration is 100 ns, timing one iteration is meaningless; time 10⁶ of them and divide, or use a cycle counter.
3. **Do not warm up so hard that you measure a different machine.** Long warm-up can push a GPU into thermal throttling or a CPU off its turbo boost — in which case your "steady state" is a thermally degraded state that production (with idle gaps) never sees. Steady state on an idle, cold machine and steady state in a hot, shared cluster are different objects; report which one you measured.

Steady state also connects to warm-up's cousin, *cold vs. warm caches*: a warm-cache measurement is the right steady state for a kernel whose working set fits in cache in production; it is a flattering fiction for a streaming kernel whose every iteration in production reads fresh data. The question "steady state *of what regime*" is always implicit.

### 1.3 End-to-end versus kernel-only timing: local speedups can vanish globally (PERF-2.5)

A kernel-only timing brackets one operation — typically the GPU kernel or the innermost function — and an end-to-end timing brackets the entire workload the user cares about: process start to exit, or job submission to result file. Both are legitimate; the failure mode is **substituting one for the other in an argument**.

The arithmetic that connects them is Amdahl's (Theme 4 will formalize it later): if a region is a fraction *f* of total runtime and you speed it up by factor *s*, total time shrinks by

```text
T_new / T_old = (1 − f) + f / s        → total speedup = 1 / ((1 − f) + f/s)
```

Small example. A profiler shows the SpMV kernel at 10 s of a 400 s run (f = 2.5%). You rewrite it with a better storage format and the kernel drops to 2 s — a 5× kernel speedup, impressive in isolation. End to end: 400 → 392 s, a **1.02× total speedup**. The kernel-only number is real; the conclusion "this optimization mattered" is false. The same arithmetic kills the reverse claim: an optimization that looks small locally (10% on a kernel) but applies to 60% of runtime is worth more than a 10× kernel win on 1%.

The second reason kernel-only numbers fail to transfer is **overlap**. On a GPU timeline (Theme 4 weeks ahead: Reading GPU Timelines) a kernel may execute concurrently with copies or other kernels. Making one overlapped kernel faster shortens nothing until it becomes the last one standing — only *exposed* time (non-overlapped) contributes to the critical path. This is the kernel-level preview of PERF-14.8's "exposed time" concept: total activity and critical-path activity are different quantities, and kernel-only timing measures the former while the user experiences the latter.

A worked contrast, written as two timing scopes around the same code:

```text
Scope A — kernel only:     t(record e1) → K → t(record e2)         = 4.0 ms
Scope B — end to end:      t(host) → [alloc, H2D, K, D2H, free] → t(host) = 61 ms
```

Scope A says the kernel is 6.6% of the run. The remaining 57 ms — allocation, two transfers, and a device synchronize — is invisible to Scope A. An engineer who optimizes K by 2× spends effort on 4 ms of a 61 ms run. The Nsight Systems *timeline* view exists precisely to make this decomposition visible before you commit to optimizing the wrong thing: "start broad, then zoom in" (PERF-7.7) is the methodology this topic motivates.

When is kernel-only timing the right instrument? When you are characterizing a *component* in isolation (library QA, kernel bottleneck classification, roofline studies), provided you then report the fraction of a representative end-to-end run that the component occupies. When is end-to-end the right instrument? Whenever the claim is about *user-visible performance* — and always as the final validation of an optimization campaign (PERF-26.9: re-measure end-to-end).

One subtlety: end-to-end numbers are contaminated by everything — environment, allocator state, scheduler, filesystem. That is not a defect of the measurement; it is the definition of what the user experiences. The discipline is to report both scopes with their conditions, not to average them into one meaningless number.

### 1.4 Inclusive versus exclusive time: two columns, two different questions (PERF-2.6)

When a profiler reports time per function, it must choose an accounting convention:

```text
exclusive (self) time   = time spent executing the function's own instructions
inclusive (children)    = self + all time spent in functions it called (transitively)
```

The two answer different questions. Exclusive time answers **"where is the machine spending cycles?"** — it is what you read to find the code to optimize (an inner loop with a hot instruction sequence). Inclusive time answers **"what is expensive to reach?"** — it identifies heavy *paths* and *orchestrators*: a function whose self time is 0% but whose inclusive time is 80% is not itself slow, but everything it calls is.

The canonical example is `main`. Self time near zero; inclusive time ~100% of the run. Neither number is wrong; they are different facts. The path from `main` to the hot loop is the inclusive attribution.

Two production tools make the distinction explicit, and both are worth reading as documentation of the concept:

- **Linux `perf`.** With call chains recorded, `perf report` shows two overhead columns: **Self** ("this is the value that perf shows traditionally and sum of all the self overhead values should be 100%") and **Children** — "the children overhead is calculated by adding all period values of the child functions so that it can show the total overhead of the higher level functions even if they don't directly execute much." The perf manual also warns about the property that makes inclusive columns confusing at first: **the Children column can sum to more than 100%** across rows, because each parent re-accumulates the time of everything beneath it — the same samples are counted once in the child's row and again in every ancestor's row. That is not a bug; it is what inclusive means.
- **GNU gprof.** The flat profile lists `self seconds` and `self ms/call`; the call graph lists `self` and `children` columns per function, with the manual's own caveat about how children time is *estimated* by attributing call counts × average callee time — an assumption that can misattribute when a callee's cost varies by call site.

A small worked example (gprof-style), numbers in seconds:

```text
index %time   self  children        name
[1]   100.0   0.1    48.9           main
                0.1    48.9    1/1  → solver_driver
[2]    97.9   2.0    47.0           solver_driver
                8.0    39.0    500/500 → spmv
                6.0     0.0    500/500 → dot
[3]    16.3   8.0    39.0           spmv          ← self 8.0, children 39.0, incl. 47.0
                39.0    0.0          → gather_kernel
[4]    79.6  39.0     0.0           gather_kernel ← the actual hot loop
```

Reading exclusively, you conclude `gather_kernel` (39 s self) is the target — correct, that is where cycles burn. Reading inclusively, you also learn the *shape* of the cost: every path from `main` through `solver_driver`/`spmv` to `gather_kernel` carries it, so a structural fix (fusing gather into SpMV, eliminating the call path entirely, changing data layout so gather disappears) can remove the whole 39 s — a redesign the exclusive view alone would not suggest. Conversely, if `spmv`'s 39 s of children were spread over 500 calls, the inclusive view tells you the per-call path is cheap and only the *aggregate* matters.

GPU tools face the same choice. Nsight Systems' timeline is inclusive by construction (you see every kernel and its nesting in time); Nsight Compute profiles one kernel launch at a time and reports its *own* metrics — an exclusive view. The complementarity is deliberate: use Nsight Systems to find *which* kernel (inclusive reasoning over the whole run), then Nsight Compute to dissect it (exclusive reasoning over one kernel).

The discipline this topic teaches: **when someone reports "function X takes T seconds," ask which convention — self or inclusive — before believing any conclusion drawn from it.** A vendor slide saying "our library call is 30% of runtime" can mean self (the library's own code is the bottleneck) or inclusive (everything it calls — possibly *your* callbacks — is), and the two imply opposite fixes.

### 1.5 Synchronization and timing: asynchrony makes naive timing meaningless (PERF-2.7)

The final topic is the one that makes GPU and distributed timing categorically harder than CPU timing: **on an asynchronous machine, a timer read is only a fact about the work you timed if the work is guaranteed to have executed between the two reads.**

**The GPU case.** A kernel launch is asynchronous: `kernel<<<...>>>()` returns immediately; the kernel executes later, on the device. Host-side timing around a launch therefore measures *launch overhead*, not execution:

```text
t0 = now();  K<<<...>>>();  t1 = now();        // measures launch API cost (~µs), NOT K
```

The fix is to make the host wait before reading the second timestamp — `cudaDeviceSynchronize()` (or a stream/event sync) between the launches and the second timer read. The NVIDIA blog on CUDA performance metrics puts it plainly: without the barrier "this code would measure the kernel launch time and not the kernel execution time."

But host-synchronized timing has its own cost: it stalls the pipeline, and — worse for benchmarking — the *synchronization itself* perturbs the measurement (more in PERF-2.8, and PERF-7.5's tracing overhead). The refined instrument is the **CUDA event**: `cudaEventRecord(start, stream)` and `cudaEventRecord(stop, stream)` insert GPU-side timestamps into the stream; `cudaEventElapsedTime` reports the wall time between them with ~0.5 µs resolution, using the GPU's own clock, without forcing the CPU to block inside the measured region. Because events are recorded *in stream order*, the pair brackets exactly the operations enqueued between them — an elegant solution to the asynchrony problem, with its own documented caveats:

1. **Cross-stream contamination.** The CUDA Runtime API documentation itself warns that if either event was recorded in a non-NULL stream, "the resulting time may be greater than expected... Any number of other different stream operations could execute in between the two measured events, thus altering the timing in a significant way." Event pairs bracket a *stream interval*, not a *kernel*; if other streams' kernels interleave, you measure them too.
2. **Empty-stream semantics.** `cudaEventRecord(e, 0)` on the default (blocking) stream interacts with stream-ordering rules — another way the "same" measurement changes meaning with context.
3. **Sync placement changes the program.** Adding `cudaDeviceSynchronize()` per iteration serializes launches that were previously pipelined; you measure a *different execution schedule* than production. `CUDA_LAUNCH_BLOCKING=1` (the debug mode that syncs after every launch) makes "applications run substantially slower" per the CUDA Programming Guide — useful for locating errors, catastrophic as a benchmarking environment.

The general principle: **synchronization is both a correctness requirement for timing and a perturbation of the thing timed.** Every serious harness resolves the tension the same way — synchronize *outside* the measured window (or use device-side timestamps), keep the timed region free of host round-trips, and be explicit about what stream(s) the timed interval covers.

**The distributed case.** `MPI_Wtime()` returns "an elapsed time on the calling processor" — a per-process clock; the MPI standard's attribute `MPI_WTIME_IS_GLOBAL` exists precisely because *clocks across ranks are not guaranteed to be synchronized*. Two consequences:

- A duration measured as `MPI_Wtime() difference on one rank` is safe (same clock, monotone within a rank, modulo OS interference).
- A difference *across* ranks (rank A's start vs. rank B's stop) is only meaningful if clocks are synchronized (hardware clock sync, or measured skew correction) — otherwise you have added an unknown inter-rank offset to your measurement.
- Even with perfect clocks, comparing timestamps across ranks answers "who finished first" only if the events are causally ordered — a barrier or handshake must establish that A's end precedes B's start before you can subtract their times.

This is why timeline tools for MPI applications (e.g. Extrae/Vampir, Nsight Systems with NVTX + MPI interception) log per-rank traces with local clocks and do skew correction in post-processing rather than trusting raw cross-rank subtraction. It is also the seed of PERF-10.7 (rank-to-rank timeline comparison) and PERF-18 (load imbalance): waiting at a barrier is *real* time that a naive per-rank sum will misattribute.

**The multi-rank amplification.** Synchronization costs are not additive — they amplify. A single rank delayed by a small OS "detour" (an interrupt, a page fault) can hold up every other rank at the next collective. Beckman et al.'s classic OS-noise studies measured this on Blue Gene/L: injecting periodic detours into a noiseless system showed collectives (barrier, allreduce, alltoall) are the operations most sensitive to desynchronization — small periodic noise on few nodes can stall large machines, one reason why TOP500-class systems run lightweight kernels or dedicate a core to OS work (core specialization). For timing methodology, the lesson is: per-rank timing of a synchronized program largely measures *who waited for whom*, not local compute speed — the subject of Theme 4's load-balance modules.

### 1.6 How the five topics interlock

The topics are one workflow, not five facts:

```text
        ┌── warm-up (2.3): decide what counts as setup ──┐
        │                                                 ▼
   timed region ──► steady state (2.4): stable repeated behavior
        │                                                 │
        │        ┌── scope (2.5): kernel-only vs end-to-end ──┐
        │        │                                            │
        ▼        ▼                                            ▼
   accounting (2.6): self vs inclusive        asynchrony (2.7): sync before reading
        │                                                    │
        └────────────────► the number finally means something ◄┘
```

A measurement is trustworthy only after all five questions are answered: *Was it warmed up? Is it steady-state? At which scope? Under which accounting? Synchronized how?* The twelve-rules paper in Section 2.1 is, at heart, this checklist applied to published benchmark claims.

## 2. Key Developments / News

### 2.1 The benchmarking methodology canon: Hoefler & Belli's twelve rules (SC'15)

**What happened.** At SC 2015, Torsten Hoefler and Roberto Belli published *Scientific Benchmarking of Parallel Computing Systems: Twelve Ways to Tell the Masses when Reporting Performance Results* (DOI: 10.1145/2807591.2807644) — a peer-reviewed methodology paper that treats performance reporting as a scientific measurement practice, in the direct lineage of Bailey's 1991 "Twelve Ways to Fool the Masses."

**What it actually says (technically).** The paper's rules are the publishable versions of today's curriculum topics. Several map one-to-one onto this volume: report the *environment* (hardware, software, clock state — warm-up and steady-state context); prefer *timings over ratios* and never summarize ratios alone ("Rule 34/42": avoid summarizing ratios — summarize the underlying costs, because averaging speedups hides bimodal behavior); use the *arithmetic mean for costs* and the *harmonic mean for rates* (the cost/rate duality of PERF-2.2, made statistical); report *variability* (multiple repetitions, in tomorrow's volume PERF-3.x); and report *end-to-end or clearly scoped* measurements rather than cherry-picked inner loops — the kernel-only vs. end-to-end trap of PERF-2.5. The paper also prescribes stating whether a parallel speedup baseline is one process or best serial run — an inclusive-vs-exclusive-style ambiguity in how a number was produced.

**Why it matters.** It is the rare methodology paper that became operational: these rules are cited in benchmarking policies, review checklists, and the reporting practices of MLPerf and vendor benchmark disclosures. For a learner, it converts "be careful" into a checklist you can apply to any performance claim — including your own.

**Connection to today's topics.** Rules about ratios, means, repetitions, and scoping are precisely PERF-2.3–2.7 generalized: warm-up/steady-state discipline is *when* to measure, scoping and accounting are *what* to measure, synchronization is *how* to measure without corrupting the result.

**What to watch next.** The paper's arXiv version (arXiv:1507.00652) is freely readable; the same authors' later "twelve ways to fool the masses with deep learning" follow-ups extend the checklist to ML benchmarks, where warm-up (JIT, autotuning caches) and measurement-scope tricks are endemic.

### 2.2 Google Benchmark v1.9.x: warm-up discipline as library API (Jan 2025 – Jan 2026)

**What happened.** Google's C++ microbenchmark library `google/benchmark` — the de-facto standard for C/C++ microbenchmarks in HPC-adjacent software (LLVM, Abseil, many vendor libraries) — shipped a series of releases through 2025, v1.9.5 landing January 22, 2026 (per the GitHub release history and Bazel Central Registry).

**What technically changed / is demonstrated.** The library embodies steady-state methodology as API surface: `--benchmark_min_warmup_time` (warm-up iterations discarded before timing), adaptive iteration-count selection until the timed region exceeds `--benchmark_min_time` (so short kernels are repeated enough to beat timer resolution), `--benchmark_repetitions` with automatic mean/σ reporting, and `--benchmark_report_aggregates_only`. Recent releases (1.9.x) were mainly robustness and packaging work — Python bindings fixes, MSVC deprecation warnings, pkg-config generation, CI modernization — i.e., the methodology features are stable and the library is in maintenance mode; there is no new timing semantics to learn from the changelog itself.

**Why it matters.** It is the most widely deployed implementation of the warm-up/steady-state contract: thousands of projects inherit correct measurement discipline by default (warm-up discarded, adaptive repetition, per-run variance reported) rather than reimplementing naive loops. When a benchmark result comes from this library, the reader knows which methodology questions were already answered.

**Connection to today's topics.** PERF-2.3/2.4 are its design center; the adaptive iteration logic is the practical resolution of the timer-resolution problem PERF-2.8 will cover next.

**What to watch next.** The v2 branch carries experimental features (registering benchmarks, stricter statistical reporting); if you benchmark C++ seriously, reading its user guide's "Timing and Repetition Control" section end-to-end is 20 minutes well spent.

### 2.3 CUDA lazy module loading: when the vendor moved warm-up costs into your timed window (2022–2023, still current)

**What happened.** NVIDIA introduced lazy loading of CUDA modules (kernel code containers) as an opt-in in CUDA 11.7/11.8 and made it the default behavior in the 12.x series (on Linux, from 12.2 by default; the CUDA Programming Guide now states lazy loading is enabled by default on all platforms as of CUDA 12.3+, controllable via `CUDA_MODULE_LOADING`).

**What technically changed.** Before, module loading happened eagerly at context initialization — a large up-front cost, amortized across all kernels whether used or not. Now each kernel's module loads on first launch. Startup time and context memory footprint drop substantially for library-heavy applications (the 11.8 release blog quantified the win); the cost moves to the *first launch of each kernel*.

**Why it matters.** This is a vendor-level redesign of *where warm-up costs live*, and NVIDIA's documentation explicitly warns of the measurement consequence: lazy loading "may skew performance measurements by moving CUDA module initialization into the measured execution window," with the recommended mitigations being — verbatim — "do at least one warmup iteration prior to measurement" or "preload the benchmarked kernel prior to launching it." A change in runtime defaults silently changed the meaning of naive timing harnesses worldwide: harnesses that once measured only kernel execution now measure execution plus a one-time module load, and the skew lands on whichever kernel happens to be first in the sweep.

**Connection to today's topics.** PERF-2.3 (a warm-up effect created by default), PERF-2.4 (why warm-up must be deliberate, not assumed), and PERF-2.7 (the load can even require a device-wide synchronization on first launch, interacting with concurrency assumptions).

**What to watch/understand next.** If you benchmark GPUs: pin `CUDA_MODULE_LOADING` explicitly in your harness, or preload all kernels (e.g., via `cudaFuncGetAttributes`) before timing; if you benchmark MPI+GPU codes, remember both ends now have lazy initialization costs (MPI dynamic linking, CUDA modules) that only a deliberate warm-up phase removes.

### Further Reading

- **Hoefler & Belli SC'15 paper (arXiv:1507.00652)** — the full twelve rules with examples; the single best deep-dive companion to this volume. *Research paper — 60–90 min deep dive.*
- **Google Benchmark User Guide, "Timing and Repetition Control"** — warm-up, adaptive iterations, repetitions, aggregate reporting as implemented API; read it next to your own harness. *Technical documentation — 20 min.*
- **CUDA Programming Guide §2.5 (Asynchronous Execution) + §4.7 (Lazy Loading)** — the two sections that govern GPU timing validity; skim §2.5.3.3 (timing operations in streams) closely. *Technical documentation — 30 min.*
- **perf-report(1) man page, "Overhead calculation" section** — the definitive short reference on Self vs. Children accounting. *Technical documentation — 10 min.*
- **Paoloni, *How to Benchmark Code Execution Times on Intel IA-32 and IA-64* (Intel white paper, 2010)** — cycle-counter measurement methodology (RDTSC/RDTSCP serialization), the classical treatment of PERF-2.8's subject; read as a preview. *Whitepaper — 45 min.*
