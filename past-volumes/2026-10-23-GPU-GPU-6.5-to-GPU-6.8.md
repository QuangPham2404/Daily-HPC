## 0. Concise Summary

The last GPU day (October 5) ended inside the host: cores, caches, memory controllers, NUMA. Today we cross the boundary that separates that host world from the devices it serves — the PCI Express fabric — and then follow one data transfer all the way down to the hardware that executes it.

We start with **PCIe root complexes and system topology** (GPU-6.5): PCIe is not a bus but a *tree* rooted in each CPU socket's uncore, and the shape of that tree — which GPU, NIC, or NVMe drive hangs off which root port, with or without a switch in between — is a physical locality map that software can consult and must respect. We then make that map actionable (**GPU-6.6**): an MPI rank, its GPU, its staging buffers, and its NIC form a locality group, and misplacing any member costs latency and bandwidth on every message. Next comes the piece the OS hides from you (**GPU-6.7**): host memory is not one thing. Pageable `malloc` memory can be moved by the OS at any instant, so DMA engines cannot touch it — pinned (page-locked) memory is the contract that makes a physical address stable long enough for hardware to transfer data, at the price of making that memory unswappable and expensive to pin. Finally (**GPU-6.8**) we look at how bytes actually move: descriptor rings, DMA engines, and the interrupt machinery (INTx → MSI → MSI-X) by which a device reports completion — the mechanism underneath every `cudaMemcpyAsync`, every RDMA transfer, and every GPUDirect Storage read.

The through-line of the day: **the CPU programs, the devices move the data.** A modern HPC node is a small federation of DMA engines (GPU copy engines, NICs, NVMe controllers) that the CPU orchestrates through descriptors, pinned memory windows, and completion interrupts — and every one of those mechanisms is constrained by where it sits in the PCIe tree.

Two developments connect this directly to the current industry moment. Astera Labs' **Orion** rack architecture (October 2026) promotes the PCIe Gen 6 switch fabric to the organizing principle of an entire rack — up to 160 accelerators pooled on 320-lane Scorpio X-Series switches with CXL memory trays — a validation of today's topology-first worldview at rack scale. And Microchip's **Switchtec Gen 6** switches (the first 3 nm Gen 6 parts, sampling since October 2025) show what the Gen 6 transition does to the fan-out layer: PAM4 signaling, FLIT encoding with FEC, and signal-integrity constraints that make the humble PCIe switch a leading-edge silicon problem.

## 1. Learn the Concepts

### 1.1 The PCIe tree of a server: root complexes, root ports, switches (GPU-6.5)

**Why a tree, not a bus.** The original PCI was a shared bus: every device saw every transaction, and arbitration decided who spoke next. PCI Express replaced it with a *point-to-point, switched fabric*. A **root complex (RC)** — physically inside the CPU package, in the same uncore/IOD as the memory controllers — originates one PCIe tree. It exposes **root ports**, each a link that can go directly to an **endpoint** (a GPU, NIC, or NVMe controller) or to a **PCIe switch**, which fans one upstream link out into multiple downstream links. Devices are addressed by **BDF** (bus:device:function), and the chain of bus numbers from root port to device encodes the physical path a transaction must take. When you run `lspci -PP` or `lspci -t`, you are reading this tree: for example, AMD's Instinct cluster documentation shows an MI300X whose full path (`00:01.1/01:00.0/02:00.0/03:00.0/04:00.0/05:00.0`) reveals it sits behind a root port, a switch, and a retimer/bridge chain — and shows the adjacent NIC sharing the same early hops.

**The fan-out problem.** An 8-GPU node needs 8 × 16 = 128 lanes just for the GPUs, plus NICs and NVMe. A server CPU provides on the order of 80–128 lanes per socket (AMD's SP5 parts: 128 Gen 5 lanes; NVIDIA's new Vera CPU: 88 Gen 6 lanes, 96 in Vera Rubin systems). Three canonical arrangements cover nearly every real server, and each is a different compromise:

```text
Direct attach (no switch)              Switch-based (dual root)
socket 0                socket 1       socket 0                socket 1
┌──────────────┐  UPI/  ┌────────────┐ ┌──────────────┐  UPI/  ┌────────────┐
│ cores  DRAM  │  xGMI  │ cores DRAM │ │ cores  DRAM  │  xGMI  │ cores DRAM │
│ root ports   │◄──────►│ root ports │ │ root ports   │◄──────►│ root ports │
└─┬───┬───┬───┬┘        └─┬──┬───┬──┬┘ └──┬────────┬──┘        └──┬──────┬──┘
 x16  x16 x16 x16        x16 x16 x16 x16   x16       x16           x16     x16
  │   │   │   │          │  │   │   │      │        │             │       │
GPU0 GPU1 GPU2 NIC     GPU3 GPU4 GPU5 NIC ┌┴──SW0──┐┌┴──SW1──┐  ┌┴──SW2──┐┌┴──SW3──┐
                                         GPU0 GPU1 GPU2 GPU3  GPU4 GPU5 GPU6 GPU7
                                         (+NIC, NVMe behind switches)
```

- **Direct attach**: each GPU hangs on its own root port. Lowest latency (no middleman), and each GPU has a non-shared path to host memory — but every GPU-GPU transfer between GPUs on *different* root ports must be routed through the root complex, and cross-socket pairs additionally cross the inter-socket fabric. Supermicro's and Exxact's server guides both describe this as the classic HPC arrangement.
- **Switch-based**: GPUs sit behind a switch. Two GPUs under the *same* switch can DMA to each other through the switch alone — full x16 bandwidth each, simultaneously, without touching the host — while the (typically x16) uplink to the CPU is shared when several GPUs stream to or from host memory at once. A switch hop adds latency on the order of 100 ns (practitioner-measured figures for Gen 4/5 parts), cheap for bulk transfers, less so for small latency-critical ones.
- **Single root**: all GPUs behind switches hanging off one socket (even in a 2-socket box), trading balanced CPU resources for a single, uniform PCIe domain.

**Peer-to-peer and the root-complex boundary.** A PCIe transaction (a **TLP**) is routed hop by hop: a switch can forward it directly to the target downstream port if the destination is local, otherwise it goes upstream toward the root complex, which routes it across to another tree or through the inter-socket link. This is why **P2P locality classes** exist at all: same-switch peers take the fast path; different-tree peers on the same socket traverse the RC; peers across sockets traverse the socket link (UPI/xGMI) — and on some multi-root-complex sockets (Intel has shipped multiple RCs within one package since Skylake), even single-socket peers can be effectively separated. One further trap: **ACS (Access Control Services)**, an isolation capability used heavily in virtualization, can force peer traffic upstream through the root complex instead of letting the switch forward it directly — practitioners on switch-based machines report needing to disable ACS to recover full same-switch P2P bandwidth. The lesson is not "disable ACS" but that *the fast path is a configuration*, not a guarantee.

**Reading it in practice.** NVIDIA exposes the answer in one command: `nvidia-smi topo -m` prints the affinity matrix between GPUs, NICs, and CPU/NUMA domains:

| Code | Meaning |
|---|---|
| `NV#` | connected by # bonded NVLinks |
| `PIX` | traversing a single PCIe switch |
| `PXB` | traversing multiple PCIe switches (no host bridge) |
| `PHB` | traversing the PCIe host bridge (CPU root complex) |
| `NODE` | same NUMA node, different host bridges |
| `SYS` | traversing the inter-socket fabric (UPI/xGMI) |

The ordering `PIX → PXB → PHB/NODE → SYS` is, roughly, an ordering of latency and available bandwidth for device-to-device traffic. Treat this matrix the way you treated `numactl -H` last module: the first artifact to collect on any machine before writing a line of placement-sensitive code. (NVLink-dominated systems move most GPU-GPU traffic off PCIe entirely, which is why an `NV12`-rich matrix is the goal state for dense training nodes — that scale-up fabric is Module 8's subject.)

### 1.2 Locality as a first-class constraint: cores, NUMA nodes, GPUs, NICs (GPU-6.6)

**The distance matrix.** Combine the last module's NUMA map with today's PCIe tree and an HPC node becomes a matrix of physical distances, each with a cost:

| From → To | Path | Rough penalty |
|---|---|---|
| core → local DRAM | IMC | baseline (~100 ns) |
| core → remote socket DRAM | UPI/xGMI + remote IMC | +40–100% latency, less bandwidth |
| core → GPU on same socket | root port, x16 | PCIe latency + link bandwidth |
| core → GPU on other socket | socket link + root port | both penalties stack |
| GPU → NIC, same tree | switch or RC | P2P-capable (fast path) |
| GPU → NIC, other socket | SYS path | staging through host, higher latency |

Nothing here is new physics — it is sections 1.1 and last module's NUMA composed into one table. What is new is the *unit of placement*: in a GPU node, the object you place is not a thread but a **locality group**: one MPI rank (its pinned cores), its GPU, its host staging buffers, and its network interface.

**Why each member matters.**

- **Rank ↔ GPU.** A rank driving a GPU on the other socket pays the socket crossing on every launch, every staging buffer touch, and every synchronization read of GPU state — the 10–30% tax flagged last module, now with the mechanism named: the root port the GPU sits behind belongs to the *other* socket's root complex.
- **Buffers ↔ NUMA node.** Pinned staging buffers (next section) are physical memory: they live on one socket's controllers forever, chosen at allocation/first touch. Pin them on the GPU's socket. NVIDIA engineers explicitly recommend `numactl`-style CPU/memory affinity so each GPU communicates with its nearest core complex and its memory — the fewer inter-socket hops per transfer, the lower the latency and the less the socket link is contended.
- **NIC ↔ GPU.** The NIC is itself a PCIe endpoint on one socket. For GPUDirect RDMA (device-to-device DMA between NIC and GPU, Theme 2's upcoming module), the classical requirement is that GPU and NIC share a root complex — Microway's long-standing guidance — with cross-root-complex configurations degrading to host-relayed paths. AMD's cluster acceptance documentation is the most explicit industrial statement of the rule: map each GPU to its *nearest* NIC, on the same NUMA node and root complex, and even rename interfaces (`ai0` next to GPU 0) so the mapping survives into job scripts.

**Making the scheduler aware.** On a cluster this becomes a *scheduling* problem, not just a per-process one. Slurm's topology plugin (`topology.conf`, typically `topology/tree`) lets you describe the switch-level structure of the fabric so that multi-node jobs land on network-adjacent nodes; within a node, `--gpus_per_node`, GRES, and explicit `--cpu_bind`/`--mem_bind` (or hwloc-based binding files) express the locality group. The tools that feed all of this: `lstopo` (hwloc's graphical topology dump — the single best bird's-eye view of a node), `lspci -PP`/`lspci -t` (the PCIe tree), `nvidia-smi topo -m` (the affinity matrix), `numactl -H` (NUMA distances). Reading a machine with these four commands before benchmarking on it is the professional habit this module exists to build.

**The HPL connection, concretely.** In a distributed LU factorization, the panel broadcast streams a column block from one rank's memory to all others. If the source rank's panel buffer was first-touched on the wrong socket, or its NIC is `SYS` from its GPU, the broadcast — already a communication phase with little compute to hide behind — runs measurably slower than the machine's wiring allows, for the entire run. Multiply by every communication phase in the benchmark. This is why topology-aware binding shows up as whole-percent HPL deltas on multi-socket GPU nodes, and why you should treat "which path did these bytes take?" as the first diagnostic question of Theme 2's curriculum.

### 1.3 Host memory from a device's point of view: pageable and pinned (GPU-6.7)

**What the OS does behind `malloc`.** An address returned by `malloc` is virtual. The OS backs it with 4 KiB physical pages, mapped through page tables, and it retains the right to *change that mapping at any time*: pages can be evicted to swap, migrated between NUMA nodes, or re-mapped as copy-on-write after a `fork`. This malleability is the feature that makes virtual memory work — and it is *incompatible with DMA*. A device's DMA engine operates on **physical addresses** it was programmed with; it knows nothing of page tables. If the OS moves a page while a transfer is in flight, the DMA lands in whatever now occupies that physical frame — silent corruption. The CUDA Handbook puts the mechanism exactly: the VMM's **page-locking** service marks pages ineligible for eviction so their physical address cannot change; drivers can then program DMA hardware with those physical addresses.

So host memory, from a device's perspective, comes in exactly two kinds:

- **Pageable** — ordinary `malloc`/`new`/stack memory. Movable, swappable, abundant, cheap to allocate. Invisible to DMA.
- **Pinned (page-locked)** — memory that has been locked down: `cudaMallocHost()` / `cudaHostAlloc()` allocate it directly; `cudaHostRegister()` page-locks an *existing* range (essential when a third-party library owns the buffer). Physical addresses stable, DMA-able, async-transfer-capable — but unswappable and costly to create.

**What a pageable transfer actually does.** The CUDA driver cannot DMA from your `malloc` buffer, so for a pageable `cudaMemcpy` it silently inserts a stage: the driver allocates an internal pinned buffer (a few MB), the *CPU* copies your data into it, the DMA engine transfers from there, and for large transfers the process repeats chunk by chunk. The consequences are exactly what you would predict from the diagram:

```text
pageable path:                                pinned path:
app buffer (malloc)                           app buffer (cudaMallocHost)
   │ ① CPU memcpy                              │
   ▼                                           ▼
driver's pinned staging buffer  ──② DMA──►  DMA ──► device memory
   │                                           (one traversal, no extra copy)
   └─② DMA ──► device memory
```

1. **An extra CPU-executed copy** — the host burns cycles and DRAM bandwidth producing no useful work (the data crosses host DRAM twice on the sender alone).
2. **Higher latency**, most visible on small and medium transfers.
3. **Chunking** for large transfers, at the mercy of the driver's staging-buffer size.
4. **No true async.** `cudaMemcpyAsync` on pageable memory generally cannot proceed without the host — the driver must copy *now* — so the call degrades to synchronous behavior (small transfers are the documented exception in practice). Overlap patterns built on pageable buffers simply do not overlap.

NVIDIA's classic transfer-optimization post measured this on 2012-era hardware: pageable ~2.3 GB/s versus pinned ~5.8 GB/s on the same PCIe Gen 2 link — a 2.5× gap from staging alone. On modern machines the raw numbers are far higher and the gap narrower, but the *structure* of the penalty is unchanged; a community-measured modern example (RTX 4090) found a serialized pageable pipeline at 175 ms versus 99 ms for an overlapped pinned one — 1.76× end-to-end for what is essentially the same bytes and the same link.

**What pinning costs.** Nothing in the OS is free:

- **Allocation latency.** Pinning is page-granular bookkeeping — a 1 GiB buffer is ~262,000 individual 4 KiB pages, each of which must be located, locked, and mapped for the device. `cudaMallocHost` of large buffers is dramatically slower than `malloc`, which is why high-performance codes allocate a **pinned pool once** and rotate buffers through it (the standard double- or triple-buffering ring: fill slot *k* while DMA drains slot *k−1*).
- **Unswappable memory.** Pinned pages are exactly the pages the OS cannot use to relieve memory pressure. Over-pin a node and everything else on it degrades — NVIDIA's guidance is blunt: don't over-allocate pinned memory; test to find how much your application actually needs.
- **NUMA permanence.** A pinned page stays on the socket where it was first touched — forever. Pinning from the wrong node (section 1.2) bakes the mistake in.
- **A special case: write-combined pinned memory** (`cudaHostAllocWriteCombined`) trades away CPU read speed (the memory is uncached for the CPU) for faster host-to-device writes — useful for one-way producer buffers, pathological if the host ever reads them back.

**The continuity note.** Two weeks ago (DIST-6.1, October 13) you met pageable-versus-pinned as *the first law of GPU communication*: NICs, like copy engines, can only touch pinned memory, and a pageable staging buffer silently re-introduces the copy you were trying to delete. Last week (DIST-6.5/6.6, October 20) you met the *registration cache* — the trick that makes pinning's cost amortizable by keeping regions locked across messages. Today's addition is the OS-level *why*: pinning is not a CUDA ritual, it is the `mlock`-class service a virtual-memory kernel must expose for *any* DMA device — GPU, NIC, NVMe, or capture card — and every DMA-capable API you will ever use (CUDA, InfiniBand verbs, `io_uring`, DPDK) is built on the same contract.

### 1.4 Moving bytes without the CPU: DMA, descriptors, and interrupts (GPU-6.8)

**The alternative is intolerable.** A CPU could move data by programmed I/O — `mov` instructions writing each word into device registers (how `outsb`-style transfers and some early engines worked). At 128-byte-per-cycle-class store throughput contending with real work, a CPU pushing 64 GB/s across PCIe would be doing almost nothing else. **Direct Memory Access** exists so it doesn't have to: a DMA engine is a small state machine, on the device, that is a *bus master* — it issues PCIe read/write transactions on its own behalf. The CPU's job shrinks to *describing* the work and *learning* when it is done. That division — program, then reap — is the whole section.

**Descriptor rings: how devices receive instructions.** The universal pattern (NICs, NVMe controllers, GPU copy engines, DMA engines generally) is a ring of **descriptors** in *host memory*, cooperatively managed:

```text
host DRAM
┌────┬────┬────┬────┬────┬────┐   each descriptor: {src addr, dst addr,
│ D0 │ D1 │ D2 │ D3 │ D4 │ …  │   length, flags, status}
└────┴────┴────┴────┴────┴────┘
   ▲ driver writes descriptors here
   │                        ▲ device fetches them as bus master,
doorbell MMIO write ────────┘ executes the transfer, writes status back
("ring doorbell": 4–8 byte write that says "N new descriptors ready")
```

The driver fills free slots with *physical* addresses (via the pinned-and-mapped windows of section 1.3 — the two topics are one mechanism), then writes a tiny **doorbell** register on the device. The device fetches descriptors over PCIe, moves the data, and marks completion in the descriptor's status field. Note what is *absent*: no CPU involvement per byte, no interrupts per descriptor. Thousands of transfers can flow per doorbell. GPUDirect Storage's design documents describe exactly this shape at the filesystem layer — the file system breaks a contiguous GPU virtual range into a **scatter-gather list** of physical pages that is handed to the storage device's DMA engine.

**Cache coherence — the quiet luxury.** On modern x86 and Arm servers, DMA is *cache-coherent*: PCIe transactions snoop the CPU caches, so a DMA write is visible to subsequent CPU reads without explicit flushing. This is a property of the interconnect and memory system, not of PCIe itself — some embedded/SoC systems are non-coherent and require explicit cache maintenance around DMA. HPC server programmers live on the coherent side, but should know the border exists, because it explains why "just DMA it" is not a universal primitive on every platform (a fact that recurs when we reach coherent CPU-GPU systems, Module 9).

**Completion: from shared wires to per-queue vectors.** How does the device tell the CPU "done" or "packet received"? The history is a study in removing bottlenecks:

1. **Legacy INTx**: a physical (or virtualized) interrupt line, level-triggered, one per function, *shared* among devices. The OS must query every sharing device to find the source; shared handlers can't use fast acknowledgments. 
2. **MSI (Message Signaled Interrupts)**: the device signals by performing a *memory write* to a special address, whose data selects a vector. No shared lines. Crucially, per the Linux kernel's MSI guide, the interrupt write cannot pass the device's preceding data writes — by the time the interrupt is raised, the data has landed in memory, so the handler needs no device-register readback to order things.
3. **MSI-X**: extends MSI with a per-vector table (up to 2048 vectors) and per-vector masking. Now *each queue, each engine, each event source* gets its own vector — which means each can be steered, via IRQ affinity, to a *specific core*, ideally on the NUMA node that owns the device. Interrupt locality is section 1.2's placement problem recurring one layer down: the completion handler for GPU *k*'s or NIC *j*'s traffic should run on the cores of the socket the device hangs off.

**Interrupt versus polling.** An interrupt costs microseconds and disturbs the core it lands on (context switch, cache pollution). At high packet/transfer rates, per-event interrupts become their own bottleneck — the standard answer (Linux NAPI on NICs) is *hybrid*: interrupt to notice activity, then switch to polling while the queue is busy, re-arming interrupts when it drains. CUDA exposes the same trade to the application: a host thread waiting on an event can **spin** (busy-poll — lowest latency, burns a core), **yield**, or **block** (`cudaDeviceScheduleBlockingSync` — a true wait, adds wakeup latency). Latency-critical tight loops spin; well-behaved shared nodes block. There is no free option, only a choice of where to pay.

**The GPU instantiation: copy engines.** All of this lands in the hardware you have already met. A GPU's **copy engines (CEs)** — the asynchronous engines of GPU-5.7 — are DMA engines with their own queues. `cudaMemcpyAsync` on a stream enqueues a descriptor; a CE, not an SM and not the CPU, executes it; the stream's ordering couples it to kernel launches so that transfers and compute overlap. The same engines service peer-to-peer copies through the switch fabric of section 1.1. And **GPUDirect Storage** composes everything from today into one path: an NVMe device's DMA engine writes *directly into GPU memory* through the PCIe tree (no host bounce buffer — the data may pass the root complex physically, but no host DRAM copy occurs), with `cuFile` stream APIs ordering I/O against kernel execution, and the filesystem's control-path code (still on the CPU) building the scatter-gather list. That is the thesis of the day in a single feature: **the CPU programs; the devices move the data; the completion comes back as an interrupt on the right core.**

**Tying the module together.** Follow one 1 GiB host-to-device transfer end to end: the app calls `cudaMemcpyAsync` on a pinned buffer first-touched on socket 0 (6.7, 6.2); the driver builds a descriptor with the buffer's physical pages (6.7) and rings a copy-engine doorbell (6.8); the CE issues PCIe reads that enter the tree at the GPU's root port — same socket as the buffer, because the rank was bound that way (6.6, 6.5); data flows without CPU intervention; completion is written back and surfaces as a CUDA event (6.8). Four topics, one mechanism. Module 7 pushes across this boundary for good: the discrete CPU-GPU memory model, PCIe's protocol details, and every trick (zero-copy, unified memory) for hiding the boundary it draws.

## 2. Key Developments / News

### 2.1 Astera Labs' Orion: the PCIe Gen 6 fabric becomes the product (October 2026)

**What happened.** At OCP Global Summit 2026, Astera Labs announced **Orion**, a compute-agnostic, rack-scale reference architecture for AI inference. It comprises six production-ready reference designs — compute tray (Orion-CT), fabric tray (FT), memory tray (MT), fabric board (FB), link board (LB), and the rack — validated as a system and managed by COSMOS Rack Manager and Fabric Manager software. Systems will be built and sold through ODM/OEM partners (Accton and Hyve validated at announcement), with availability starting Q1 2027.

**What technically changed.** The organizing element of Orion is not a CPU or a GPU: it is a **320-lane PCIe Gen 6 switch fabric** built on Astera's Scorpio X-Series, scaling pods from 8 to 160 accelerators of the buyer's choosing. Around it: Aries retimers on the link boards (Gen 6 signal conditioning for the long PCB and cable runs), and **Leo CXL controllers in the memory tray** — fabric-attached pooled memory aimed squarely at KV-cache capacity in long-context inference. In other words, the rack is architected as a PCIe fabric with compute plugged into it, rather than compute with a fabric inside it.

**Why it matters.** This is today's curriculum at rack scale. (1) It is GPU-6.5 generalized: the switch/fabric layer — fan-out, P2P routing, uplink sharing — is promoted to the *primary* design decision, exactly the layering section 1.1 described at node scale. (2) The memory tray is a new answer to GPU-6.7's question "what kinds of host memory exist?": CXL-attached, fabric-pooled memory is neither local DRAM nor device memory, but a third, latency- and bandwidth-intermediate tier — and CXL 3.1 appears in Vera-class hosts' PCIe stacks this generation. (3) The competitive context makes it interesting: NVIDIA contributed the Vera Rubin NVL144 MGX rack spec to OCP while keeping NVLink as its scale-up fabric, and AMD built Helios on OCP's Open Rack Wide; Orion is the merchant-silicon counter-proposal — the fabric as an open product, the accelerator as a commodity slot. Astera says PCIe 6 products (Scorpio switches and Aries retimers) crossed half its revenue in mid-2026 — a company-reported figure, but an indication of how fast Gen 6 silicon is moving from sampling to deployment.

**Connection and what to watch.** Orion's economics — tokens per second per dollar per watt on inference — live or die on the same locality and bandwidth questions as an HPL node: what shares an uplink, what P2P paths exist, where memory sits. Watch Q1 2027 systems from the ODMs, the Scorpio X production ramp, and how UALink (the open accelerator-fabric alternative backed by most of the rest of the industry) positions against a PCIe-based scale-up fabric.

### 2.2 Microchip Switchtec Gen 6: first 3 nm PCIe Gen 6 switches, and what Gen 6 changes underneath

**What happened.** Microchip introduced its **Switchtec Gen 6** PCIe switch family (announced October 13, 2025; sampling to qualified customers), built on a 3 nm process — the first PCIe Gen 6 switches at that node — with up to 160 lanes, 20 ports, and 10 protocol stacks per device (144-lane variants also offered), plus non-transparent bridging for multi-host systems and multicast within a domain. A low-lane-count version (48/64 lanes) for storage and enterprise designs was slated for Q2 2026.

**What technically changed.** Gen 6 doubles per-lane bandwidth to 64 GT/s — a Blackwell-class GPU's Gen 6 port is 256 GB/s aggregate — but the *how* changed more than the *how much*: PAM4 signaling (four voltage levels per symbol instead of two), FLIT-mode encoding with forward error correction (FEC), larger transaction tags for more outstanding requests, and new power-management states. Each of these raises the signal-integrity bar: PAM4 eyes are small, channels that carried Gen 5 need retimers or better materials at Gen 6, and FLIT/FEC changes the latency and retry structure of every link. A switch that must fan 160 such lanes out non-blocking, per-port hot-plug controllers included, is a leading-edge analog/digital design problem — hence 3 nm and hence the security additions Microchip emphasizes (hardware root of trust, post-quantum CNSA 2.0 cryptography) for infrastructure that increasingly carries multi-tenant fabrics.

**Why it matters and how it connects.** The merchant PCIe switch is the component that makes *every* topology from section 1.1 possible — direct-attach works only while lane counts happen to match, and it was switches that let 8-GPU servers exist before 128-lane CPUs did. Gen 6's retiming and FEC requirements are also why today's newest platforms (Vera CPUs with 88–96 Gen 6 lanes, AMD's Venice with 128) put switch and fabric design back at the center of node architecture — the same forces Orion exploits one level up. For an HPC engineer, the practical takeaway is that the switch hop — its ~100 ns-class latency, its shared uplink, its P2P and ACS behaviors (section 1.1) — is becoming *more* consequential per generation, not less, and reading a vendor's switch topology diagram is now a required skill in both directions: for dense fan-out inside the node and for fabric-attached resource pools above it.
