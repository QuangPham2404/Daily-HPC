## 0. Concise Summary

Last Friday's issue closed with GPU-5.1's inventory question — *what can simultaneously reside on an SM/CU?* Today we answer the two questions that naturally follow: **how full are those resident slots** (occupancy), and **who decides what runs where and when** (scheduling).

GPU-5.2 develops occupancy as arithmetic rather than folklore: the number of resident warps is the **minimum over several independent hardware limits** — warp slots, block slots, registers, and shared memory — worked through a full H100-style example and its AMD CDNA4 counterpart. The lesson that recurs all day: **occupancy is a latency-hiding budget, not a score to maximize.** GPU-5.3 and GPU-5.4 examine the two *soft* limits inside that minimum — the register file, where the compiler trades resident warps against spills and you trade occupancy against instruction-level parallelism, and shared memory, where tiling decisions trade arithmetic intensity against residency. GPU-5.5 moves above the SM: how the block dispatcher greedily assigns work, why blocks must be independent by construction, what wave quantization costs at grid scale, and how Hopper's thread-block clusters add a co-scheduling granularity above the block. GPU-5.6 closes with concurrent kernels: streams make overlap *possible*, but the same occupancy math decides whether two kernels actually co-reside — and across processes nothing truly overlaps without MPS, because separate contexts are time-sliced, not spatially shared.

Three developments map directly onto this material. AMD's July 2026 ROCm blog derives MI355X (CDNA4) occupancy from first principles and measures matrix-bound kernels holding ~97% of peak at ~12% occupancy — the strongest vendor-published demonstration yet that maximum occupancy is the wrong target. A September 2026 arXiv paper (KerColle) shows the CTA dispatcher's greedy admission causes head-of-line blocking that leaves large fractions of a modern GPU idle during vision-language-action inference. And an April 2026 systematic evaluation of MPS vs MIG quantifies exactly when concurrent execution across processes pays (+30%) and when it backfires (−30% under memory contention).

## 1. Learn the Concepts

### 1.0 From inventory to policy

GPU-5.1 established *what* fits on an SM: a fixed number of warp slots, a fixed number of block slots, a register file, and a shared-memory SRAM. That inventory is static hardware fact. Today's five topics are the software-facing consequences of that inventory:

- **GPU-5.2** — how full the warp slots are (occupancy), computed as the minimum over all the limits;
- **GPU-5.3 / GPU-5.4** — the two limits you actually control at compile time (registers) and launch time (shared memory);
- **GPU-5.5** — the hardware policy that fills the slots (block scheduling) and its grid-scale artifact (wave quantization);
- **GPU-5.6** — what happens when *multiple* kernels compete for the same slots at once.

The through-line is a single idea worth stating up front: **an SM is a fixed set of physical resources, and every scheduling decision — compiler, launcher, dispatcher, or runtime — is just an argument about how to divide it.**

### 1.1 GPU-5.2 — Occupancy

**What occupancy measures.** Occupancy is the ratio of *active* (resident) warps on an SM to the maximum number the SM supports:

```
occupancy = resident warps per SM / max warps per SM
```

On NVIDIA datacenter GPUs the denominator has been 64 warps per SM since Volta (Ampere tuning guide, Hopper tuning guide), with 48 on some consumer-class parts (compute capability 8.6, 12.0). On AMD CDNA parts the same quantity is counted per SIMD unit: a CDNA2/CDNA3/CDNA4 SIMD holds at most 8 wavefronts (a wavefront is AMD's 64-thread warp), capped at 32 waves per compute unit. "Resident" means something specific: the wave's registers are allocated and its execution state lives on the SM. A resident warp may be stalled, waiting, or running — residency is a *resource* concept, not a *progress* concept. Occupancy therefore says nothing about whether the resident warps are doing useful work; it only says how many are parked on the SM.

**Why it exists.** Recall GPU-4.10's Little's-law argument: to saturate a memory system you need enough independent requests in flight, and to hide instruction and memory latency you need other warps ready to issue whenever one stalls. Occupancy is the *capacity* to do that. With only two resident warps, a single long-latency load can idle the whole SM; with 48 resident warps, the scheduler almost always has someone else to run. But capacity to hide latency is not the same as latency actually hidden — a point we will return to, because it is the most misunderstood fact in GPU performance.

**The occupancy calculation.** The number of blocks that can be resident on one SM is the minimum over four independent limits:

```
blocks_per_SM = min( warp-slot limit,      max_blocks_per_SM,
                     register limit,       shared-memory limit )
```

Each limit is a hardware budget divided by what one block consumes, floored to a whole number:

- **Warp slots:** max warps per SM ÷ warps per block.
- **Block slots:** a hard cap — 32 blocks per SM on A100, H100, and Blackwell CC 10.0 (16 on CC 8.6).
- **Registers:** register file ÷ (registers per thread × threads per block), with allocation granularity applied.
- **Shared memory:** shared-memory capacity per SM ÷ shared memory per block.

Occupancy then follows: `blocks_per_SM × warps per block ÷ max warps per SM`.

**A worked H100 example.** Take a kernel launched as 256-thread blocks (8 warps per block), compiled to 48 registers per thread, using 10 KB of shared memory per block. The Hopper SM offers 64 warp slots, 32 block slots, 65,536 32-bit registers, and 228 KB of shared memory (227 KB max per block) — figures from the Hopper Tuning Guide.

- Warp slots: 64 ÷ 8 = **8 blocks**.
- Block slots: **32 blocks**.
- Registers: 48 × 256 = 12,288 registers per block; 65,536 ÷ 12,288 = 5.33 → **5 blocks**.
- Shared memory: 227 KB usable ÷ 10 KB = 22.7 → **22 blocks**.

The minimum is 5 blocks → 40 resident warps → **62.5% occupancy**, and the binding resource is the register file. Nothing about the other limits matters — improving any of them changes nothing until registers do. Now push registers down: at 40 registers per thread, 10,240 registers per block gives 6.4 → 6 blocks → 48 warps → **75%**. At 32 registers: 8,192 per block gives exactly 8 blocks, which also saturates the warp-slot limit → 64 warps → **100%**. This is the dial that `-maxrregcount`, `__launch_bounds__`, and `__maxnreg__` turn (GPU-5.3), and it illustrates why occupancy is *predictable statically*: register and shared-memory usage are compile-time and launch-time properties, so the whole calculation can be done before the kernel ever runs. NVIDIA ships exactly this computation in the runtime API (`cudaOccupancyMaxActiveBlocksPerMultiprocessor`, `cudaOccupancyMaxPotentialBlockSize`) and in Nsight Compute's occupancy section; `--resource-usage` (or `-Xptxas -v`) prints the per-kernel register and shared-memory numbers you need as input.

**Allocation granularity — the silent tax.** Registers are not allocated one at a time. On Hopper they are granted per warp in chunks of 256 registers. A kernel using 63 registers per thread needs 63 × 32 = 2,016 per warp, which rounds up to 2,048 — so 63 and 64 registers per thread cost *exactly the same* occupancy (65,536 ÷ 2,048 = 32 warps = 50%), while 65 registers per thread rounds 2,080 up to 2,304, dropping the SM to 28 warps (43.75%). AMD behaves identically in spirit: on CDNA4, VGPRs round to groups of 8, and AMD's own example shows a kernel reporting 100 VGPRs per lane actually consuming 104 — the difference between 5 resident waves per SIMD (62.5%) and 4 (50%). Four invisible registers cost a quarter of the occupancy. This is why occupancy math must use the *allocated* counts from the binary, not the ideal ones.

**The AMD version of the same calculation.** AMD's CDNA occupancy math is structurally identical but with one twist worth internalizing, because AMD documented it in detail in a 2026 blog post (see §2.1). A CDNA4 compute unit (CU) is four SIMD units, each with a private vector register file (VGPRs, 512 entries per lane, shared between regular and accumulator registers) and ~800 scalar registers (SGPRs), while the local data share (LDS, AMD's shared memory) is a single 160 KB scratchpad *per CU*, shared by all four SIMDs. So the register limits produce *waves per SIMD* while the LDS limit produces *workgroups per CU* — different units that must be converted before taking the minimum. The bridge is how a workgroup's waves land: a 256-thread workgroup is 4 waves, spread one per SIMD, so each resident workgroup contributes one wave to every SIMD. AMD's worked example: a 256-thread workgroup using 128 VGPRs per lane, 50 SGPRs, and 32 KB of LDS yields VGPR limit ⌊512/128⌋ = 4 waves/SIMD, SGPR limit 16, and an LDS limit of ⌊64/32⌋ = 2 workgroups/CU on MI300X (CDNA3, 64 KB LDS) versus ⌊160/32⌋ = 5 on MI355X (CDNA4, 160 KB). The same kernel is LDS-bound at 25% occupancy on CDNA3 and register-bound at 50% on CDNA4 — a generational change in *which* limiter binds, from growing one budget.

**Theoretical versus achieved occupancy.** Two refinements matter in practice. *Theoretical occupancy* is what we computed above — what the SM could hold given the kernel's resources. *Achieved occupancy* is what the profiler reports per kernel, averaged over its execution, and it can be lower for a reason that has nothing to do with resources: if the grid does not contain enough blocks to fill every SM (the tail effect of GPU-5.5), or if the kernel has phases with few eligible warps, achieved occupancy drops. When Nsight Compute shows achieved occupancy far below theoretical, the cause is either grid shape or dependent-instruction stalls — not launch configuration.

**Why maximum occupancy is not maximum performance.** Here is the conceptual heart of this topic. Occupancy buys latency-hiding *capacity*. Once enough independent work is in flight to cover the latency of the critical path, additional resident warps add nothing — and they cost something: more warps means fewer registers per thread (the file is fixed), more pressure on the cache hierarchy from more concurrent working sets, and more scheduler arbitration. Both vendors now state this explicitly. NVIDIA's tuning guides steer you toward "the launch configuration that maximizes device utilization" for your kernel, not blanket-maximum occupancy; AMD's MI355X guide goes further and *measures* it — a matrix-core microbenchmark holding ~97% of the MI355X's MXFP8 peak at ~12% occupancy, because a handful of waves each carrying eight independent MFMA accumulator chains supply all the instruction-level parallelism (ILP) the matrix unit needs. The deep symmetry: **ILP within a warp and TLP (thread-level parallelism) across warps are two currencies that buy the same latency-hiding, and the register file is the budget they compete for.** A well-tuned GEMM — including the HPL/HPL-MxP kernels you have benchmarked — deliberately runs at modest occupancy with large register-resident accumulator tiles, trading resident warps for per-warp independent work. When you profile, treat low occupancy as a *question* (is something else limiting?) rather than a *finding*.

### 1.2 GPU-5.3 — Register pressure

**The mechanism.** The compiler assigns every live value in a kernel — loop counters, loaded operands, address arithmetic, accumulator fragments — to registers, subject to the hardware cap (255 per thread on Ampere/Hopper/Blackwell; 63 in the Fermi era). "Register pressure" is the demand for simultaneously live values. It rises with exactly the things fast kernels do: deeper unrolling (more values in flight per iteration), larger per-thread tiles (more accumulators), and software pipelining (loads issued ahead of use). Since the per-SM register file is fixed at 64K 32-bit registers, every extra register per thread directly reduces how many threads can be resident — GPU-5.2's worked example showed 48→32 registers per thread buying 62.5%→100% occupancy on an H100.

**Spilling.** When live values exceed the available registers, the compiler *spills* them to per-thread **local memory** (LMEM). "Local" is a euphemism: local memory is backed by the same DRAM as global memory, private per thread, and cached in L1/L2. A spill turns one register move into a store plus a load, adds address-computation instructions, and — if the line is evicted before the reload — generates real DRAM traffic. NVIDIA's classic training material on register spilling works a finite-difference stencil where forcing 32 registers per thread (to reach 1024 resident threads) produced 44 bytes of spill traffic per thread; removing the cap let the compiler use 46 registers with no spills and ran 1.22× faster *despite lower occupancy*. The same material shows the opposite case: when spills stay in L1 (99% hit rate) and amount to ~1.6% of instructions, the high-occupancy version wins. So spilling is not automatically a loss — it is a bandwidth and instruction-count question, and the profiler answers it (`local_load`/`local_store` counters, spill bytes reported at compile time). The error is treating either "no spills" or "max occupancy" as the goal instead of measuring.

**The controls.** Three knobs exist, at different scopes, all documented in the CUDA Programming Guide's launch-bounds section:

- `__launch_bounds__(maxThreadsPerBlock, minBlocksPerMultiprocessor)` — a per-kernel *contract*: "this kernel will never launch with more than maxThreadsPerBlock threads, and I want at least minBlocksPerMultiprocessor blocks resident." The compiler first derives the register ceiling L that satisfies the residency target, then optimizes under it — reducing register usage (possibly spilling) if it exceeds L, and *raising* usage toward L when extra registers would cut instruction count. The single-argument form is also a portability guard: it prevents "too many resources requested for launch" errors on future hardware by bounding the worst-case per-block footprint.
- `__maxnreg__(N)` — a per-kernel hard register cap (compiles to the `.maxnreg` PTX directive); mutually exclusive with `__launch_bounds__` on the same kernel.
- `--maxrregcount N` — a per-file cap applied to every kernel in the compilation unit; ignored for kernels carrying their own qualifier.

The critical subtlety: these knobs do not make the kernel use fewer registers by fiat — they force the compiler to *fit*, and the compiler's tools for fitting are spilling and re-materialization (recomputing a value instead of storing it). You are choosing where the pressure goes: into DRAM traffic (spills), into extra instructions, or into lower occupancy. Measure which side loses least.

**Reading the binary.** The register count is emitted into the cubin and reported by `--resource-usage` (e.g., "Used 48 registers, 0 bytes spill"). For AMD, `llvm-objdump` on the code object exposes `.vgpr_count`/`.sgpr_count` (and spill counts) — the inputs to the occupancy math of §1.1. In a profiling loop, this is the first number to look at before any timeline: it tells you which limiter you are living under before the kernel even runs.

**Connections.** Register pressure is the *compile-time* face of occupancy; shared memory (next) is its *launch-time* face. The ILP-vs-TLP trade reappears in §2.1 as measured data. And when you later study warp specialization (producer/consumer kernels where some warps only move data), recognize it as a *scheduling* answer to register pressure: warps with different roles get different register budgets in effect, because they execute different code.

### 1.3 GPU-5.4 — Shared-memory capacity constraints

**The mechanism.** Shared memory is allocated at block granularity and held for the block's entire lifetime: the per-block amount (static + dynamic) is claimed when the block launches and returned only when it retires. Two ceilings therefore apply simultaneously, and either can bind:

- **Per-SM capacity:** 164 KB on A100, 228 KB on H100 and Blackwell CC 10.0 (128 KB on CC 12.0 parts).
- **Per-block maximum:** 163 KB on A100, 227 KB on H100, 99 KB on CC 12.0.

The block limit from shared memory is `⌊per-SM usable ÷ per-block usage⌋` — and unlike registers, this you control at *launch* time via the dynamic shared-memory size, which makes it the fastest occupancy experiment available: change one `cudaFuncSetAttribute` value and re-measure.

**The carveout.** Since Volta, shared memory and L1 cache are the *same physical SRAM*, split at runtime into a "carveout" (`cudaFuncAttributePreferredSharedMemoryCarveout`). A kernel that opts for the maximum shared-memory configuration sacrifices L1 capacity, and vice versa — so the shared-memory occupancy limit is not even a fixed number until the carveout policy is settled. The compiler's default heuristics pick a carveout from the kernel's declared usage; performance-sensitive code sets it explicitly.

**The 48 KB default wall.** Devices since compute capability 7.0 permit a block to use *more* than 48 KB of shared memory only via **dynamic** shared memory and an explicit opt-in: `cudaFuncSetAttribute(kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, bytes)`. Forget the opt-in with a >48 KB request and the launch fails with an invalid-argument error — a rite of passage for anyone writing large-tile GEMMs. The runtime also answers the inverse question — "how much shared memory can I use if I insist on N blocks resident?" — with `cudaOccupancyAvailableDynamicSMemPerBlock`, which is the right call when you want a specific occupancy (say, exactly 2 blocks for a double-buffered pipeline) and need the maximum tile that fits.

**A worked example with HPL flavor.** Consider a GEMM panel kernel that stages a 128×128 fp32 tile in shared memory: 128 × 128 × 4 B = 64 KB per block. On an H100 with full carveout: ⌊227/64⌋ = 3 blocks per SM × 8 warps per block = 24 resident warps → 37.5% occupancy. On an A100: ⌊163/64⌋ = 2 blocks → 16 warps → 25%. Now halve the tile (a 128×64 tile = 32 KB): H100 fits 7 blocks → 56 warps → 87.5%. This is the fundamental GEMM tuning dial in miniature: **the shared-memory tile sets arithmetic intensity (how many FLOPs each loaded byte feeds) and simultaneously sets occupancy (how many blocks hide the memory latency).** Large tiles amortize DRAM traffic but leave fewer warps to hide it; small tiles hide latency well but repeat traffic. The optimum is found by profiling across the dial, which is exactly why libraries like cuBLAS ship kernel-selection heuristics over tile shapes. HPL and HPL-MxP inherit the same trade through their vendor GEMM layers — the panel/trailing-update shapes choose the point on the dial.

**AMD's asymmetry.** On CDNA, the LDS is per-CU while register files are per-SIMD (§1.1). Consequence: the LDS limit is spent by the *workgroup* (which may spread its waves across all four SIMDs), and the register limit by each SIMD's wave slots. NVIDIA has no such asymmetry — its SM sub-partitions each hold their own register file but share one shared-memory SRAM per SM, so the same conversion dance exists implicitly. The practical takeaway either way: when the profiler says "occupancy limited by shared memory," the fix is a tiling decision, not a launch-configuration tweak.

**Connections.** This topic is the capacity constraint behind GPU-4.3 (shared memory as a staging buffer) and the resource side of GPU-5.5 (blocks cannot launch unless their shared-memory claim fits the target SM). Ahead, thread-block clusters (§1.4) make shared memory a *distributed* resource across a few SMs, and warp-specialized Hopper kernels (TMA pipelines) exploit large per-block allocations precisely because they run few blocks per SM by design.

### 1.4 GPU-5.5 — Block/workgroup scheduling

**The dispatch pipeline.** When the host launches a grid, the blocks do not carry an SM assignment. A hardware dispatcher — NVIDIA's work distributor, AMD's equivalent in the command processor — watches every SM's free warp slots, block slots, registers, and shared memory, and greedily assigns the next block to any SM that can host it. The essential properties:

1. **Blocks are assigned when resources allow, not in a guaranteed order.** Anywhere in the grid is possible; the hardware makes no promise about *when* a given block starts.
2. **A block lives entirely on one SM.** Its registers and shared memory are per-SM physical resources, so no block ever straddles SMs.
3. **Blocks are independent by contract.** The programming model guarantees no inter-block synchronization or communication (until the exceptions below). This is *why* the dispatcher can be greedy and dumb: correctness never depends on dispatch order. It is also why algorithms with inter-block dependencies must be restructured (global atomics and flags with memory ordering per GPU-4.11, cooperative launch, or fused into one block's work).

The design lesson: **block independence is what buys the GPU its fire-and-forget scheduling.** Contrast a CPU OS scheduler, which must support arbitrary blocking and communication and therefore carries the machinery of preemption and priorities; the GPU's contract with the programmer is "don't depend on order, and I'll keep every SM fed with zero scheduling intelligence."

**Dispatch order and L2 locality.** Blocks are issued roughly in linear grid order (x fastest, then y, then z in CUDA's default rasterization). Since consecutive blocks often touch neighboring data, this ordering produces a *streaming* L2 access pattern: data loaded by a block is largely gone (evicted) by the time distant blocks want adjacent tiles. High-performance kernels — CUTLASS GEMMs prominently — apply **thread-block swizzling**: relabeling blocks so that the ~hundreds of blocks co-resident across the SMs at any instant are exactly those whose tiles overlap in B-matrix columns, concentrating reuse inside the L2 window. This is GPU-4.9's cache-locality topic operating one level up: not which addresses a warp touches, but which *blocks* are co-resident.

**Wave quantization.** Multiply blocks-per-SM (from §1.1's occupancy math) by the SM count: that is a **wave** — the number of blocks the GPU can run simultaneously. A grid of *k* waves plus a remainder runs the remainder as a mostly-empty final wave. Example: a kernel fitting 2 blocks per SM on a 132-SM H100 has a 264-block wave; a grid of 1,000 blocks runs 3 full waves plus 208 blocks — a final wave at 79% SM occupancy, and since many such kernels are tile-count-bound, up to a fifth of the machine idles at the end. Mitigations, in increasing invasiveness: pad/choose grid dimensions so the remainder is zero or the tail overlaps with other work; split work *unevenly* so each SM's final assignment matches its speed; or abandon the grid abstraction with a **persistent kernel** — launch exactly one wave of blocks, each looping over work items pulled from an atomic counter or static range. Persistent kernels eliminate tail loss and per-kernel launch overhead, at the cost of doing your own load balancing; they are standard in production HPL-MxP-class GEMM implementations (stream-K and split-K schedulers are the tiled-matrix expression of the same idea: cutting the iteration space so every SM gets the same amount of work, not the same number of tiles).

**Guaranteed co-residency: cooperative launch.** Some algorithms (iterative solvers with a global barrier per step) need *all* blocks resident at once. `cudaLaunchCooperativeKernel` provides exactly that: the runtime rejects grids larger than the co-resident maximum computed from the kernel's own occupancy. This is the one place where occupancy math stops being a performance question and becomes a **correctness requirement** — your grid must fit one wave.

**Thread-block clusters (Hopper+).** Hopper added a residency granularity between block and grid: up to 8 blocks (16 non-portably on H100, via `cudaFuncAttributeNonPortableClusterSizeAllowed`) can be declared a **cluster**, guaranteed co-resident on SMs within the same GPC, with distributed shared memory — each block can directly read and write the shared memory of its cluster peers. Clusters change scheduling from "blocks anywhere" to "clusters on one GPC," which is why NVIDIA recommends computing cluster occupancy with `cudaOccupancyMaxActiveClusters` and warns that large cluster sizes reduce the maximum active blocks across the GPU. Mechanically, clusters exist to make multi-SM pipelines (TMA-fed, warp-specialized kernels sharing staged tiles) legal without going through global memory.

**Head-of-line blocking.** One final dispatcher behavior, normally invisible but recently measured at scale (§2.2): the dispatcher fills SMs *in launch order*. When a large-grid kernel occupies every SM, the *next* kernel's blocks — even tiny ones needing idle functional units — wait for a retiring wave. The dispatcher has no notion of "these resources are free but those are busy"; block admission is all-or-nothing per SM. This is the hardware fact behind most "two streams should overlap but don't" surprises.

### 1.5 GPU-5.6 — Concurrent kernels

**Serialization by default.** Launch two kernels with no stream argument and they run strictly one after the other: both land in the *default stream*, whose semantics are to serialize against other blocking work. To get overlap you must use **streams** — ordered command queues of kernels and copies — and launch the kernels into *different* streams. But streams are a *permission*, not a guarantee. The programming model says kernels in different streams *may* execute concurrently; whether they do depends on resources and on what else holds the GPU.

**What actually constrains overlap.** Two kernels overlap only to the extent their combined footprint fits:

- If kernel A's occupancy (§1.1) already fills every SM, kernel B's blocks queue until A's blocks retire — overlap happens only at the wave boundary (the head-of-line effect of §1.4).
- If A and B together exceed registers, shared memory, or block slots, the dispatcher interleaves them partially.
- If both saturate the same bottleneck (say, both are DRAM-bound), overlap gains nothing — you are time-multiplexing one saturated resource, not using idle ones.

Concurrent execution pays when the kernels are *complementary*: a small kernel that cannot fill the machine (grid too small, or occupancy-limited by its own resources) runs alongside another that uses what the first leaves idle. Inference serving exploits this constantly — many small GEMMs and elementwise kernels co-scheduled to keep tensor cores and memory pipes simultaneously busy. For HPL-class work the opposite holds: one giant GEMM fills the GPU, and the right design is a *single* kernel (possibly persistent, §1.5's tail-loss argument), not concurrency.

**Priorities and the queue depth.** Streams carry priorities (`cudaStreamCreateWithPriority`) that bias the scheduler's choice when queues contend — a hint, not a reservation. And on the hardware side, the number of *hardware* work queues is finite and much smaller than the streams a program can create: the driver multiplexes many software streams onto fewer hardware queues. This was not always so, and the history is instructive (§1.4's dispatcher met its match in multi-core hosts): Fermi multiplexed every stream onto a *single* hardware work queue, serializing concurrent launches through false dependencies. Kepler's **Hyper-Q** raised this to 32 simultaneous hardware-managed connections — from multiple streams, MPI ranks, or host threads — and added the **Grid Management Unit (GMU)** to manage, pause, and queue grids (including GPU-launched grids, enabling dynamic parallelism). The lesson generalizes: *the hardware queue structure, not the API, defines what can overlap.*

**Processes change everything.** All of the above assumes one CUDA context. Work from *different contexts* — which is what separate processes have — **cannot execute concurrently** on the GPU: the hardware time-slices between contexts, swapping scheduling state, with each process taking the whole GPU in turn (NVIDIA's MPS documentation describes exactly this). Four MPI ranks sharing one GPU therefore serialize even when each rank's kernels are tiny. **MPS (Multi-Process Service)** removes this: an MPS server gives its clients a shared connection and one set of scheduling resources, and since Volta, clients submit work directly to the GPU with their own address spaces — kernels from different processes genuinely co-reside and fill each other's holes. MPS even provisions resources per client (limiting each client's fraction of SMs via its active-thread-percentage setting). The trade: MPS shares *everything* — L2, DRAM bandwidth, SMs — so co-resident processes contend; MIG, the alternative, physically partitions the GPU into isolated slices with private memory systems, trading that flexibility for hard isolation. §2.3 quantifies this trade. Green contexts (recent CUDA) bring a similar partitioning idea *inside* one process — disjoint SM sets per green context — though the runtime documentation is explicit that disjoint SMs alone do not guarantee concurrency or forward progress.

**Hardware support for tighter overlap.** Modern architectures keep chipping at the seams between kernels: Hopper's **programmatic dependent launch** lets a dependent kernel begin before its predecessor fully drains (the predecessor triggers the next launch at a chosen point; the dependent kernel waits at an explicit synchronization point before touching unready data), converting inter-kernel dead time into overlap. Copy engines (GPU-5.7's subject, next Friday) do the same for data movement. But the governing rule is unchanged and worth carrying forward: **concurrency is a resource-fitting problem wearing a scheduling costume** — the same min-over-limits arithmetic of §1.1, applied across two kernels instead of one.

**A correctness warning.** Treating *possible* concurrency as *guaranteed* is a deadlock recipe: if kernel A spins waiting for data that only kernel B will produce, and B's blocks cannot launch until A's retire, the program hangs. Streams promise nothing here. The only co-residency guarantee in the model is cooperative launch (§1.4). If you must handshake between concurrent kernels, bound the wait (timeout) or restructure — this is the GPU-side analogue of distributed deadlock, and the cure is the same: never block on a party that may not be scheduled.

## 2. Key Developments / News

### 2.1 AMD publishes first-principles occupancy math for MI355X (CDNA4)

**What happened.** In July 2026, AMD's ROCm blog published "Occupancy Math on the AMD MI355X GPU (CDNA4): A From-First-Principles Guide" (Shekhar Pandey, Liz Li, Andy Luo) — a vendor-authored walkthrough deriving occupancy by hand from a compiled kernel's binary.

**What it demonstrates technically.** Three things of direct curricular value. First, the four-limiter model made concrete: occupancy is min(VGPR limit, SGPR limit, LDS limit, workgroup/barrier slots), with the per-SIMD versus per-CU unit conversion (§1.1). Second, CDNA4's architectural facts that change the math: the vector register file is 512 entries per lane *shared* between regular VGPRs and matrix accumulators (breaking the MI100/MI200 assumption of a separate accumulator file), and LDS grew 2.5× from 64 KB (CDNA3) to 160 KB per CU — which flips real kernels from LDS-bound to register-bound. Third, and most important, a controlled measurement: sweeping instruction-level parallelism (1–8 independent MFMA accumulator chains per wave) against independently throttled occupancy shows the matrix core holding ~97% of peak (~4.8 of ~5 PFLOP/s MXFP8) at **12% occupancy**. One well-fed wave per SIMD with eight independent accumulators saturates the matrix unit; the extra resident waves that higher occupancy would buy contribute nothing.

**Why it matters and how it connects.** This is the strongest vendor-published refutation of "maximize occupancy" as a tuning target — on the hardware that competes directly with NVIDIA's for exascale GEMM throughput. It maps one-to-one onto GPU-5.2 (the limiter arithmetic), GPU-5.3 (registers as the currency that buys ILP), and GPU-5.4 (LDS as the generational lever). The ILP-vs-TLP framing also explains *why* the rocBLAS kernels profiled in AMD's companion ATT blog post (September 2026) deliberately run 3 waves per SIMD — low occupancy by design, more registers per wave, parallelism harvested inside the instruction stream instead.

**What to watch next.** Whether the unified accumulator/regular register file persists in CDNA5, and whether occupancy tooling (the profiler's limiter attribution) becomes as first-class on ROCm as Nsight Compute's occupancy section is on CUDA.

### 2.2 KerColle: the block dispatcher's head-of-line blocking, measured

**What happened.** A September 2026 arXiv preprint, "KerColle: Unlocking Fine-Grained GPU Concurrency in Vision-Language-Action Models" (arXiv:2609.22335), characterizes why GPU concurrency fails in VLA inference and proposes a scheduling layer to fix it.

**The technical finding.** VLA inference has two decoupled phases — a large vision-language model phase (big GEMMs) and an action-head phase (hundreds of micro-kernels of a few microseconds each). Profiling on Ada, Hopper, and Blackwell shows median SM throughput of 18–30% of peak. The cause is precisely §1.4's dispatch behavior: a VLM GEMM launches ~768 CTAs; with only 2 CTAs resident per SM given its register footprint, the kernel drains in ~3 waves, and the dispatcher's greedy in-order admission leaves the action-head kernels queued behind entire waves despite idle functional units — head-of-line blocking at the CTA level. Naive two-stream overlap therefore achieves almost nothing. KerColle's scheduler uses live SM utilization and per-kernel resource footprints to co-schedule kernels with complementary resource needs, reporting (in simulation, across two architectures and four VLA models) throughput gains up to 28%, average 20.5%, and measurably higher warp occupancy than the baseline dispatcher.

**Why it matters and how it connects.** This is GPU-5.5 and GPU-5.6's "concurrency is a resource-fitting problem" thesis turned into a measured pathology: the block scheduler's *correctness-neutral greed* — the very property that keeps GPU dispatch cheap — is a performance bug when workloads mix wave-scale and microsecond-scale kernels. Note the claim status: the gains are simulation results, not shipped-hardware measurements; treat the diagnosis as solid (it follows from documented dispatch behavior) and the 28% as a research claim.

**What to watch next.** Whether vendor dispatchers absorb the lesson (admission policies aware of resident-kernel resource mixes), and whether scheduling frameworks like this reach production inference stacks — the same pressure that produced persistent kernels and stream-K in the GEMM world.

### 2.3 MPS vs MIG under systematic evaluation: when spatial sharing pays

**What happened.** An April 2026 arXiv preprint, "A comprehensive evaluation of spatial co-execution on GPUs using MPS and MIG technologies" (arXiv:2604.22430), systematically benchmarks NVIDIA's two mechanisms for letting multiple applications share one GPU — MPS (logically shared resources) and MIG (physical partitioning).

**The technical content.** The paper's headline trade-off: in favorable scenarios MPS improves performance up to 30% and cuts energy ~20% — especially using MPS's per-client provisioning (the active-thread-percentage limit) to keep one client from monopolizing SMs. But under memory-system contention, MPS *degrades* performance by ~30%: co-resident kernels share L2 and DRAM bandwidth, and interference can swamp the gains. MIG's hard partitioning eliminates memory contention entirely, giving consistent improvements — but its coarse, rigid partition sizes and per-instance overhead make it a poor fit for workloads that do not align with slice boundaries. (Both mechanisms build directly on §1.5's machinery: MPS replaces cross-process *time-slicing* with true co-residency; MIG replaces co-residency with disjoint resources.)

**Why it matters and how it connects.** Multi-tenant GPU sharing is now the default operating mode of every HPC center and inference cluster, and the paper quantifies the two failure modes that matter for a working engineer: resource monopolization (fixable with provisioning) and memory contention (fixable only with isolation). It is the real-world version of today's closing lesson — concurrency decisions are resource-allocation decisions — extended from two kernels in one process to many processes on one device.

**What to watch next.** Green-context-style intra-process partitioning maturing into a scheduler-facing API, and whether future architectures expose reservable memory-system resources (the paper's data suggests that is where MPS's residual risk lives).
