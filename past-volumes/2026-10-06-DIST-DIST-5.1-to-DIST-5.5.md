## 0. Concise Summary

Modules 1–4 built the *vocabulary* of distributed communication: what a message is, how send/receive works, what collectives exist and which algorithm skeletons implement them. Module 5 now builds the *arithmetic*. Today's five topics construct the performance models that let you predict, from a handful of measured parameters, how long a message will take — and, more importantly, which layer of the system is holding it back.

The backbone is the **α-β (Hockney) model** (DIST-5.1): the time to move a message of *m* bytes is *T(m) = α + mβ*, a fixed startup cost plus a per-byte cost. It looks almost too simple to be useful, yet it is the model inside MPICH's runtime collective-algorithm selection, HPL's scalability analysis, and SimGrid's network simulation — because it composes: once every layer is expressed in α's and β's, you can add them along a path, plug them into collective formulas, and differentiate to find optimal tree radices or chunk sizes. Its crucial derived quantity is the **half-bandwidth message size m½ = α·B**, the size at which the two terms balance — below it you are buying latency, above it you are buying bandwidth.

The next three topics dissect what α and β actually contain. **Serialization time** (DIST-5.2) is the irreducible part of β: even a perfectly engineered link clocks bytes out at a finite rate, so 1 MiB takes ~42 µs on 200 Gb/s InfiniBand no matter how clever the software is. **Software overhead** (DIST-5.3) is the part of α that no hardware improvement removes on its own: MPI request allocation, message matching, protocol decisions, copies — measured at ~1.1 µs (about a thousand CPU cycles) of pure MPI-stack overhead on Blue Gene/P, and *growing* with message count rather than message size. This is where the **LogP family** enters: LogP splits α into network delay *L*, CPU overhead *o*, and per-message gap *g* — a separation that matters because the CPU is free to compute while *L* elapses but not while *o* does. LogGP then adds the per-byte gap *G* for long messages, which is exactly the β of Hockney by another name.

The last two topics are about the gap between catalog numbers and reality. **Effective versus link bandwidth** (DIST-5.4) catalogs every layer that shaves the advertised rate: encoding overhead, protocol headers, extra copies, directionality accounting, single-stream limitations, and — most insidiously — path collisions, which can hold a perfectly healthy fat-tree to roughly a quarter of its bisection bandwidth during synchronized collectives. **Injection bandwidth** (DIST-5.5) names the per-*endpoint* limit: how fast one process, one core, one NIC, or one GPU can push traffic into the fabric, as opposed to how fast the fabric can carry it.

Three developments anchor the models in current practice: the **Ultra Ethernet 1.0 specification** (June 2025), whose packet-spraying transport is essentially a 573-page argument about raising *effective* bandwidth toward link bandwidth; the **800 Gb/s endpoint era** (ConnectX-8 / Quantum-X800), where the arithmetic of injection bandwidth forced PCIe into its sixth generation; and a **2025 HPDC paper** that uses a Hockney-shaped model — link bandwidth plus per-chunk pipeline overhead — to steer multipath intra-node GPU communication, proof that the two-parameter model born on 1990s clusters is still the working language of GPU-era performance engineering.

## 1. Learn the Concepts

Notation carries over from the earlier volumes: *p* ranks, *m* the message size in bytes, **α** the per-message startup latency, **β = 1/B** the per-byte cost on a link of bandwidth *B*, and **γ** the per-byte reduction cost introduced on October 3. September 12 (DIST-1.6/1.7) defined latency and bandwidth qualitatively and observed that small messages are latency-sensitive while large ones are bandwidth-sensitive; today we make that observation quantitative. October 3 (DIST-4.11) used α-β-γ to cost out collective algorithms; today we open the black box and ask where the numbers come from and where they lie.

### 1.0 The model ladder

Communication performance models form a thirty-year ladder, each rung adding one distinction that the previous one blurred:

| Model (year) | Formula / parameters | What it added |
|---|---|---|
| Postal (1992) | *T(m) = λ* | latency exists at all |
| Hockney (1994) | *T(m) = α + mβ* | bandwidth; size-dependent cost |
| LogP (1993) | *L, o, g, P* | CPU overhead ≠ network delay; finite message rate |
| LogGP (1995/97) | + *G* (gap per byte) | long messages have their own, faster rate |
| pLogP (2000) | *o_s, o_r, L(m), g(m)* | parameters depend on message size; sender ≠ receiver |
| LogGPO | overhead of `MPI_Wait` | real MPI completion costs, overlap fidelity |

The surprising fact is that the second rung never fell off: Hockney is still the workhorse inside MPI libraries, HPL analyses, and simulators, while the LogP rungs are what you reach for when the question is *who* is paying a cost — CPU or wire — and *can it be overlapped*. William Gropp's parallel-computing lectures frame exactly this: the simple model is *T = s + rn*; LogP exists to separate what the *processor* spends (overhead *o*) from what the *network* spends (delay *L*).

### 1.1 The alpha-beta model (DIST-5.1)

**The problem.** You need to predict communication time before running code — to size a halo exchange, choose a collective algorithm, decide a chunk size, or estimate whether a scaling plan is even feasible. A full network simulator is too slow and needs too much detail. You need a model with two or three numbers you can measure in five minutes.

**The model.** The time to transfer *m* bytes point-to-point is

```
T(m) = α + m·β        (β = 1/B)
```

**α** (startup, seconds) is everything that happens once per message: the API call, protocol selection, request creation, matching, the NIC being told to start, and the fixed transit delay of the first byte. **β** (seconds per byte) is the marginal cost of each additional byte — on a clean link, the reciprocal of its bandwidth. The model's physical picture is a pipeline: after paying α to "open the tap," data flows out at rate *B*.

The history is worth a minute because it explains the model's shape. The postal model (Bar-Noy and Kipnis, 1992) modeled message cost as a pure latency *λ* — every message costs the same, regardless of size. Hockney (1994), formulating performance for the Intel Paragon, added the *m/B* term: *t(m) = L + m/B*. Roger Hockney came from vector-computer performance modeling, where his 1989 *f½* parameter expressed the arithmetic intensity needed to reach half of peak performance on a memory-limited pipeline. The communication model inherits the same rational-function shape: define the **half-bandwidth message size**

```
m½ = α·B          (α / β in per-byte units)
```

and the effective bandwidth of a single transfer, *B_eff(m) = m/T(m) = B·m/(m + m½)*, reaches half of *B* exactly at *m = m½*. This is the message-size twin of Hockney's half-performance vector length — the same "how big before the fixed cost stops mattering" reasoning, transplanted from vector registers to network links.

**A worked example.** Take a representative HDR InfiniBand cluster: α ≈ 2 µs, B = 25 GB/s (200 Gb/s). Then:

| Message | T(m) | Latency share | B_eff |
|---|---|---|---|
| 1 KiB | 2.04 µs | 98% | 0.5 GB/s |
| 50 KiB (= m½) | 4.0 µs | 50% | 12.8 GB/s |
| 4 MiB | 170 µs | 1.2% | 24.7 GB/s |

Read the table as three regimes. At 1 KiB you could quadruple the link speed and barely notice: you are buying α. At 4 MiB you could halve α and barely notice: you are buying β. The crossover lives at m½ = 50 KiB — which is precisely why MPI libraries switch protocols (eager → rendezvous) and algorithms (tree → ring) in the tens-of-kilobytes range, and why "small" and "large" message regimes appeared in every collective cost table on October 3.

**Fitting the model.** You measure a ping-pong (round-trip) at several message sizes, halve the round-trip times, and fit a line of *T* against *m*: the intercept is α, the slope is β. Two practical warnings, both from the measurement literature. First, fit *per protocol regime*: an eager message and a rendezvous message have different α and β (the eager path copies; the rendezvous path sets up RDMA), so a single line fitted across the protocol threshold is wrong on both sides of it. Hoefler's *LogGP in Theory and Practice* devotes most of its effort to exactly this: parameters must be assessed per message-size class, because "most modern communication systems use message-size dependent protocols." Second, quote the measurement conditions (window size, core placement, clock) — the same hardware yields different α and β under different benchmark methodology, a point we return to in DIST-5.4.

**Why such a crude model survives.** Because it composes and differentiates. A two-hop relay costs 2α + mβ-ish; a binomial broadcast over lg p rounds costs lg p·(α + mβ); an optimal chunk size for pipelining a large transfer is found by setting the derivative of a α-β expression to zero. The MPICH library uses Hockney-style models at runtime to pick among collective implementations; HPL's scalability analysis is built on the Hockney model; SimGrid, the standard large-scale distributed-systems simulator, uses it as its network model. When the October 3 volume derived that a ring all-reduce moves 2(p−1)/p·m bytes per rank and a tree moves ~2·lg p·m, the α-β machinery underneath was today's topic.

**Where it breaks.** The model assumes the endpoint is otherwise idle: it has no notion that the CPU is busy, that the link is shared, or that two transfers contend. It cannot tell you whether you can *hide* communication behind computation — for that you need to know whether a cost is CPU time or wire time, which is exactly LogP's contribution (next, via DIST-5.3). And it is silent about topology, which is DIST-5.7/5.8 (hop count, bisection) later in this module.

### 1.2 Serialization time (DIST-5.2)

**The claim to justify:** even an *ideal* link — zero software, zero queuing, infinitely fast transceivers at the ends — still needs finite time to deliver a message. Why?

Because bandwidth is a *rate*, not a speed. A 200 Gb/s link moves 25 bytes per nanosecond, one after another. The first byte arrives after the propagation delay, but the last byte cannot leave before the first *m* bytes have been clocked onto the wire:

```
T_serialize(m) = m / B
```

This is the β-term of Hockney with all overheads stripped away — the physical floor. Distinguish it from **propagation delay**, the time a single bit needs to physically traverse the medium: light in fiber travels ~2×10⁸ m/s, about 5 ns/m, so 30 m of intra-rack fiber costs ~150 ns and a 2 km inter-building link ~10 µs. Propagation depends on *distance*; serialization depends on *size*. Total wire time for one hop is propagation + serialization.

**Numbers worth internalizing.** For a 1 MiB (2²⁰ bytes = 8.39 megabits) message:

| Link | Rate | T_serialize(1 MiB) |
|---|---|---|
| HDR InfiniBand | 200 Gb/s (25 GB/s) | 41.9 µs |
| NDR InfiniBand | 400 Gb/s (50 GB/s) | 21.0 µs |
| XDR / 800G Ethernet | 800 Gb/s (100 GB/s) | 10.5 µs |
| PCIe Gen5 x16 | 64 GB/s per direction | 16.4 µs |

Two conclusions follow. First, no protocol cleverness, no CPU tuning, and no algorithm change beats the floor: if your algorithm must move 8 MiB per step over one HDR link, 335 µs per step is gone before you write a line of code. This irreducibility is why HPL works so hard to overlap panel broadcasts with trailing-matrix updates (a preview of DIST-15.5): the bytes *must* flow for β·m seconds, so the only question is whether anything useful happens meanwhile. Second, as links get faster the serialization of *small* messages collapses toward irrelevance — a 4 KiB packet at 800 Gb/s serializes in 41 ns — which shifts the entire burden of small-message cost onto the fixed terms (α, software overhead, propagation). The faster the network, the more everything except bandwidth matters.

**Serialization at each hop.** A naive store-and-forward switch receives the whole packet, then re-serializes it: a path of *h* hops costs roughly *h·(m/B)* plus *h*·propagation. Modern HPC fabrics use **cut-through (wormhole) switching**: a switch starts forwarding a packet after reading its header, so the message is pipelined through the fabric and the total wire time is close to *header-propagation through h hops + one serialization*. The per-hop header latency (hundreds of nanoseconds in InfiniBand-class switches) is why hop count still matters even with cut-through — the quantitative treatment is DIST-5.7.

**The marketing corollary.** Serialization also exposes how bandwidth numbers are quoted. InfiniBand and Ethernet port rates (200G, 400G, 800G) are *per direction*; the link is full duplex. PCIe is conventionally quoted as the *sum* of both directions: "128 GB/s for a Gen5 x16 slot" means 64 GB/s each way. When a vendor slide multiplies a NIC rate by two or sums a duplex bus, divide before doing any α-β arithmetic — this bookkeeping error alone accounts for a surprising number of broken performance predictions, and it returns in DIST-5.4.

### 1.3 Software overhead (DIST-5.3)

**The problem.** The measured latency of a 1-byte MPI message on a modern cluster is on the order of a microsecond or two. Light crosses the whole machine in less time; the NIC is clocking at sub-nanosecond bytes. Where do the microseconds go? They go to software — and software cost does not shrink when you buy a faster link.

**Dissecting one send.** Trace a blocking `MPI_Send` of a small eager message:

```
sender app          → MPI layer        : validate args, choose protocol,
                                        allocate/init request object
                    → transport (UCX)  : look up memory region, build work
                                        request, ring the NIC "doorbell"
                    → NIC              : DMA the packet from host memory,
                                        compute checksum, serialize to wire
                    → wire             : propagation + serialization
                    → remote NIC       : DMA payload into a pre-posted or
                                        unexpected-message buffer
                    → remote MPI layer : match (source, tag, communicator),
                                        copy if eager, complete the request
                    → receiver app
```

Every arrow is CPU cycles, DMA engine time, or wire time. Hockney's α throws all of them into one number. The **LogP** model (Culler et al., PPoPP 1993; CACM 1996) makes the crucial split:

- ***L*** — network latency: the time a message spends *in the wire and switches*, from the sender's NIC release to the receiver's NIC arrival.
- ***o*** — overhead: the time the *processor* is busy sending or receiving (both ends pay it: effectively 2o + L for a short message end-to-end).
- ***g*** — gap: the minimum interval between consecutive message *sends* (or receives) by one processor; 1/g is that processor's sustained message rate.
- ***P*** — the number of processors.

The split matters because of what the CPU can do meanwhile: while *L* elapses the processor is *free*; while *o* elapses it is *not*. This is the formal answer to "can I overlap communication with computation?" — you can overlap the *L* part, never the *o* part. Gropp emphasizes a second consequence: matching-based message passing has an overhead that grows with the number of queued messages — the receiver must scan posted receives or a queue of unexpected messages — so *o* is not even constant; it degrades exactly in the communication patterns (many small messages, unpredictable ordering) where it hurts most.

**Measured magnitudes.** The classical data points:

- 2003 (SC'03 comparison of MPI over InfiniBand, Myrinet, Quadrics): raw InfiniBand verbs latency 6.9 µs; MPI on top of it 9.5 µs — roughly 2.6 µs of MPI-layer cost per message. Quadrics MPI reached 4.3 µs.
- 2008 (Argonne, Blue Gene/P study of "non-data" MPI overheads): the MPI stack added ~**1.1 µs** — about **1000 CPU cycles** on the 850 MHz PowerPC 450 — for pre- and post-data processing, on top of the underlying DCMF communication layer. The same study showed the cost of a receive *growing linearly with the receive-queue depth*, and request allocation/queueing turning a blocking send-receive into something measurably more expensive than raw data movement.
- 2013 (Cray SeaStar study, CUG): a thin proprietary communication layer (CCI) sustained over **1 million messages per second** from a single node — one message every 960 ns — a 6× improvement in injection rate over the generic stack, purely by removing software.

The pattern across two decades: link speeds multiplied a hundredfold; per-message software overhead shrank maybe 5–10×. Every generation, the software term becomes a *larger fraction* of small-message latency — which is why small-message latency has been stuck near the microsecond scale for years while bandwidth keeps doubling, and why message *aggregation* (fewer, larger messages) is the perennial optimization.

**Long messages: LogGP.** LogP was built for short messages, assuming long ones are just sequences of short ones spaced by *g*. But RDMA-capable NICs gave long messages their own, faster path — the CPU sets up one transfer and the NIC's DMA engines stream it. **LogGP** (Alexandrov et al., 1995; JPDC 1997) adds a fifth parameter ***G*, the gap per byte** for long messages, with 1/G the long-message bandwidth:

```
short:  T ≈ 2o + L
long:   T ≈ 2o + L + (m − 1)·G
```

Notice *G is Hockney's β*, and (2o + L) is Hockney's α decomposed into its CPU and wire parts. The two models converge for large *m*; LogGP simply carries more structure for small *m* and for overlap reasoning. The successors refine this: **pLogP** makes the parameters functions of message size and splits sender/receiver overhead (*o_s*, *o_r*); **LogGPO** adds the overhead that `MPI_Wait` itself introduces, which plain LogGP (assuming perfect overlap) systematically underestimates.

**GPU-era software overhead.** Nothing about GPUs repealed this topic; they complicated it. A 2025 characterization of AMD MI300A systems (arXiv 2508.11298) found MPI with *CPU staging* — the "naive" path through host memory — achieving *lower* small-message latency than direct GPU-to-GPU transfers, because requesting a transfer from the SDMA engines costs more than a CPU-side copy of a few kilobytes. The software overhead now includes device-side queue mechanics, and the "obviously better" direct path is only better above a size threshold. When we reach GPUDirect RDMA (DIST-7.5), the α of the fast path will be exactly this story at network scale.

### 1.4 Effective bandwidth versus link bandwidth (DIST-5.4)

**The problem.** Your cluster has "400 Gb/s per node." Your application moves 1 GB between two ranks and it takes 40 ms. That is 25 GB/s — half the line rate. Nothing is broken; this gap is systematic, and understanding its sources is the difference between reading spec sheets and reading systems.

**Definition.** Link (line) bandwidth *B_link* is the physical rate of the slowest physical link on the path. **Effective bandwidth** is useful application bytes delivered divided by elapsed time:

```
B_eff(m) = m / T(m) = B · m / (m + m½)
```

— the same hyperbola from DIST-5.1: it *approaches* B asymptotically and equals B/2 at m = m½. But the measured asymptote itself lands below B_link. The gap decomposes layer by layer:

**1. Encoding.** The wire carries framing bits that are not data: PCIe 3.0+ uses 128b/130b encoding (1.5% loss); 200G+ SerDes use PAM4 with forward error correction, with PCIe 6.0 targeting under 2% overhead. Line rate counts them; your application doesn't.

**2. Protocol headers.** Every packet carries headers around your payload: an IP+TCP stack spends 40 bytes per 1500-byte frame (~2.7%); jumbo frames (9000 B) cut this to ~0.4%; InfiniBand's link+transport headers (~20 B against 2–4 KB MTUs) cost under 1%. Small effect per packet, but it scales with packet count, not message size.

**3. Copies and staging.** Every intermediate buffer between the application and the wire costs bandwidth. Eager messages copy through internal buffers; host-staged GPU communication copies *twice* — GPU-to-host, then host-to-NIC — traversing the PCIe bus twice and running at the speed of a single-threaded memcpy (measured at ~11.7 GB/s on MI300A-class hardware — nowhere near any 400 Gb/s NIC).

**4. Directionality accounting.** As established in DIST-5.2: NIC rates are per direction; PCIe slot numbers are usually bidirectional sums. Comparing a "128 GB/s" Gen5 x16 against a "400 Gb/s = 50 GB/s" NIC is comparing 64 against 50 — the correct comparison, but only after dividing.

**5. One stream cannot fill a modern pipe.** A single TCP stream on a 100 Gb/s AWS network measured ~9.5 Gb/s — under 10% of line rate — while 72 concurrent pairs on the same hardware saturated it (~13 GB/s). The causes are per-stream limits everywhere: TCP congestion windows, single-core processing, one NIC queue pair. This is *the* motivation for the multi-pair `osu_mbw_mr` benchmark (Section 1.5). Even RDMA-based MPI and NCCL "are unable to saturate bandwidth with small messages" (measured on NDR-400 systems in a 2025 ICPP study) — the fixed per-operation costs of Section 1.3 dominate before the bytes can.

**6. Path collisions.** Even a perfect network can deliver a fraction of its bisection to your workload. Ethernet fabrics balance traffic by hashing each *flow* to a path (ECMP). Collective communication produces few, huge, *synchronized* flows — if two of them hash to the same uplink, they share it while a parallel uplink sits idle, and because the collective finishes when its slowest transfer finishes, the collision sets the time. A simple simulation — throw *n* equal flows uniformly onto *n* equal paths, take the hottest path's load — gives ~2.6× the mean load at n = 8 (≈39% utilization) and ~4× at n = 64 (≈25%). This is not a failure of the fabric; it is a load-balancing *design* (per-flow hashing) mismatched to the traffic pattern (few giant synchronized flows). It is the central argument in the Ultra Ethernet redesign discussed in Section 2, and the formal treatment is DIST-5.8 (bisection bandwidth) and DIST-8.7 (oversubscription).

**7. Measurement methodology.** Measured "bandwidth" is a property of the benchmark as much as the network. The OSU bandwidth test posts a *window* of W in-flight messages before waiting — larger windows raise measured bandwidth (amortizing per-message overhead) but also change what you are measuring; the HPC Advisory Council's tuning guides show the same HDR hardware measuring differently with core placement, NUMA BIOS settings, and window size. Report the methodology with the number.

**Putting numbers on it.** Representative measured efficiencies:

| System / path | Line rate | Measured | Efficiency |
|---|---|---|---|
| AWS C5n, 100 Gb/s, 1 TCP pair (osu_bw) | 12.5 GB/s | 1.18 GB/s | 9% |
| Same, 72 pairs (osu_mbw_mr) | 12.5 GB/s | ~13 GB/s | ~100% |
| EPYC Rome node pair, HDR IB, bidirectional (osu_bibw, W=512) | 50 GB/s (2×25) | 48.9 GB/s | 98% |

The contrast between rows 1–2 is the whole of DIST-5.5 in one experiment; row 3 shows that when the conditions are right (large messages, both directions, deep window, tuned placement), modern stacks genuinely reach ~98% of the physical rate — the losses in rows 1–2 are *system* properties, not physics.

### 1.5 Injection bandwidth (DIST-5.5)

**Definition.** Injection bandwidth is the rate at which a single *endpoint* — one process, one core, one NIC port, one GPU — can push new traffic into the fabric. Link bandwidth is a property of a *path*; injection bandwidth is a property of a *source*. Aggregate node bandwidth is limited by whichever is smaller:

```
B_node = min( k · B_inj ,  Σ B_rails )      for k concurrent injecting streams
```

**Why one stream is not enough.** A 400 Gb/s NIC moves 50 GB/s. A single CPU core issuing and servicing transfers sustains far less — bounded by its message rate (1/(o+g) messages per second, from LogP) times message size, and by its memcpy rate if staging. The AWS numbers above: one pair injected 1.18 GB/s; it took 72 pairs to reach line rate. In message-rate terms: the 72-pair configuration delivered ~18 million 1-byte messages per second in aggregate — roughly 250K messages/s per pair, i.e., ~4 µs of per-message work per core, exactly the (o + g) scale of Section 1.3. Injection bandwidth is LogP's *g* (and *G*) wearing an engineering name.

**How systems raise it.** Every technique is an attack on one term of the endpoint's serial path (CPU → memory bus → PCIe → NIC → fabric):

- **More injectors**: multiple processes, multiple cores placed NUMA-local to the NIC (the "1 per core" `osu_mbw_mr` configuration), multiple queue pairs. The LANL benchmark suite standardizes this as separate "one per NIC" vs "one per core" measurements — the difference *is* the node's injection scaling.
- **Deeper windows**: posting W in-flight messages pipelines the per-message overheads; the bandwidth benchmark methodology from Section 1.4 exists precisely to measure injection, not just links.
- **Offloading the injection**: with RDMA, the CPU pays *o* once per transfer and the *NIC's DMA engines* become the injectors — which is why RDMA raises single-pair bandwidth as well as lowering CPU load.
- **More rails**: multiple NICs per node (multi-rail), each feeding a parallel network — but only useful if the *internal* path (PCIe, socket interconnect) can feed them, which is the arithmetic below.

**The GPU version of the question.** In a GPU node, "who injects?" has four different answers: the CPU (staged memcpy — slowest, but paradoxically lowest *latency* for small messages per the MI300A study); the NIC's DMA engines (GPUDirect RDMA — the fast path we meet properly in DIST-7.5); the GPU's copy engines (NVLink-to-NVLink peer transfers); and, increasingly, GPU threads themselves (device-initiated communication, NVSHMEM — DIST-10.8). Injection bandwidth per GPU is then `min` over the whole chain from GPU HBM through every switch and link to the first fabric port.

**The arithmetic that reshaped endpoint design.** The endpoint's internal path must not be narrower than its network port, or you paid for bandwidth you cannot reach:

- PCIe Gen5 x16 = 64 GB/s per direction = **512 Gb/s** — enough for one 400 Gb/s NIC, *not* enough for two (800 Gb/s combined), and *not* enough for one 800 Gb/s NIC.
- A ConnectX-8-class 800 Gb/s NIC needs 100 GB/s per direction — beyond Gen5 x16, hence PCIe Gen6 and NIC-integrated PCIe switching in the newest reference designs (Section 2.2).
- Per-GPU NIC pairing (one NIC per GPU, eight per node) sidesteps the host entirely: each GPU gets its own rail, and the node's injection bandwidth is the *sum* over GPUs rather than the *share* of one socket link.

This is why "just add a faster NIC" fails so reliably: effective bandwidth is the minimum over every stage, and upgrading the last stage only moves the bottleneck left. Section 2.2 is a live example.

**Where this lands in the model.** With per-endpoint injection limit *B_inj* and per-path link bandwidth *B_link*:

```
B_eff(single pair)  = min( B_inj , B_link )
B_eff(k streams)    = min( k · B_inj , B_link )     (until the link saturates)
```

One compact table maps today's five topics onto the model parameters:

| Today's concept | Hockney | LogP/LogGP | System quantity |
|---|---|---|---|
| Startup (5.1) | α | 2o + L | measured small-message latency |
| Serialization (5.2) | mβ | (m−1)G | m / B_link |
| Software overhead (5.3) | inside α | o, g | CPU cycles; message rate 1/g |
| Effective bandwidth (5.4) | m/(α+mβ) | fitted asymptote | measured, methodology-dependent |
| Injection (5.5) | per-endpoint β | G, g per source | streams × per-stream rate |

Keep this table; Module 5 continues with contention, hop count, bisection bandwidth, and scaling effects (DIST-5.6–5.9), each of which adds one more column to it.

## 2. Key Developments / News

### 2.1 Ultra Ethernet 1.0: a specification-length argument about effective bandwidth

**What happened.** The Ultra Ethernet Consortium (UEC) — founded by Meta, Microsoft, Oracle, and now counting over a hundred members including AMD, Arista, Broadcom, Cisco, HPE, and Intel — published version 1.0 of its specification in June 2025, with point releases continuing since. Ultra Ethernet keeps standard Ethernet physical layers and IP routing, and replaces the transport with the **Ultra Ethernet Transport (UET)** aimed at 1k–100k-endpoint AI and HPC fabrics.

**What technically changed.** Four design decisions define UET. (1) **Packet spraying**: the packets of a single message are spread across *all* available paths, with an entropy value in the header letting unmodified switches distribute them per packet — replacing per-flow ECMP hashing. (2) **Relaxed delivery ordering**: since sprayed packets arrive out of order, the transport offers multiple delivery modes — reliable unordered delivery for bulk payloads, ordered delivery where MPI-style matching semantics require it — with a selective-ACK bitmap for loss detection, deliberately discarding the go-back-N semantics that RoCEv2 inherited from InfiniBand and that made reordering fatal. (3) **Packet trimming**: a congested switch, instead of dropping a packet, may truncate it to a small minimum size (on the order of 1/64 of the frame) and mark it, giving the receiver a near-immediate loss signal without waiting for a timeout. (4) **New congestion control (NSCC)**: sender-based and window-driven across *all* sprayed paths at once (a single congestion window tracking aggregate path capacity), derived from the published SMaRTT algorithm, with a receiver-driven mode as an alternative — and no dependence on a lossless PFC fabric, which becomes a backstop rather than the foundation. The stated performance goal is characteristically model-shaped: reach **full wire rate within one round-trip time** — an explicit attack on the α term, the startup cost of filling a fat pipe.

**Why it matters.** This is the first large-scale, multi-vendor attempt to give Ethernet InfiniBand-class semantics for collective-dominated traffic without the lossless-fabric fragility of RoCEv2. If UET-capable NICs and switches deliver, the HPC network market changes shape.

**Connection to today's concepts.** The entire specification is an engineering response to DIST-5.4. The ECMP collision analysis from Section 1.4 — a synchronized collective realizing only ~25–40% of a fat-tree's available bandwidth because giant flows hash onto the same links — is the founding argument of the packet-spraying design: spraying raises *effective* bandwidth toward *link* bandwidth by removing per-flow path collisions. NSCC's "full rate in one RTT" goal is the α-β model stated as a design requirement: minimize the startup region so that transfers spend their time in the β region. And the loss-detection redesign (SACK bitmaps, trimming) exists precisely because the *old* ordering assumptions were load-bearing for the old loss model — a clean example of how one performance decision (reordering for utilization) forces re-derivation of the whole protocol stack above it.

**What to watch.** UET-capable NICs and switches reaching the market and interoperating; how MPI and UCX map onto unordered vs ordered delivery modes (a matching-semantics question); first independent measurements of *effective* bisection bandwidth on UET fabrics versus the ~⅓ efficiency of ECMP-hashed baselines.

### 2.2 The 800 Gb/s endpoint: injection arithmetic in hardware

**What happened.** NVIDIA's current-generation networking pairs the **ConnectX-8 SuperNIC** — 800 Gb/s, supporting both XDR InfiniBand and 800G Ethernet, compliant with InfiniBand Architecture v1.7 — with Quantum-X800 InfiniBand and Spectrum-X Ethernet switches. In NVIDIA's HGX and NVL-class reference architectures, the design point is **one ConnectX-8 per GPU**: eight per HGX node, and in a GB300 NVL72 rack 72 NICs at 800 Gb/s each — an aggregate scale-out demand on the order of 57.6 Tbps per rack by vendor-referenced analyses.

**What technically changed.** Beyond the doubled line rate, the architectural move is *inside the endpoint*: ConnectX-8 integrates a PCIe switch (48-lane PCIe Gen6 class, per vendor and industry analyses), letting the GPU reach the NIC without transiting the host CPU's root complex. BlueField-4, announced for the Vera Rubin generation, continues the pattern at 800 Gb/s with a co-packaged next-generation NIC.

**Why it matters, in today's arithmetic.** Run the DIST-5.5 calculation: 800 Gb/s is 100 GB/s per direction. A PCIe Gen5 x16 host path delivers 64 GB/s per direction — *less* than the NIC can move. An endpoint built that way would have an effective bandwidth of 512 Gb/s no matter what the fabric did; the NIC would be idle a third of the time even at perfect network utilization. The Gen6 switch integration and per-GPU NIC pairing are direct answers: remove the host bus from the GPU→fabric path entirely, and give each GPU its own rail so node injection is a *sum* of independent paths rather than a *share* of one. This is the cleanest recent demonstration of the module's central lesson — effective bandwidth is a minimum over every stage of the endpoint, and the stage you forget is the one that limits you.

**What to watch.** Whether real applications realize proportional gains (the NIC upgrade only pays where the rest of the chain — GPU fabric, PCIe, software stack — was already the bottleneck); multi-NIC rail-aware software (DIST-9.10) maturing fast enough to actually stripe single transfers across 800G ports.

### 2.3 A 2025 performance model for intra-node GPU communication: Hockney's long career

**What happened.** A 2025 HPDC paper, *Accelerating Intra-Node GPU Communication: A Performance Model* (Sojoodi et al.), built an analytical model for **multipath intra-node GPU transfers** — data moving between GPUs across combinations of NVLink and PCIe — and used it to select communication paths inside a UCX-based MPI implementation (driving GPU-to-GPU transfers as one-sided PUT/GET operations). The model's terms: link bandwidth per path, and per-chunk pipeline overhead — the α-plus-β skeleton with a pipeline refinement, fitted to modern GPU interconnects.

**Why it matters.** The 2025 GPU node is the most communication-asymmetric machine HPC has ever mass-deployed — NVLink, PCIe peer access, host staging, multiple copy engines, several possible paths between any two GPUs — and the response of current research is not a simulator or a learned predictor but an *analytical two-term model with measured parameters*: choose the path the model says is fastest. The same paper notes, in passing, that Hockney's model remains the network model of SimGrid. The lineage runs unbroken: Paragon clusters (1994) → MPICH collective selection (2005) → HPL scaling analysis → GPU path selection (2025).

**Connection to today.** This is today's topic list applied: the model shape is DIST-5.1; the per-chunk overhead term is DIST-5.3's cost made explicit; multipath selection under a per-path bandwidth limit is DIST-5.5's `min` over stages. When the curriculum reaches GPUDirect RDMA and NCCL transport selection (Modules 7 and 9), the decision procedures there are built on exactly this kind of model — which is why Module 5 exists before them.

**What to watch.** Model-guided runtime path selection becoming standard in UCX/Open MPI; recalibration of these models on Blackwell/MI350-class topologies where NVLink switch counts and PCIe generations have moved again.
