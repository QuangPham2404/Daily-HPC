## 0. Concise Summary

Tuesday's volume (DIST-7.1→7.5) established the RDMA mechanism: verbs, queue pairs, memory registration, and GPUDirect RDMA, where the NIC's DMA engine reads and writes GPU memory through the PCIe BAR window. Today we finish Module 7 and open Module 8 by asking the questions a system architect actually faces: *where* the GPU and NIC sit relative to each other on PCIe (DIST-7.6), *which kernel machinery* lets a NIC legally touch GPU memory (DIST-7.7), *when* the direct path wins versus when host staging wins (DIST-7.8), and how the *control path* — not just the data path — is migrating from CPU to GPU (DIST-7.9). We then begin the hardware module with the anatomy of the network interface card itself (DIST-8.1), because every software decision above is ultimately a statement about NIC capabilities.

The unifying theme is that "GPUDirect RDMA works" is not a binary. The same software stack may run at 11 GB/s or at 250 MB/s depending on which PCIe hops separate the GPU from the NIC, and a topology-aware communication library must detect this and choose between the zero-copy fast path and a staged fallback. The mechanism-level picture: PCIe peer-to-peer transactions are only guaranteed to behave well through switches; crossing a CPU-internal root complex adds contention with host traffic; crossing a socket interconnect (QPI/UPI) is close to a cliff.

Three developments connect this to the current HPC world. First, a Koç University paper published this month ("GPU-Initiated Communication: Dissecting Down to the Bone") is the first rigorous public dissection of the GPU-initiated submission path — measuring the true cost of GPU threads posting work requests versus a tuned CPU proxy, with sobering findings about queue sharing. Second, NCCL 2.28's Device API with GPU-Initiated Networking (GIN) brings device-side communication into the dominant collective library. Third, the BlueField-4 DPU and ConnectX-9 SuperNIC — the latter now in general availability — change both the GPU↔NIC interface (PCIe Gen6) and the NIC's own internal architecture, directly reshaping everything in today's lesson.

By the end you should be able to look at `nvidia-smi topo -m` output on any node and predict, before running a single benchmark, which communication paths will be fast and which will be traps.

## 1. Learn the Concepts

### 1.1 Where we are: from mechanism to system

From DIST-7.3–7.5 you know the mechanics: to let a NIC touch GPU memory, the memory must be pinned, mapped into the GPU's BAR1 window, and registered with the NIC, yielding memory keys that appear inside RDMA work requests. That story was deliberately *local* — one GPU, one NIC, one queue pair. Today we zoom out to the system level. Four facts drive everything:

1. PCIe is a tree, and not all hops are equal.
2. GPU memory is not ordinary RAM — it sits behind a device driver that must explicitly participate in any external access.
3. The direct path is not always the fastest path end-to-end.
4. Even with a perfect data path, the *control* path (who posts work requests and rings doorbells) has its own costs.

### 1.2 DIST-7.6 — GPU↔NIC topology

**The problem.** GPUDirect RDMA is a PCIe peer-to-peer transaction: the NIC issues read/write transactions aimed at the GPU's BAR1 aperture instead of at DRAM. PCIe guarantees such transactions work *within* a hierarchy rooted at one root complex, but says nothing about performance when the path traverses a CPU's internal PCIe host interface or a socket-to-socket link. The NVIDIA GPUDirect RDMA documentation states the requirement plainly: the two devices must share the same upstream PCIe root complex, and it distinguishes three situations by what sits on the path:

- **PCIe switches only** — optimal; peer traffic never touches the CPU.
- **A single CPU/IOH (root complex) between them** — works, but the CPU's PCIe host logic is now an intermediary; in particular, *peer-to-peer read bandwidth* has historically been severely limited on some processor generations.
- **A socket interconnect (QPI/UPI) between two root complexes** — may be extremely performance-limited or not work reliably. This is effectively outside the "same root complex" contract.

**Why hops matter, mechanically.** A NIC read of host DRAM is the common case a CPU's PCIe interface is optimized for: posted writes and read completions flowing to memory controllers. A NIC read of a GPU is a peer transaction that the root complex must *route* toward another downstream port. Two mechanisms punish this. First, **transaction turnaround**: peer reads require the root complex to forward the read request down another port and hold state while waiting for the completion — the interface limits how many such transactions can be outstanding, so read bandwidth becomes latency-limited rather than bandwidth-limited. Second, **contention and ordering logic**: peer traffic competes with host memory traffic inside the root complex and, on multi-socket parts, must cross the coherent interconnect (QPI on the Ivy Bridge era, UPI today), whose protocol was designed for cache-line-granularity coherence traffic, not bulk DMA streaming.

**The canonical measurement.** NVIDIA's 2014 benchmark post ("Benchmarking GPUDirect RDMA on Modern Server Platforms") remains the clearest public quantification of these effects, and every number below is from it. On an Ivy Bridge dual-socket platform with ConnectX-3 FDR InfiniBand and a K40:

- **Host → GPU write** (NIC pushing into GPU memory): ~9.8 GB/s on dual rails, about 20% below the host-to-host ceiling of 12.3 GB/s — an architectural limit of the platform, not the link.
- **GPU → host read** (NIC fetching *from* GPU memory): only **3.4 GB/s**, rising to **3.7 GB/s** when the K40's application clock was boosted from 745 MHz to 875 MHz. The authors' diagnosis: the CPU-integrated PCIe host interface restricts the number of in-flight transactions, making read bandwidth latency-limited; boosting the GPU clock shortens the round trip of each completion and recovers ~10%. A clock-dependent network bandwidth is the signature of a latency-limited path.
- **Through a PCIe switch (PLX) instead**: host→GPU reached **11.6 GB/s** and GPU→GPU **7 GB/s**, approaching the PCIe Gen3 x16 practical peak of ~12 GB/s. The switch forwards peer transactions without involving the CPU at all.
- **Across the inter-socket QPI link**: when the transmitting NIC fetched data from a GPU hanging off the *other* socket, bandwidth fell to **~1.1 GB/s**; when the NIC *pushed* data to a GPU across QPI, it collapsed to **250 MB/s**. That is a 40× degradation from the switched configuration — not a tuning issue but a structural one.

The 2014 numbers are old, but the *taxonomy* is permanent, and you can reproduce the diagnosis on any modern node.

**Reading the topology of a real node.** Two commands tell you everything:

```text
$ lspci -t                 # PCI tree: who hangs off which switch/root port
$ nvidia-smi topo -m       # GPU×GPU and GPU×NIC affinity matrix
```

`nvidia-smi topo -m` prints a matrix whose entries — `NV#` (NVLink), `PIX` (same internal PCIe switch), `PXB` (multiple switches, same root complex), `NODE` (same host but multi-hop PCIe), `SYS` (across the socket interconnect, e.g. NVLink between sockets or UPI), `PHB` (same PCIe host bridge) — are precisely the fast-path/fallback inputs a communication library consumes. A NIC listed as `PIX` or `PXB` relative to a GPU is a GPUDirect candidate; `SYS` marks the QPI/UPI trap.

**How modern systems resolved this.** The 2014 pain came from a shared, badly-placed NIC. Modern GPU servers eliminate the problem by construction, and the DGX H100 is the textbook example: eight single-port ConnectX-7 InfiniBand adapters — **one dedicated 400 Gb/s NIC per GPU** — plus two dual-port ConnectX-7 for storage/management, hung off an interposer board connected to both CPU trays. Each GPU gets a full PCIe Gen5 x16 path (32 GB/s per direction) to its own NIC, so there is no shared-NIC arbitration and no cross-socket hop on the data path. This per-GPU NIC design is what makes *rail-optimized* fabrics possible: NIC *k* of every node connects to rail-*k* leaf switches, so GPU *k*↔GPU *k* traffic across the cluster stays on one plane end-to-end. The lesson of DIST-7.6 generalizes: **topology is a design input, not a runtime accident** — the fix for the QPI cliff was not software, it was attaching one NIC to every GPU.

### 1.3 DIST-7.7 — Peer memory and kernel/driver support

**The problem.** In DIST-7.3 you saw RDMA memory registration for *host* memory: the kernel pins user pages via `get_user_pages()`, and the NIC gets physical addresses plus a key. GPU memory breaks every step of that. It is not managed by the normal memory subsystem, its "physical addresses" from a PCIe device's point of view are BAR1 windows (from DIST-7.5), it belongs to a device driver (NVIDIA's) that owns the page tables, and pages can migrate or be freed asynchronously. No generic kernel API could pin it — someone had to teach the RDMA subsystem how to call into the GPU driver.

**The peer-memory client mechanism.** The InfiniBand core exports a *peer-memory client* interface: a kernel module can register itself as a provider of "foreign" memory that `ib_reg_mr` can then map. For NVIDIA GPUs this is the **`nvidia-peermem`** module, shipped inside the GPU driver package since the R470 branch (exposed in CUDA 11.4). Per the GPUDirect RDMA documentation, `nvidia-peermem` "registers the NVIDIA GPU with the InfiniBand subsystem by using peer-to-peer APIs provided by the NVIDIA GPU driver." When a userspace library calls `ibv_reg_mr()` on a GPU virtual address, the ib_core kernel layer invokes the peer-memory client, which calls the NVIDIA driver's kernel API (`nvidia_p2p_get_pages()`), receives a page table describing the BAR1 mapping, and hands the NIC a DMA-able view of GPU memory. Registration then proceeds exactly as for host memory — same memory keys, same work requests, same QPs.

The lineage matters for reading older documentation: the original out-of-tree module was Mellanox's `nv_peer_mem` (repo `Mellanox/nv_peer_memory`), and you will still see `lsmod | grep nv_peer_mem` in older runbooks. It was integrated into the GPU driver as `nvidia-peermem` and deprecated as a separate component from R470. Both names refer to the same function: making GPU memory look like pinnable peer memory to the RDMA stack. A hard prerequisite is kernel-side RDMA peer-memory support — historically via MLNX_OFED patches, now upstream.

**What the GPU driver actually provides.** `nvidia-peermem` is a thin shim; the real work happens in the NVIDIA driver's `nvidia_p2p_*` kernel API, which is also what a *third-party* device driver (non-Mellanox NIC, frame grabber, custom FPGA) would call directly to build its own GPUDirect path. The API surface and its constraints, from the official design documentation:

- `nvidia_p2p_get_pages(va, size, ...)` pins a 64KB-aligned GPU virtual range and returns a page table for programming DMA engines; `nvidia_p2p_put_pages()` unpins.
- The caller must register a **callback** that the NVIDIA driver invokes *synchronously* if it must revoke the mapping (e.g. the userspace process frees the buffer or exits). The callback must clean up outstanding DMA references and call `nvidia_p2p_free_page_table()`; it may block for milliseconds. This callback is the safety valve that keeps a NIC from DMA-ing into memory that has been reallocated.
- **BAR1 is the scarce resource.** Pinned GPU memory consumes BAR1 space in 64KB chunks; Kepler-class GPUs exposed as little as 256 MB (32 MB reserved). On data-center GPUs with large BARs (multi-GB, backed by "Resizable BAR" in BIOS), the constraint relaxes, but `nvidia-smi -q`'s "BAR1 Memory Usage" remains the first thing to check when GPUDirect registrations fail — DOCA documentation explicitly lists undersized BAR1 as a cause of mmap failures.
- **Pinning is expensive (up to milliseconds)**, which is why DIST-6.6's registration caches and the documented "lazy unpinning" strategy exist: keep regions pinned after use, evict LRU-style on BAR pressure.
- **IOMMUs must be disabled or in 1:1 pass-through**, because GPUDirect RDMA assumes all devices see the same physical addresses.
- **Memory ordering is the sharpest edge.** The documentation is explicit: only CPU-initiated CUDA APIs order GPUDirect RDMA operations as observed by the GPU. A kernel reading a buffer *while* the NIC is writing it is a data race — the kernel may see stale, partial, or out-of-order data. Buffers intended for RDMA should be flagged with `cuPointerSetAttribute(..., CU_POINTER_ATTRIBUTE_SYNC_MEMOPS, ...)`, which forces CUDA memory operations on that allocation to be synchronous with respect to the host. We return to this in DIST-7.9, because device-initiated communication had to *fix* this ordering gap.

**The current transition: DMA-BUF.** `nvidia-peermem` is now the *legacy* mapping mode. The modern path is the Linux kernel's own **DMA-BUF** mechanism: GPU memory is exported as a dma-buf file descriptor (via `cuMemGetHandleForAddressRange()` with `CU_MEM_RANGE_HANDLE_TYPE_DMA_BUF_FD`), and the RDMA stack registers it through `ibv_reg_dmabuf_mr()` — no out-of-tree peer-memory client involved. Prerequisites are recent: Linux kernel ≥ 6.2, libibverbs ≥ 1.14.44, and NVIDIA open kernel modules. NVIDIA's GPU Operator documentation now treats DMA-BUF as the default and `nvidia-peermem` as the opt-in legacy option, and the CUDA 13.0 changelog shows the older `nv-p2p` APIs being deprecated on Tegra platforms in favor of upstream kernel APIs. The architectural meaning: GPU memory registration is being standardized *into the kernel* rather than bolted on by vendor shims — which is exactly what a heterogeneous-memory future (GPUs, DPUs, CXL devices) needs.

### 1.4 DIST-7.8 — Fast path versus fallback path

**The problem.** Given a buffer that lives in GPU memory and a NIC, a communication library faces a decision every send: use the direct GPUDirect path, or stage the data through host memory? The wrong choice can cost an order of magnitude. This topic is the *reasoning framework* — and it is exactly the logic implemented inside UCX, Open MPI's default GPU transport layer.

**When the direct (fast) path is available.** All of the following must hold, and each failure has a specific fallback:

1. **Memory is registered and mappable** — `nvidia-peermem` or DMA-BUF loaded, BAR1 space available, buffer pinned (DIST-7.7). If not: staging.
2. **Topology is sane** — GPU and NIC share a root complex without a socket hop (`PIX`/`PXB`, not `SYS`) (DIST-7.6). If not: staging may beat a 250 MB/s peer path.
3. **The message is large enough** — direct RDMA pays registration and doorbell costs that are amortized by bandwidth; for a few bytes, the fixed costs dominate.
4. **The memory type cooperates** — CUDA *managed* (migratable) memory must be staged: UCX explicitly disabled RDMA zero-copy for managed buffers because pages can migrate between host and GPU mid-flight and the NIC's registration would go stale — a correctness issue, not a performance one.

**The fallback machinery, concretely.** UCX implements GPU staging as a multi-stage rendezvous pipeline (its "3-stage rndv"): (1) DMA/copy the data from the sending GPU buffer into a *pinned host staging buffer*, (2) RDMA-write from that buffer across the network into a pinned staging buffer on the receiver, (3) copy from the staging buffer into the receiving GPU buffer. The staging buffers are pre-registered once, so the per-message cost is two extra PCIe copies — the exact copies GPUDirect RDMA was invented to remove, now re-introduced deliberately because the direct path is worse or impossible.

**When staging actually wins.** Three regimes, in order of practical importance:

- **Broken/suboptimal topology.** Against the QPI/UPI cliff, two well-placed PCIe copies at 10+ GB/s each crush a 250 MB/s peer path. The UCX pull request that introduced the 3-stage pipeline lists "GPUDirectRDMA transfers are inefficient if GPU and NIC are in different PCIe topology" as a design motivation.
- **Small messages.** For latency-bound small transfers, the relevant comparison is fixed cost vs fixed cost. UCX's `gdr_copy` path — which maps GPU memory to the host via GDRCopy so the CPU can write into it directly — reduces short-message host→device latency from ~8.6 μs to ~3 μs in UCF Consortium measurements, precisely because it removes one staging copy while keeping the cheap control path. Note the inversion: for small messages the *library* wants CPU involvement (cheap, low-latency), and for large messages it wants the NIC (bandwidth).
- **Unregisterable memory.** Managed memory, or buffers allocated through paths the NIC cannot map.

**How libraries encode this.** The selection is a per-transfer decision driven by capability queries (is the pointer a device pointer? is registration possible?), topology queries (the DIST-7.6 matrix), and message-size thresholds (rendezvous protocols switch at tunable fragment sizes — UCX exposes `UCX_RNDV_FRAG_SIZE` with separate host/GPU defaults). Nothing here is heuristic magic; it is the systematic enumeration of "which preconditions for the fast path failed, and what is the cheapest alternative."

**The same decision in modern device-initiated stacks.** NCCL's GIN (Section 2.2) bakes this exact fork into its plugin architecture: a *GDAKI* backend where GPU threads drive the NIC directly, and a *Proxy* backend where device-side calls are relayed to a CPU thread over lock-free queues when the hardware or configuration does not support the direct path. Fast path versus fallback is not a one-time software choice — it is a runtime property, re-evaluated per system, and today's third development (Section 2.1) shows even a *tuned CPU proxy* can beat the "fast" GPU path under specific conditions.

### 1.5 DIST-7.9 — GPUDirect Async and evolving direct-communication models

**The problem.** Everything so far optimized the *data path*. Look again at a GPUDirect RDMA send from the perspective of *who does work*: the NIC moves the bytes, but a **CPU thread** still (1) waits for the GPU kernel producing the data to finish, (2) builds the work request (WQE), (3) rings the NIC doorbell, (4) later polls the completion queue. For a CUDA-aware MPI program this forces `cudaStreamSynchronize()` before `MPI_Send` — the CPU is the coordinator, and every communication is a kernel-launch boundary. The GPUDirect Async family, introduced at SC 2015 and in CUDA 8.0, attacks exactly this: moving the *control path* to the GPU. The original paper (Hamidouche et al., JPDC 2017 — "GPUDirect Async: Exploring GPU synchronous communication techniques for InfiniBand clusters") framed it cleanly: P2P and RDMA optimized data movement; Async offloads *control*.

**Two models, then a third.** The original Async specification defined:

- **Stream Asynchronous (SA)**: communication is issued from CUDA streams — asynchronous with respect to the host, synchronous within the stream. The NIC operation becomes a stream item the GPU can order against kernels.
- **Kernel-Initiated (KI)**: threads *inside a running CUDA kernel* trigger and synchronize network operations. This is the radical one — no kernel boundary at all.

The research-community summary that matters: SA/KI still required the CPU to have pre-registered resources, so "the GPU can only initiate messages previously registered by the CPU" — control was moved, but not *transferred*. The complete transfer arrived with **IBGDA** (InfiniBand GPUDirect Async), NVSHMEM's transport since v2.7.0, built with Mellanox on new experimental OFED verbs (the `ibv_gpu` family). In IBGDA the GPU submission path is fully self-sufficient:

1. A CUDA thread constructs a WQE **in GPU memory** (the queue lives in device memory, registered with the NIC).
2. The thread rings the NIC **doorbell** by writing to the NIC's user-access region, which is mapped so the GPU can reach it over PCIe.
3. The NIC — which can DMA from GPU memory thanks to GPUDirect RDMA — fetches the WQE and executes it; completions land in a completion queue that GPU threads poll.

No CPU instruction executes anywhere in the loop. The measured consequences, from NVIDIA's NVSHMEM/IBGDA technical post: for sub-1 KiB block-put operations, throughput up to **9.5×** higher than the proxy path; put rates reaching **180 million operations/s**, approaching the ConnectX-6's ~215 MOPS message-rate ceiling; and with automatic coalescing of warp-contiguous puts, effective operation rates approaching 2000 MOPS because many logical operations share one NIC message. The proxy path was the bottleneck it removed: one CPU thread serially replaying device-side calls cannot scale with the number of issuing CUDA blocks.

**The memory-ordering debt.** DIST-7.7's warning — a GPU kernel racing a concurrent NIC write is a data race — becomes acute when the *same kernel* that computes also receives. DOCA GPUNetIO documents the fix: for **pre-Hopper** GPUs, receivers must run a memory-consistency algorithm (polling a trailing flag/last-packet marker before consuming payload), while Hopper added hardware ordering of incoming PCIe writes (the `CUGPUDirectRDMAWritesOrdering` device attribute) that relaxes this requirement. This is a beautiful example of hardware and software co-evolving: the software model exposed the ordering gap; the architecture fixed it.

**Where the model stands now.** DOCA GPUNetIO is the productized layer: device functions (`doca_gpu_dev_eth_txq_*`, verbs equivalents) let CUDA kernels prepare WQEs and ring doorbells directly (`doca_gpu_dev_eth_txq_ring_db`) or hand them to a CPU proxy handler, plus GPU-visible semaphores for kernel-to-kernel signaling. NCCL 2.28's GIN (Section 2.2) rides on it. The trajectory across ten years is coherent: **data path to the NIC (2013), control path to the GPU (2015→2022), integration into mainstream collectives (2025)** — with the fallback proxy kept permanently alongside, per DIST-7.8's logic.

### 1.6 DIST-8.1 — Network Interface Cards

Module 8 opens with the device all of the above presumes. A modern HPC NIC is best understood as a **specialized, programmable DMA-and-protocol processor** with a PCIe front end, a fabric front end, and a queue-based programming model. Its anatomy:

**PCIe front end.** The host (or GPU) interface: lane count and generation set the ceiling on everything. PCIe Gen4 x16 ≈ 32 GB/s, Gen5 x16 ≈ 64 GB/s bidirectional, Gen6 doubles again — the ConnectX-9 in Section 2.3 is among the first NICs with a Gen6 x16 host interface, sized so the host link never bottlenecks its 800 Gb/s (100 GB/s) ports. The NIC's BARs expose its registers — including the doorbell regions — for user-space mapping (kernel bypass, DIST-7.1).

**Queues and the submission model.** Send and receive work queues (in InfiniBand terms, the SQ/RQ of a queue pair, DIST-7.2) are descriptor rings in *host* (or, with GPUDirect Async, *GPU*) memory. Software posts work requests, rings a doorbell (a write to a mapped register), and the NIC's DMA engines fetch descriptors and payloads by DMA. Completions are written to completion queues as CQEs that software polls or receives via interrupts/events. This is why message *rate* is a first-class NIC spec alongside bandwidth: each message costs at least one descriptor fetch, one doorbell, and one completion — the 215 MOPS (ConnectX-6) and 260 M msg/s (ConnectX-7-class platform in Section 2.1) ceilings are queue-and-doorbell mechanics, not wire speed. Standard tools to probe exactly this: `ib_write_bw`, `ib_send_lat`, `ibv_ud_pingpong` from the perftest suite.

**Fabric front end and link speeds.** Ports (InfiniBand/Ethernet "VPI" on NVIDIA adapters), SerDes rates (e.g., 200G PAM4 SerDes on ConnectX-9), and per-port speed (100/200/400/800 G) define the wire side. An 8-port 400G Quantum-2 switch or a 64-port 800G switch is a different beast from a NIC, but the *endpoint* bandwidth you can inject is fixed at the NIC port.

**DMA engines.** Multiple engines handle inbound/outbound copies, RDMA reads/writes, and (on BlueField-class devices) general-purpose DMA that other devices — including GPUs, via GPUDirect Async — can command.

**Offload capabilities** — the NIC's "processor" nature, in increasing order of ambition:

- *Packet-level*: checksum offload, TSO/LRO, VLAN/VXLAN processing.
- *Transport-level*: the RDMA transport itself — reliable connections, retransmission, pacing, congestion control (the RoCE/IB CC machinery) executed in hardware. This is the offload that makes kernel bypass safe.
- *Collective-level*: SHARP — reductions performed *inside the switches*; the NIC participates by tagging/aggregating multicast traffic, turning all-reduce traffic from O(N) per-node bytes toward O(1). NVLink SHARP and "multimem" instructions are the intra-node analogue.
- *Programmable*: BlueField-class DPUs run a full ARM SoC (BlueField-4: 64 Neoverse V2 cores, 128 GB LPDDR5x, a 16-core/256-thread DOCA-programmable data-path accelerator) — a NIC that is a computer, able to host storage, security, and even application services off the host's critical path.

**Why this matters for everything above.** Every topic in Module 7 was secretly a NIC-capability story: topology (DIST-7.6) constrains the NIC's DMA reach; peer memory (DIST-7.7) is what lets its DMA engines see GPU RAM; fast-vs-fallback (DIST-7.8) is a cost model over NIC mechanics; GPUDirect Async (DIST-7.9) is the NIC's queue model extended to a second processor. When Section 2.3 describes a SuperNIC, read it as: the same anatomy, pushed until the NIC is a co-processor of the GPU.

## 2. Key Developments / News

### 2.1 "GPU-Initiated Communication: Dissecting Down to the Bone" — the first rigorous measurement of the GPU submission path (Koç University, October 2026)

**What happened.** A Koç University group (Baydamirli, Ismayilov, Oktay, Unat) published arXiv:2610.01380 on October 1, 2026, a measurement study of GPU-initiated communication at the GPU–NIC boundary — the mechanism from DIST-7.9 — across NVIDIA H100, H200, B200, and GB200 platforms with ConnectX-7-class InfiniBand. To separate hardware cost from library cost, they built *mini-gda* and *mini-proxy*, minimal transports implementing only the GPU-submission and CPU-proxy paths, and measured them alongside NVSHMEM (IBGDA), NCCL GIN, DeepEP, UCCL-EP, MSCCL++, and fabric-lib.

**What was demonstrated.** The bare hardware path is fast: a minimal GPU-side submission issues an operation in **0.7 μs** and completes it in **4.0 μs**. But production libraries add **up to 4.6 μs** of issue time through queue management, memory-ordering fences, and completion-scope bookkeeping — meaning library overhead can dwarf the mechanism itself. Two findings reframe DIST-7.8's fast-path logic. First, *a tuned CPU proxy matches or beats the GPU-initiated path on an idle machine* — the GPU path's advantage appears under load and contention, not statically; it costs a dedicated core whose operating state (C-states, frequency) sets its latency. Second, the costs are *structural*: sharing one queue with bulk traffic raises small-message latency by **one to three orders of magnitude**; reaching the platform's 260 M msg/s ceiling requires doorbell batching and queue parallelism; communication code resident in a kernel reduces GPU block occupancy even when unused; and all-to-all traffic loses 59% of NIC message rate at ~3,000 active connections.

**Why it matters and what to watch.** This is the study the MoE-training world needed: DeepEP and NCCL GIN performance is now dominated by exactly these queue-management and ordering choices, not by the doorbell mechanism itself. For your own reasoning: "GPU-initiated is faster" is a hypothesis to be tested per workload, not a law — and the paper's submission-path-vs-end-to-end distinction is the DIST-7.8 cost model made empirical. Watch for NIC-side queue scalability improvements (the 3,000-connection cliff) in next-generation firmware.

### 2.2 NCCL 2.28 Device API with GPU-Initiated Networking (GIN): device-side collectives reach the mainstream (NVIDIA, November 2025)

**What happened.** NVIDIA published arXiv:2511.15076 ("GPU-Initiated Networking for NCCL") describing the Device API introduced in NCCL 2.28, with three operation modes: **LSA** (load/store-accessible, for NVLink/PCIe), **Multimem** (NVLink SHARP in-fabric reduction instructions), and **GIN** (network RDMA).

**What technically changed.** GIN is a three-layer architecture: host-side NCCL Core APIs that set up *device communicators* and register *collective memory windows*; device-side APIs — remote put/get/atomic operations callable from inside CUDA kernels; and a plugin layer with the dual semantics of DIST-7.8: a **GDAKI backend** (GPU threads drive the NIC via DOCA GPUNetIO, the DIST-7.9 mechanism) and a **Proxy backend** (lock-free GPU→CPU queues over standard RDMA) for hardware where the direct path is unavailable. The demonstrated integration is DeepEP, the Mixture-of-Experts communication library — the workload class whose fine-grained all-to-all dispatch/combine traffic is precisely what kernel-initiated communication was built for. In their two-H100 benchmarks (4–128 B messages), GIN GDAKI round-trip latency is 16.7 μs — already comparable to NVSHMEM's CPU-proxy IBRC at 16.0 μs, with NVSHMEM IBGDA at 24.3 μs (consistent with 2.1's finding that library overhead, not mechanism, dominates).

**Why it matters.** NCCL is the default communication library of the AI ecosystem; absorbing device-initiated communication into it moves GPUDirect Async from a research/PGAS-library feature to default infrastructure. The curriculum connection is direct: LSA/Multimem/GIN is a per-transport instantiation of the fast-path/fallback decision (DIST-7.8), and GDAKI is the productized IBGDA path (DIST-7.9). Watch: whether HPC MPI stacks adopt the same device-API pattern, and whether the Proxy backend becomes a permanent production mode rather than a compatibility shim.

### 2.3 BlueField-4 and ConnectX-9: 800 Gb/s, PCIe Gen6, and the NIC-as-computer (announced at GTC Washington D.C.; ConnectX-9 firmware GA February 2026; BlueField-4 early availability with Vera Rubin platforms in 2026)

**What happened.** At GTC Washington D.C., NVIDIA revealed the BlueField-4 DPU and ConnectX-9 SuperNIC. ConnectX-9 firmware reached general availability in February 2026 (v82.48.1000), with the current release line at v82.50.1002. BlueField-4 enters early availability as part of Vera Rubin platforms in 2026.

**What technically changed.** ConnectX-9 delivers up to **800 Gb/s per port** over InfiniBand and Ethernet (200G SerDes, up to 8 split ports) and, per NVIDIA's firmware documentation, "drives up to 1.6 Tb/s of throughput to Rubin GPUs" — dual-port aggregate matched to one Rubin-class GPU's scale-out needs — with programmable I/O and hardware congestion control, integrated with Spectrum-X Ethernet and Quantum-X800 InfiniBand. Its host interface is **PCIe Gen6 x16**, which matters beyond speed: per DIST-7.6, the GPU↔NIC link is the resource GPUDirect performance is bounded by, and Gen6 is the first generation with the bandwidth headroom for 800G ports plus peer traffic. BlueField-4 integrates a **Grace CPU (64× Arm Neoverse V2)** with up to 128 GB LPDDR5x, a DOCA-programmable 16-core/256-thread data-path accelerator, 800 Gb/s networking, and the ASTRA security architecture — NVIDIA claims 6× the compute of BlueField-3 and support for AI factories 4× larger.

**Why it matters.** This is DIST-8.1's anatomy rendered in a product: the "NIC" is now a Grace-based computer whose queues a GPU can program directly (DIST-7.9), whose DMA engines reach GPU memory (DIST-7.7), and whose host link finally has slack for peer-to-peer traffic (DIST-7.6). The one-NIC-per-GPU discipline continues (1.6 Tb/s per Rubin GPU), and the trend to watch is the NIC and GPU converging into one co-programmed unit — the endpoint of the whole GPUDirect trajectory.
