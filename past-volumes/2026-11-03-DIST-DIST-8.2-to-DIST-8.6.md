## 0. Concise Summary

Yesterday's topic (DIST-8.1) ended at the network interface card — the point where a node hands packets to the fabric. Today we cross that boundary and study the fabric itself: the switches, the protocols that run on them, the topologies that wire them together, and the routing intelligence that keeps them from collapsing under congestion.

The lesson builds in one chain. **HPC switches** (DIST-8.2) are high-radix, cut-through, credit-flow-controlled crossbars whose job is to move packets between ports with nanosecond-scale arbitration. **InfiniBand** (DIST-8.3) is the canonical HPC fabric built from such switches: a subnet managed by a subnet manager, with per-virtual-lane credit-based flow control that makes the fabric lossless, and an RDMA transport offloaded into the HCA. **Ethernet for HPC** (DIST-8.4) asks a harder question: can the commodity ecosystem reach the same properties? RoCEv2 gets RDMA onto Ethernet but needs Priority-based Flow Control (PFC) to avoid drops, and PFC introduces head-of-line blocking and congestion spreading — problems that DCQCN, HPE Slingshot, and now the Ultra Ethernet specification attack head-on. **Network topology** (DIST-8.5) determines what the fabric can physically deliver: fat trees/Clos networks buy full bisection bandwidth at high cost, dragonflies cut the number of expensive optical global links, and toruses serve stencil locality cheaply. Finally, **adaptive routing** (DIST-8.6) is the software/mechanism layer that lets a fabric dodge its own congestion by choosing among the multiple paths a rich topology provides — packet-by-packet in InfiniBand and Slingshot switches.

The two developments this issue sit exactly on this chain: the **Ultra Ethernet Consortium's 1.1 specification** (released October 12, 2026), which extends the open Ethernet-for-AI/HPC stack with in-network collectives and richer congestion signaling; and **NVIDIA's Quantum-X800 co-packaged-optics InfiniBand switches entering large-scale deployment** (Lambda's 10,000+ GPU AI factory announced at GTC 2026), which attacks the power and reliability cost of the optical layers that fat-tree fabrics depend on.

Why this matters: in a multi-GPU cluster, the network is a first-class compute component. HPL's panel broadcasts, HPL-MxP/NCCL all-reduces, and every distributed training step live or die by bisection bandwidth, latency, and congestion behavior — all properties set by the fabric decisions covered today.

## 1. Learn the Concepts

### 1.1 HPC switches (DIST-8.2)

**Problem.** A cluster with thousands of endpoints needs a way for *any* node to reach *any* node at nearly full link speed, simultaneously with thousands of other such conversations. A single switch cannot have 10,000 ports, so the fabric must be built from many switches — and those switches must forward packets at line rate with queueing delay measured in nanoseconds, not the microseconds-tolerant world of enterprise Ethernet.

**Core mechanism.** An HPC switch is a crossbar surrounded by buffers and arbiters:

```
        input ports            crossbar             output ports
   ──▶ [buffer][arb]──┐   ┌───────────────┐   ┌──[arb][buffer] ──▶
   ──▶ [buffer][arb]──┼──▶│  N × N        │──▶┼──[arb][buffer] ──▶
   ──▶ [buffer][arb]──┘   │  crossbar     │   └──[arb][buffer] ──▶
                          └───────────────┘
```

- **Crossbar**: an N×N switching matrix that can connect any input to any output simultaneously. Its cost grows as O(N²), which is why port counts ("radix") per chip are bounded (tens to ~144 today).
- **Buffering**: if two packets target the same output port in the same cycle, one must wait. Switches use input queueing, output queueing, or combined input/output queueing with virtual output queues (VOQs) — a per-destination queue at each input that prevents one blocked packet from stalling packets headed elsewhere.
- **Arbitration**: a scheduler decides which buffered packets may cross the crossbar each cycle, under quality-of-service rules (weighted round-robin over priorities, in InfiniBand's case over virtual lanes).
- **Flow control between hops**: to avoid dropping packets when an output buffer fills, each link runs credit-based flow control — the downstream side grants upstream transmit "credits" per virtual lane, and an upstream port with no credits must stop. This is the mechanism that makes lossless fabrics lossless, and we will meet it again as a defining property of InfiniBand.

**Cut-through vs. store-and-forward.** A store-and-forward switch receives a whole packet, verifies it, then forwards it — simple, but latency scales with packet size. A cut-through switch begins forwarding as soon as the header identifies the output port, typically before the payload arrives. InfiniBand switches are cut-through, which is a large part of why switch-only latency is on the order of 100–200 nanoseconds and end-to-end RDMA latency lands under 3 microseconds, while typical Ethernet stacks run several times higher (per Mellanox/NVIDIA's published comparisons).

**Radix is the key design variable.** For a fixed total bandwidth, a switch can be built with few wide ports or many narrow ports. High-radix designs (many ports) are preferred for large systems because a network's diameter — the number of switch hops between distant nodes — falls as radix rises, cutting latency and serialization costs. The commercial frontier keeps climbing: NVIDIA's Quantum-2 switch silicon provides 64 ports at 400 Gb/s (NDR); the Quantum-X800 generation provides 144 ports at 800 Gb/s for 115.2 Tb/s of non-blocking throughput in one chassis; HPE's Rosetta (Slingshot) provides 64 ports at 200 Gb/s per direction (25.6 Tb/s bidirectional).

**In-network computing.** Modern HPC switch ASICs are not pure forwarding engines. NVIDIA's Quantum-3 generation embeds SHARP (Scalable Hierarchical Aggregation and Reduction Protocol) engines that perform reductions *inside* the switch as data transits, so an all-reduce's data crosses the fabric once instead of twice. This is a preview of DIST-8.9 (network offload); the architectural point today is that the switch has become an active participant in collective algorithms, not just wires.

**Trade-offs.** Bigger buffers absorb bursts but add latency and power. Higher radix reduces hop count but pushes switches toward a single-die or multi-die packaging limit (Quantum-X800's 144 ports run 200 Gb/s SerDes per lane). And, crucially for the next two topics, everything a switch does — credit flow control, virtual lanes, arbitration, cut-through forwarding — is defined by the fabric's link-layer protocol: InfiniBand or Ethernet.

### 1.2 InfiniBand (DIST-8.3)

**Problem.** By the late 1990s, HPC nodes had outgrown shared buses and enterprise networks: the cluster interconnect needed microsecond-scale latency, lossless delivery, and an RDMA programming model with no kernel in the data path. The InfiniBand Trade Association (founded 1999 by Intel, IBM, HP, Sun, Compaq, Dell, Microsoft) specified such a fabric from the physical layer up.

**Architecture: subnets, HCAs, switches, and the subnet manager.** An InfiniBand **subnet** is a set of endpoints (HCAs — host channel adapters, the InfiniBand NICs from DIST-8.1) and switches under one logical management domain. Every port gets a 16-bit **local identifier (LID)** assigned by the **subnet manager (SM)**, a software entity that discovers the fabric, computes routing tables (linear forwarding tables, LFTs, loaded into every switch), and distributes them. There is no distributed routing protocol — routing is centrally computed and statically installed, which is deterministic and fast but means route quality is only as good as the SM's routing engine (fat-tree, up-down, min-hop engines; this becomes important in §1.5 and §1.6). Subnets interconnect through routers using global identifiers (GIDs, IPv6-format addresses) and GRH headers.

**Link layer: virtual lanes and credit-based flow control.** An InfiniBand packet's local routing header carries a 4-bit **service level (SL)**. Switches map SLs to **virtual lanes (VLs)** — independent transmit/receive buffer sets per port with their own flow-control credits. The specification allows 16 VLs (15 data + 1 management, VL15, which is exempt from flow control); typical switch implementations expose 8. Because credits are granted **per VL**, a congested VL stalls only itself: traffic with guaranteed QoS on other lanes keeps flowing over the same physical link. This is the architectural answer to head-of-line blocking at the link level, and credit units are small — 64 bytes — so the granularity is fine.

This credit discipline is what makes InfiniBand **lossless**: a switch never drops a packet due to buffer overflow, because it only transmits when the downstream port has advertised buffer space. (Packets are dropped only on component failure.) The price is that circular credit dependencies — "credit loops" — can deadlock a fabric; avoiding them is a routing-engine constraint we will revisit in the topology section.

**Transport: RC, UC, UD, and RDMA verbs.** Above the link layer, InfiniBand offers transport services: **reliable connection (RC)** — dedicated queue pairs with acknowledgment, retransmission, and in-order delivery; **unreliable connection (UC)**; and **unreliable datagram (UD)**. RC QPs do per-packet sequencing and go-back-N-style recovery in hardware. All of this is exposed to applications through **verbs** (queue pairs, work requests, completion queues — the same interface that GPUDirect RDMA builds on from Theme 7), with the kernel bypassed for data movement. This is why an RDMA write costs ~1–2 μs end-to-end: no copies, no syscalls, no kernel scheduling on the critical path.

**Link speeds.** InfiniBand lanes have scaled from 2.5 Gb/s (SDR, ~2003) to 200 Gb/s per lane in the current XDR generation, with 4×-wide links as the standard module width:

| Generation | 4× link bandwidth | Era |
|---|---|---|
| SDR | 10 Gb/s | 2003 |
| DDR | 20 Gb/s | 2005 |
| QDR | 40 Gb/s | 2008 |
| FDR | 56 Gb/s | 2011 |
| EDR | 100 Gb/s | 2014 |
| HDR | 200 Gb/s | 2017 |
| NDR | 400 Gb/s | 2021 |
| XDR | 800 Gb/s | 2023– |

**Why it dominates HPC.** Lossless credit-controlled links, sub-3 μs RDMA latency, kernel bypass, centralized deterministic routing, and — with SHARP — in-network collectives, all specified and interoperable. InfiniBand and enhanced-Ethernet fabrics together dominate the top of the TOP500; InfiniBand remains the reference point every alternative is measured against.

**Trade-offs.** It is a niche ecosystem (one dominant silicon vendor), more expensive per port than commodity Ethernet, and its scaling story (subnet size, routing engine quality, SM failover) requires operational care. That tension — performance versus ecosystem economics — is precisely what drives the next topic.

### 1.3 Ethernet for HPC (DIST-8.4)

**Problem.** Ethernet won the world: the chips, cables, optics, and switch ecosystems are enormous and cheap. But stock Ethernet plus TCP/IP is a poor HPC fabric: kernel-resident TCP adds latency and CPU overhead, copies data, and treats packet loss as normal. HPC wants RDMA semantics — which assume a lossless network — on top of commodity Ethernet.

**RoCE v1/v2.** RDMA over Converged Ethernet (RoCE) puts InfiniBand-style RDMA transport (queue pairs, verbs) directly on Ethernet frames. RoCEv2 adds a UDP/IP header beneath the InfiniBand-format transport header, making RDMA traffic routable across L3 data center networks. RoCEv2 inherits the RoCE standard's congestion-control hooks (ECN marking), but the transport itself assumes packet loss is *rare*: with go-back-N recovery (as in the classic ConnectX implementations), throughput collapses once loss exceeds roughly 0.1% — so the fabric must be made effectively lossless.

**PFC: losslessness by force.** The IEEE 802.1Qbb Priority Flow Control mechanism lets a switch whose ingress queue for a given (port, priority) is near overflow send a PAUSE frame upstream, silencing that priority class on that link until a RESUME. Up to eight priority classes exist. PFC works — drops from buffer overflow mostly disappear — but it is a blunt instrument:

- **Head-of-line blocking**: the pause applies to a whole port/priority, not to the offending flow. Innocent flows sharing the paused link stop too.
- **Congestion spreading**: one downstream bottleneck cascades PAUSEs hop by hop upstream until senders far away are frozen — a congestion *tree* growing backwards through the fabric.
- **Deadlock risk**: PAUSE-induced circular buffer dependencies can, in pathological routing situations, deadlock the fabric.

These are not theoretical: Microsoft's DCQCN paper (SIGCOMM 2015) documents all three from production datacenters.

**DCQCN: congestion control on top of PFC.** DCQCN (Data Center QCN) is an end-host, rate-based congestion control for RoCEv2: switches mark packets with ECN when queues cross a threshold; receivers echo the signal back (CNPs); NIC senders cut their rates and ramp back up. Deployed in Mellanox NICs across Microsoft's datacenters, it dramatically improved throughput and fairness — but it *complements* PFC rather than replacing it, because flows start at line rate and bursts can overflow buffers faster than a round trip of control feedback.

**Vendor-specific enhanced Ethernet: Slingshot and Spectrum-X.** HPE Slingshot takes a different route: standard Ethernet signaling at the edge (100/200 Gb/s ports), but a Slingshot-specific link layer *between* Rosetta switches — link-layer retransmission instead of PFC-style pause trees, packet-by-packet adaptive routing, and a hardware congestion-control scheme that tracks every in-flight flow and throttles only congestion contributors (details in §1.6). NVIDIA's Spectrum-X similarly adds adaptive routing and telemetry-based congestion control to Ethernet switching paired with SuperNICs. The pattern is clear: to make Ethernet HPC-grade, vendors modify the fabric's behavior while keeping Ethernet's physical layer and (mostly) its ecosystem.

**Ultra Ethernet: standardizing the fix.** The Ultra Ethernet Consortium (founded 2023 by AMD, Arista, Broadcom, Cisco, Eviden, HPE, Intel, Meta, Microsoft; now 100+ members) published its 1.0 specification in June 2025 and 1.1 in October 2026. Ultra Ethernet deliberately *abandons* the lossless-network assumption: its Ultra Ethernet Transport (UET) is a new transport designed for microsecond RTTs, line-rate startup (no TCP-style slow start), sender-based windowing with ECN/RTT telemetry, optional packet trimming under congestion, and multipath-friendly delivery that tolerates (and can exploit) reordering. Switch requirements are intentionally minimal — ECMP plus basic ECN — so existing Ethernet fabrics can carry UET traffic. The 1.1 additions (scale-up profiles, in-network collectives, congestion signaling, programmable congestion management) are this issue's first key development (§2.1).

**Trade-offs.** Ethernet-for-HPC trades fabric complexity for economics. RoCEv2+PFC gives you InfiniBand-ish performance on commodity parts but with well-documented failure modes; enhanced-Ethernet fabrics fix the mechanisms but are proprietary per vendor; Ultra Ethernet aims to standardize the fixes but its hardware ecosystem is still ramping. Choosing between InfiniBand and an Ethernet variant is now a genuine engineering decision — cost, scale, interoperability, and workload mix all matter — rather than a performance no-brainer.

### 1.4 Network topology (DIST-8.5)

**Problem.** Switches from §1.1 have bounded radix, but clusters need unbounded endpoint counts. *How you wire switches together* — the topology — determines the fabric's cost, its worst-case bandwidth, its latency, and how much freedom the routing layer has.

Three properties dominate the analysis:

- **Bisection bandwidth**: cut the network into two halves in the worst possible way; bisection bandwidth is the total bandwidth crossing that cut. It caps the throughput of all-to-all and many collective patterns (any permutation that swaps the two halves must cross it).
- **Diameter**: the maximum hop count between endpoints; it sets a latency floor and multiplies per-hop congestion exposure.
- **Cost**: dominated not by switch silicon but by *cables* — especially long optical ones.

**Fat trees and Clos networks.** A fat tree (Leiserson, 1985) is a tree whose links get "fatter" (more parallel links) toward the root, so the bandwidth available between any two leaves is independent of where they sit. Modern clusters build the folded/Clos realization: edge (leaf) switches at the bottom, aggregation and spine (core) switches above, organized into **pods**. A Clos network (Clos, 1953, originally telephone crossbars) is the multistage arrangement that achieves this with uniform parts.

The canonical design rule: an edge switch in a **non-blocking** (1:1) fat tree dedicates half its ports to endpoints and half to spines. With 36-port switches, a two-level non-blocking fabric serves 324 nodes with 27 switches (18 edge, 9 spine) — NVIDIA's classic design example. At 800 Gb/s scale, a two-level fat tree of 144-port Quantum-X800 switches reaches 10,368 endpoints non-blocking (144 leaves × 72 endpoint ports). Fat trees give full bisection bandwidth and many equal-length paths (path diversity) — ideal for HPL's long panel broadcasts and bandwidth-bound collectives. The costs: roughly half of all ports are "consumed" by the fabric itself rather than endpoints, and cable count grows fast. Two further details matter operationally: fat trees must be *balanced* (equal link counts between every leaf-spine pair) or they become silently oversubscribed (DIST-8.7, next session), and routing must avoid "up-down-up" turns that create credit loops — the deadlocks of §1.2.

**Dragonfly.** Kim, Dally, Scott, and Abts (ISCA 2008) asked how to exploit high-radix switches when *cables dominate cost*. Their answer: treat a **group** of switches as one virtual router. Within a group, switches connect by cheap electrical local links; between groups, each group connects all-to-all with a smaller number of long (optical) global links. A minimal route crosses **at most one global link** — local hop to the group's gateway switch, one global hop, local hop to the destination — giving dragonfly a diameter of three with dramatically fewer global cables: their cost model showed ~20% savings over a flattened butterfly and ~52% over a folded Clos at 16K+ nodes. Cray's XC-series Aries networks, and today's HPE Slingshot systems (Frontier, Aurora, El Capitan) use dragonfly-family topologies. The trade: a minimal path between two groups is pinned to the single (or few) global link(s) connecting them, so adversarial traffic patterns can saturate global links even when most of the fabric is idle — unless routing goes *non-minimal*, detouring through an intermediate group to spread load. That behavior is exactly what adaptive routing (§1.5) provides, which is why dragonfly and adaptive routing are architecturally inseparable.

**Torus and mesh.** A k-ary n-cube (mesh without wrap-around; torus with) connects each node to its 2n nearest neighbors — e.g., a 3-D torus, Blue Gene/Q's 5-D torus, or the 6-D Tofu interconnect of the K computer and Fugaku. Properties are the mirror image of fat trees: diameter grows with node count (a torus has no hop-count ceiling), and bisection bandwidth grows only with the square-root-ish cross-section rather than with N — but *nearest-neighbor traffic* (stencil exchanges in CFD, lattice QCD, molecular dynamics) never leaves the local links, cable runs are short and electrical, and cost per node is superb. Tori dominate where the *algorithm's* communication is local; fat trees and dragonflies dominate when communication partners are unpredictable (HPL, AI training).

A compact comparison:

| Topology | Bisection | Diameter | Cable cost | Needs adaptive routing? | Example systems |
|---|---|---|---|---|---|
| Fat tree / Clos | Full (if 1:1) | Small, fixed | Very high (many equal-length copper/optical) | Helpful, not essential | Most InfiniBand clusters |
| Dragonfly | High per cost | 3 (minimal) | Low global-link count (optical), moderate local | **Essential** (non-minimal escape paths) | Frontier, Aurora, El Capitan (Slingshot) |
| Torus / mesh | Grows slowly | Grows with N | Low (short electrical) | No (dimension-order routing) | Blue Gene/Q, Fugaku (Tofu D) |

### 1.5 Adaptive routing (DIST-8.6)

**Problem.** Every routing scheme must map each (source, destination) pair onto one of the many physical paths a rich topology offers. *Static* routing fixes this once — InfiniBand's SM computes an LFT at fabric configuration time, balancing path counts per link (up-down, min-hop, or "scatter-ports" variants that randomize local choices). But static balancing is blind to the actual *time-varying* traffic: an incast, a hot all-reduce, or one unlucky permutation can pile many flows onto one path while parallel paths sit idle. In a fat tree this wastes bisection bandwidth; in a dragonfly it can saturate the single global link between two hot groups while other global links carry nothing.

**Mechanism: decide per packet (or per flow), from local state.** Adaptive routing moves the output-port decision into the switch's forwarding path, at run time:

```
static:   (dst LID) → [LFT table]           → fixed output port
adaptive: (dst LID) → [AR group = {p1..pk}] → pick output by port load
```

The subnet manager still defines the *candidate* set (the AR group — all ports that lead to the destination), but the switch chooses among candidates using observed congestion: typically the current occupancy/queue depth of each candidate output port.

**InfiniBand adaptive routing.** In NVIDIA/Mellanox fabrics the SM's Adaptive Routing Manager scans switches, configures AR groups and AR-aware forwarding tables, and enables AR. Because different packets of one message may now take different paths and arrive out of order, the endpoint must tolerate reordering — HCAs of the ConnectX-5 generation onward support the required packet reordering, and the SM only enables AR where endpoints do (middleware that relies on strict ordering can require care). A complementary mechanism, Adaptive Routing Notification (ARN), is designed to let upstream switches learn about downstream congestion or faults; deployment of the full ARN machinery has lagged the basic load-based AR. Measured studies on HDR fabrics (De Sensi et al., Simula/ETH) confirm AR substantially improves utilization under adversarial patterns in fat trees, while also documenting fairness pathologies such as the parking-lot effect, where arbitration interactions starve some flows.

**Slingshot's fine-grained AR.** HPE's Rosetta switch estimates load for up to four candidate minimal and non-minimal paths per packet — congestion approximated by candidate output ports' request-queue depths, shared on-chip through a ring and between neighboring switches by piggybacking ~4 bytes of congestion information on acknowledgment packets (in the reverse direction, per forwarded packet). Unordered traffic (RDMA-style) is rerouted **packet by packet**; ordered traffic (TCP/IP flows) is rerouted **flow by flow** to preserve sequence. Because non-minimal paths consume more link-seconds, Slingshot biases selection back toward minimal paths — the load-spreading benefit is traded against the extra network load it creates.

**Adaptive routing and congestion control are complements.** AR fixes *mid-fabric* congestion by steering around hot links; it cannot fix *endpoint* congestion (an incast into one NIC — no alternative destination port exists). Slingshot therefore pairs AR with a hardware congestion-control scheme that tracks every in-flight flow between endpoint pairs and applies backpressure specifically to the flows contributing to the endpoint hot spot, without penalizing bystanders — attacking the same victim-flow problem that PFC's blunt pauses cause in RoCEv2 (§1.3). The division of labor: **topology provides path diversity; adaptive routing exploits it reactively per hop; congestion control constrains senders end-to-end.**

**Connections.** These five topics form one stack: switches (8.2) implement the link protocol (8.3, 8.4); the wiring plan (8.5) determines what paths exist; adaptive routing (8.6) picks among them dynamically. Two curriculum topics tomorrow extend directly: DIST-8.7 (oversubscription — what happens when the fat tree is deliberately *not* 1:1) and DIST-8.8 (congestion in depth — hot spots, queue buildup, head-of-line blocking formalized). For HPL specifically: a 1:1 fat tree plus AR is the configuration that keeps HPL's broadcast-heavy panels near peak; on dragonfly systems HPL relies on non-minimal adaptive routing to keep global links from serializing long-distance row swaps. And every property here — losslessness, bisection, rerouting — carries straight into NCCL ring/tree algorithm choices on multi-node GPU systems (Theme 9).

## 2. Key Developments / News

### 2.1 Ultra Ethernet 1.1: in-network collectives and programmable congestion control come to the open Ethernet stack

**What happened.** The Ultra Ethernet Consortium released version 1.1 of its specification on October 12, 2026 (v1.0 shipped June 2025). v1.1 extends the original transport/congestion-control/RDMA work with: a **Unified Local profile** for scale-up networks (accelerator interconnects with one switch tier or none); a **Unified Forwarding Header** that overlays addressing onto the Ethernet MAC header, saving ~20 bytes versus a traditional IPv4 header, plus reduced inter-packet gaps (~11 bytes saved); **In-Network Collectives (INC)**; **Congestion Signaling (CSIG)**, a 4- or 8-byte tag that every switch on a path can update with worst-case queueing delay or bottleneck bandwidth and that the receiver returns to the sender; and **Programmable Congestion Management (PCM)**, which makes the endpoint's congestion-control and load-balancing algorithms loadable programs instead of fixed NIC firmware. A **UET Verbs** mapping eases porting of existing RDMA applications.

**What technically changed.** Two things stand against today's curriculum. First, INC is Ethernet's standardized answer to InfiniBand SHARP: the consortium's own analysis notes that a traditional all-reduce sends each value across the network twice (reduce, then broadcast — 2 GB sent per 1 GB result), while switch-side reduction halves that and cuts the log-n hop latency of tree broadcasts. Second, CSIG attacks the core weakness of ECN — a single bit that says "somewhere, something" — by carrying *quantitative* path state back to senders, and PCM acknowledges that congestion-control algorithms now evolve faster than NIC silicon generations. UEC is also coordinating with OCP: the ESUN (Ethernet for Scale-Up Networking) working group has grown to 175 members since its 2025 launch, and SUE-T brings a UET-based transport to scale-up fabrics — at the OCP Global Summit 2026, Broadcom reported Ethernet scale-up already in production at more than five hyperscalers.

**Why it matters and what to watch.** This is the first credible open, multi-vendor path to InfiniBand-class behavior (multipath, receiver-credit and sender-based congestion modes, collective offload) on Ethernet economics — and notably it doubles down on §1.3's lesson: UET does *not* require a lossless fabric, but designs the transport for controlled loss and reordering instead. Ecosystem evidence is accumulating (AMD's 400 GbE Pensando Pollara, positioned by AMD as the first UEC-compliant NIC, with vendor-claimed ~10% RDMA throughput over ConnectX-7-class hardware — a vendor claim, not an independent measurement; VIAVI's UET test gear; FPGA implementations). Watch for compliance-tested, interoperable UEC NICs and switches — the gap between "on every roadmap" and "in the rack" was the recurring theme at AI Infra Summit 2026 — and for whether INC deployments match SHARP's maturity.

### 2.2 NVIDIA Quantum-X800 co-packaged optics: attacking the power and reliability cost of the fat tree

**What happened.** At GTC 2026 (March 2026), Lambda announced it is deploying NVIDIA Quantum-X800 InfiniBand **co-packaged optics (CPO)** switches — silicon photonics integrated into the switch package — in an AI factory with 10,000+ Blackwell Ultra GPUs. Follow-up engineering posts (June 2026) detail the Q3450-LD: a 4U, liquid-cooled, 144×800 Gb/s XDR switch with 115.2 Tb/s non-blocking capacity, where fiber-array connectors feed light directly into photonic engines on the switch package, with 18 field-replaceable external laser modules feeding 144 MPO ports (lasers stay external precisely because they are the component that must be serviceable).

**What technically changed.** In a conventional fat tree at this scale, the switch ASIC drives electrical signals across the board to pluggable OSFP transceivers that convert to optics — every 800 Gb/s port needs its own DSP-and-laser module. Lambda's engineering estimate for a 128,000-GPU deployment: roughly 655,000 discrete pluggable transceiver modules across the switching fabric. CPO removes those modules from the signal path (shorter electrical runs, no per-port DSP), cutting switch power and, more importantly for availability, cutting the number of failure points that turn into fabric-wide congestion events when links flap — in AI-factory terms, every network failure is GPU idle time.

**Why it matters and the connection.** §1.4's lesson was that fat trees buy bisection bandwidth with cable and optics count; CPO is a direct attack on the cost function of that trade (and on the reliability of the lossless-credit machinery of §1.2, since link flapping perturbs credit loops and SM-driven routing). The XDR switches themselves carry the full modern InfiniBand feature set — SHARP v4 in-network reductions, adaptive routing, telemetry-based congestion control (NVIDIA cites 9× the in-network computing capacity of the prior generation). Watch: deployment telemetry from Lambda's build (power per switch, optical-failure rates versus pluggables), NVIDIA's silicon-photonics roadmap extending CPO to smaller radixes, and whether Ultra Ethernet/ESUN fabrics adopt co-packaged optics as fast as InfiniBand does.

### Further Reading

- *Intro to InfiniBand for End Users* (whitepaper above) — foundation reading, ~30 min; the cleanest short tour of the architecture covered in §1.2.
- Kim et al., ISCA 2008 dragonfly paper — deep dive; read §1–3 for the cost model that motivates the entire topology (why cables, not silicon, decide network design).
- De Sensi et al., *An In-Depth Analysis of the Slingshot Interconnect* (arXiv:2008.08886) — research paper; the best public dissection of production adaptive routing + hardware congestion control, with microbenchmarks.
- DCQCN (SIGCOMM 2015) — the reference on why PFC-based lossless Ethernet is hard; sections 2 and 6 are the essential parts.
- UEC 1.1 specification and announcement (links above) — primary source; skim the INC and CSIG chapters to see tomorrow's "network offload" (DIST-8.9) topic arriving in a standards body.
