## 0. Concise Summary

Today closes out the scaling-theory module and opens the profiling module — deliberately, in one issue, because the second half is the laboratory for the first half.

We start with the two "pathological" outcomes of parallel scaling. **Superlinear speedup** (S(N) > N) looks like a free lunch but is almost always a signal that the *baseline* was starving: when a fixed problem is spread across more processors, each slice may fit in cache and run disproportionately faster, or the parallel algorithm may do fundamentally less work than the serial one. **Scaling collapse** is the opposite pathology: past some processor count, adding resources makes the run *slower*, because per-node work shrinks toward zero while latency-bound collectives, synchronization, and load-imbalance tails grow or refuse to shrink. Both phenomena break the naive S(N) ≤ N expectation, and both force you to treat performance as a property of the *system* (machine + memory hierarchy + network + algorithm), not of the code alone.

Predicting limits is not enough — you must observe where time actually goes. That is the profiling module. **Instrumentation** inserts event-recording code and yields exact, complete event histories at a per-event cost that explodes in message-heavy codes; **sampling** periodically photographs the program and yields statistical estimates at bounded overhead. **Timeline profiling** lays events out per resource (thread, stream, rank, NIC) against time, exposing gaps, overlap, skew, and the critical path; **statistical profiling** (perf record, Nsight IP/backtrace sampling) histograms sampled program counters into hot-function rankings. The scaling models from Section 1 tell you *what to look for*; the tools in Sections 1.4–1.5 tell you *where it actually is*.

Three developments anchor this in the real world: the **Nsight Systems 2026.6.1** release, which is productizing timeline analysis for multi-node GPU systems and even AI agents; an **SC25 study of multi-node LLM inference** that documents scaling collapse live — decode-phase communication reaching ~70% of total latency at 32 GPUs on Alps; and a **2026 theoretical result** showing superlinear scaling can arise from input-stream locality alone, no extra cache required.

## 1. Learn the Concepts

### 1.1 Finishing the scaling story: when the curve bends the wrong way

Recall where we left off: Amdahl's law caps strong-scaling speedup at 1/f for serial fraction f, Gustafson's law explains why scaled-size problems scale better, and parallel efficiency S(N)/N measures how much of the machine you actually convert into useful throughput. Both laws quietly assume a model: **the same total work W, executed by the same algorithm, at the same per-element cost**, just divided among N processors. Today's first two topics examine what happens when reality violates each assumption in turn — first in your favor (superlinearity), then against you (collapse).

### PERF-6.7 — Superlinear speedup

**The claim to examine.** Speedup is S(N) = T₁/T_N, and the folklore bound is S(N) ≤ N. Why should that hold? Because with N processors you can execute at most N units of work per unit time, so finishing a fixed W can never take less than W/(N·r) time (r = per-processor rate). The bound is a *theorem about that model*. It fails the moment the model fails — and the model fails in two well-understood ways.

**Mechanism 1: tiered memory — the parallel run is not the serial run.** Every modern machine has multiple memory speeds: registers, L1/L2/L3, DRAM, and (on clusters) remote nodes. When you spread a fixed problem across N processors, the per-processor working set shrinks by ~N, and each slice can fall into a faster tier. The serial run pays DRAM latency for data that the parallel run serves from cache. This is not "cheating" — it is a genuine change in the cost per element of the *same* work.

A concrete cost model (adapted from the classic treatment in Grama et al.'s *Introduction to Parallel Computing* and Gustafson's 1988-era analyses): suppose a memory-bound loop has an 80% cache hit rate on one processor, with 2 ns hits and 100 ns DRAM misses.

```
Serial:     AMAT₁ = 0.80 × 2 ns + 0.20 × 100 ns = 21.6 ns/access
Split ×4:   hit rate rises to 95% (working set ÷ 4)
            AMAT₄ = 0.95 × 2 ns + 0.05 × 100 ns = 6.9 ns/access
```

The memory system alone is now 21.6/6.9 ≈ **3.1× faster per access**, *independent of* the 4× parallel execution. Multiply the effects and total speedup can exceed 4. Gustafson documented exactly this on the Alliant FX/8: a problem spread across all eight processors fit into cache and beat 8×. A taxonomy study by Bader et al. (FedCSIS 2016) catalogs the mechanisms; the cache/tiered-memory one is the most common, but crucially it appears **only in a range** of processor counts and problem sizes — the slice must be small enough to fit cache but not so small that overheads dominate.

**Mechanism 2: work reduction — the parallel algorithm does less work.** For search and branch-and-bound problems, parallel exploration prunes differently. Search a tree depth-first for a node labeled S with two processors, one per subtree: whichever processor finds the target first stops the search. The parallel run expands only the nodes on the "lucky" side; the serial run may expand the entire tree. Here W_parallel < W_serial genuinely — the speedup is real but reflects an *algorithmic* difference, not hardware heroics. The same effect appears in sparse linear algebra (fill-in changes with ordering and partitioning) and in Monte Carlo (early-exit criteria trip at different times).

**The engineer's reading of superlinearity.** A speedup plot that exceeds the diagonal is not a celebration; it is a diagnostic. Ask, in order:

1. **Is the baseline proper?** A tuned serial baseline (blocked for cache, vectorized) shrinks or erases the effect. If S(N) > N only against a naive baseline, the finding is about the baseline.
2. **Where is the cache cliff?** If superlinearity appears for N in [8, 32] and vanishes after, your per-node slice crossed a cache-capacity boundary. That tells you the *memory-bound* character of the kernel — information you can exploit directly (block sizes, data layout).
3. **Did total work change?** Instrument FLOPs executed or nodes visited, not just time. If work dropped, you are comparing algorithms, and the honest claim is about the algorithm, not the machine.

**Connection to HPL and dense solvers.** In HPL the work is fixed and known exactly (2/3n³ + 2n² FLOPs), so genuine work-reduction superlinearity is impossible, and GEMM's blocked working sets are already cache-resident by design — so superlinear HPL speedups essentially never appear. Where superlinearity *does* appear in practice: graph search (BFS/DFS), branch-and-bound optimization, adaptive mesh refinement (load splits change refinement work), and any sparse kernel whose per-process working set crosses a cache threshold under partitioning. When you see S(N) > N in a benchmark, your first hypothesis should be a **memory-tier transition**, your second an **algorithmic work change** — and you now have the profiling tools (Sections 1.4–1.5) to confirm which.

### PERF-6.8 — Scaling collapse

Collapse is the mirror image: past some N, T(N) *increases* — adding resources makes the job slower. It is not exotic. On production systems it is the *expected* end of every strong-scaling curve; the only questions are where the minimum sits and how steeply time rises afterward.

**Where the non-shrinking and growing terms come from.** Write the execution-time model with the terms we have been accumulating all week:

```
T(N) = f·W/r            (serial fraction — Amdahl floor; does not shrink)
     + (1-f)·W/(N·r)    (parallel work — shrinks like 1/N)
     + β·s(N)           (bandwidth term — per-node bytes / link bandwidth)
     + α·k·log₂N        (latency term — k latency-bound collectives per step)
     + wait(N)          (synchronization/imbalance — tail effects)
```

Collapse happens when the sum of the non-1/N terms stops shrinking (a constant floor only *flattens* the curve) and something *grows*. The two classic growers:

- **Latency-bound collectives.** A reduction on small messages costs ~α·log₂N regardless of message size. Each doubling of N adds one α to every collective, and codes that do many small collectives per step (implicit solvers, convergence checks, global norms) multiply this by k per step.
- **Surface-to-volume communication under strong scaling.** Split a 512³ stencil domain across N nodes: per-node compute ∝ n³/N but per-node halo ∝ (n³/N)^(2/3). The comm/compute ratio grows as N^(1/3) — efficiency erodes smoothly, and once the per-step work approaches the latency floor, time turns upward.

**A worked collapse (illustrative model, not measured data).** Take one timestep of a 512³ stencil: 50 FLOPs/cell ⇒ 6.7 GFLOP per step. Node rate 100 GFLOP/s ⇒ T₁ = 67 ms. Halo exchange costs 6·n_p²·32 bytes per node at 10 GB/s (n_p = per-node cube side). The step also does k = 10 small global reductions at α = 5 µs each, cost α·log₂N apiece:

| N | compute W/N | halo (β-term) | 10·α·log₂N | T(N) | Speedup | Efficiency |
|---|---|---|---|---|---|---|
| 8 | 8.400 ms | 1.26 ms | 0.15 ms | 9.81 ms | 6.8× | 85% |
| 64 | 1.047 ms | 0.315 ms | 0.30 ms | 1.66 ms | 40× | 63% |
| 512 | 0.131 ms | 0.079 ms | 0.45 ms | 0.66 ms | 102× | 20% |
| 1024 | 0.065 ms | 0.050 ms | 0.50 ms | 0.62 ms | 109× | 11% |
| 4096 | 0.016 ms | 0.020 ms | 0.60 ms | 0.64 ms | 105× | 2.6% |

Read the table twice. First: efficiency collapses smoothly — 85% → 2.6% — as the shrinking compute exposes first halo traffic, then latency. Second: total time has a **minimum near N ≈ 1500** and then *rises*. Requesting 4096 nodes is strictly worse than 1024 — you pay for 4× the machine and finish later. This is scaling collapse in miniature, and it is why an HPC engineer's reflex on a bad strong-scaling curve is to ask "what is the *minimum* of T(N), not how far can I push S(N)?"

**The three usual suspects, as diagnosis rules:**

1. **Communication growth** (bandwidth or latency): comm time grows or stays flat while compute shrinks. Signature: efficiency decays smoothly; timeline shows exposed communication phases lengthening relative to compute.
2. **Synchronization amplification**: per-step barriers convert small rank-to-rank skew into full-rank waiting. Signature: the slowest rank determines step time; other ranks show idle blocks before collectives. (This is where PERF-18 will formalize tail latency and barrier amplification.)
3. **Serial fraction floor**: a fixed serial region (I/O, setup, a global norm) that 1/N cannot touch. Signature: curve flattens far above zero and no amount of nodes helps — Amdahl made visible.

**Connection to HPL.** HPL strong scaling collapses by the same mechanisms with domain-specific costumes: panel factorization is dependency-heavy and hard to parallelize (a serial-ish fraction), the panel broadcast grows with the process grid, and lookahead exists precisely to overlap that communication with trailing updates — when lookahead depth is exhausted, broadcast time is exposed and the curve bends. PERF-24 will return to this with phase timing; for now note that *every* collapse diagnosis begins the same way: measure where the time went as N grew. Which is exactly the transition to profiling.

### 1.2 Opening the profiling module: observing instead of assuming

The scaling models above are hypotheses-generating machines: they tell you *which* resource should be limiting at which N. Profiling is how you test those hypotheses. The module's first three topics establish the two fundamental measurement strategies (record everything versus sample periodically) and the two fundamental views (time-ordered timeline versus aggregated statistics).

### PERF-7.1 — Instrumentation versus sampling

**Instrumentation** inserts recording code at points of interest: a library wrapper logs every `MPI_Send` and kernel launch; a compiler inserts enter/exit events for instrumented functions (`-finstrument-functions`, OPARI2 for OpenMP regions); you sprinkle NVTX ranges by hand. Every event that passes a probe is recorded — nothing is inferred. **Sampling** never touches your code's structure: a timer or hardware-counter overflow interrupts the program every so often, and the interrupt handler records where execution was (program counter, call stack), nothing else. After the run, the samples form a statistical picture.

**Why the choice matters: the observer effect at HPC event rates.** Instrumentation costs a fixed per-event overhead — call it 100–500 ns to write timestamps and an event record into a buffer. That sounds negligible until you multiply by HPC event rates. A message-passing code with 1 µs point-to-point messages generates ~2×10⁶ events/s per rank (send + receive). At 250 ns/event:

```
2×10⁶ events/s × 250 ns = 0.5 s of measurement overhead per second of execution
```

— 50% **clock dilation**, and worse: the overhead lands *on the communication path*, so the profile systematically exaggerates communication cost. You would "learn" that MPI is the bottleneck when the profiler manufactured that bottleneck. This is PERF-7.5 (tracing overhead) arriving early, and it is the reason tool design centers on overhead budgets: Score-P, for example, is explicitly engineered as a scalable measurement infrastructure whose per-event cost is kept low enough for production runs, and even so its documentation culture warns about trace-size explosion at scale.

Sampling inverts every property. At a 1 kHz sample rate with ~5 µs of per-sample work (read PC, walk the stack, write the record), overhead is ~0.5% and *bounded regardless of program behavior*. But nothing is exact: a function's sample share is an estimate of its time share, with sampling error ~1/√n; rare short functions may not appear at all (a 10 µs function has ~1% chance of appearing in any given 1 ms sample window).

**The hybrid that real tools actually are.** Modern profilers are not pure either strategy — they instrument *cheap, low-frequency boundaries* and sample *everywhere else*:

- **Nsight Systems** instruments the CUDA runtime/driver API (thousands of calls per second — affordable) and simultaneously samples CPU instruction pointers and backtraces. The User Guide describes exactly this: NVTX ranges mark code regions, the timeline projects them onto GPU activity, and yellow-orange IP/backtrace sample marks sit under each thread row, hoverable for their stack traces.
- **Score-P** instruments MPI/OpenMP boundaries (event counts per rank are message-rate × steps, manageable with filtering) and supports sampling as a low-overhead substrate.
- **perf** (Linux) is sampling-native (`perf record`) with *counting-mode* instrumentation (`perf stat`) for whole-run totals.

**Selection rule of thumb.** Instrument when you need *exact event semantics* — message matching, collective participation, per-call durations, and anything you will correlate across ranks; and keep the instrumented boundary rate ≤ ~10⁵/s/rank. Sample when you need *where does the time go inside compute* at bounded overhead. If you find yourself instrumenting inside an inner loop, you are about to measure the profiler.

### PERF-7.2 — Timeline profiling

A timeline is the simplest possible visualization with the highest information density in HPC: **rows are resources; the x-axis is time; marks are events with duration.** A single Nsight Systems report can show, in one aligned view: OS threads (with user-mode green / kernel-mode red), CUDA API calls, per-stream kernel bars, host↔device memcpy bands, NVTX ranges, and — on newer releases — NIC and NCCL activity rows. The MPI-world equivalents are OTF2 traces collected by Score-P and displayed in Vampir: one row per rank/process, events for sends, receives, and collectives.

**What timelines see that aggregates cannot.** A flat "GPU utilization 45%" number is four different diseases: kernels too small to fill the device; launch-bound gaps; exposed memcpy; or dependency stalls. On a timeline these are visually distinct, and the Nsight Systems User Guide makes the mechanism explicit — *correlation*: click a kernel bar and the tool highlights the CPU-side `cudaLaunchKernel` that produced it, with arrows connecting the two rows. Row-height encodes utilization (the guide documents that a stream bar's height is the average occupancy over the pixel's timeslice, gray = max), and stream rows are prefixed with the percentage of context time they consume (`% stream = 100 × streamUsage / contextUsage`).

**The symptom → mechanism reading grid** (this is the core skill of this topic):

| Timeline symptom | Likely mechanism | Curriculum link |
|---|---|---|
| Regular small gaps before every kernel on one stream | Kernel-launch overhead dominating (launch-bound) | PERF-9.2, 13.1 |
| Long idle gap after a `cudaDeviceSynchronize`/collective | Host synchronization / dependency stall | PERF-10.5 |
| memcpy bars never overlapping kernel bars | Exposed transfers — no compute-copy overlap | PERF-14.3 |
| One rank's rows shifted right vs. peers, then idle-before-collective | Skew amplified at the barrier — the waiting ranks are not the slow rank | PERF-18.3/18.7 |
| Kernel bar heights fine, but gaps *between* phases | Orchestration (host-side prep) — CPU-GPU gaps | PERF-9.8 |

Two of those rows deserve emphasis because they close the loop to this morning. **Skew-then-wait** is scaling collapse mechanism 2 made visible: you can *see* the barrier converting small skew into full-rank idle. **Exposed communication** is mechanism 1: communication that does not overlap with compute lands on the critical path verbatim. A timeline of the same code at N=64 and N=1024, compared rank-by-rank, is often the fastest way to identify *which* collapse mechanism owns your curve — the aggregated scaling plot tells you *that* you collapsed; the timeline tells you *why*.

**The one hard engineering problem: clocks.** A multi-rank timeline is only as trustworthy as the clock synchronization across nodes. If rank A's trace says the broadcast "started" after rank B's says it "ended," you will diagnose skew that does not exist. Production tools treat this explicitly — Nsight Systems added an unprivileged *vClock* virtual-clock alignment for multi-report views precisely because physical clock sync (PTP) is rarely available on every node; Score-P/OTF2 record per-rank clocks and apply synchronization post-hoc. Rule: never compare inter-rank timestamps closer than the known sync error; compare *durations* and *ordering* within a rank freely.

**Cost control.** Timeline traces are instrumentation-driven, so PERF-7.1's overhead math applies with interest at scale: 1000 ranks × 2×10⁶ events/s × 64 bytes/event ≈ 128 GB/s of trace. The professional pattern is *selective tracing*: trace a few iterations via capture ranges (`nsys profile --capture-range`, or `cudaProfilerStart/Stop`), or trace a representative few ranks and extrapolate — then zoom into one rank with full detail.

### PERF-7.3 — Statistical profiling

Statistical profiling answers a narrower question than the timeline — *which code consumes the time* — and answers it at near-zero overhead, which is why it is nearly always the **first** profiling step (the "start broad" habit of PERF-7.7, coming later in this module).

**Mechanism: the PMU overflow interrupt.** This is worth understanding at the hardware level, because it explains both the power and the biases of the method. CPUs contain a Performance Monitoring Unit (PMU) with a handful of programmable counters. `perf record` (per the Linux perf design, and as documented in NVIDIA's Grace tuning guide) configures a counter — say, CPU cycles — to *overflow* every N events. Each overflow raises an interrupt; the handler records the instruction pointer, timestamp, thread id, and optionally the call chain into a ring buffer, which `perf report` later histograms by symbol. The elegant consequence: **the sampling period is measured in events, not time**. A code region generating twice the cycles is sampled twice as often — the sample histogram is automatically proportional to the event being counted.

That last point is the deep feature. Choosing the sampling event chooses the question:

- sample on **cycles** → where is time spent (the default hot-function view);
- sample on **cache-misses** → which functions cause memory traffic (a poor-cache-behavior map);
- sample on **branch-misses** → where control flow hurts.

One run, different event, different bottleneck hypothesis. This is statistical profiling as an *instrument panel*, not just a ranking.

**The statistical assumptions — and their failure modes.**

1. *Proportionality*: sample share ≈ time share. Holds when sampling is independent of program behavior. Fails under **aliasing**: a periodic timer at exactly 100 Hz can lock onto periodic code (a 10 ms timestep loop) and systematically sample the same phase of it. This is why the field convention is `-F 99` (or 997) — deliberately prime-ish frequencies to decorrelate from program periodicity.
2. *Sufficient count*: the error on a function's share is ~1/√n_samples. A 30-second run at 99 Hz gives ~3000 samples — fine for a 40% function (±0.9 pp), useless for a 0.5% function (~15 samples, ±26% relative). To resolve a small function you need a longer run or a higher rate, i.e., you trade overhead for resolution. (perf's frequency mode auto-tunes the period to hit the requested rate — the exact mechanism the Stack Overflow perf documentation describes: counter set to overflow, autotuned period, IP + callstack recorded per overflow.)
3. *Attribution*: a flat view attributes time to the leaf function; call-graph sampling (`-g`, frame-pointer or DWARF unwind) attributes it to the *path* — which matters enormously when `malloc` shows up hot from five different callers with different culpability. This is the inclusive/exclusive distinction from PERF-2.6 returning in statistical clothing.

**Reading a statistical profile like an engineer.** The output of `perf report` is a hypothesis table, not a verdict — the counter-interpretation module (PERF-23) will formalize this, but the habit starts now: a hot function is a *location*, not a *cause*. `my_stencil_kernel` at 62% of samples on the cycles event means "time goes here"; whether the cause is cache misses, poor vectorization, or simply doing the algorithm's necessary work is answered by re-sampling on a different event or reading the counters — `perf stat -e cycles,instructions,cache-misses,cache-references` in counting mode gives the ratios (IPC, miss rate) that turn location into mechanism.

**The closing loop.** Notice what the three profiling topics give you relative to the morning: superlinear speedup's diagnosis rule #2 asks "did the working set cross a cache boundary?" — answered by cache-miss sampling and counter ratios. Collapse diagnosis asks "is it communication growth, sync amplification, or serial floor?" — answered by a timeline read of the same phase at two scales (exposed comm vs. skew-then-wait vs. a fixed serial block). The scaling models generate hypotheses; instrumentation and sampling are the two ways of collecting evidence; the timeline and the histogram are the two ways of reading it. That is the entire performance-engineering loop of PERF-26 in miniature, and the rest of this module equips each step in turn.

### 2.1 Nsight Systems 2026.6.1: timeline profiling productized for multi-node — and for agents

NVIDIA's Nsight Systems 2026.6.1 release (per the official release notes and developer-forum announcement) is a densely relevant one for today's topics. On the *measurement* side: CUDA 13.5 support, CUDA kernel tooltips now showing CTA/CGA occupancy, and — directly on PERF-7.2's clock problem — improved **vClock** time-alignment accuracy in multi-report views. On the *multi-node* side: NCCL GPU operations now render as one range per operation with expandable per-channel communicator rows (previously one range per channel, which visually fragmented collective timelines), and the bundled `nccl_pace` recipe investigates collective progress and consistency across ranks and iterations — which is precisely the "compare the same region across ranks" skill of timeline reading, automated. On the *workflow* side, the release folds an "agent skill" into the product and adds three CLI commands — `query` (read-only SQL over a report), `docs`, and `survey` (top-level report summary) — explicitly designed so that AI agents (and humans scripting analyses) can drive timeline analysis without the GUI.

Why it matters for today's concepts: the historical bottleneck of timeline profiling at scale — trace size, clock alignment, and the human cost of reading 64 rank-lanes — is being attacked exactly where PERF-7.2 located it. Straggler-style recipes (an `nccl straggler` analysis landed in 2025-era releases; `nccl_pace` extends the family) automate the diagnosis grid's "skew-then-wait" row. Watch next: whether recipe-generated "insights" (10 bundled recipes now emit observations and suggested follow-ups) hold up as trustworthy first-pass diagnoses, or whether they institutionalize PERF-7.8's correlation-versus-causation trap.

### 2.2 SC25: communication overhead is collapsing strong scaling in multi-node LLM inference

At SC25 in St. Louis (Nov 16–21, 2025), Singhania et al. (University of Maryland, with LLNL) presented the poster *"Understanding Communication Bottlenecks in Multi-Node LLM Inference,"* built on their Yalis inference framework, with measurements on the Alps and Perlmatter supercomputers. The findings are a live specimen of PERF-6.8: strong-scaling LLM inference with tensor parallelism scales poorly beyond a node, and the cause is communication, not compute. In the decode phase, communication time on Alps rose 8.9× at 8–16 GPUs and 10.4× at 32 GPUs versus 4 GPUs — reaching about 70% of total latency at 32 GPUs. The poster summary explicitly attributes this to compute scaling far faster than communication bandwidth on newer GPU generations, which is this morning's surface-to-volume story with attention/MLP activations in place of stencil halos. A second finding sharpens it: NCCL's all-reduce, while efficient intra-node, was outperformed cross-node by MPI for 256 KB–2 MB messages on Slingshot networks; the team's custom all-reduce (presented in the accompanying UMD talk) achieves 1.9–3.6× lower latency in that regime.

Read as a performance-engineering case: the collapse minimum sits at the node boundary, the growing term is latency-bound small-message collectives (two per transformer layer per step), and the remedy under investigation is algorithm/protocol change — smaller effective messages, better collective implementations — rather than more hardware. Caveats as ever: poster-scale results, two specific systems, and workload-dependent message sizes; the 70% figure is their measurement on their configurations, not a universal constant. (SC26 convenes next week — Nov 15–20, 2026, in Chicago — where multi-node inference scaling and collective performance will predictably dominate the HPC-for-ML track again.)

### 2.3 Superlinear speedup gets a 2026 theory upgrade — no cache required

A 2026 paper in the Symposium on Algorithmic Foundations of Distributed Systems (Köppeler, Pacut, Lévai, Addanki, Schmid, Rétvári — LIPIcs, SAND 2026) gives PERF-6.7 a contemporary theoretical treatment: *"More Bang for the Buck: Superlinear Scaling with Distributed Self-Adjusting Systems."* The authors show superlinear scaling in a pure-software setting — distributed self-adjusting data structures (move-to-front lists, splay-style reordering) behind a load balancer that splits an input stream among k workers. The mechanism is elegant: each worker sees a *smaller and more predictable* input stream, so per-worker locality improves (the self-adjusting structure reorders faster toward each stream's working set), reducing effective job size — superlinearity from **input-stream locality**, with no additional cache capacity. Their model frames superlinear speedup as the superposition of a locality job-size-reduction factor and ordinary parallel speedup, and — matching the FedCSIS taxonomy's field observation — predicts it appears in a *range* of k and vanishes once workers saturate or the structure degenerates into a hash table.

The connection to today's lesson is direct: this is Gustafson's "shifting algorithm profile" mechanism (the *mix* of routine costs changes with scale) recast for distributed services, and a reminder that the superlinearity diagnosis checklist should include a third entry beyond cache-tier transitions and work reduction: *locality structure induced by partitioning itself*. For HPC workloads the practical relative of this effect is per-rank working sets that become more cache-friendly under domain decomposition not just because they are smaller, but because their access sequences become more predictable.

### Further Reading

- **Helmbold & McDowell, "Modeling Speedup(n) greater than n" (ICPP 1989)** — the classic formal treatment of superlinear speedup; short and rigorous. *Foundation — 20 min.*
- **Grama et al., CS525 Chapter 5 slides** — scaling metrics, isoefficiency, superlinearity worked examples; the cleanest single refresher for this whole module arc. *Foundation — 30 min.*
- **Nsight Systems User Guide, "Timeline View" sections** — then reproduce on your own box: `nsys profile` a small CUDA code, find one gap, one overlap, one sync. *Hands-on — 30 min.*
- **perf tutorial (Brendan Gregg's "perf Examples" page or the Red Hat chapter above)** — run `perf stat -e cycles,instructions,cache-misses` then `perf record -F 99 -g` on the same binary; compare what each teaches. *Hands-on — 20 min.*
- **Score-P + Vampir quickstart (vi-hps.org)** — the MPI-world counterpart: collect an OTF2 trace of a 4-rank job and read one collective in the timeline. *Hands-on — 45 min.*
