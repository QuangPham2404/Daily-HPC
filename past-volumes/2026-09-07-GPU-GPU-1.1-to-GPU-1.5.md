## 0. Concise Summary

Today opens Theme 1 at the foundations: what a processor physically does, why CPUs and GPUs diverged into two different machines, the forms of parallelism hardware can exploit, the execution models (scalar, vector, SIMD, SIMT, SPMD) that connect programs to silicon, and the latency-versus-throughput distinction that explains almost every GPU design decision.

The central idea of the issue: **a GPU is not a "fast CPU."** Both processors fetch, decode, and execute the same kinds of instructions over the same kinds of data — but they spend their transistor budgets on opposite things. A CPU buys *single-thread latency* with branch predictors, out-of-order windows, and large caches, because serial programs have dependent instruction chains that no amount of parallel hardware can shorten. A GPU buys *aggregate throughput* with hundreds of simple, replicated execution lanes, because graphics and dense scientific workloads supply millions of independent operations, and the cheapest way to keep silicon busy is to switch to other work rather than to accelerate any single stream.

The lesson builds this quantitatively. We use the execution-time equation (instructions × cycles-per-instruction × clock period) to account for where time goes, walk a dot-product loop instruction by instruction, map Flynn's taxonomy onto real chips (a modern CPU is a MIMD of SIMD cores; a GPU is a MIMD of SIMT streaming multiprocessors), and use a Little's-Law-style argument to show why a GPU needs thousands of resident threads to hide ~500 cycles of memory latency — including a worked calculation showing that saturating an H100's 3.35 TB/s of HBM3 requires roughly 2 MB of loads in flight at every instant.

Two developments anchor this in the real world: the June 2026 TOP500 list, where China's CPU-only LineShine debuted at No. 1 with 2.198 exaflop/s on HPL amid five exascale systems; and NVIDIA's July 2026 Rubin architecture deep-dive, whose headline numbers (224 SMs, 288 GB HBM4 at 22 TB/s, 50 petaflops of NVFP4) are directly readable — and critique-able — using exactly the tools from today's lesson.

## 1. Learn the Concepts

### 1.1 What a processor actually does (GPU-1.1)

Strip away everything incidental, and every general-purpose processor — the Zen 4 core in an MI300A, the SM of an H100, the A64FX core of Fugaku — implements the same contract, inherited from the von Neumann model: **a program is a sequence of instructions stored in memory; the processor repeatedly fetches one, decodes what it means, and executes it against data.**

The loop has a small, universal set of actors:

```text
            +---------+     +----------+     +------------------+
 memory --> |  fetch  | --> |  decode  | --> |  execute units   | --> memory
            | unit    |     | + regs   |     | ALU / FPU / LS   |
            +---------+     +----------+     +------------------+
                  ^               |                 |
                  +--- PC --------+---- control ----+
                   (program counter)   (branches)
```

- **The program counter (PC)** holds the address of the next instruction. It normally increments; branches and jumps overwrite it.
- **Registers** are the small, fastest storage directly addressed by instructions. Every arithmetic instruction's operands and result pass through them.
- **Execution units** do the actual work: integer ALUs, floating-point units (which implement fused multiply-add, the workhorse of scientific code), load/store units that talk to the memory system, and special-function units.
- **Control** resolves branches and exceptions — deciding *what runs next*.

Crucially, the **instruction set architecture (ISA)** — the set of instructions, registers, and visible behaviors — is a *contract*, not a description of the hardware. The x86-64, Armv9, and RISC-V ISAs tell the software world what the machine must appear to do; the manufacturer is then free to build it however it likes. The same contract has been implemented by radically different microarchitectures, from simple in-order cores to deeply out-of-order superscalars. NVIDIA GPUs expose their own contract (PTX/SASS beneath CUDA); the CUDA programming guide is careful to say the conceptual hardware model — a GPU is a collection of **streaming multiprocessors (SMs)**, grouped into **graphics processing clusters (GPCs)**, each SM holding a register file, a unified data cache, and functional units — is a programming model, and the physical realization may vary.

Why does this abstraction matter for HPC? Because performance analysis is only possible when you can separate the two accounts every program spends:

1. **Instruction execution** — how many instructions, at what rate.
2. **Data movement** — how many bytes must cross how far.

The canonical accounting identity from Hennessy and Patterson's quantitative approach (the methodology that won them the 2017 Turing Award) is:

```text
Time/program = Instructions/program × Cycles/instruction × Seconds/cycle
```

Every optimization you will ever do — vectorization, tiling, memory coalescing, warp occupancy, tensor cores — attacks one of these three factors. Keeping this decomposition in mind prevents the most common reasoning error in performance work: optimizing one term while making another worse.

**A concrete walk-through.** Consider the inner loop of a dot product, `s += a[i]*b[i]`, on a simple scalar machine. Per iteration you need, roughly:

```text
loop:  load   f1, 0(r1)        ; 1 memory read
       load   f2, 0(r2)        ; 1 memory read
       fmadd  f0, f1, f2, f0   ; 1 useful FLOP-pair (a*b + s)
       addi   r1, r1, 8        ; advance pointer
       addi   r2, r2, 8        ; advance pointer
       addi   r3, r3, -1       ; decrement counter
       bne    r3, r4, loop     ; branch
```

Seven instructions retire per iteration, of which **one** does arithmetic the algorithm asked for. The other six — address arithmetic, loop control, and the loads themselves — are the tax of the von Neumann model. Two observations follow, and they drive the entire history of processor design:

- The useful-to-overhead instruction ratio is terrible for scalar execution of array code. If many elements undergo the *same* operation, the control overhead should be *amortized* across them — this is data-level parallelism, and it is why vector and SIMD hardware exists (Topic 1.4).
- The two loads are the actual bottleneck in most real codes, not the multiply-add. Moving data is slow and expensive; arithmetic is nearly free. This fact — the **memory wall** — is why the rest of the GPU memory hierarchy (Theme module 4) exists, and it is the root cause of the latency-vs-throughput discussion in Topic 1.5.

One more foundational point: a GPU is *also* just this fetch-decode-execute machine. Nothing exotic happens at the instruction level — SMs fetch load/store/arithmetic instructions from memory and execute them against registers. All of the GPU's reputation for speed comes from *what fraction of the chip is allowed to do this work* and *how many instruction streams it keeps in flight* — which is precisely the subject of the next topic.

### 1.2 CPU vs GPU design goals (GPU-1.2)

If both processors execute the same kinds of instructions, why do they look so different? The answer is that they optimize different quantities.

**Latency** is the time for one operation to complete — e.g., 500 ps for an L1 hit, ~100 ns for a DRAM access. **Throughput** is operations completed per unit time across the whole machine. A single-core CPU is a latency machine: it minimizes the completion time of *one* serial instruction stream. A GPU is a throughput machine: it maximizes total work completed per second across *thousands* of streams, cheerfully making any single stream slower.

**Why CPUs must chase latency.** Most general-purpose code — operating systems, parsers, game logic, the control flow of a simulation — contains serial dependence chains: instruction *n+1* consumes instruction *n*'s result. No amount of parallel hardware shortens a chain; Amdahl's law guarantees that the serial fraction eventually dominates. So a CPU core spends its transistors making each dependent step as fast as possible:

- **Branch prediction and speculation**: the front-end guesses which way a branch goes and keeps fetching down that path, so the pipeline never idles waiting for the branch to resolve.
- **Out-of-order execution**: a wide window of instructions is examined each cycle; any instruction whose operands are ready issues immediately, even if an earlier instruction is still waiting — squeezing ILP out of serial code (Topic 1.3).
- **Large, deep caches**: most of a server CPU's die area is cache, cutting average memory latency.

**Why GPUs can chase throughput.** A graphics shader runs per-pixel; a mesh in a CFD solver has millions of cells; a dense matrix has millions of independent multiply-accumulates. The workload itself supplies enormous numbers of *independent* operations. If one operation stalls on memory, the hardware can simply switch to another of the thousands of available operations — a strategy called **latency tolerance** or **latency hiding** (Topic 1.5) — so the elaborate latency-*reduction* machinery of a CPU is largely wasted silicon. The transistor budget instead goes to **replicating execution units**.

**Transistor accounting, with real numbers.** NVIDIA's Hopper whitepaper describes the full GH100 chip as 80 billion transistors on an 814 mm² die, organized into 8 GPCs and 144 streaming multiprocessors, with each SM providing 128 FP32 CUDA cores, 4 fourth-generation tensor cores, and 256 KB of combined shared memory/L1 — plus 60 MB of L2 and 6 HBM3 stacks. Consumer Blackwell's GB202 packs 92.2 billion transistors into 192 SMs, each with 128 CUDA cores, a 256 KB register file, and 128 KB of L1/shared memory. Now compare a server CPU: a large fraction of its area is L3 cache, prediction structures, and out-of-order scheduling logic — circuitry whose *purpose* is to accelerate a single instruction stream rather than to execute more of them in parallel. Roughly speaking:

```text
CPU die:   [ big caches ][ prediction+OoO control ][ modest ALUs ]
GPU die:   [ modest caches ][ thin control ][ massive replicated ALUs ]
```

This shows up directly in the machine's *shape*. A modern CPU core issues at most a handful of instructions per cycle to its execution ports. An SM is organized into four sub-partitions, each with its own warp scheduler and issue port — only four instructions per cycle per SM — but each instruction is a 32-lane warp instruction executed for 32 threads at once, and the SM keeps up to 2,048 threads resident (Hopper-class limits). The GPU issues *fewer decisions per second* but each decision moves *32× more data*, and there are ~132 SMs (shipping H100 SXM5) making those decisions in parallel.

| Dimension | Latency-oriented CPU core | Throughput-oriented GPU (SM aggregate) |
|---|---|---|
| Design goal | Finish one stream ASAP | Total work per second |
| Clock | High (~3–5 GHz server) | Lower (~1.5–2 GHz) |
| Control logic | Large (predictors, renaming, OoO windows) | Thin (simple in-order warp schedulers) |
| Cache area share | Large (L3 dominates die) | Small (SM-level 128–256 KB, chip L2) |
| Hardware multithreading | 2–4 threads/core | Thousands of threads/SM |
| Stall on memory? | Try to prevent (prediction, prefetch) | Expected and tolerated (switch warps) |
| Sweet spot | Serial/branchy/irregular code | Dense, regular, independent data |

**The two processors need each other.** Real applications are hybrids: setup, control flow, I/O, and irregular phases are latency-sensitive; the numeric heart is throughput-hungry. That is why an HPC node pairs them — and why the pairing is tightening. AMD's Instinct MI300A, the processor inside the El Capitan supercomputer, integrates 24 Zen 4 CPU cores and 228 CDNA 3 GPU compute units in one package with 128 GB of HBM3 shared coherently between them at 5.3 TB/s. Hennessy and Patterson's 2019 Turing Lecture argued exactly this trajectory: with the end of Dennard scaling and Moore's law slowing (they noted single-core performance was improving only ~3% per year by 2017), further gains must come from **domain-specific architectures** — hardware shaped to the parallel structure of the workload — rather than from faster general-purpose cores. The GPU is the most successful domain-specific architecture in HPC history; the MI300A APU and NVIDIA's Grace/Rubin superchips are the next tightening of that coupling.

### 1.3 Forms of parallelism (GPU-1.3)

"Parallelism" is not one thing. Hardware exploits several distinct kinds, and the vocabulary matters because each kind maps to different circuitry. The four classical forms:

**Instruction-level parallelism (ILP)** — overlapping *instructions within one instruction stream*. Two mechanisms:

- *Pipelining*: split instruction execution into stages (fetch → decode → execute → memory → write-back) so that while instruction *n* is decoding, instruction *n−1* executes and *n−2* fetches. A 5-stage pipeline completes up to 5× the instructions per cycle of a non-pipelined design using nearly the same hardware:

```text
cycle:    1    2    3    4    5    6    7
instr 1:  IF   ID   EX   MEM  WB
instr 2:       IF   ID   EX   MEM  WB
instr 3:            IF   ID   EX   MEM  WB
```

- *Superscalar issue and out-of-order execution*: issue multiple instructions per cycle, and let independent instructions execute ahead of stalled ones (enabled by register renaming, which removes false data dependencies). A modern CPU core is a wide ILP machine; an individual GPU thread's instruction stream gets little ILP help from hardware, but ILP within a thread still matters — compilers interleave independent iterations precisely so the GPU has ready instructions to issue.

**Data-level parallelism (DLP)** — applying the *same operation* to many data elements. `a[i] = b[i] + c[i]` for a million `i` is pure DLP. DLP is what vector units, SIMD lanes, and GPU warp execution all harvest. It is the cheapest parallelism to exploit because one instruction's worth of fetch/decode/control overhead amortizes over all the elements it processes — directly fixing the 7-instructions-per-useful-FLOP problem from Topic 1.1.

**Thread-level parallelism (TLP)** — many independent instruction streams, each with its own program counter and register state. Two flavors: *hardware multithreading* (one core holds several thread contexts and switches among them when one stalls — GPUs take this to the extreme with thousands of resident threads) and *multicore/manycore* (replicate whole cores; a 144-SM GPU is a manycore of throughput cores).

**Task-level parallelism** — independent *jobs* running concurrently, coordinated at the software level: separate MPI ranks on separate nodes of a cluster, separate simulation ensembles, or independent GPU kernels in a pipeline. This is the scale-out dimension that Theme 2 (distributed HPC) is built on.

**The forms compose, and real machines use all of them at once.** This is the key systems insight. Take an HPL run on a GPU cluster:

```text
task level:      HPL split over N nodes (MPI)                    → TLP across nodes
per-GPU:         thousands of concurrent threads in blocks       → TLP + DLP within SMs
per-warp:        32 lanes execute one instruction together       → DLP (SIMT)
per-thread:      compiler-unrolled FMAs with independent operands → ILP
inner GEMM:      tensor cores consume matrix tiles               → DLP at extreme width
```

Or a modern CPU: it is a MIMD machine (many cores) whose cores exploit ILP (superscalar out-of-order) and DLP (AVX-512 or SVE vector units). The same program exposes all four forms simultaneously at different scales.

The corollary that matters for everything that follows: **hardware can only overlap work that software actually supplies.** A GPU's 2,048 resident threads per SM are useless if the program only offers one. This is why parallelizing the *algorithm* — exposing DLP and TLP — is the prerequisite for all GPU performance, and it is why this curriculum studies execution models next.

### 1.4 Scalar, vector, SIMD, SIMT, and SPMD (GPU-1.4)

These five terms describe programs and hardware at different levels, and HPC conversations constantly confuse them. Let's fix the vocabulary precisely.

**Flynn's taxonomy.** Michael Flynn's 1972 classification counts instruction streams and data streams: **SISD** (one instruction, one data stream — a classic uniprocessor), **SIMD** (one instruction, many data streams), **MISD** (many instructions, one data stream — rare; systolic arrays are sometimes argued as examples), and **MIMD** (many instructions, many data streams). The taxonomy is coarse but durable: a modern multicore CPU is MIMD *whose individual cores contain SIMD units*; a GPU is MIMD *at the chip level* (SMs run independent instruction streams) with SIMT execution *inside each SM*.

**Scalar execution.** One instruction operates on one (or one pair of) elements: `fmadd f0, f1, f2, f0`. The dot-product loop in Topic 1.1 was scalar. Simple, flexible — and wasteful when the same operation applies to a whole array.

**Vector execution.** The idea predates GPUs by decades: instructions whose operands are *vector registers* holding N elements. The Cray-1 (1976) made vector registers the centerpiece of supercomputing; today's survivors include Arm SVE (the A64FX CPU in Fugaku implements 512-bit SVE — one vector instruction processes 16 FP32 or 8 FP64 elements) and RISC-V's RVV extension, plus x86 AVX-512. A vector machine shortens the dot-product loop: the two loads, the multiply-add, and the pointer updates are issued *once* per 16-element vector rather than once per element, and the pipeline streams elements through the functional unit.

**SIMD.** In modern usage, SIMD means the vector idea implemented as *replicated lanes* inside a processor: a 512-bit vector unit is physically 16 parallel 32-bit lanes that all execute the same instruction on different elements. Compiler auto-vectorization and intrinsics (`_mm512_fmadd_ps`...) target these lanes. The constraint: all N elements genuinely undergo the same operation at the same time.

**SIMT — single instruction, multiple threads.** This is NVIDIA's execution model, and it is best understood as **SIMD with a thread-based programming interface**:

- The programmer writes *per-thread scalar code* — an ordinary loop body as if for one element (SPMD, below). No vector intrinsics, no explicit lane management.
- The hardware groups threads into **warps of 32** (AMD: wavefronts of 32 or 64; Intel: subgroups). A warp issues as one instruction across 32 SIMD-like lanes — so the *hardware* is vector/SIMD-shaped.
- Unlike a pure SIMD machine, each thread has its own register state (and, since Volta, effectively its own program counter and an active mask), so threads can legitimately take different branch paths — at a cost (branch divergence, Topic GPU-2.7) — and can be scheduled and synchronized independently.

SIMT is the pragmatic middle ground: the programmer keeps the simplicity of writing scalar, per-element code, while the hardware still amortizes one instruction fetch/decode over 32 threads' work. The cost of that convenience is a set of rules — threads in a warp move together, memory access patterns matter (coalescing, GPU-4.7), divergence serializes — that every CUDA/HIP/SYCL programmer eventually must internalize.

**SPMD — single program, multiple data.** SPMD is a *programming style*, not a hardware mechanism: one program source is launched many times, each instance operating on a different portion of the data, with instances distinguished by an index. A CUDA kernel is SPMD: the same `__global__` function runs as thousands of program instances; `threadIdx` is what makes instance *i* different from instance *j*. MPI programs are SPMD at cluster scale: every rank executes the same binary, differing by rank ID. OpenMP and SYCL follow the same shape. The distinction to keep straight:

```text
SPMD  = how the SOFTWARE is structured (one program, many instances)
SIMD  = how HARDWARE executes (one instruction, many lanes)
SIMT  = the bridge: per-thread software, warp-vectorized hardware
```

**A concrete CUDA example.** Vector addition, the "hello world" of SPMD:

```cuda
__global__ void saxpy(float a, float* x, float* y, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;  // my global instance index
    if (i < n)                                      // guard against overlaunch
        y[i] = a * x[i] + y[i];                     // one scalar statement...
}
```

What hardware does with this: the host launches a grid of thread blocks; blocks are assigned to SMs; on an SM, threads are formed into warps of 32; each warp executes the four instructions (index arithmetic — integer ALU; compare — predicate; two loads, one store or the multiply-add — FP lane) *once for all 32 threads*. If `i` values across a warp are contiguous (they are, here), the 32 loads coalesce into a small number of memory transactions (GPU-4.7). One instance of `y[i] = a*x[i] + y[i]` looks scalar in the source, and is executed as a 32-wide vector operation by the machine. That is SPMD compiled to SIMT.

| Term | What it describes | Example |
|---|---|---|
| Scalar | 1 instruction : 1 element | Classic RISC loop |
| Vector / SIMD | 1 instruction : N elements via wide registers/lanes | Cray-1, AVX-512, A64FX SVE |
| SIMT | SIMD-shaped hardware behind a per-thread interface | NVIDIA SM warp execution, AMD wavefronts |
| SPMD | One program source, many data-indexed instances | CUDA/HIP kernels, MPI ranks |

### 1.5 Latency versus throughput (GPU-1.5)

The most counterintuitive fact about GPUs, for newcomers, is that a GPU is *slower* than a CPU at nearly every individual thing it does — lower clock, simpler control, no deep out-of-order window, longer memory latency in cycles — and yet delivers 10–100× the aggregate FLOP/s on suitable code. Resolving this paradox is the single most useful mental model in GPU computing.

**The accounting identity.** From queueing theory, a unit can only stay busy if enough work is *available* to it during every busy period. A useful form of Little's Law for our purposes:

```text
Concurrency required = Throughput target × Latency of each operation
```

Applied to instruction issue: to issue one instruction every cycle on a scheduler that serves warps with a dependent instruction every *L* cycles, you need roughly *L* warps with ready instructions available to that scheduler. Now plug in realistic GPU numbers. A global-memory load on a modern GPU takes on the order of 400–600 cycles (DRAM is far away even when it is stacked HBM). A single thread — one warp on one scheduler — stalls that whole time. But if the scheduler has many warps resident, it simply issues from the others, and by the time it cycles back, the first warp's data has arrived. The latency didn't get *faster*; it got *invisible* — provided there is enough other work. That is why Hopper-class SMs keep up to 64 warps (2,048 threads) resident per SM: it is an explicit engineering decision to supply the concurrency that latency hiding requires, rather than the silicon to attack latency itself.

**Two strategies for the same wall.** Both CPUs and GPUs hit the memory wall — arithmetic is nearly free, data movement is not — but they answer it differently:

- **Latency reduction** (CPU): caches to shorten the average access, prefetchers to start loads early, out-of-order execution to find independent work within one stream. Works when the workload has little exposed parallelism.
- **Latency tolerance** (GPU): accept long latencies; keep thousands of streams so that no cycle is ever idle waiting. Works when the workload supplies massive TLP + DLP.

Neither is universally better. A branchy, pointer-chasing, serial code gives a GPU nothing to hide latency *with* — and a dense matrix product gives a CPU's sophisticated core too little parallelism to saturate its vector units. This is why "can this be parallelized, and how much data does it share?" is always the first question, before any hardware discussion.

**Bandwidth is the throughput ceiling; concurrency determines whether you reach it.** Little's Law applies to the memory system too, and here is a worked example with real numbers. An H100 SXM5 has 3.35 TB/s of HBM3 bandwidth. A DRAM access on such a system takes very roughly 500–600 ns end to end. Then:

```text
Bytes in flight required = 3.35e12 B/s × 600e-9 s ≈ 2.0 MB
```

At every instant, about **2 MB of load requests must be outstanding somewhere in the chip** for the memory system to run at full rate — spread over 132 SMs, that is ~15 KB of in-flight loads per SM, or on the order of a hundred 128-byte cache lines per SM. If your kernel doesn't generate that much concurrency (too few threads, too little ILP, dependent loads back-to-back), you *cannot* saturate HBM no matter how good the algorithm's arithmetic intensity is. This is the deep reason behind occupancy analysis (GPU-5.2) and the memory-latency-versus-bandwidth distinction (GPU-4.10): bandwidth is a rate ceiling; achieving it is a concurrency problem.

**Why dense linear algebra is the GPU's home field.** A matrix multiply of dimension *n* performs O(n³) FLOPs on O(n²) data — its *arithmetic intensity* (FLOPs per byte moved) grows with problem size. With enough data reuse (tiling), the kernel generates enormous independent multiply-accumulate work per byte fetched: DLP from the tile's elements, ILP from independent accumulations, TLP from thousands of tiles. Every form of parallelism from Topic 1.3 is available at once — which is exactly what latency hiding needs, and why HPL (a dense LU factorization built on GEMM) routinely achieves 70–90% of a machine's peak FP64 rate. Conversely, HPCG — the graph/sparse benchmark with irregular memory access and little reuse — typically extracts only 1–3% of peak. The same hardware, wildly different achieved throughput: the difference is entirely whether the workload supplies the concurrency and locality that the memory system demands.

Carry this model forward: warps and scheduling (GPU-2.x) are the mechanism that supplies instruction-level concurrency; the memory hierarchy (GPU-4.x) exists to raise effective bandwidth and lower effective latency; occupancy (GPU-5.2) measures whether enough threads are resident to hide latency; and everything in performance engineering (Theme 4) is ultimately about balancing supplied concurrency against a fixed bandwidth ceiling.

## 2. Key Developments / News

### 2.1 The June 2026 TOP500: LineShine debuts at No. 1 as five exascale systems come online

**What happened.** At ISC 2026 in Hamburg (June 23, 2026), the 67th TOP500 list was released. LineShine, a previously unlisted system at the National Supercomputing Centre in Shenzhen built by the Shenzhen Cloud Computing Center, debuted at No. 1 with 2.198 exaflop/s Rmax on HPL — more than 20% ahead of the previous No. 1. It is the first China-based system to lead the list since Sunway TaihuLight in 2017, and the fifth exascale machine overall. El Capitan (LLNL) holds at 1.809 exaflop/s (No. 2), Frontier at 1.353 (No. 3), Aurora at 1.012 (No. 4), and Europe's JUPITER Booster at exactly 1.000 (No. 5).

**What technically changed.** LineShine is a **CPU-only** design: 13,789,440 cores of LingKun LX2 processors (304 cores at 1.55 GHz) on a LingQi interconnect. Read through today's lesson, this is a striking architectural statement: a throughput machine built from an enormous number of modest, slow-clocked cores — the GPU philosophy (replicate simple units; let parallelism supply throughput) implemented without GPUs. The list as a whole now exhibits near-maximal architectural diversity: a custom Chinese manycore CPU design, AMD APU-based systems (El Capitan's HPE Cray EX255a pairs 4th-gen EPYC host CPUs with MI300A APUs — 24 Zen 4 cores + 228 CDNA 3 compute units + 128 GB coherent HBM3 per package — 11.34M cores in total, at 60.94 GFLOP/s/W), an Intel GPU exascale system (Aurora), NVIDIA Grace-Hopper systems (JUPITER, Alps), a cloud system (Azure Eagle, H100-based), and Fugaku's A64FX Arm CPUs with 512-bit SVE vectors. Five different answers to the same question — where should the FLOP/s come from?

**Why it matters, and the connection to today's concepts.** First, remember what Rmax *is*: the measured rate on HPL, a dense FP64 benchmark — i.e., a **throughput** number for a workload with maximal arithmetic intensity, which is precisely why the list is dominated by architectures built for DLP at scale (today's Topics 1.3–1.5). El Capitan's 1.809 exaflop/s against its 2.821 exaflop/s Rpeak is a 64% HPL efficiency — a number you can now reason about: the missing 36% is the accumulated cost of load imbalance, communication, and every cycle the machine couldn't fill with useful work. Second, the contrast between HPL and HPCG on the *same* machines shows the lesson of Topic 1.5 in public data: Fugaku, at 442 petaflop/s on HPL, delivers about 16 petaflop/s on HPCG (still No. 3 on that benchmark) — roughly 27× lower — because sparse, irregular workloads cannot supply the concurrency and locality that throughput hardware needs to hide latency. Third, energy: El Capitan's 60.94 GFLOP/s/W is a reminder that with Dennard scaling dead, *performance per watt* — not raw FLOP/s — is the binding constraint on machine design (Hennessy and Patterson's central argument).

**What to watch.** The November 2026 list (SC26); whether Chinese self-designed systems continue to appear given limited submission visibility; and the growing weight of HPCG, Green500, and HPL-MxP (mixed-precision) as complements to the FP64 HPL ranking — each probing a different point of the latency/throughput/locality space this curriculum is building the tools to understand.

### 2.2 Inside NVIDIA Rubin: 336 billion transistors, HBM4, and a 22 TB/s memory subsystem

**What happened.** On July 21, 2026, NVIDIA published a detailed technical blog on the Rubin GPU — the compute heart of the Vera Rubin platform announced at GTC in March 2026 and shipping in systems in the second half of 2026. The announcement fills in the architecture behind the marketing: 336 billion transistors; two reticle-limited compute dies unified on-package by the NV-HBI die-to-die link; 224 SMs; 896 Tensor Cores (4 per SM) with a third-generation Transformer Engine; up to 288 GB of HBM4 delivering up to 22 TB/s; NVLink 6 at 3,600 GB/s for scale-up; NVLink-C2C at 1,800 GB/s to the 88-core Vera CPU (NVIDIA's first fully in-house "Olympus" Arm cores); and PCIe Gen 6 host connectivity.

**What technically changed — read through today's concepts.** Nearly every headline number is an instance of Topics 1.1–1.5:

- **224 SMs** is the throughputs-by-replication strategy (Topic 1.2) taken further: more transistors (enabled by the dual reticle-limited die + NV-HBI packaging) buy more replicated SM building blocks, not a faster core.
- **HBM4 doubling the interface width versus HBM3e** is a bandwidth story — and bandwidth is the ceiling that determines whether all those SMs can be fed (Topic 1.5). NVIDIA states the 22 TB/s is a 2.8× increase over Blackwell/Blackwell Ultra.
- **50 petaflops of NVFP4** (a 4-bit floating format) versus much lower rates at higher precision is the precision-throughput trade-off: narrower operands mean more lanes per mm² and fewer bytes per FLOP (a trade we will quantify properly in GPU-3.7).
- **The Vera CPU + coherent NVLink-C2C** is the CPU↔GPU coupling trend from Topic 1.2 taken to its current extreme — CPU and GPU memory presented as a single coherent pool for the latency-sensitive control code, HBM4 for the throughput code.

It is also worth doing the balance arithmetic the press releases don't: 22 TB/s ÷ 50 PFLOP/s (NVFP4) ≈ 0.44 bytes per FLOP. A GPU can only sustain peak rate on workloads whose arithmetic intensity (after cache reuse) exceeds that ratio — a demanding threshold, and the reason NVIDIA paired the announcement with a new Tensor Memory Accelerator and locality features rather than FLOP/s alone. (This calculation is my own interpretation of the published numbers, not an NVIDIA claim.)

**Why it matters for HPC.** HPC inherits the SM/Tensor Core evolution directly: dense linear algebra (Theme 3) maps onto tensor cores, and mixed-precision HPL-MxP-style workflows live exactly on the NVFP4/FP8 throughput curve. Note also what was *not* the headline: FP64. For scientific codes that need full precision, the HPC-relevant question for the Rubin generation is the FP64 rate and its price/performance, which NVIDIA has not made the centerpiece — a live example of how a vendor's design goals (here, agentic-AI inference throughput per watt) shape an architecture that HPC then adapts to. The Vera Rubin NVL72 rack (72 Rubin GPUs + 36 Vera CPUs under NVLink 6) is claimed to train MoE models with one-fourth the GPUs of the Blackwell platform and deliver up to 10× inference throughput per watt — vendor claims that the HPC community will now test against its own workloads, exactly as this curriculum will teach you to do.
