## 0. Concise Summary

Today we open Theme 3 with the objects that everything else in dense numerical linear algebra is built from: scalars, vectors, and matrices, and the four canonical operations — matrix addition, scalar multiplication, dot products, matrix-vector products, and matrix-matrix multiplication — that LAPACK, BLAS, HPL, and HPL-MxP are assembled out of.

The single most important idea of the day is the **arithmetic-intensity ladder**: for n×n problems, matrix addition moves O(n²) numbers and performs O(n²) additions; matrix-vector multiplication moves O(n²) numbers but performs O(n²) multiply-accumulates (barely more arithmetic than data); and matrix-matrix multiplication moves O(n²) numbers but performs O(n³) arithmetic. Climbing that ladder is what turns dense linear algebra from a memory-transport problem into a compute problem, and it is *the* reason Level-3 BLAS (GEMM) dominates HPL and why whole GPUs are increasingly built as GEMM engines.

We connect the ladder to the real world with three developments: the June 2026 TOP500 list, where China's CPU-only LineShine system took No. 1 on HPL at 2.198 exaflop/s yet ranked only fourth on the mixed-precision HPL-MxP benchmark at 7.92 exaflop/s (a 3.6× speedup, versus 9.2× for El Capitan's matrix-core hardware); DeepSeek's open-source DeepGEMM library, which sustains up to 1550 TFLOP/s of FP8 GEMM on an H800 — barely 300 lines of core kernel — by making fine-grained scaling and accumulation-precision choices explicit; and NVIDIA's Blackwell architecture, whose fifth-generation tensor cores consume 4-bit NVFP4 blocks with per-16-element scale factors directly inside the matrix units, pushing the same reuse idea down to the bit level.

Why it matters: every optimization you will ever make on HPL, HPL-MxP, GEMM kernels, or GPU tile schedulers is, at bottom, a decision about how to reorganize these five primitive operations so that more arithmetic happens per byte moved.

## 1. Learn the Concepts

### 1.1 Scalars, vectors, and matrices (HPL-1.1)

Everything in numerical linear algebra reduces to rectangular arrays of numbers stored in contiguous memory. Before we can talk about performance we need to be precise about the objects themselves, because **how we index them determines how we store them, and how we store them determines how fast they move**.

A **scalar** is a single number — in HPC, a floating-point value of some precision (64-bit FP64, 32-bit FP32, 16-bit FP16/BF16, or 8/4-bit formats; we treat the bit-level structure of these in Theme-3 Module 3). A **vector** x ∈ ℝⁿ is an ordered list of n scalars, written x = (x₁, x₂, …, xₙ)ᵀ. A **matrix** A ∈ ℝ^(m×n) is a rectangular table of m·n scalars with m rows and n columns; the entry in row i, column j is aᵢⱼ.

Two indexing conventions dominate HPC, and they are not interchangeable:

- **Column-major** (Fortran, LAPACK, BLAS, HPL): consecutive memory addresses run *down* a column. The element aᵢⱼ sits at linear offset `(j-1)·lda + (i-1)`, where **lda (leading dimension)** is the allocated row count of the stored array, ≥ m. 
- **Row-major** (C, C++, PyTorch, cuBLAS with a transposition flag): consecutive addresses run *along* a row: offset `(i-1)·n + (j-1)`.

The leading dimension deserves a first-principles explanation, because you will meet it in every BLAS call. A matrix "with leading dimension lda" is really a *view* into a bigger rectangle: memory holds a lda×n buffer, and our m×n matrix occupies its top m rows. When lda = m the storage is exact; when lda > m (a *padded* storage) the gap between columns improves alignment or vectorization, a trick used inside HPL and in every blocked algorithm we will meet later.

Why does any of this matter at the hardware level? Because DRAM and caches move data in **cache lines** (typically 64 bytes = 8 FP64 values) and GPUs move data in contiguous **coalesced** chunks. An algorithm that strides through memory with stride 1 per element (the "fast" direction of the storage convention) streams full cache lines; an algorithm that strides with stride lda touches one useful word per line and wastes up to 8× the memory bandwidth. Identical mathematics, different loop order, wildly different speed — you will see this concretely in GEMV below.

**Storage cost.** An n×n matrix occupies n² scalars — 8n² bytes in FP64. A 100,000×100,000 FP64 matrix needs ~75 GB, which already exceeds a single node's memory; this O(n²) footprint is *the* reason HPL must distribute its matrix across nodes (Theme-3 Module 10) and why we will spend so much effort organizing data movement around it.

### 1.2 Matrix addition and scalar multiplication (HPL-1.2)

The simplest matrix operations are element-wise:

```
C = A + B          c_ij = a_ij + b_ij        (m·n additions)
C = αA             c_ij = α · a_ij           (m·n multiplications)
```

Cost model for m = n:

```
                arithmetic      data moved (read+write)
A + B           n² adds         3n² scalars
αA              n² muls         2n² scalars
```

Both operations are **O(n²) arithmetic on O(n²) data** — an arithmetic intensity of about 1 FLOP per 4 bytes read+written in FP64 (counting a fused multiply-add as 2 FLOPs where applicable). That ratio is the defining property of this whole class of operations: **the machine must move one operand per operation**, so the achievable speed is capped by memory bandwidth, not by FLOP/s. On a modern server CPU with ~200 GB/s of streaming bandwidth and ~3 TFLOP/s of FP64, a bandwidth-capped kernel tops out at roughly 200×10⁹ / 4 ≈ 50 GFLOP/s — about 2% of peak arithmetic. This is not an inefficiency to be engineered around by trying harder; it is a structural property of the operation itself, and the only escape is to change the *algorithm* so that each loaded operand participates in more arithmetic.

Two implementation notes that will echo throughout the curriculum:

- **AXPY** (y ← αx + y, "A X Plus Y") is the Level-1 BLAS archetype of exactly this pattern; matrix addition is just AXPY applied column by column (or row by row). Its name will reappear when we dissect BLAS levels (Theme-3 Module 4).
- **Fusion**: αA + βB (GEneral Matrix scaled SUM, `gemm`-adjacent epilogues aside) is implemented as one pass over memory, not two, because each pass costs n² loads+stores. The general lesson — *fuse element-wise passes to avoid re-streaming matrices* — is the same one that motivates epilogue fusion in modern GEMM kernels (Theme-3 Module 17), where scaling, bias, and activation are folded into the GEMM epilogue instead of running as separate bandwidth-bound kernels.

Element-wise ops are also the standard "epilogue" vocabulary of every GEMM library: when DeepGEMM or cuBLAS writes C = α·(A·B) + β·C, the +βC term is exactly the matrix-scaled-add we just defined, executed on the output tile while it is still in registers — at zero extra memory traffic.

### 1.3 Dot products (HPL-1.3)

The dot (inner) product of two vectors x, y ∈ ℝⁿ is

```
s = xᵀy = Σᵢ xᵢ·yᵢ        (n multiplies, n-1 additions)
```

It is the fundamental **multiply-accumulate (MAC)** pattern: a chain of `s += x[i]*y[i]`. Three properties make it the workhorse of everything that follows.

**(a) It is a reduction.** The n products must all be collapsed into one scalar. Sequentially, that is a dependency chain of length n: each addition waits for the previous one. Hardware breaks the chain by **tree reduction**: with p lanes, compute p partial sums in parallel, then combine — log₂(p) steps instead of p. A vector CPU unit with 8 FP64 lanes, or a GPU warp doing a shuffle-based reduction across 32 lanes, is executing exactly this tree. The cost model: n²/8 arithmetic "cycles" become ~n/8 + log₂(8) — the point is that the reduction pattern converts a latency-bound chain into a throughput-bound one, provided there are enough independent dot products in flight (and in matrix kernels there always are).

**(b) It is the quantum of GEMM.** Every entry of a matrix product is a dot product; every entry of a GEMV is a dot product. When NVIDIA quotes "tensor cores," the hardware is doing, per instruction, many small fixed-size dot products (e.g., 8×4×8 or larger fragments) with the accumulate built in.

**(c) It is where floating-point rears its head — and where precision choices are made.** A dot product of length n commits up to n-1 roundings; the error grows at worst proportionally to n·ε (ε = machine epsilon) for well-scaled data — tiny, but the *mechanism* (non-associativity of FP addition) is the same one that later decides whether an FP16 factorization needs iterative refinement (Theme-3 Modules 14–15). Modern hardware gives a partial escape: the **fused multiply-add (FMA)** computes xᵢ·yᵢ + s with a single rounding, doubling throughput and halving accumulation error. Two subtleties worth flagging now:
  - On matrix-core hardware, **multiply precision and accumulate precision are separate design choices**: NVIDIA FP8 tensor-core multiply accumulates into FP32; DeepSeek's DeepGEMM goes further and performs a *second-level* accumulation promotion on CUDA cores because, on Hopper-class tensor cores, FP8 accumulation inside the tensor core is not precise enough for long-K dot products. The choice of where the rounding happens is a performance/accuracy decision made at the kernel level, not something the hardware fixes for you.
  - The accumulation order matters for reproducibility: tree reductions give different (usually slightly *more* accurate) answers than serial sums. Same mathematics, different bits.

**Cost model.** One dot product: 2n FLOPs on 2n loads — intensity ~1 FLOP/8 bytes. As a standalone kernel it is hopelessly memory-bound (this is Level-1 BLAS territory). Its salvation, as we show next, is **embedding it inside an operation that reuses one operand across many dot products**.

### 1.4 Matrix-vector multiplication (HPL-1.4)

Now the first genuinely structural operation: y = Ax with A ∈ ℝ^(m×n), x ∈ ℝⁿ, y ∈ ℝ^m:

```
yᵢ = Σⱼ aᵢⱼ xⱼ        — each output is a dot product of a ROW of A with x
```

Equivalently, by linearity:

```
y = Σⱼ xⱼ · A[:,j]     — y is a linear combination of the COLUMNS of A, weighted by x
```

These two views compute the same thing but touch memory differently, and the difference is the whole lesson:

- **Row view (dot-product form):** stream a row of A (contiguous in row-major), dot with x (fits in cache, reused across all m rows). Each element of A is loaded exactly once.
- **Column view (AXPY form):** stream a column of A (stride lda in row-major — the *slow* direction), scale it by xⱼ, accumulate into y (stays in cache). Again each element of A is loaded once, but now the A stream is strided.

Either way, the accounting for the n×n case is: n² multiply-accumulates = 2n² FLOPs, while the *unavoidable* traffic is n² elements of A (plus negligible x, y). Arithmetic intensity ≈ 2 FLOPs per 8 bytes = ¼ FLOP/byte. On our 200 GB/s, 3 TFLOP/s CPU, that caps the kernel at ~50 GFLOP/s — **about 2% of peak, structurally, forever**. This is the defining property of Level-2 BLAS (GEMV): *each element of A participates in exactly one arithmetic operation*. No amount of vectorization changes the ratio; only changing the operation does.

And yet GEMV is everywhere: it is the shape of neural-network *decode* (one token against a weight matrix), of the iteration kernel inside iterative solvers, and of every panel-level operation in blocked LU. Making it fast is not about FLOP/s but about saturating bandwidth — which is why, when you profile a tall-skinny or low-parallelism GEMV on a GPU, you will see it pinned at the DRAM roofline, not the compute roofline. (Notably, in DeepGEMM's published small-M results, the M=64 and M=128 FP8 GEMMs report 206–645 TFLOP/s *and* memory bandwidth figures of 1500–2600 GB/s — the small-M regime of GEMM behaves like a GEMV, chasing bandwidth rather than compute.)

One more property that matters later: in y = Ax, **columns of A are independent** (each contributes xⱼ·A[:,j] to y) and **rows are independent** (each produces one yᵢ). That is a lot of available parallelism — but all of it shares the single bottleneck of streaming A once. Compare this with matrix-matrix multiplication next, where parallelism *and* intensity both explode.

### 1.5 Matrix-matrix multiplication (HPL-1.5)

The end of the ladder. C = AB with A ∈ ℝ^(m×k), B ∈ ℝ^(k×n), C ∈ ℝ^(m×n):

```
c_ij = Σₗ a_il · b_lj          (each entry: dot product of row i of A with column j of B)
     = Σₗ A[:,l] · B[l,:]      (each term: outer product of a column of A and a row of B)
```

The **outer-product (GEMM) form** is the one that matters for performance, and it deserves a careful look. Write the sum over the contraction index l explicitly:

```
C = Σₗ₌₁ᵏ A[:,l] · B[l,:]
  = A[:,1]B[1,:] + A[:,2]B[2,:] + … + A[:,k]B[k,:]
```

Each term A[:,l]·B[l,:] is a **rank-1 update**: it touches *every* entry of C, using one column of A (m values) and one row of B (n values). Now count reuse per element of the operands:

```
Outer-product pass l:   load A[:,l] (m values) + B[l,:] (n values)
                        perform 2mn FLOPs updating ALL of C
```

Across the full product, each element of A is used **n times** (once per column of B), each element of B **m times**, and each element of C accumulates k contributions. Total: 2mnk FLOPs — O(n³) for square matrices — against O(n²) operand storage. **Arithmetic intensity grows with problem size**: for n×n×n GEMM in FP64, ~2n³ FLOPs over ~3n²·8 bytes ≈ n/12 FLOP/byte. At n = 4096 that is ~340 FLOP/byte; at n = 16,384, ~1,370. Once n is large enough that a block of C and the current panels of A and B fit in fast memory, the operation is decisively **compute-bound** — the first operation on our ladder with that property.

This single fact organizes all of dense HPC:

- **BLAS levels** (Module 4) are literally this ladder: Level 1 = vector ops O(n) work on O(n) data; Level 2 = matrix-vector O(n²) on O(n²); Level 3 = matrix-matrix O(n³) on O(n²). The BLAS standard's own history makes the point: the Level-2 and Level-3 interfaces were specified in 1984–86 and 1987–88 *specifically* because vector and cache-based machines could not be exploited through Level-1 calls alone — the interface had to expose matrix-shaped work so implementers could block and reuse.
- **LAPACK, ScaLAPACK, HPL** are built by restructuring Gaussian elimination/LU so that as much work as possible becomes GEMM (Modules 6–11). In blocked right-looking LU, the trailing-matrix update A₂₂ ← A₂₂ − A₂₁·A₁₂ is a GEMM and accounts for the overwhelming majority of the ~⅔n³ FLOPs of the factorization; the panel factorization (Level-2-ish, low intensity) is the part that resists speedup. Remember this split — it is the engine of HPL tuning and the seed of HPL-MxP's design.
- **GPUs are, to first order, GEMM engines.** Tensor cores exist because the dot products inside GEMM have a fixed small structure that hardware can replicate massively; the rest of the GPU (memory hierarchy, TMA, tile schedulers) exists to keep those cores fed. When NVIDIA's Blackwell documentation says the second-generation Transformer Engine enables 4-bit FP4 with micro-tensor scaling "to optimize performance and accuracy," it is describing exactly the reuse-plus-precision game at the bottom of our ladder: store operands in NVFP4 (4-bit values with per-16-element FP8 scale factors), apply scales *inside* the tensor core, accumulate in FP32. Same C = Σₗ A[:,l]B[l,:], same reuse argument — but with 16× less operand traffic than FP64 and proportionally higher effective intensity.

**Worked micro-example.** Take m = k = n = 2, A = [[1,2],[3,4]], B = [[5,6],[7,8]]:

```
Outer-product form:
  C = A[:,1]·B[1,:] + A[:,2]·B[2,:]
    = [1]·[5 6] + [2]·[7 8]
      [3]           [4]
    = [5  6 ]   +  [14 16]
      [15 18]      [28 32]
    = [19 22]
      [43 50]
```

Check with the dot-product view: c₁₁ = 1·5+2·7 = 19 ✓; c₂₂ = 3·6+4·8 = 50 ✓. Two rank-1 updates, each element of A used twice (n = 2), each of B twice (m = 2), four MACs per output entry (k = 2) — total 2mnk = 16 FLOPs. Now imagine n = 100,000: same structure, 2×10¹⁵ FLOPs, and this is precisely the regime of a big HPL run.

**The ladder, summarized:**

| Operation | FLOPs (n×n) | Min data movement | Intensity (FP64) | Bound by |
|---|---|---|---|---|
| A + B | n² | 3n² elems | ~0.25 FLOP/B | memory bandwidth |
| xᵀy | 2n | 2n elems | ~1 FLOP/B | memory bandwidth |
| Ax | 2n² | n² elems | ~0.25 FLOP/B | memory bandwidth |
| AB | 2n³ | 3n² elems (with reuse) | ~n/12 FLOP/B, grows with n | compute (for large n) |

The border between "memory-bound" and "compute-bound" is set by the machine's **balance point** (FLOP/s ÷ bytes/s). Every performance story in the rest of this theme — blocking, packing, tiling, look-ahead, communication-avoiding algorithms, mixed precision — is a story about pushing work up this ladder or about moving the ladder's ratios into hardware.

## 2. Key Developments / News

### 2.1 June 2026 TOP500: LineShine takes No. 1 on HPL — but HPL-MxP tells the other half of the story

**What happened.** At ISC 2026 in Hamburg (June 23, 2026), the 67th TOP500 list debuted "LineShine," installed at the National Supercomputing Centre in Shenzhen, China, as the new No. 1: **2.198 exaflop/s on HPL** from 13,789,440 cores, ~80% of its 2.736 exaflop/s theoretical peak. It is the first system to exceed two sustained exaflop/s using **CPUs only** — the custom LingKun platform with 304-core LX2 processors at 1.55 GHz, the proprietary LingQi interconnect, and Kylin OS, with no NVIDIA or AMD silicon. El Capitan (LLNL) drops to No. 2 at 1.809 exaflop/s, followed by Frontier (1.353), Aurora (1.012), and JUPITER Booster (1.000) — five exascale-class systems for the first time.

**What changed technically — read the benchmark, not the crown.** The instructive part for this curriculum is the **HPL-MxP mixed-precision companion list**. There, El Capitan remains No. 1 at **16.7 exaflop/s (a 9.2× speedup over its HPL score)**, Aurora is second at 11.6 (11.5×), Frontier third at 11.4 (8.4×) — and LineShine, despite HPL dominance, is only **fourth at 7.92 exaflop/s, a 3.6× speedup**. The spread is a direct, system-scale demonstration of Section 1.5: HPL-MxP factors the matrix in low precision and recovers FP64-accuracy via iterative refinement, so its speedup over HPL is essentially a measurement of how much faster a machine's low-precision matrix engines are than its FP64 units. El Capitan's MI300A matrix cores deliver ~9×; LineShine's general-purpose CPU cores, with no dedicated low-precision accelerators, deliver ~3.6×. A CPU-only design can win the FP64 benchmark and still lose the mixed-precision one — the arithmetic-intensity ladder and the precision hierarchy are two different axes of machine design.

**Why it matters / what to watch.** HPL measures the machine your CFigures simulations run on; HPL-MxP measures the machine your mixed-precision AI and HPC workloads run on, and the June 2026 list shows these are no longer the same ranking. Watch the HPL-MxP rules, too: since the June 2025 release the minimum factorization precision is 16-bit floating point (the rules cite the lack of theory for general square systems below FP16) — a live example of benchmark design chasing hardware capability while numerical analysis tries to keep up. When we reach Modules 14–16 (mixed precision, iterative refinement, HPL-MxP structure) we will dissect exactly why FP16-plus-GMRES-refinement is considered numerically safe and where it can fail.

### 2.2 DeepGEMM: ~1550 TFLOP/s of FP8 GEMM from a deliberately small kernel

**What happened.** DeepSeek's open-source **DeepGEMM** library (GitHub, MIT license) reports up to **1550 TFLOP/s on an H800** for FP8 GEMMs — performance that matches or exceeds expert-tuned libraries — from a codebase whose original core kernel was only around 300 lines of CUDA. First released February 2025 for Hopper (SM90), it now supports SM90/SM100 (Blackwell), added weight-gradient kernels, MoE grouped GEMMs, and in April 2026 a "Mega MoE" that fuses expert-parallel dispatch, two FP8×FP4 GEMMs, SwiGLU, and the combine step into one kernel with communication overlapped.

**What technically changed.** Three design choices, all of which are today's curriculum in kernel form:
1. **Fine-grained scaling.** DeepSeek-V3's training scheme quantizes activations per 1×128 block and weights per 128×128 block to FP8 (E4M3) with FP32 scale factors, rather than scaling whole tensors. Tiny magnitudes stay representable in FP8's narrow dynamic range — precision made *local*.
2. **Explicit accumulation-precision management.** Because FP8 tensor-core accumulation on Hopper is not accurate enough over long contraction lengths, DeepGEMM performs **two-level accumulation**: the tensor core accumulates a partial dot product, which is then promoted and accumulated in higher precision on CUDA cores. Multiply precision and accumulate precision as *separate, explicit* choices — precisely the (c) discussion of Section 1.3.
3. **JIT specialization.** All kernels compile at runtime with shapes and block sizes baked in — the same "specialize the GEMM to the shape" philosophy as vendor BLAS microkernels, just made lightweight.
On Blackwell (SM100), the library's scaling-factor format changed to packed UE8M0 with a TMA-aligned transposed layout — evidence of how the scaling scheme must co-evolve with the hardware's data-movement engines.

**Why it matters.** A competitive GEMM stack no longer requires a vendor-scale team; the "GEMM is a solved problem" assumption is gone, and the winning techniques — fine-grained scaling, explicit accumulation promotion, shape-specialized JIT kernels — are exactly the algorithmic knobs that HPL-MxP-style benchmarks reward. For us, it is a readable (~few-hundred-line) reference implementation of Section 1.5's outer-product machinery plus Section 1.3's precision machinery. Watch how its grouped-GEMM "contiguous layout" constraint (M-axis grouping, expert segments aligned to the GEMM block size) is a matrix-shape/load-balance problem — Module 19 material arriving early.

### 2.3 Blackwell's NVFP4: block-scaled 4-bit operands consumed inside the tensor core

**What happened.** NVIDIA's Blackwell-generation GPUs (B200/GB200, B300/GB300) introduced fifth-generation tensor cores (tcgen05) and the NVFP4/MXFP4 4-bit formats with native support "at up to 4× the BF16 rate" (per NVIDIA's architecture page and Swordfish kernel measurements), along with the second-generation Transformer Engine for automatic precision selection. This is now the mainstream path for LLM inference kernels (FlashInfer, vLLM, SGLang, cuBLAS, CUTLASS all ship NVFP4 paths), and independent engineers have published kernels matching or beating cuBLAS on NVFP4 (e.g., Pranjal Shankhdhar's "Outperforming cuBLAS on NVFP4" write-up reaching ~99% of cuBLAS; the open Swordfish family sustaining 1,444 TFLOP/s with INT4-quantized weights on a B200 at ~90% of cuBLAS dense BF16).

**What technically changed — the format is a data-movement scheme, not just "fewer bits."** NVFP4 stores each value in 4-bit E2M1 (1 sign, 2 exponent, 1 mantissa — only the magnitudes 0, 0.5, 1, 1.5, 2, 3, 4, 6 are representable). Alone, that is useless for matrices; the format's power is that **every 16 consecutive values along the contraction dimension share an 8-bit UE4M3 scale factor**, so the effective storage is 4.5 bits/value. The dequantized value is (4-bit value) × (group scale), and — the key architectural point — **tcgen05.mma applies the scale factors inside the tensor core instruction itself**, reading E2M1 data plus scales and accumulating into FP32. No separate dequantize pass over memory. Beyond the format, Blackwell also moved GEMM accumulators out of per-thread registers into dedicated **tensor memory (TMEM)**, enabling larger tiles and cleaner mainloop/epilogue overlap — and the GB300's largest MMA shape grew from K=64 to K=96 at the same cycle count, i.e., ~50% more dot-product work per instruction.

**Why it matters / the connection.** Map it onto today's ladder: a 4-bit block-scaled operand cuts bytes moved per element by 16× versus FP64 (and ~4.5× versus FP16), which multiplies arithmetic intensity by the same factor — the same reuse argument of Section 1.5, applied at the bit level. The per-16 scale factors are Section 1.3's "where do we round" question, answered with fine-grained scaling in hardware; FP32 accumulation preserves the dot product's accuracy floor. And the FP4 panel of the June 2026 HPL-MxP list (where El Capitan's 9.2× speedup lives) is the same design philosophy at supercomputer scale. One caution for later: E2M1's seven nonzero magnitudes and the 16-element group structure mean FP4 success is *workload-dependent* — the Transformer Engine's per-layer precision selection exists precisely because not every layer survives 4 bits. When we reach Module 14 (mixed-precision numerics) we will quantify why, and Module 17 covers the kernel-side costs (conversion, alignment, tile shapes) that make "4× the BF16 rate" a ceiling, not an entitlement.
