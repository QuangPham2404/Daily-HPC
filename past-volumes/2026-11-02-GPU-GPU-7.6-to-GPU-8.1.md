## 0. Concise Summary

Last Monday's volume (GPU-7.1→7.5) built the discrete system: two memories, one PCIe wire, pinned staging buffers, and Unified Virtual Addressing (UVA) — one address *numbering* across host and device. Today we walk the rest of the spectrum from discrete to unified, and it is worth naming the four different things the word "unified" can mean, because vendors blur them constantly: unified **numbering** (UVA, done), unified **location** (managed memory moves pages so data sits where it is used), unified **contents** (coherence: CPU and GPU caches agree), and unified **translation** (one page table for CPU and devices, via the IOMMU and ATS).

Managed memory (GPU-7.6) is a *runtime-managed data-placement service*: the GPU takes page faults, and a hardware page-migration engine copies 64 KB–2 MB pages across the interconnect on demand. It is a wonderful productivity feature with a measurable cost — NVIDIA's own measurements put naive demand paging at roughly half the bandwidth of an explicit prefetch, because page-by-page fault service serializes driver work that a bulk `cudaMemcpyAsync` amortizes. Zero-copy (GPU-7.7) is the opposite philosophy: stop trying to unify anything, let GPU load/store instructions reach host memory directly over PCIe, and accept that every access pays PCIe latency and bandwidth instead of HBM. The arithmetic shows why each pattern owns a regime: data touched once favors zero-copy, data reused favors copying into HBM.

Coherence (GPU-7.8) is the property that makes fine-grained CPU↔GPU sharing correct without runtime ceremony, and it is what distinguishes the two current architectural answers — NVIDIA's NVLink-C2C on Grace Hopper and AMD's MI300A APU — from the classic PCIe-attached discrete GPU. The IOMMU (GPU-7.9) is the security and translation substrate underneath all device traffic: it maps device-visible addresses to physical memory per process, and with ATS/PRI it even lets devices fault like CPUs, removing the pinning requirement. Finally, GPU-8.1 opens Module 8 with the arithmetic that forces dedicated GPU interconnects into existence: a ring allreduce across 8 GPUs moves 1.75× the tensor size per GPU, and PCIe's ~60 GB/s per direction is simply not a serious number next to 450 GB/s of NVLink per direction.

Three developments tie this to the current industry. NVIDIA's Rubin CPX (October 2026) is a new GPU class that deliberately hangs 30 PFLOPS of NVFP4 compute off only 2 TB/s of GDDR7 and a PCIe Gen6 x16 link — the same arithmetic-intensity calculus as zero-copy, applied at product scale. NVIDIA also quietly revised Vera Rubin's specs downward in September (NVLink 6 from 3.6 to 3.0 TB/s per GPU), a reminder that interconnect bandwidth is a system-balance decision, not a marketing constant. And the June 2026 TOP500: a CPU-only Chinese system (LineShine, 2.198 EFlop/s) now leads, with the coherent MI300A-based El Capitan second at 1.809 EFlop/s — while AMD's MI400 generation pushes the APU idea further with 432 GB HBM4 per GPU.

## 1. Learn the Concepts

### 1.1 The spectrum of "unified"

Before the mechanisms, fix the taxonomy. A heterogeneous system can unify four separable things:

| Property | Question it answers | Mechanism | Topic |
|---|---|---|---|
| Numbering | Does one pointer value mean the same to CPU and GPU? | UVA | GPU-7.5 (done) |
| Location | Does data *sit* in the right memory automatically? | Managed memory / page migration | GPU-7.6 |
| Contents | Do CPU and GPU caches agree about a shared variable? | Hardware coherence (C2C, APU) or software discipline | GPU-7.8 |
| Translation | Do CPU and devices share one virtual→physical mapping? | IOMMU, ATS, HMM/SVM | GPU-7.9 |

Zero-copy (GPU-7.7) sits deliberately *outside* this progression: it unifies nothing except the pointer value, and instead extends the GPU's load/store path across the interconnect. Keeping these four axes separate is what lets you read a Grace Hopper or MI300A spec sheet critically: GH200 unifies all four (ATS gives one page table; C2C gives coherence); a PCIe-attached H100 unifies numbering only. When a vendor says "unified memory," ask *which axis* — the answer determines whether your code gets correctness for free, or just convenience at a performance price.

### 1.2 GPU-7.6 — Managed / Unified Memory: the runtime as a placement service

**The problem.** In the explicit model you, the programmer, own placement: `cudaMalloc`, `cudaMemcpy`, `cudaFree`, in the right order, on the right stream. This is verbose and brittle — and for data structures whose consumer is data-dependent (a sparse lookup table, an octree, a hash grid), you cannot know what to copy until the kernel runs. Managed memory makes placement a *service*: allocate with `cudaMallocManaged` and dereference from either side; the system moves data at page granularity to whoever touches it.

**Mechanism, by hardware generation.** The CUDA Programming Guide distinguishes several "unified memory paradigms" because the mechanism is not one thing — it depends on whether the GPU can take page faults at all [1]:

- **Pre-Pascal (Kepler, Maxwell):** no GPU page-faulting. The runtime attaches the *entire* managed allocation to the device at kernel launch and migrates it back before host access — a bulk copy at synchronization boundaries, serialized with execution. The blog-era description is exact: on a K80 the runtime "migrates all managed pages back to the device before each kernel launch, adding overhead that does not appear in the kernel profile" [3]. Worse, host access to managed memory while a kernel is running is not a fault — it is a segfault, because nothing exists to resolve the conflict.
- **Pascal and later:** the GPU implements a **page migration engine** and a 49-bit virtual address space large enough to span all system memory. Managed pages get real GPU page-table entries, and the MMU faults on non-resident accesses. The fault path: the accessing threads stall, the fault is delivered to the driver, which (1) unmaps the page on the CPU side, (2) DMA-copies the page (typically 64 KB–2 MB, far coarser than the 4 KB CPU page) across the interconnect, (3) maps it into the GPU's page tables, and (4) restarts the faulting instructions [1][3]. Hardware **access counters** on the GPU track which pages are being touched remotely, feeding driver heuristics that batch and predict migrations [4]. Concurrency becomes real: CPU and GPU can both touch managed memory; the page-level view stays consistent because the page lives in exactly one place at a time.
- **Fault batching:** a naive kernel that faults page-by-page pays the full driver round-trip per page. The GPU actually groups faults — the driver services a *fault group* covering many pages in one transaction, which is why NVIDIA's tuning advice ("assign one warp per page so faults arrive in dense groups") matters so much [2].

**Measured cost.** NVIDIA's own benchmark of a streaming workload over PCIe is the cleanest quantification available: naive on-demand migration reached **5.4 GB/s**, versus **10.9 GB/s** for `cudaMemPrefetchAsync` and **11.4 GB/s** for a plain `cudaMemcpyAsync` — demand paging at roughly half of achievable copy bandwidth [2]. Restructuring the kernel so each warp walks exactly one 64 KB page closed most of the gap (on-demand within ~30% of explicit copies), but the ordering the author states is worth memorizing: *for large contiguous regions, on-demand access with migration will never beat explicit bulk copies or prefetches* [2]. The mechanism explains the ranking: a bulk copy is one descriptor per gigabyte; demand paging is one driver transaction per handful of pages, with page-table updates and CPU-side unmap work interleaved with kernel execution.

**Oversubscription: the real payoff.** Where managed memory is not merely convenient but *enabling* is when the working set exceeds GPU memory. When the GPU faults and HBM is full, the driver **evicts** a victim page back to host memory before admitting the new one [4][5]. This is classic demand paging, and it shares the classic failure mode: a cyclic access pattern slightly larger than HBM thrashes pages across the interconnect. NVIDIA's oversubscription study of a Jacobi-style stencil found the winning strategy was to *stop faulting* — pin a static partition of the data on the GPU, mark the rest host-resident, and never let the heuristic guess again [5].

**The control APIs.** Two calls convert managed memory from "automatic" to "steerable":

```c
cudaMemAdvise(ptr, len, cudaMemAdviseSetReadMostly,  device);
cudaMemAdvise(ptr, len, cudaMemAdviseSetPreferredLocation, device);
cudaMemPrefetchAsync(ptr, len, device, stream);
```

`ReadMostly` lets the runtime replicate pages instead of migrating them (no write-back path to worry about); `PreferredLocation` pins the fault target; prefetch issues an explicit bulk migration on a stream, overlapping with compute [4]. The workflow that matters in practice: keep the `cudaMallocManaged` allocation for code clarity, then add advice + prefetch until the profiler stops showing fault traffic.

**Beyond `cudaMallocManaged`.** On Linux with recent kernels, **Heterogeneous Memory Management (HMM)** extends the same fault-and-migrate machinery to ordinary `malloc`'d memory: CPU page faults on GPU-touched ranges trigger migration in the other direction, with the CPU's page tables updated by the kernel. The CUDA guide classifies this as full unified memory *with software coherency* — contrasted with the hardware-coherency path (ATS on Grace Hopper) we meet in §1.4 [1]. The distinction: HMM still *moves* pages; hardware coherence lets both sides cache the *same* physical memory without moving anything.

**Connection.** Managed memory unifies *location* and nothing else. It buys placement automation, not shared visibility: a CPU read of a GPU-resident managed page is itself a migration event. For true simultaneous sharing, you need coherence (7.8) — or you sidestep the whole question with the crudest tool in the box, which is where zero-copy begins.

### 1.3 GPU-7.7 — Zero-copy and mapped host memory: renting remote access

**Mechanism.** Allocate host memory with `cudaHostAlloc(..., cudaHostAllocMapped)` (or page-lock an existing range with `cudaHostRegister`). Under UVA the host pointer *is* the device pointer — no `cudaHostGetDevicePointer` dance needed on modern systems — and a kernel can simply dereference it. There is no copy, no migration, no staging buffer. Each load or store becomes a PCIe transaction that travels to the root complex and reads or writes system DRAM [1][7].

That last sentence contains the entire performance model. Mapped host memory is uncached on the GPU side (the L2 does not retain it, in line with practitioner measurements of ~32-byte transaction granularity and no caching benefit [6]), so **every** access crosses the interconnect:

- Bandwidth ceiling = PCIe, not HBM: on a Gen5 x16 system roughly 50–60 GB/s effective, against 3.3 TB/s of HBM3 on an H100-class part — a ~60× gap. NVIDIA forum guidance from engineering staff puts it plainly: "Zero copy best possible access bandwidth would be the PCIe transfer speed… GPU onboard memory can easily be in the 60–120 GB/s range [on those generations], so easily 10–20× faster" for repeated access [6].
- Latency: hundreds of nanoseconds minimum, versus ~500 ns–1 µs only for the *first* HBM access in a cache line and a few ns for L2 hits thereafter.

**The amortization arithmetic.** Suppose a kernel reads a V-byte region R times (R = reuse factor). Copying costs `V/B_copy + R·V/B_HBM`; zero-copy costs `R·V/B_PCIe`. With B_copy ≈ 50, B_HBM ≈ 3300, B_PCIe ≈ 60 GB/s, break-even is at R ≈ 1.2 — **two reuses already justify copying**. This is why the standard practitioner advice is "use zero-copy when data is read once, written once, or touched sparsely" [7], and it is the same arithmetic-intensity condition that governs the whole discrete model (7.1): only streaming, high-flops-per-byte phases tolerate the wire.

**Where zero-copy genuinely wins.**

1. **Sparse, unpredictable access.** A 1 GB lookup table of which the kernel touches a few thousand random entries: copying the whole table wastes 99.9% of the transfer. Zero-copy pays PCIe only on the entries actually touched [7].
2. **Fine-grained CPU↔GPU signaling.** A pinned flag the GPU polls (or atomically bumps) for work arrival — copying is meaningless for 4 bytes; you need shared *visibility*, which is precisely what a mapped word provides. (This is also, note carefully, a manual coherence protocol — see 7.8.)
3. **Integrated systems.** On a Jetson-class SoC, CPU and GPU share one physical DRAM; zero-copy is not a performance hack but the *honest* model — a "copy" there would copy from memory to itself through a fake device alias.
4. **Write-combined host memory.** `cudaHostAllocWriteCombined` gives the host side an uncacheable, write-combining buffer that accelerates host→device transfer — with the severe caveat that *host* reads of it are very slow; it is a one-way firehose [7].

**Where it loses.** Any access pattern with reuse — stencil sweeps over a grid resident in host memory, matrix panels consulted many times, accumulation loops. The measured pattern in the NVIDIA forum thread is typical: a kernel that ran 1.9 ms with `cudaMemcpy` ran 2.7 ms with zero-copy even in a fairly streaming case, and degrades far worse as reuse grows [6]. Zero-copy also competes for the same root-complex bandwidth as your real `cudaMemcpy` traffic and NIC DMA (a system-level contention point from 7.2/7.3).

**Connection.** Zero-copy is the degenerate point of the managed-memory design space: migration granularity shrinks from 2 MB pages to individual cache-line transactions, and the driver's batching intelligence is replaced by nothing at all. It works exactly when the access pattern is so sparse that even one page of movement is waste. Managed memory and zero-copy are thus two points on a granularity axis — and both still *move or reach across* the boundary. The next topic asks what it would take to stop treating the boundary as a data-motion problem at all.

### 1.4 GPU-7.8 — Memory coherence between CPUs and accelerators

**Coherence vs. consistency.** Two terms the HPC literature keeps sharp and marketing blurs: **cache coherence** is the property that all processors see a single agreed value for each memory location (no stale copies in private caches); **memory consistency** is the rules for the *ordering* of accesses (what sequence of writes a reader may observe). You need coherence for a shared flag to work at all; you need a consistency model to know whether the flag's write is observed *before* the data it guards.

**Why the discrete system has neither.** In a PCIe-attached server, the CPU's coherence domain ends at the root complex. The GPU's L2 and the CPU's L3 never snoop each other; a `cudaMemcpy` is not just data movement but a *coherence protocol implemented in software*: the API's synchronization semantics guarantee that when the copy returns, both sides agree about that buffer's contents. This is why the explicit model is verbose — the verbosity *is* the protocol. The tools that exist at this boundary are deliberately narrow:

- `cudaDeviceSynchronize()` / stream events: bulk ordering points;
- mapped host memory + volatile/atomics on pinned words: a hand-rolled message protocol (7.7);
- system-scope fences (`__threadfence_system()`) and system-scope atomics on newer architectures: exactly-enough ordering for single-word communication, still nothing for cached data blocks.

**The coherent alternative, mechanism-level.** Two shipping architectures remove the boundary:

- **NVIDIA Grace Hopper (GH200).** The NVLink-C2C chip-to-chip interconnect (900 GB/s total, 450 GB/s per direction — about 7× a Gen5 x16 link, at 1.3 pJ/bit) is a *coherent* fabric: the Grace CPU can cache GPU-resident HBM at **cache-line granularity**, the GPU can access LPDDR5X directly, and both sides execute native atomic operations into either memory [8]. With ATS (§1.5), CPU and GPU share a single per-process page table, so the CPU heap, thread stacks, and memory-mapped files are simply *addressable* by GPU code — "extended GPU memory" of ~608 GB per superchip, visible to the OS as NUMA nodes [8]. The coherence protocol itself is directory-based invalidation, consistent with an AMBA CHI-style protocol — established not by the datasheet but by the ISMM 2026 empirical litmus study we covered two Mondays ago, which also found the GPU's *internal* coherence relies on write-through and self-invalidation rather than classical writer-initiated invalidation [9].
- **AMD MI300A (El Capitan's APU).** The opposite packaging philosophy: 24 Zen 4 CPU chiplets, 6 CDNA 3 XCDs (228 CUs), and 128 GB of HBM3 on one package, unified at 5.3 TB/s behind a coherent Infinity Fabric. The 256 MB Infinity Cache sits *beyond* the coherence point — both CPU and GPU clients share it without probes or flushes — and all eight HBM stacks are interleaved uniformly (NPS1), so there is no "CPU memory" or "GPU memory" at all, one physical pool with one fact about every line [10]. This is why El Capitan's programming model (HIP with managed allocations) can treat the node as a single memory image.

**What coherence buys, and what it costs.** The gains: no page migration for sharing (only *caching* of remote lines), fine-grained producer–consumer pipelines (GPU computes a tile, CPU consumes it via a flag protocol at cache-line granularity instead of buffer-granularity copies), and fast cross-device atomics for work queues [8]. The costs are just as physical: every remote access still crosses C2C at 450 GB/s per direction — an order of magnitude under HBM bandwidth — so coherence improves *correctness and latency of sharing*, not the bandwidth of streaming. And the ISMM paper's lesson stands: "cache-coherent" does not tell you the *consistency model*; independently compiled CPU and GPU code sharing memory needs the model verified (CMCM on GH200), not assumed [9].

**Connection.** Coherence unifies *contents*. But for CPU code and GPU code to even agree on *which* physical bytes a pointer names, translation itself must be shared — which is the IOMMU's story.

### 1.5 GPU-7.9 — IOMMU, address translation, and device memory access

**The problem.** Devices that master the bus issue *physical* addresses; CPUs and GPUs compute with *virtual* addresses. In the oldest model, the driver reconciles this by brute force: pin the buffer (so physical pages cannot move), build a scatter-gather list of physical page frames, and program the device with those. Three deficiencies: (1) the device can DMA anywhere it is told — a malicious or buggy device (or one tricked by a compromised driver) can overwrite all of system memory; (2) virtual memory semantics break — you cannot DMA to a page that isn't resident, so anything involving demand paging is off-limits; (3) per-process isolation is impossible when every device shares one flat physical view.

**The IOMMU (DMA remapping).** An IOMMU sits on the path from PCIe to system memory and translates every device transaction: device presents an **I/O virtual address (IOVA)**, the IOMMU consults I/O page tables (built by the kernel from `dma_map` / VFIO calls) and rewrites the transaction to a physical address — or blocks it if unmapped. Everything follows from this one mechanism:

- **Isolation:** a VM or container given a GPU via VFIO can only DMA into memory the hypervisor mapped for it. This is the security foundation of modern accelerator virtualization, and the reason "IOMMU groups" appear in every passthrough setup guide.
- **Simpler DMA:** buffers do not need to be physically contiguous; the I/O page tables provide scatter-gather in translation.
- **Address translation services (ATS):** a device-side TLB. The device caches translations it obtains from the IOMMU, so steady-state DMA pays no remap latency; the kernel keeps the device TLB coherent with CPU page tables via invalidations [11].

**Shared virtual memory (SVM/SVA).** The full extension: tag each device transaction with a **PASID** (process address-space ID), so the IOMMU translates it *in that process's page tables* — the device now uses the same virtual addresses as the CPU code that launched it. With the **Page Request Interface (PRI)**, a device whose ATS lookup misses can ask the OS to fault the page in, exactly like a CPU page fault; the Linux kernel's SVA documentation is explicit that this removes the pinning requirement for DMA — the device participates in demand paging as a first-class citizen [11]. This is the same ATS concept NVIDIA uses across NVLink-C2C: on GH200 it is what lets CPU and GPU share one per-process page table (§1.4) [8]. (CUDA's HMM path is the software-coherent cousin: same goal, reached by kernel fault handlers instead of IOMMU hardware [1].)

**Costs.** Translation is not free: every IOTLB miss adds latency to a DMA, and huge working sets with poor reuse translate poorly (the reason `dma_map` of gigabytes used to hurt, and why peer-to-peer traffic is often mapped with large pages or bypasses where legal). For GPUs specifically, ATS+PRI trades the classic GPU contract — "memory is pinned, physical, fast" — for the CPU contract — "memory is virtual, faultable, shared." Which contract an architecture chooses is now a genuine design axis, not a detail.

**Connection.** With translation, coherence, placement, and numbering all covered, the heterogeneous *node* is architecturally complete — one GPU or one superchip talking to one CPU. The next question is what happens when there are eight of them, because that is where the interconnect arithmetic stops being forgiving.

### 1.6 GPU-8.1 — Why multiple GPUs need dedicated interconnects

**The problem, quantified.** Take the single most common multi-GPU communication pattern in both HPL-style linear algebra and deep learning: the **allreduce** — every GPU ends with the sum of its per-GPU array (a row of the distributed matrix product, a gradient tensor). On a ring of N GPUs, the standard ring-allreduce algorithm has each GPU send and receive `2(N−1)/N · V` bytes for a V-byte tensor [12]. For N = 8 and V = 1 GB (a modest FP16 gradient tensor):

- over PCIe Gen5 x16 (~60 GB/s per direction): 1.75 GB ÷ 60 GB/s ≈ **29 ms** per iteration;
- over NVLink 4 (450 GB/s per direction per GPU, H100-class): 1.75 GB ÷ 450 GB/s ≈ **3.9 ms**.

At a 100 ms training iteration or a 200 ms HPL iteration, the PCIe version burns ~15–30% of the step purely on the collective — *before* counting the fact that PCIe traffic also contends with host transfers. And allreduce is the *polite* pattern: Mixture-of-Experts routing and fast Fourier transforms demand all-to-all, which multiplies the pressure. Dense linear algebra is no kinder: the look-ahead panel broadcast in HPL (a theme we will meet properly in Module 3's HPL volumes) serializes the algorithm behind the broadcast bandwidth of one 1 MB panel every N·(block) flops.

**Why PCIe specifically falls behind.** Three structural reasons, all from 7.2's mechanics:

1. **Width.** A GPU gets at most x16. NVLink was designed from the start as an *aggregate* of many narrow, close-coupled links — 18 links on H100, each carrying far more than a PCIe lane, terminated directly at the GPU die rather than through a host root complex.
2. **Topology.** PCIe is a tree rooted in the CPU; GPU-to-GPU traffic through a shared switch is fine, but across root complexes it crosses UPI, and peer-to-peer through the CPU contends with everything else the host is doing (the hierarchy we dissected in the DIST-7.6 volume). NVLink builds a direct GPU-to-GPU (and, via NVSwitch, all-to-all) fabric with no host in the loop.
3. **Protocol purpose.** PCIe is a general-purpose I/O protocol — discovery, enumeration, config space, arbitrary devices. NVLink is a cache-coherent-class memory protocol between exactly the processors that need it: remote loads, stores, and atomics, with multicast support in recent generations.

**What "dedicated interconnect" buys beyond bandwidth.** Because NVLink carries load/store/atomic semantics (not just DMA), one GPU can dereference a pointer into another GPU's HBM — peer-to-peer memory access, the topic of GPU-8.2 — and the software stack can implement collectives as direct memory traffic rather than staged copies. The generations escalate exactly along the axis Module 8 will trace: NVLink 4 at 900 GB/s per GPU (Hopper), NVLink 5 at 1.8 TB/s (Blackwell), NVLink 6 at 3.0–3.6 TB/s per GPU (Rubin, per current NVIDIA specifications — see §2.2 for the September revision) [13].

**The system-balance view.** A useful mental model for everything ahead in Module 8: each GPU contributes `B_link` of injection bandwidth into the scale-up fabric and needs `B_mem ≈ 3–8 TB/s` of local HBM bandwidth. The ratio `B_mem/B_link` (roughly 4:1 on NVLink-4/5 systems) is the *communication tolerance* of the architecture: algorithms must amortize communication by at least that many bytes of local work per byte moved. PCIe-only systems have a tolerance near 60:1 — which is why they only host embarrassingly parallel workloads comfortably. When Rubin CPX (§2.1) attaches 30 PFLOPS to ~1 Tb/s of PCIe anyway, it is betting the workload's arithmetic intensity makes that ratio acceptable — the same bet zero-copy makes in §1.3, at a thousand times the scale.

**Connection.** This topic is the doorstep of Module 8: peer-to-peer access (8.2), NVLink's own link-level mechanics (8.3), switched fabrics (8.4), AMD's Infinity Fabric answer (8.5), topology mathematics (8.7–8.9), and the scale-up/scale-out boundary (8.10). Keep the 29 ms vs 3.9 ms allreduce in mind — nearly everything that follows is an engineering response to that gap.

## 2. Key Developments / News

### 2.1 NVIDIA Rubin CPX: a PCIe-attached GPU, on purpose (October 2026)

**What happened.** At the AI Infra Summit (October 2026), NVIDIA announced **Rubin CPX**, "a new class of GPU purpose-built for massive-context processing" — million-token inference prefill, long-context code generation, generative video. Per NVIDIA's announcement: 30 PFLOPS of NVFP4 compute, 128 GB of GDDR7 (NVIDIA's first GDDR7 data-center GPU), 3× faster attention than GB300 NVL72, shipping in the Vera Rubin NVL144 CPX rack platform (8 exaflops NVFP4, 100 TB fast memory, 1.7 PB/s aggregate memory bandwidth) by late 2026 [14].

**What technically changed.** The architecture is the interesting part, and SemiAnalysis's analysis nails the mechanism: prefill is compute-bound (processing a fresh long prompt is one dense forward pass — high arithmetic intensity, little KV-cache reuse), so a prefill-specialized GPU can be "skinny on memory bandwidth and relatively fat on compute." Rubin CPX is a monolithic die with 128 GB of GDDR7 at ~2 TB/s and — the figure that matters for today's curriculum — **only 16 lanes of PCIe Gen6 (~1 Tb/s unidirectional) for off-chip I/O, versus 14.4 Tb/s of NVLink 6 on the R200 Rubin GPU it sits beside** [15]. It is not an island in the NVL144 CPX rack: CPX dies share trays with R200s and can hand decode-phase work (KV caches) to their HBM-equipped siblings.

**Why it matters, and the connection.** This is the zero-copy/copied-data arithmetic of GPU-7.6/7.7 applied at product scale. NVIDIA's mainstream answer to "how does data reach compute" is NVLink + HBM (14.4 Tb/s + 20.5 TB/s per R200); the CPX answer is "when the workload streams data once and computes hundreds of flops per byte, PCIe Gen6 and GDDR7 suffice, and the BOM cost of HBM is waste." The same company now sells both answers simultaneously in one rack — the strongest possible demonstration that *no interconnect is "fast" or "slow" in the abstract; bandwidth adequacy is a function of the workload's bytes-per-flop ratio*. For HPC readers the corollary is familiar: this is precisely the HPL/HPCG split (dense streaming compute vs. bandwidth-starved sparse memory traffic) reappearing as silicon product segmentation. Watch: whether "prefill/decode disaggregation" spreads beyond inference into HPC serving patterns, and whether GDDR7-class GPUs appear in traditional HPC nodes as cost-optimized alternatives to HBM parts.

### 2.2 Vera Rubin's spec revision: NVLink 6 walks back from 3.6 to 3.0 TB/s (September 2026)

**What happened.** In September 2026, NVIDIA quietly revised the published Vera Rubin specifications; the change surfaced in October via IT Home, ServeTheHome, Wccftech, and others comparing archived spec pages. Per-GPU NVLink 6 bandwidth dropped from 3.6 TB/s to **3.0 TB/s** (−17%), HBM4 bandwidth from 22 to **19.2 TB/s** (−13%, achieved by dropping stack speed from ~10.75 to 9.375 Gbps/pin), the NVL72 rack's NVLink aggregate from 260 to 216 TB/s — while scale-out *networking* bandwidth was revised *up* from 28.8 to 32.4 TB/s [16][17].

**What technically changed.** Two things. First, the HBM4 trim is a memory-yield/speed-bin decision — shipping 8 stacks at a slower, more reliable pin rate — the same physics that governs every HBM generation's gap between announcement and production parts. Second, the NVLink cut keeps the GPU's scale-up-to-memory ratio in a familiar band: 19.2 TB/s local memory against 3.0 TB/s scale-up injection is a 6.4:1 communication tolerance, right where Hopper (3.35:0.9 ≈ 3.7:1) and Blackwell (8:1.8 ≈ 4.4:1) sit — NVIDIA chose balance over a headline number.

**Why it matters, and the connection.** For everything Module 8 will cover, this revision is a live lesson in reading interconnect claims: NVLink bandwidth is not a constant of nature but a per-product decision traded against memory bins, switch silicon, and power — and announcement-stage numbers are targets, not measurements. For TOP500 watchers, the ratio also sets expectations: at 6.4:1, communication-avoiding formulations matter on Rubin exactly as they did on Hopper. Watch: whether the numbers hold through first production shipments (ServeTheHome reports hardware is now arriving [16]), and how AMD's MI455X (§2.3) lands against the revised figures.

### 2.3 TOP500 June 2026: a CPU-only system leads, and coherence is now the mainstream (June 2026)

**What happened.** The 67th TOP500 list (ISC 2026, Hamburg, June 23, 2026) debuted **LineShine** at No. 1 — a Chinese system at the National Supercomputing Centre in Shenzhen built on the custom LingKun platform: 304-core LX2 CPUs at 1.55 GHz, 13.79 million cores total, the proprietary LingQi interconnect, and 2.198 EFlop/s on HPL, ending El Capitan's run and becoming the fifth exascale system and the first Chinese No. 1 since Sunway TaihuLight in 2017. El Capitan (HPE Cray EX255a, **AMD MI300A** APUs) holds No. 2 at 1.809 EFlop/s; Frontier, Aurora, and JUPITER Booster (GH200-based) round out the exascale five. On HPCG, LineShine leads with 22.0 PFlop/s, El Capitan second at 17.41 [18].

**What technically changed.** Two architecture stories are embedded in the top five. First, LineShine's HPL-to-HPL-MxP ratio (2.198 EF HPL vs 7.92 EF HPL-MxP, a modest 3.6×) confirms a CPU-only design without low-precision matrix accelerators — peak HPL through core count and interconnect, not tensor cores. Second, positions 2 and 5 are *coherent heterogeneous* systems: El Capitan's MI300A nodes (Zen 4 + CDNA 3 sharing 128 GB HBM3 coherently — the architecture of §1.4) and JUPITER's GH200 superchips (NVLink-C2C coherence). The coherence question of GPU-7.8 is no longer a niche: it is the load-bearing design decision of two of the world's five exascale machines.

**Why it matters, and the connection.** El Capitan's HPCG result (17.41 PFlop/s — 0.96% of its HPL, but far ahead of most GPU systems) is widely attributed in part to exactly the mechanism of §1.4: a unified, coherent memory pool removes the host-staging tax that penalizes irregular, communication-heavy codes on discrete GPUs. Meanwhile AMD is doubling down: the Instinct MI400 generation (CDNA 5) brings 432 GB of HBM4 per GPU at 23.3 TB/s, and the MI455X-based Helios rack couples 72 GPUs into a 31 TB shared HBM4 "pod" over the UALoE fabric with single-hop all-to-all [19] — coherence from the package extended to the rack. The trajectory to watch for Module 8 and beyond: the NUMA-like hierarchy of §1.4 (host memory, HBM, peer HBM) growing another tier — *rack-shared memory* — with NVLink Fusion, UALoE, and CXL competing to define it.
