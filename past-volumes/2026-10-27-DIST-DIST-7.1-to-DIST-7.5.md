## 0. Concise Summary

The last DIST volume ended at the point where a CUDA-aware MPI implementation decides to move GPU-resident data with "RDMA" instead of staging it through host memory. Today we open the hood on that word. Module 7 of the DIST curriculum — RDMA and GPUDirect RDMA — starts with five topics that form one causal chain: what RDMA *is* semantically (DIST-7.1), the queue-based hardware interface — verbs, queue pairs, completion queues — through which software drives it (DIST-7.2), the memory-registration machinery that makes direct device access safe (DIST-7.3), the precise mechanical distinction between ordinary DMA and RDMA (DIST-7.4), and finally GPUDirect RDMA, which points the NIC's DMA engine at GPU memory instead of host memory (DIST-7.5).

The single most important idea of the day: **RDMA is not magic cross-machine access — it is two local DMA engines coordinated by pre-exchanged addressing and authorization data.** The sender's NIC DMA-reads the payload out of local memory, the network carries it, and the receiver's NIC DMA-writes it into local memory. What makes it "remote" is that the *sender* specifies the receiver's virtual address plus a key, and the receiver's CPU is never on the data path. Once you see that decomposition, GPUDirect RDMA stops being a buzzword: it is simply the statement that the two *local* DMA legs may target GPU memory through the PCIe BAR window, with the remote side none the wiser.

Three developments tie this to the current HPC world. First, NVIDIA's October 2026 unification of GPU-initiated RDMA under an open-source DOCA GPUNetIO layer — where CUDA kernels themselves post work queue entries and ring NIC doorbells — is a direct escalation of today's verbs/queue-pair model. Second, the Ultra Ethernet Consortium's Specification 1.0 (June 2025) is a ground-up re-architecture of the RDMA transport for million-endpoint fabrics, challenging assumptions baked into the per-queue-pair ordered-stream model you will learn today. Third, ConnectX-8 — an 800 Gb/s SuperNIC with an integrated PCIe Gen6 switch now shipping in GB300-class systems — changes the very GPU↔NIC PCIe path that bounds GPUDirect RDMA performance.

By the end of this issue you should be able to trace a single inter-node `MPI_Send` of a GPU buffer byte-by-byte — every queue, every key, every DMA — and say exactly which hardware does what.

## 1. Learn the Concepts

### 1.1 Where we are: below the communication library

From DIST-6.4 you know that a CUDA-aware MPI implementation accepts a `cudaMalloc` pointer in `MPI_Send`, detects that it is a device pointer through CUDA's Unified Virtual Addressing, and chooses a transport: CUDA IPC inside a node, RDMA zero-copy between nodes, staged copies as fallback. From DIST-6.5–6.6 you know that GPU memory must be pinned and mapped into the GPU's PCI Base Address Register (BAR) window before a NIC can address it, and that libraries keep registration caches to avoid re-paying that cost.

What we have *not* yet dissected is the machinery underneath: what "RDMA" actually means as an operation, what interface the CPU uses to command the NIC, what the NIC checks before it is allowed to touch memory, and how the whole thing relates to the plain DMA that every device in a machine already does. That is Module 7. Today's five topics build that picture from semantics down to the GPU-specific path, and next Tuesday's DIST-7.6–7.9 will complete it with topology, driver support, and fast-vs-fallback reasoning.

### 1.2 DIST-7.1 — Remote Direct Memory Access

**The problem.** A conventional sockets-based send traverses the full kernel network stack: the application copies data into a kernel buffer (or the kernel copies from user pages), TCP/IP headers are processed, the NIC is fed through descriptors, and on the receiver the process repeats in reverse — kernel receive buffers, protocol processing, a final copy into the application's buffer. Each message costs several memory copies, at least two context transitions per side, and CPU cycles for protocol processing. At message rates of millions per second — which large MPI jobs and modern distributed training absolutely generate — the CPU becomes a data-moving appliance, and end-to-end latency sits in the tens of microseconds.

**The RDMA contract.** RDMA removes the remote CPU from the data path entirely. Its three defining ingredients, in the canonical phrasing used since the Virtual Interface Architecture work that led to InfiniBand:

1. **Kernel bypass** — the application posts work directly to the NIC from user space (memory-mapped queues and registers), so the fast path involves no system call.
2. **Asynchronous work queues** — operations are *posted* and later *completed*, decoupling software from the data transfer itself and enabling overlap of communication with computation.
3. **Remote direct placement ("one-sided" operations)** — the incoming message itself carries the destination address; the receiver's NIC places the payload directly into the target buffer with zero copies and zero CPU involvement. The receiver's CPU may not even be scheduled.

The one-sided operations are the heart of it:

- **RDMA Write** — the sender's NIC writes a block of local memory into a *specific address* in the receiver's memory.
- **RDMA Read** — the sender's NIC fetches a block *from* a specific address in the receiver's memory.
- **RDMA Atomics** — a remote compare-and-swap or fetch-and-add on a 8-byte value, the primitive that later enables flags and counters in one-sided programming models (you will meet them again in NVSHMEM, Module 10).

Contrast this with **Send/Receive**, the two-sided message semantics: the receiver must have *pre-posted* a receive descriptor telling its NIC where an incoming message may be placed, and each incoming message consumes one of those descriptors. Both models are zero-copy; the difference is *who* knows the destination address — the sender (RDMA) or the receiver (Send/Receive). MPI's rendezvous protocol for large messages uses exactly this distinction: after a small handshake, the receiver reveals `(address, key)` for its application buffer and the sender RDMA-writes (or reads) directly into it.

A subtlety worth knowing because it bites real programs: the completion of an RDMA Write at the *initiator* guarantees that the responder's NIC has accepted the data — per the InfiniBand Architecture specification it is not, in the base model, a guarantee that the data is globally visible in the responder's memory yet. Upper layers add flush/fence semantics when that guarantee is needed (NVSHMEM's `quiet`, for example). File this away; it explains why "the write completed" is sometimes not the same as "the reader can see it".

The payoff, measured: RDMA write round-trip times on modern InfiniBand hardware are on the order of 1–2 µs, versus tens of microseconds for kernel TCP — with effectively all of the CPU left free, and payload bytes crossing each host's memory system exactly once (at the NIC's DMA, and not again).

### 1.3 DIST-7.2 — RDMA verbs and queue pairs

**The interface.** "Verbs" is the name for the API through which software commands an RDMA-capable NIC (InfiniBand HCA, RoCE NIC, or iWARP NIC). The name comes from the specification treating `post_send`, `poll_cq`, and friends as *verbs* — abstract operations each vendor implements. The Linux user-space implementation is `libibverbs` (part of rdma-core): verbs operate on objects that live in the NIC's own memory, mapped into the process.

**The central object: the queue pair (QP).** A QP is a communication endpoint — conceptually the RDMA analogue of a socket, but *a hardware resource*. It consists of two work queues:

```
        Queue Pair (QP) — one per communication endpoint
 ┌────────────────────────────────────────────────────┐
 │  Send Queue (SQ)          Receive Queue (RQ)       │
 │  ┌────┬────┬────┐        ┌────┬────┬────┐          │
 │  │WQE │WQE │WQE │        │WQE │WQE │WQE │          │
 │  └────┴────┴────┘        └────┴────┴────┘          │
 │   posted by CPU:           posted by CPU:           │
 │   RDMA Write/Read/         "next message may be     │
 │   Send, with SGEs          placed in this buffer"   │
 └──────────────┬─────────────────────────┬────────────┘
                │ completions             │ completions
                ▼                         ▼
        ┌─────────────────────────────────────┐
        │  Completion Queue (CQ)              │
        │  CQE CQE CQE ...  (FIFO, polled)    │
        └─────────────────────────────────────┘
```

- **WQE** ("work queue element", pronunciation "wookie") — a work request the NIC will execute: an opcode (RDMA Write, RDMA Read, Send, …), a list of scatter/gather elements (SGE) describing local buffers by `(address, length, local key)`, plus — for one-sided ops — the *remote* virtual address and remote key, and flags.
- **CQE** ("cookie") — the completion entry the NIC writes when a WQE finishes, retrievable with `ibv_poll_cq`. Buffers may only be reused after their CQE is polled. Multiple QPs can share one CQ, which is how libraries keep polling efficient at scale.
- **Doorbell** — the memory-mapped NIC register the CPU writes (a plain x86 store to a BAR mapping, no syscall) to tell the NIC "new WQEs are ready in the queue". On Mellanox/NVIDIA NICs an optimization called **BlueFlame** writes the *entire first WQE* through the doorbell register so small operations never require the NIC to fetch the descriptor from host memory.

**How a transfer proceeds.** For an RDMA Write: the CPU builds a WQE in the SQ (in host memory, mapped to the NIC), rings the doorbell; the NIC's DMA engine fetches the WQE, validates keys, DMAs the payload out of local memory, transmits; the responder NIC validates the remote key, DMAs the payload into the target buffer, ACKs; the initiator NIC writes a CQE. The CPUs on both sides did nothing except post and (eventually) poll. That is the entire fast path — no interrupts, no kernel, no copies.

**Connection state and transport types.** A QP is a state machine (RESET → INIT → RTR → RTS before it can send). To connect two QPs, the two processes exchange identifying information — queue pair numbers, port/GUID addresses, and the remote key of the memory to be accessed — through an out-of-band channel (MPI and NCCL use a TCP socket or shared memory for this bootstrap). The transport service chosen for the QP determines reliability:

| Service | Semantics | Where used |
|---|---|---|
| RC — Reliable Connection | Ordered, lossless, one dedicated peer | MPI, NCCL, NVSHMEM (the HPC default) |
| XRC — eXtended RC | RC semantics, many remote QPs share resources | Large MPI jobs on Mellanox fabrics |
| UC / UD — Unreliable | No ordering / no delivery guarantee | Multicast, discovery, some RLNC research |

RC's ordered-stream-per-QP model is what makes MPI semantics natural — and, as Section 2.2 will show, it is precisely the property the Ultra Ethernet transport redesigns at scale.

**Why this design exists.** The queue model converts network I/O into ordinary asynchronous device work, exactly like a GPU command queue: submit descriptors cheaply, overlap execution, harvest completions in batches. It also makes the interface *device-neutral* — the same verbs drive InfiniBand and RoCE hardware — which is why MPI, NCCL, UCX, and storage stacks can all sit on one API.

### 1.4 DIST-7.3 — Memory registration in RDMA

**The problem.** A NIC's DMA engine works in *physical/bus addresses*, but applications hand it *virtual* addresses. Virtual pages can be swapped out, migrated by NUMA balancing, or remapped at any moment — a DMA engine chasing a stale translation would corrupt whatever now occupies that physical page. Before the NIC may DMA to or from a buffer, three things must therefore be established:

1. **Pinning** — the virtual range is translated to a list of physical pages that are locked in place (`get_user_pages()` in Linux). The pages cannot migrate while the registration is live.
2. **Mapping** — the NIC is programmed with that page list (a scatter/gather translation table or an IOMMU mapping) so it can translate the buffer's virtual addresses itself, on the fly.
3. **Authorization** — the NIC is told *what kinds* of access are permitted.

The verb that does all three is `ibv_reg_mr()`: it registers a **memory region (MR)** — `(base address, length)` plus an access mask (`LOCAL_WRITE`, `REMOTE_READ`, `REMOTE_WRITE`, `ATOMIC`, …) — within a **protection domain (PD)**, and returns two keys:

- **lkey (local key)** — used in SGEs by the *local* CPU when posting WQEs against this memory.
- **rkey (remote key)** — the handle a *remote* peer must present to DMA into (or read from) this region. The receiver's NIC checks the rkey on every incoming one-sided operation; a mismatch is a protection fault delivered as a failed completion, not a silent corruption.

The key design insight is that **authorization is pre-negotiated, per region, with the hardware** — the remote CPU never mediates, yet the memory is still protected. RDMA is "unprotected direct access" only in the sense that no *software* checks each operation; the NIC's key check *is* the protection.

**Cost, and how real stacks manage it.** Registration is expensive: pinning touches every page of the region, and for GPU memory (as established in DIST-6.5) building the BAR mapping can cost up to milliseconds. For host memory, registering a large buffer costs on the order of tens of microseconds — small per message, ruinous per *message rate*. This is exactly why DIST-6.6's registration caches exist, why MPI libraries use fast re-registration/memory-window techniques for rendezvous buffers, and why `IBV_SEND_INLINE` exists (payloads under ~100 bytes can be embedded directly in the WQE, requiring no registration at all).

**Modern relaxations.** Two developments soften the pin-everything model and both matter for GPU systems:

- **On-Demand Paging (ODP)** — register a region *without* pre-pinning; the NIC faults pages in through the kernel on first touch (`IBV_ACCESS_ON_DEMAND`). Trades a first-access penalty for registration that is nearly free; excellent for sparsely touched huge regions.
- **dma-buf registration** — `ibv_reg_dmabuf_mr()` registers memory exported by another driver through the Linux dma-buf framework. This is the mechanism the GPU world is migrating toward for RDMA access to device memory, replacing the older `nvidia-peermem` peer-memory module path you met in DIST-6.5. Keep this name in mind; it returns in Section 2.

### 1.5 DIST-7.4 — DMA versus RDMA

These two terms are routinely conflated because they share a mechanism. The distinction is worth stating precisely.

**DMA (Direct Memory Access)** is the *local* capability: a device's engine moves data between that device and system memory (or between two devices through the fabric's peer-to-peer addressing) without the CPU copying word-by-word. Your NIC DMAs packets into ring buffers; your NVMe drive DMAs blocks into user pages; a GPU copy engine DMAs the payload of `cudaMemcpy` across PCIe. Scope: **one machine's bus**. Addressing: **physical/bus addresses**, guarded by the IOMMU or the driver's mapping. Initiated by: **software on that machine** programming a descriptor.

**RDMA** is the *network* capability: the memory being read or written belongs to a **remote** endpoint, the operation is specified by the *initiator*, and the remote CPU is uninvolved. Crucially, though, RDMA is *implemented out of local DMA legs*:

```
RDMA Write of buffer B from node A to node B, decomposed:

 A: CPU posts WQE ──▶ A's NIC DMAs payload OUT of A's memory   ← local DMA, node A
                          │
                          ▼  network packets (carry B's VA + rkey)
                          │
 B:                 B's NIC validates rkey,
                    DMAs payload INTO B's memory               ← local DMA, node B
```

| Dimension | DMA | RDMA |
|---|---|---|
| Scope | Within one host/box | Across the network, node to node |
| Who specifies the target | Local software (descriptor) | The *initiating* endpoint's WQE |
| Target addressing | Physical / bus address, IOMMU-checked | Remote *virtual* address + rkey, NIC-checked |
| Remote CPU involvement | n/a (no remote) | None — by definition |
| Relationship | Building block | Two coordinated local DMA legs + transport |

So the honest statement is: **RDMA = (local DMA) + (network transport) + (pre-exchanged keys and addresses that make the remote leg direct)**. The "R" is about *authority and addressing*, not a new kind of physics.

Why this decomposition matters — two payoffs. First, it demystifies GPUDirect (next section): making "RDMA work with GPU memory" reduces to making the *local* DMA legs able to target GPU memory; nothing about the wire protocol changes. Second, it clarifies performance analysis: an RDMA operation's cost is the sum of descriptor fetch, local DMA, serialization, remote DMA, and completion — and each leg is bounded by the local bus. A 400 Gb/s NIC moving data to GPU memory over a PCIe Gen5 x16 link (~64 GB/s theoretical, ~50 GB/s practical) is bounded by the *PCIe leg*, not the network — until the next generation of both (Section 2.3).

### 1.6 DIST-7.5 — GPUDirect RDMA

**The problem, recalled.** DIST-6.2 quantified the staged path for GPU-resident data: `GPU → host DRAM (D2H) → NIC → network → NIC → host DRAM (H2D) → GPU`. Per message that is four PCIe crossings, multiple passes of the payload through host DRAM, and CPU cycles on both ends orchestrating the copies.

**The mechanism.** GPUDirect RDMA (introduced with Kepler-class GPUs and CUDA 5.0) lets the NIC's DMA engine treat GPU memory as a first-class DMA target. Because all PCIe devices share one physical address space, the NIC can issue reads and writes against the GPU's BAR window exactly as it does against system memory. The enabling steps, per NVIDIA's design documentation:

1. The communication library detects the pointer is a device pointer (via CUDA's UVA metadata — DIST-6.4).
2. The buffer is **pinned in 64 KB-aligned chunks** — for GPU memory this means calling into the NVIDIA kernel driver (`nvidia_p2p_get_pages()` historically, or the dma-buf export path on current stacks) to obtain a stable page table and a BAR1 mapping, rather than Linux's `get_user_pages()`.
3. The mapping is registered with the NIC as usual (lkey/rkey; Section 1.4).
4. One correctness requirement that is easy to miss: the buffer must have `CU_POINTER_ATTRIBUTE_SYNC_MEMOPS` set, which forces CUDA's own asynchronous operations on that buffer to be synchronous with respect to the host — otherwise a concurrently running kernel writing the buffer could race the NIC's DMA.
5. Thereafter the NIC DMAs payload directly out of (or into) GPU memory over PCIe — the WQE itself still posted by the CPU through the normal verbs path.

The result: payload PCIe crossings drop from four to two per message (one per node), host DRAM traffic for the payload drops to zero, and the CPU leaves the data path entirely.

```
Staged path (per node):   GPU HBM ──PCIe──▶ host DRAM ──PCIe──▶ NIC
GPUDirect path (per node): GPU HBM ══PCIe (BAR1)══▶ NIC
```

**The resource that gets consumed: BAR1.** The mapping of GPU memory for peer access lives in the GPU's BAR1 aperture — a PCI Base Address Register window, historically as small as 256 MB per GPU (with ~32 MB reserved for driver use) on Kepler-class parts, and 16 GB+ ("resizable BAR") on modern Tesla-class GPUs. Pinned GPU memory occupies BAR space in 64 KB chunks; exhaust it and new registrations fail, which is one reason registration caches evict lazily (DIST-6.6). You can watch the consumption live: `nvidia-smi -q` reports BAR1 Memory Usage, and a multi-GPU communication workload pinning many large buffers will visibly eat into it.

**Both ends need their own support.** Following the decomposition from Section 1.5: for a GPU-to-GPU RDMA Write, the *sender's* NIC must DMA out of GPU memory, and the *receiver's* NIC must DMA into GPU memory. Each leg is a local property of that node — driver, BAR mapping, registration — and the remote NIC neither knows nor cares that the peer buffer is GPU memory; it just validates an rkey and writes. This asymmetry-by-node is why cluster bring-ups so often produce one-directional performance surprises: a misconfigured peer-memory module on *one* node degrades traffic in *both* directions involving that node.

**What GPUDirect RDMA does not (yet) remove.** Note carefully what is still CPU-owned in this model: *posting the WQE and ringing the doorbell*. The CPU left the data path but not the control path. Every message still requires the host to build and submit a descriptor (or batch of them). Eliminating that — letting a CUDA kernel post WQEs and ring doorbells itself — is GPUDirect Async / GDA-KI, curriculum topic DIST-7.9 and, conveniently, this month's biggest development (Section 2.1).

### 1.7 One message, end to end: putting the five topics together

To bind the five topics into a single mental execution trace, follow one inter-node `MPI_Send` of a 1 MiB GPU buffer, sender rank on node A, receiver on node B, running CUDA-aware MPI over InfiniBand with GPUDirect RDMA:

| Step | What happens | Topic |
|---|---|---|
| 0 | Sender calls `MPI_Send(devptr, …)`; MPI checks UVA metadata → device pointer; receiver's matching `MPI_Recv` posted a device buffer | 6.3–6.4 |
| 1 | Registration cache lookup on both buffers: HIT → reuse lkey/rkey; MISS → pin GPU pages (64 KB chunks, BAR1 map), register MR, cache it | 1.4 / 6.5–6.6 |
| 2 | Rendezvous handshake over a control message: receiver sends `(remote VA, rkey)` of its GPU buffer | 1.2 |
| 3 | Sender's CPU builds an RDMA-Write WQE: SGE = `(devptr, 1 MiB, lkey)`, remote = `(rva, rkey)`; posts to the QP's send queue; rings the doorbell | 1.3 |
| 4 | A's NIC fetches the WQE, checks the lkey, **DMAs the payload out of GPU memory through BAR1** (local DMA leg) | 1.4, 1.5, 1.6 |
| 5 | Packets carry B's virtual address + rkey; B's NIC validates the rkey, **DMAs the payload into B's GPU memory through its own BAR1** (remote DMA leg) | 1.2, 1.6 |
| 6 | B's NIC ACKs; A's NIC writes a CQE; sender's MPI polls it and completes the send; receiver completes on its own schedule | 1.3 |
| 7 | Bytes crossed PCIe twice per node — GPU↔NIC — and never touched host DRAM or a CPU register on either side | 1.6 |

Read the table once more and notice how each curriculum topic owns exactly one slice of the mechanism: semantics (1.2), control interface (1.3), authorization/pinning (1.4), the DMA decomposition (1.5), and the GPU-specific placement (1.6). When a real workload underperforms, the diagnostic questions fall out of the same table: was the buffer registered (cache hit rate)? Is BAR1 exhausted? Which path did the bytes take — and was the message size even large enough for the zero-copy path to win? That last question — when the staged path or GPU-initiated control path actually beats GPUDirect — is precisely where the curriculum goes next (DIST-7.8–7.9).

## 2. Key Developments / News

### 2.1 NVIDIA unifies GPU-initiated RDMA under an open-source DOCA GPUNetIO (October 2026)

**What happened.** On October 6, 2026, NVIDIA published a technical blog and an open-source release (github.com/NVIDIA-DOCA/gpunetio) consolidating "GDA-KI" — GPUDirect Async Kernel-Initiated communication — into a single foundation that NCCL, NVSHMEM, UCX/NIXL, DeepEP/HybridEP, and Holoscan all build on, instead of each maintaining a private implementation of GPU-initiated RDMA.

**What technically changed.** Today's curriculum established that after GPUDirect RDMA, the CPU still owns the control path: it posts WQEs and rings the doorbell. GDA-KI moves that control path onto the GPU itself. A CPU-side setup phase creates the transport objects (queue pairs via `mlx5dv`) and exports a descriptor *into GPU memory*; thereafter a persistent CUDA kernel posts WQEs to queues that live in GPU memory, rings the NIC doorbell by writing to registers MMIO-mapped into the CUDA address space (or writes the whole WQE through the doorbell — BlueFlame), and polls CQEs that the NIC writes back into GPU memory — all via GPUDirect RDMA in the reverse direction. The NIC fetches work descriptors *from GPU memory* using the same peer-access mechanism of Section 1.6. Concrete integrations: NCCL's GPU-Initiated Networking (GIN) API has used the open-source GPUNetIO Verbs path as a backend since NCCL 2.27, with the blog showing reduce-scatter speedups over the CPU-driven path that grow as messages shrink; NVSHMEM 3.7 gained a `gpunetio` transport that preserves the older IBGDA transport's performance while substantially shrinking its implementation; NVIDIA's NVQLink quantum-control reference stack reports ≈2.6 µs minimum round-trip forwarding latency on IGX Thor with a Blackwell GPU and ConnectX-7.

**Why it matters and how it connects.** This is the logical completion of a forty-year arc: the message path has been stripped of kernel, host memory, and now the host *processor* itself — CUDA threads doing what Section 1.3's CPU did. It also validates the registration/dma-buf machinery of Section 1.4 at production scale: doorbells, WQEs, and CQEs are now registered GPU buffers like any payload. For MoE-style training with millions of tiny messages, the CPU proxy was the bottleneck — NVSHMEM's own earlier IBGDA measurements showed peak bandwidth reachable at 2 KiB messages (with 64 issuing thread blocks) instead of 16 KiB (4 blocks), and up to 9.5× higher small-message put throughput (vendor-reported, ConnectX-6).

**What to watch.** A useful companion is the October 2026 arXiv paper "GPU-Initiated Communication: Dissecting Down to the Bone" (arXiv:2610.01380), which independently benchmarks IBGDA, NCCL GIN, DeepEP and others across H100–GB200 platforms and quantifies the costs (doorbell batching, queue parallelism, reduced SM occupancy from resident communication kernels). Also watch whether `NVSHMEM_REMOTE_TRANSPORT=gpunetio` becomes the default in production stacks — a good canary for the maturity of the unified layer.

### 2.2 Ultra Ethernet Specification 1.0: re-architecting RDMA transport for million-endpoint scale (June 2025)

**What happened.** The Ultra Ethernet Consortium (UEC) — founded 2023 by AMD, Arista, Broadcom, Cisco, Eviden, HPE, Intel, Meta, Microsoft, Oracle, and others under the Linux Foundation — released Specification 1.0 on June 11, 2025: a complete Ethernet-based communication stack (link, transport, software APIs, security, management) aimed at AI and HPC workloads at scales beyond what InfiniBand deployments have reached.

**What technically changed.** UEC 1.0 defines the **Ultra Ethernet Transport (UET)**, described by the consortium as "modern RDMA for Ethernet and IP". Where today's RoCEv2 inherits the model you learned in Section 1.3 — a reliable, *ordered* byte stream per queue pair, carried over a single path chosen by ECMP hashing, over a lossless fabric maintained with PFC — UET embraces the opposite design point: packet spraying across *all* available paths, per-packet multipath, out-of-order delivery with reassembly at the NIC, selective (not go-back-N) retransmission, and both sender- and receiver-side congestion control. The RDMA-style semantics — one-sided direct placement, registered memory, queue-based submission — are preserved, but the transport underneath is rebuilt so that a fabric with hundreds of thousands of endpoints uses every link on every flow rather than pinning each QP to one hashed path.

**Why it matters and how it connects.** This is a direct, real-world interrogation of DIST-7.2: the per-QP ordered-stream contract that makes RC transports simple for MPI is exactly what limits scaling-out on Ethernet fabrics (stranded bandwidth under ECMP, congestion hot spots, PFC-induced head-of-line blocking — topics that return in DIST-8.5–8.8). UEC's bet is that keeping the verbs-era *semantics* while relaxing *ordering* buys both compatibility and scale. Backwards compatibility with deployed APIs is an explicit UEC goal, and vendors (AMD's Pollara 400 NIC, Broadcom's roadmap) are already building UEC-capable silicon.

**What to watch.** The UEC compliance and interoperability programs — the press release notes implementations and compliance efforts already in progress — and whether MPI/UCX/NCCL expose UET-specific features (per-packet spraying, receiver-side congestion signals) or absorb them invisibly under the existing verbs-like surface.

### 2.3 ConnectX-8: PCIe Gen6 and an integrated switch reshape the GPU↔NIC path (2025)

**What happened.** NVIDIA's ConnectX-8 SuperNIC — detailed at Hot Chips 2025 and covered extensively since — is an 800 Gb/s NIC now in volume deployment as the first PCIe Gen6 SuperNIC, shipping in HGX B300 and GB300 NVL72 systems and in RTX PRO Servers from major OEMs. It serves both Quantum-X InfiniBand (XDR) and Spectrum-X Ethernet fabrics.

**What technically changed.** Three architectural facts, per NVIDIA's materials and ServeTheHome's Hot Chips coverage: (1) the device exposes 48 PCIe Gen6 lanes with an *integrated PCIe Gen6 switch* on-chip — the card is no longer just an endpoint but the fabric element that fans out to GPUs; (2) in GB300 NVL72, the NIC links to the Grace CPU over Gen5 x16 and to the B300 GPU over Gen6 x16, matching each link to what the endpoint can actually sink; (3) NVIDIA reports RDMA throughput at 800 Gb/s across message sizes from 64 KB to 1 MB. In RTX PRO 6000 Blackwell server configurations the NIC supports a 2:1 GPU-to-NIC ratio, i.e., up to 400 Gb/s of network bandwidth per GPU.

**Why it matters and how it connects.** Section 1.5's closing point was that an RDMA operation is bounded by its weakest *local* leg. With 400–800 Gb/s NICs (50–100 GB/s), a PCIe Gen5 x16 GPU link (~50 GB/s practical) becomes the bottleneck for GPUDirect RDMA traffic — which is why DIST-7.6 (GPU↔NIC topology) exists as next week's topic. Gen6 doubles per-lane bandwidth, and folding the PCIe switch into the NIC removes a discrete hop and its latency from the GPU↔NIC path. ConnectX-8 is also the hardware vehicle for the GDA-KI stack of Section 2.1 (the NVSHMEM benchmarks cited there ran on B300 + ConnectX-8 over Spectrum-X).

**What to watch.** Whether peer-vendor NICs (Broadcom's 400G "Thor", AMD's Pollara 400 — the latter explicitly UEC-oriented) converge on integrated-switch architectures or keep discrete PCIe topologies; and, closer to this curriculum, how rail-optimized designs (DIST-9.10) adapt when one NIC physically sits between multiple GPUs.
