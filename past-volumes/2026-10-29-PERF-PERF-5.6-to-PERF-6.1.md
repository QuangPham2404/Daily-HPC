## 0. Concise Summary

Yesterday the Roofline model was built: arithmetic intensity on the x-axis, performance on the y-axis, a flat compute roof, a sloped bandwidth roof, and a ridge point where the binding constraint switches. Today's issue is about turning that picture from a textbook diagram into a working instrument — and then learning where it lies to you.

We start with **operational intensity in practice** (PERF-5.6): how to actually count FLOPs and bytes for a kernel, on paper and from hardware counters. The key subtlety, inherited from Williams, Waterman, and Patterson's original 2009 paper, is that the denominator must be traffic measured *after* cache filtering — bytes that actually cross the level whose roof you are testing. We then extend the single-DRAM-roof picture to the **hierarchical Roofline** (PERF-5.7), which overlays L1, L2, and DRAM bandwidth ceilings and plots a separate intensity point per memory level — the methodology NERSC developed for GPU analysis and that Nsight Compute and AMD's rocprof-compute now ship as built-in sections. From there we take an honest inventory of **what the Roofline cannot see** (PERF-5.8): latency, dependency chains, occupancy, instruction mix, and communication are all invisible to a pure throughput model. That inventory directly motivates PERF-5.9, the **decision procedure**: given a measured point, which optimization family has headroom, and what falsifiable prediction does each one make? A ridge-point table computed from current vendor datasheets (H100, MI300X, B200, MI355X) shows that "compute-bound" and "memory-bound" are properties of the *pair* (kernel, machine), never of the kernel alone. Finally, PERF-6.1 defines **speedup** rigorously — the single most quoted and most frequently abused number in HPC — and sets up the baseline hygiene that Amdahl's and Gustafson's laws (next PERF volume) will stress-test.

Two developments connect this to the real world: the arrival of one-command empirical Roofline analysis in mainstream GPU profilers, and the wandering of FP64 ridge points across the 2023–2025 accelerator generation — including Blackwell's deliberate trade of FP64 throughput for bandwidth, which moved the B200's FP64 ridge point from H100's ~20 FLOP/Byte down to ~4.8.

## 1. Learn the Concepts

### 1.1 Counting the numerator and the denominator (PERF-5.6)

Arithmetic intensity was defined yesterday as

$$AI = \frac{\text{FLOPs performed}}{\text{bytes moved from a chosen memory level}}.$$

Both halves of that ratio are harder to pin down than they look, and the errors are asymmetric: people routinely get FLOPs roughly right and bytes badly wrong, which flatters the kernel's apparent position.

**The FLOP numerator.** The standard counting rules:

- One fused multiply-add (FMA) instruction is **2 FLOPs**, not 1. Most optimized inner loops compile entirely to FMAs, so a loop body with `k` FMAs per iteration does `2k` FLOPs per iteration.
- A GEMM computing `C = A·B` with `A` (m×k), `B` (k×n) performs `2mnk` FLOPs.
- Sparse matrix–vector multiply `y = A·x` with `nnz` nonzeros performs `2·nnz` FLOPs.
- A 7-point stencil update does roughly 7 multiply-adds per cell, i.e. ~14 FLOPs per updated point.

The trap in the numerator is **precision pathways**. On a GPU, "FLOPs" is ambiguous between vector-pipe FLOPs and matrix/tensor-core FLOPs, and the roof you may hit depends on which pipe the instructions actually take. A kernel written in FP32 can be silently executing at different throughput depending on whether the compiler emitted FFMA, HFMA2, or an MMA instruction. When profiling, do not hand-count the numerator: count *instructions* and multiply by the FLOPs each instruction performs. Nsight Compute exposes SASS-level counters for exactly this purpose (e.g. per-op execution counters for FFMA/FADD/FMUL instructions); for tensor-core kernels, an MMA instruction performs an entire small matrix product, so the multiplier depends on the MMA shape. The Nsight Compute profiling guide is explicit that when a roofline result disagrees with your expected FLOP count, the first check is whether the enabled roofline section matches the data path actually executed — including tensor roofline sections for tensor-core kernels.

**The byte denominator.** Here is the more consequential decision: bytes moved *from where*? Williams, Waterman, and Patterson were precise about this in the original 2009 CACM paper. They define *operational intensity* as operations per byte of **DRAM traffic**, and they measure total bytes as "those bytes that go to the main memory after they have been filtered by the cache hierarchy... we measure traffic between the caches and memory rather than between the processor and the caches." Two consequences follow:

1. A paper analysis that counts every load and store as a DRAM byte *underestimates* AI, because caches absorb reuse. The formal upper bound and the measured point can differ by an order of magnitude.
2. The DRAM-roof AI of a kernel is not a fixed property of the code — change the tiling and the same source file has a different DRAM AI. This is not a bug; it is precisely the mechanism the model is meant to expose.

Work through the two canonical extremes.

**SpMV (CSR format).** Per nonzero, the kernel reads an 8-byte FP64 value and a 4-byte column index: 12 bytes of matrix data per nonzero. The `x` vector entries are reused across rows (and hit cache for typical matrices), and `y` is written once per row. Ignoring the amortized vector traffic, the intensity approaches

$$AI_{\text{SpMV}} \approx \frac{2\ \text{FLOPs}}{12\ \text{bytes}} \approx 0.17\ \text{FLOP/byte}.$$

No amount of tuning changes this by more than a small factor, because the data structure itself is the bandwidth cost. SpMV sits at the far left of every Roofline chart ever drawn — which is exactly why sparse linear algebra (HPCG's inner kernels) measures single-digit percentages of peak.

**Dense GEMM.** If each of A, B, C is touched exactly once from DRAM — the best conceivable case — the minimum traffic is `8 × 3n²` bytes for an n×n problem, against `2n³` FLOPs:

$$AI_{\text{GEMM}} \ge \frac{2n^3}{24n^2} = \frac{n}{12}\ \text{FLOP/byte}.$$

For n = 1024 that is already ~85 FLOP/byte; for n = 4096, ~341. Dense GEMM can therefore live to the right of essentially any FP64 ridge point, provided the cache hierarchy is allowed to do its job — the loop structure must realize the "touch once" bound. A naive triple loop with no blocking does not: A or B gets evicted between uses, DRAM traffic multiplies by the recurrence factor, and measured AI collapses toward single digits. This is why blocking/tiling is *the* canonical GEMM optimization: it does not change the FLOP count at all; it only repairs the denominator.

**Getting the denominator from hardware.** Static analysis is for hypothesis formation; the measured point comes from counters. On NVIDIA GPUs, Nsight Compute reports DRAM traffic directly (the `dram__bytes.sum` counter family), with separate L2 and L1 traffic counters one level up; on AMD Instinct GPUs, rocprof-compute collects the memory-hierarchy transaction counts per kernel dispatch automatically and computes the roofline coordinates for you. The workflow discipline that matters: record *both* the static (pen-and-paper) AI and the measured AI. If the measured DRAM AI is far below the static estimate, the cache hierarchy is failing to deliver the reuse your analysis assumed — that gap is itself a diagnosis, and it is the entry point to the next topic.

### 1.2 One roof per memory level (PERF-5.7)

The classic Roofline draws one sloped roof: DRAM bandwidth. But a GPU (or a CPU) is a *stack* of bandwidths — L1 is faster than L2, which is faster than HBM — and a kernel can be limited by any of them. The single-roof picture answers "is this kernel compute-bound or DRAM-bound?" and is silent about everything in between.

The **hierarchical Roofline** fixes this by overlaying multiple bandwidth ceilings on the same log–log plot: one diagonal per memory level (L1, L2, DRAM, and where relevant, host/system memory over PCIe), plus the flat compute roof. Crucially, each level gets its *own* intensity point for the same kernel:

$$AI_{L1} = \frac{\text{FLOPs}}{\text{bytes crossing L1}},\quad AI_{L2} = \frac{\text{FLOPs}}{\text{bytes crossing L2}},\quad AI_{\text{DRAM}} = \frac{\text{FLOPs}}{\text{bytes crossing DRAM}}.$$

Since a cache absorbs traffic, bytes at L2 ≤ bytes at L1 and bytes at DRAM ≤ bytes at L2, so $AI_{L1} \le AI_{L2} \le AI_{\text{DRAM}}$. On the chart, one kernel appears as *several* points spread along the x-axis, each pinned under its own ceiling:

```
 perf
  ▲                ________________  compute roof
  │              /                  .
  │            /                    .        ●  ← AI_DRAM point
  │   L1 roof /                      .      ●    ← AI_L2 point
  │        / /  L2 roof              .    ●      ← AI_L1 point
  │      / / /  DRAM roof            .
  │    /_/__/________________________.________▶ AI (FLOP/byte), log scale
```

Reading the spread is the analysis. If the DRAM point sits well below the DRAM roof but the L1 point sits at its own ceiling, the kernel is L1-bandwidth-limited with excellent cache behavior — DRAM is nearly idle, and buying more HBM bandwidth would buy nothing. If all points cluster under the DRAM roof with little spread between them, the caches are transparent (little reuse), and the kernel is genuinely DRAM-bound. The gaps between the points *are* the measured cache reuse factors.

This methodology was worked out in detail by Charlene Yang, Thorsten Kurth, and Samuel Williams at NERSC/Berkeley Lab in preparation for the Perlmutter system ("Hierarchical Roofline Analysis for GPUs," *Concurrency and Computation: Practice and Experience* 32(20), DOI 10.1002/cpe.5547). Three implementation details from that paper are worth internalizing because they generalize:

1. **Peaks should be measured, not quoted.** They characterized the GPU using the Empirical Roofline Toolkit (ERT), which sweeps a synthetic kernel of controllable intensity to find the achievable (not pin-bandwidth) compute and bandwidth peaks at each level — the same sustained-vs-theoretical distinction from PERF-4.1/4.2. Their paper analyzed GPP (BerkeleyGW), HPGMG (AMReX), and conv2d (TensorFlow) this way.
2. **Not every level can be measured empirically.** ERT, as written, consistently failed to identify the L1 bandwidth on NVIDIA GPUs, so they used a theoretical L1 bandwidth with empirical L2 and HBM ceilings. Honest models carry their measurement caveats on their face.
3. **The ceilings are diagnostic, not explanatory.** Their own conclusion is refreshingly blunt: Roofline "does not inform users as to exactly what went wrong in an application's execution or the code changes required to fix it," but it does identify where to look next.

Tooling has caught up with the methodology. Today Nsight Compute ships hierarchical roofline as built-in sections (per-precision and tensor variants, e.g. the hierarchical double-precision and tensor-core roofline chart sections), where the original NVIDIA/NERSC workflow required hand-written custom section files. AMD's rocprof-compute (the production successor of the Omniperf research tool) goes one step further on the peak side: unless disabled, it *runs microbenchmarks on your actual GPU* to establish the empirical roofline before plotting your kernels against it. The 2019-era workflow — extract counters, build a spreadsheet, draw the plot yourself — is now one command.

### 1.3 What the Roofline cannot see (PERF-5.8)

The Roofline is a *throughput* model: it bounds performance by the maximum rate at which a resource can stream work, assuming you can keep that resource saturated. Every one of its blind spots comes from that assumption.

**Latency and insufficient parallelism.** A kernel that launches one thread block cannot saturate any roof, no matter its arithmetic intensity. It will sit far below both the compute and bandwidth ceilings, and the Roofline has no vocabulary to say why. The missing dimension is *concurrency*: enough independent work in flight (occupancy on GPUs, ILP on CPUs) to hide memory latency and pipeline depth. A kernel can also be genuinely latency-bound — a pointer-chasing loop with a serial dependency chain performs almost no FLOPs and almost no bandwidth, and appears "memory-bound" on the chart while the actual fix is prefetching or restructuring the dependency, not reducing traffic.

**Instruction mix.** The flat compute roof assumes ideal instructions. A DP kernel compiled without FMA fusion does at most half the roof; a kernel that mixes FPADD/FPMUL with FFMA has a *lower* effective ceiling, as Yang et al. quantified in their instruction-mix analysis. Williams et al.'s original paper handled this with sub-ceiling overlays (a "no-FMA" ceiling, an "unvectorized" ceiling below the vectorized one) — useful, but a reminder that the top roof is an upper bound on upper bounds.

**Which compute roof?** Multi-precision hardware makes "the compute roof" ambiguous: a MI300X has 81.7 FP64 vector TFLOP/s and 163.4 FP64 matrix TFLOP/s; a B200 has 75 FP32 vector TFLOP/s and 2,250 FP16 tensor TFLOP/s. Plot a mixed-precision kernel against the wrong roof and the "headroom" you compute is fiction. This is the same data-path matching problem as the FLOP numerator in 1.1.

**Communication.** The roofs are per-device. A multi-GPU kernel that moves data over NVLink or a multi-node one that moves it over the interconnect has *additional* sloped roofs (link bandwidths) that the single-GPU chart does not contain. The overlap structure (exposed vs. hidden communication — PERF-14/17 territory) is entirely outside the model.

**Denominator subtleties.** Measured AI uses *achieved* traffic. Two kernels with identical performance and identical DRAM AI can have completely different L1 traffic — indistinguishable on a single-roof chart, cleanly separated on a hierarchical one. Conversely, comparing a kernel's measured AI across machines conflates the kernel with each machine's cache sizes.

**The model bounds; it does not explain.** Per Yang et al., several of their case studies diverged from roofline expectations — a framework (TensorFlow) silently running an "FP16" kernel in FP32 with conversion overhead, autotuning picking the wrong sub-kernel at certain sizes. In every such case the plot said "below expectations" but only the counters and source said why. The correct epistemic status of a Roofline point: *evidence that constrains hypotheses*, never a diagnosis.

### 1.4 From a point on the chart to a next experiment (PERF-5.9)

The Roofline earns its keep as a decision instrument. Given a measured point `(AI, P)` for a kernel on a specific machine, run this procedure:

1. **Compute the headroom to each roof.** `P / P_compute_roof` and `P / (BW × AI)` for the bandwidth roof. Also locate the point relative to the machine's ridge point.
2. **Classify the binding constraint:**
   - *At the bandwidth roof (left of the ridge):* the kernel is achieving what the memory system can stream. The only wins are **denominator repairs** — reduce bytes per FLOP. Families: tiling/reuse (raises measured AI by cutting DRAM traffic; the point slides *right along the roof*, and up), data-layout changes and coalescing (raise the *achievable fraction* of the roof), kernel fusion (eliminates intermediate DRAM round-trips entirely), and precision reduction (FP64→FP32 halves bytes, doubling AI — the HPL-MxP lever).
   - *At the compute roof (right of the ridge):* numerator repairs — instruction mix, vectorization/tensor-core utilization, and the compute-side sub-ceilings of 1.3.
   - *Far below both roofs:* this is the most common and least self-explanatory case. The constraint is latency, occupancy, launch overhead, dependency stalls, or imbalance — none of which the chart can distinguish. Escalate to kernel-level analysis (the PERF-11/12 material) or timeline analysis (PERF-10).
3. **Write the falsifiable prediction before touching code.** "Kernel K sits at 60% of the DRAM roof with AI = 0.9. Hypothesis: uncoalesced access wastes half the transactions. Prediction: after layout change, measured AI roughly doubles and performance rises ≤2×. If measured AI is unchanged, the hypothesis is dead." The Nsight Compute documentation phrases the hierarchical version of this heuristic: if a kernel sits at the DRAM roof, improving reuse can move the achieved point toward the L2 or L1 ceiling *without changing arithmetic intensity* — i.e., change which roof binds, not where the point is.
4. **Re-measure and re-plot after the intervention.** The point should move in the predicted direction; a point that improves performance without moving as predicted means your mechanism story was wrong even if you got lucky.

To make the machine-dependence concrete, here is the FP64 ridge point — tensor/matrix-throughput peak divided by memory bandwidth — for four current datacenter accelerators, computed directly from vendor datasheets:

| GPU (FP64) | Peak FP64 (matrix/tensor) | Memory BW | Ridge point |
|---|---|---|---|
| NVIDIA H100 SXM | 67 TFLOP/s | 3.35 TB/s | ≈ 20 FLOP/B |
| AMD MI300X | 163.4 TFLOP/s | 5.3 TB/s | ≈ 31 FLOP/B |
| NVIDIA B200 | 37 TFLOP/s | 7.7 TB/s | ≈ 4.8 FLOP/B |
| AMD MI355X | 78.6 TFLOP/s | 8 TB/s | ≈ 9.8 FLOP/B |

The spread is the lesson. A dense FP64 kernel with sustained AI ≈ 10 FLOP/B is comfortably compute-side on a B200, *right at* the ridge on an MI355X, and firmly memory-side on an MI300X — the same code, three different diagnoses, and the optimization priority list reorders accordingly. For comparison, the original 2009 Roofline paper's x86 machines had ridge points of 4.4 and 6.7 FLOP/Byte, with real kernel intensities clustering at a median of 0.60 — the accelerator era pushed FP64 ridge points up (H100: 20; MI300X: 31), and the AI generation has since pulled them back down (B200: 4.8) while exploding the low-precision ones. On an MI355X, the dense FP16 matrix peak is ~2,517 TFLOP/s against 8 TB/s — a ridge point near **315 FLOP/byte**. At intensities like that, virtually nothing except very large dense linear algebra and its relatives can reach the compute roof, which is the quantitative reason data staging and reuse dominate mixed-precision benchmark design (HPL-MxP) and LLM serving alike.

### 1.5 Speedup, defined honestly (PERF-6.1)

Everything above reasons about single kernels. The number that ultimately matters — to papers, to procurements, to your own iteration loop — is **speedup**:

$$S = \frac{T_{\text{reference}}}{T_{\text{new}}},$$

the ratio of runtimes of a baseline and an optimized/parallel version of the *same computation on the same problem* (same input, same machine class, same accepted-correctness criteria). S > 1 means faster; "2×" means the new runtime is half the old. The definition is trivial; every failure mode lives in what surrounds it.

**The baseline is the hidden variable.** Speedup is only meaningful relative to a stated reference, and the choice of reference is where most abuse lives:

- *Naive-self baseline* (your first working code): honest for measuring your own optimization, but "we got 40× over our first Python port" measures the port, not the machine.
- *Previous-best baseline* (last release, best known config): the industrially relevant one; improvements are incremental by construction.
- *Best-known-implementation baseline* (a vendor library, e.g. cuBLAS/rocBLAS): the fair fight; beating it by 1.1× is worth more than beating a strawman by 10×.
- *Ideal baseline* (theoretical or sustained peak): then the quantity is not speedup but **efficiency** (PERF-1.7/4.3), and the two must not be conflated in a sentence.

**Arithmetic hygiene.** "30% faster" means $T_{new} = 0.7\,T_{ref}$, i.e. S ≈ 1.43 — not 1.30. Speedups compose multiplicatively through *time-weighted phases*, never by averaging: a kernel that runs 2× faster but occupies 10% of end-to-end runtime yields $S_{\text{total}} = 1/(0.1/2 + 0.9) \approx 1.05$×. That weighting rule is the seed of Amdahl's law (PERF-6.2), and it is why yesterday's PERF-2.5 (end-to-end vs. kernel-only timing) exists: kernel speedups are cheap; phase and application speedups are what get reported, and they must be *measured*, not extrapolated.

**Experimental hygiene.** Change one conceptual mechanism between reference and new (PERF-22 preview); keep problem size, input, hardware, clocks, and software stack identical; and respect measurement noise — if your run-to-run coefficient of variation is 3% (PERF-3.3), a claimed 1.04× speedup is not yet evidence. Report the baseline's absolute runtime, not just the ratio; a ratio with an unmeasured denominator is unfalsifiable.

**What speedup does not tell you:** why the improvement happened, whether it transfers (another machine may have a different ridge point — see the table in 1.4), or what it cost in energy, memory, accuracy, or code complexity. It is one coordinate, not a verdict.

This definition is the load-bearing wall for the next two PERF topics. Amdahl's law asks: with a fixed problem size, how does S behave as processor count grows, given a serial fraction? Gustafson's 1988 reply — built on measured 1016–1021× speedups of three Sandia codes on a 1024-processor hypercube — asks the same question after changing what is held fixed: the *runtime*, not the problem size. The entire famous dispute is an argument about which baseline and which scaling convention the speedup ratio uses. Get PERF-6.1 right and the laws become two lines of algebra; get it wrong and they become slogans.

## 2. Key Developments / News

### 2.1 Empirical Roofline analysis is now a built-in profiler feature, on both major GPU stacks

**What happened.** The Roofline methodology that once required researchers to extract raw counters, benchmark the machine's peaks separately, and assemble plots by hand is now a first-class feature of the standard vendor profilers. NVIDIA's Nsight Compute ships roofline chart sections — including *hierarchical* variants that overlay L1, L2, and DRAM bandwidth ceilings, in separate double-precision, single-precision, half-precision, and tensor-core flavors, collected under a dedicated `roofline` section set. AMD's rocprof-compute (the supported descendant of the Omniperf research tool) automates the entire pipeline on Instinct GPUs: it replays the application to collect per-dispatch hardware counters, then — unless told not to — runs a set of accelerator-specific microbenchmarks to establish the *empirical* roofline on your silicon, and emits interactive per-kernel roofline plots as part of the analysis output. Full support now covers the MI200, MI300, and MI350 (CDNA4) series.

**What technically changed.** Two things: the *ceilings* are measured rather than quoted (closing the theoretical-vs-sustainable-peak gap from PERF-4.1/4.2 by construction), and the *points* are computed from per-level traffic counters rather than hand estimates — making the hierarchical multi-ceiling analysis of PERF-5.7 the default view rather than a research workflow. NERSC's own case studies show the payoff in practice: in the BerkeleyGW GPP kernel analysis, roofline-guided optimization steps — reordering loops and replacing high-latency division and absolute-value instructions with reciprocal and squared-magnitude calculations — raised double-precision throughput from 2.5 to 2.9 TFLOP/s and exposed the memory-side bottleneck that further tiling then addressed.

**Why it matters and what to watch.** This directly operationalizes today's PERF-5.6/5.9: the cost of forming a roofline hypothesis has collapsed from an afternoon of counter archaeology to one profiling run. The remaining skill is interpretation — the profilers plot the points and ceilings; they still do not decide whether a below-both-roofs kernel is latency-, occupancy-, or dependency-limited (PERF-5.8's blind spots persist in tooling). When using these features, verify the roofline section matches the executed data path, especially for tensor-core and mixed-precision kernels — a mismatch between the section's assumed FLOP rate and the real instruction stream is the documented failure mode.

### 2.2 The FP64 ridge point is wandering — and Blackwell moved it down, not up

**What happened.** Computing FP64 ridge points from current vendor datasheets (Section 1.4's table): NVIDIA's B200 provides 37 FP64 tensor TFLOP/s against 7.7 TB/s of HBM3e — a ridge point of ≈ 4.8 FLOP/byte, versus ≈ 20 for the H100 SXM it replaces (67 TFLOP/s, 3.35 TB/s). AMD's MI355X (2025) lands at ≈ 9.8 (78.6 TFLOP/s FP64, 8 TB/s), after the MI300X (2023) pushed out to ≈ 31 (163.4 TFLOP/s, 5.3 TB/s).

**What technically changed.** Silicon allocation followed the workload. Blackwell more than doubled memory bandwidth while *cutting* FP64 tensor throughput nearly in half relative to H100 — die area and power redirected from the 64-bit floating-point datapaths toward low-precision matrix engines (FP8/FP4) and HBM3e. AMD's CDNA4 kept a strong FP64 matrix unit but let the bandwidth-per-FLOP balance shift similarly (ridge 31 → 9.8 from MI300X to MI355X).

**Why it matters.** The ridge point is the machine's summary statistic of "how hard is it to reach peak here," as Williams et al. argued in 2009 — and it has now become a *design variable* that swings by 6× between adjacent generations. Consequences worth internalizing: (1) "memory-bound" or "compute-bound" verdicts about a fixed kernel do not transfer across these machines — a sustained-AI-10 FP64 kernel is compute-side on B200 and memory-side on MI300X; (2) FP64 codes ported from H100 or MI300X to Blackwell inherit a *lower* compute roof, so expected FP64 efficiency fractions must be re-derived, not carried over; (3) in the low-precision regime the ridge points are enormous (≈ 315 FLOP/byte dense FP16 on MI355X), which is why mixed-precision benchmarks and LLM inference live or die on cache reuse and data staging rather than raw FLOP/s.

**What to watch next.** Per-precision roofline sections when analyzing any mixed-precision code (the FP64 and FP16 charts tell opposite stories on the same silicon), and the FP64 throughput figures of the post-Blackwell/post-MI350 generations — the ridge point has become a deliberate architectural dial, and each vendor's setting of it re-sorts which HPC codes run well on which hardware.

- **Nsight Compute Profiling Guide, Roofline sections** — hands-on, ~20 min; how to read the built-in charts and their per-precision variants.
- **AMD ROCm blog series, *Performance Profiling on AMD GPUs*, Part 1: Foundations** ([link](https://rocm.blogs.amd.com/software-tools-optimization/profiling-guide/intro/README.html)) — hands-on counterpart on the ROCm stack; roofline through rocprof-compute.
- **Gustafson 1988** — two pages; read the original before next week's Amdahl/Gustafson volume, and note how much of the argument is about what the speedup denominator should be.
