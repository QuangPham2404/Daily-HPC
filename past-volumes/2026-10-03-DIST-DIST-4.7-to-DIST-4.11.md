## 0. Concise Summary

Tuesday's volume (DIST-4.2→4.6) built the collective family around two axes: *who ends up holding data* (one rank or all) and *what is delivered* (copies, segments, or reduced values). Today we finish Module 4. Three entries complete the family table — **reduce-scatter** (all ranks' vectors reduced, but each rank keeps only its own segment), **all-to-all** (every rank sends distinct data to every other rank, the heaviest data-mover in MPI), and **barrier** (pure synchronization, no data at all). Then the module closes by zooming out twice: **DIST-4.10** extracts the recurring *algorithmic skeletons* — linear, binomial tree, ring, recursive doubling, Bruck/dissemination, pairwise exchange, hierarchical — that get recycled across every collective, and **DIST-4.11** builds the *cost models* that decide which skeleton a library runs for a given message size and rank count.

The unifying idea of the whole volume is that **a collective operation is an interface, not an algorithm**. `MPI_Reduce_scatter`, `MPI_Alltoall`, and `MPI_Barrier` are contracts about the final state of buffers; underneath, the library runs one of several wire patterns chosen by a cost model. Today's deep example is reduce-scatter's recursive-halving algorithm (each rank ends holding exactly one fully-reduced segment after lg p steps), all-to-all's pairwise-exchange schedule (a round-robin of perfect matchings), and the dissemination and tournament barriers from the classic 1988 Hensgen–Finkel–Manber paper. The α-β-γ cost model then ties the entire module together — and shows its own limits, because the model predicts a tie where measurement says the ring wins.

Two developments anchor the lesson in current practice: **NCCL 2.32.3** (September 17, 2026), whose release notes read like a checklist of today's topics — a new cost model for Blackwell AllGather kernel selection, a ring-based hierarchical copy-engine AllGather, and diagnostics for stalled collective kernels; and **Träff's 2024 paper on optimal reduce-scatter/allreduce**, which proves that even the classic algorithms leave provable gaps — reduce-scatter can hit the minimum round count and the minimum data volume *simultaneously*. Together they show collective cost modeling is not settled history but active engineering, from Argonne's 2005 MPICH paper to a GPU vendor's 2026 release notes.

## 1. Learn the Concepts

Notation carries over from the previous volumes: p ranks, n the message size in bytes (per rank, unless stated), α the per-message latency, β the per-byte transfer cost (1/B for link bandwidth B), γ the per-byte cost of the reduction arithmetic, and lg p = log₂ p. All of these come from DIST-1.6/1.7, now applied to collectives.

### 1.0 The completed family table

Reduce-scatter, all-to-all, and barrier fill the last rows of the collective family table from September 29:

| Operation | Input state | Output state | Pattern |
|---|---|---|---|
| **Reduce-scatter** (DIST-4.7) | each rank holds n | rank i holds reduced segment i (n/p) | all → all, combined |
| **All-to-all** (DIST-4.8) | rank i holds distinct blocks for every j | rank i holds all blocks destined for i | all → all, distinct, P² blocks total |
| **Barrier** (DIST-4.9) | — | all ranks have entered the call | all ↔ all, no data |

Three observations organize today. First, reduce-scatter is *not* a new primitive so much as the missing half of a composition: all-reduce = reduce-scatter + all-gather, which is exactly the ring allreduce already met on September 29. Understanding reduce-scatter on its own terms explains where that algorithm's two halves came from. Second, all-to-all is the only collective whose data volume grows as p² — it is bounded not by what any one rank can send, but by what the network's bisection can carry (a quantity Module 5 will formalize as DIST-5.8). Third, the barrier is the degenerate case: it moves no data, exists purely to create ordering, and therefore costs only α-terms — but it is where load imbalance becomes *visible* as idle time.

### 1.1 Reduce-scatter (DIST-4.7)

**The problem.** Every rank holds a vector of n bytes; the element-wise reduction (⊕, e.g. sum) over all ranks is needed, but no single rank wants the whole result — each rank i wants only its own segment of n/p bytes. In MPI:

```c
MPI_Reduce_scatter(sendbuf, recvbuf, recvcounts[], datatype, op, comm);
```

The result is *distributed*: rank i receives the reduction of segments `recvcounts[i]` in its region of the (conceptually concatenated) vector. Two consequences follow. It is an "irregular" primitive — the per-rank segment sizes can differ, so the scatter half is really a scatterv, and MPI-2.2 later added `MPI_Reduce_scatter_block` for the common equal-blocks case. And it is the most *bandwidth-frugal* way to combine data: no rank ever needs to hold more than n/p bytes of the answer.

Why does this primitive exist? Because concentrating a full reduced vector anywhere is wasteful, and many algorithms only need each rank's piece. In data-parallel training, the classic "allreduce the gradients" pattern is increasingly replaced by reduce-scatter + all-gather so that gradients are *sharded* across ranks rather than replicated mid-flight. In solvers, block-row-distributed matrices only need their own rows of a combined vector.

**Naive: reduce then scatter.** The old MPICH implementation ran a binomial-tree reduce to rank 0, then a linear scatterv back out. In the α-β-γ model (Thakur, Rabenseifner, and Gropp, 2005):

```
T_old = (lg p + p − 1)·α + (lg p + (p−1)/p)·n·β + lg p·n·γ
```

The bandwidth term is damning: the tree reduce pushes the *full* n up the tree (lg p copies of n across links), and only then does the scatter recover the (p−1)/p·n that each rank actually needs to receive. The reduction result passes through the root twice.

**Recursive halving: the commutative long-message workhorse.** The fix mirrors what Van de Geijn's scatter+allgather did for broadcast: never move the full vector at all. Each step, a rank exchanges with its partner *only the half of the vector that the partner's group will eventually own*, and reduces what it receives. Walk it for p = 8, vector split into segments A–H, where "A over {0,4}" means segment A reduced over ranks 0 and 4, and rank 0's partners are found by flipping successively lower bits of its rank (partner = rank XOR 4, then XOR 2, then XOR 1):

| Step | Rank 0's partner | Sends (size) | Receives (size) | Holds after local reduce |
|---|---|---|---|---|
| 1 | rank 4 | E–H from {0} (n/2) | A–D from {4} (n/2) | A–D over {0,4} |
| 2 | rank 2 | C–D over {0,4} (n/4) | A–B over {2,6} (n/4) | A–B over {0,2,4,6} |
| 3 | rank 1 | B over {0,2,4,6} (n/8) | A over {1,3,5,7} (n/8) | **A over all 8 ranks** |

Every rank runs the same schedule mirrored (rank 4 ends holding E; rank 7 ends holding H). After lg p steps, rank i holds exactly segment i, fully reduced. Bytes sent per rank: n/2 + n/4 + n/8 = (p−1)/p·n — which is the *information-theoretic minimum*, because rank i's segment n/p needs contributions from the other p−1 ranks. Cost:

```
T_rec_half = lg p·α + ((p−1)/p)·n·β + ((p−1)/p)·n·γ
```

Compare with T_old: the lg p·n·β term has collapsed to (p−1)/p·n·β, and the step count from lg p + p − 1 down to lg p.

One subtlety worth internalizing: **recursive halving requires a commutative operator**. Rank 0 receives A–D from rank 4 and folds them into its own A–D — the operands arrive in an order determined by the partner schedule, not by rank order. For MPI_SUM or MPI_MAX this is harmless; for a user-defined non-commutative op the library cannot legally reorder. MPICH handles that case with a recursive-*doubling* variant (same partners, but each step exchanges "everything except what I'll eventually own," so each rank can reduce in correct order) at the price of extra bytes: n(lg p − (p−1)/p) instead of (p−1)/p·n. It is used only for tiny messages.

**Non-power-of-two p.** Halving schedules need the process count to factor by two. MPICH's fix: fold the extra ranks first — if p = 2^k + r, the first 2r ranks pair up (even rank sends its full vector to its odd neighbor, which reduces), the odd partners drop out, and the remaining power-of-two subset runs recursive halving, with the evens returning their partners' segments at the end. The cost picks up roughly one extra round and up to 2n·β extra movement. This matters more than it sounds: the Stuttgart profiling study cited by Thakur et al. found a quarter of production runs used non-power-of-two process counts, and every recursive-doubling/halving algorithm in this module needs this same patch.

**Long messages: pairwise (ring) exchange.** For very long vectors, even recursive halving loses to a ring-style schedule: p − 1 steps, and at step k rank i reduces segment ((i + k) mod p) into an accumulator and forwards the partial sum to rank (i − 1). Each step moves exactly n/p bytes; the cost is

```
T_pairwise = (p−1)·α + ((p−1)/p)·(n·β + n·γ)
```

— the same optimal bandwidth term as recursive halving, but p − 1 latency terms instead of lg p. On paper recursive halving should always win. In practice the ring wins for long messages — a discrepancy that Section 1.5 returns to, because it is the clearest demonstration of where the simple cost model breaks.

**Connections.** Reduce-scatter + all-gather = the Rabenseifner/ring allreduce (2·lg p·α or 2(p−1)·α, bandwidth 2(p−1)/p·n·β) from September 29 — you now know both halves separately. In HPL the analogous operation never appears (HPL communicates panels, not reduced vectors); in HPL-MxP the residual norms at the end are all-reduces, and on GPU clusters NCCL's reduce-scatter/all-gather kernels carry them. Forward references: DIST-9.3 covers the GPU ring implementations; DIST-14.3 covers global reductions in solvers.

### 1.2 All-to-all (DIST-4.8)

**The problem.** Each rank holds p distinct blocks — block j destined for rank j — of s bytes each. Every rank must end up holding all blocks *addressed to it*. In MPI:

```c
MPI_Alltoall(sendbuf, sendcount, sendtype, recvbuf, recvcount, recvtype, comm);
```

The MPI-1.1 standard defines the semantics precisely: "the j-th block sent from process i is received by process j and is placed in the i-th block of recvbuf." Total data in flight: p² blocks, p·s bytes per rank in each direction. This is the only collective whose volume scales quadratically with p, and the only one where every rank is simultaneously a heavy sender *and* receiver. `MPI_Alltoallv` (with per-destination counts and displacements) is the irregular generalization that real applications with non-uniform block sizes actually use.

Where it appears: parallel FFTs (each transpose is an all-to-all of redistributed data), particle and mesh repartitioning, sparse-matrix scaling, and — the modern driver — token routing in mixture-of-experts LLM training, where every GPU ships different tokens to every other GPU's experts.

**Why naive scheduling stalls.** The obvious implementation posts all sends in rank order: every rank starts by sending to rank 0, then rank 1... Rank 0's single NIC receives p−1 messages in a burst while later ranks wait. The old MPICH fix was trivial but effective: post operations in the order (rank + i) mod p so different ranks target different destinations at each moment. That is *scheduling*, not a different algorithm — same messages, different order.

**Bruck's index algorithm: latency-optimal for tiny messages.** For very small blocks the enemy is round count. Bruck, Ho, Kipnis, Upfal, and Weathersby's 1997 "index" algorithm runs in ⌈lg p⌉ rounds using store-and-forward: each rank first rotates its send buffer up by i blocks, and in round k sends to rank (i + 2^k) mod p all blocks whose index has bit k set, receiving from (i − 2^k) mod p into those same slots. Blocks ride through intermediate ranks; after ⌈lg p⌉ rounds every block has reached its destination, and a final local inverse rotation restores order. The cost:

```
T_bruck = lg p·α + (n/2)·lg p·β      (n = total per-rank volume, p a power of two)
```

The price of logarithmic rounds is *more than minimal data*: each block is forwarded through up to lg p hops, so the volume term carries a lg p/2 factor instead of 1. That is exactly the tree-vs-ring trade from September 29, now inside a single operation. MPICH measured the Bruck implementation winning up to roughly 256 bytes per block, where α dominates and the extra copies are noise.

**Pairwise exchange: bandwidth-optimal-ish for long messages.** For large blocks, extra hops are unaffordable; instead schedule the p(p−1)/2 block exchanges directly. With p a power of two, round k (k = 1 … p−1) pairs every rank with partner = rank XOR k, and the pair exchanges their mutual blocks:

| Round (p = 4) | Matched pairs | Rank 0 sends / receives |
|---|---|---|
| 1 | (0,1) (2,3) | block 0→1 / block 1→0 |
| 2 | (0,2) (1,3) | block 0→2 / block 2→0 |
| 3 | (0,3) (1,2) | block 0→3 / block 3→0 |

Each round is a *perfect matching* — no two pairs contend for the same NIC — and the p−1 rounds decompose the complete graph K_p (a 1-factorization). Every block goes directly, source to destination, no hops:

```
T_pairwise = (p−1)·α + n·β
```

For non-power-of-two p the XOR schedule breaks; MPICH uses a spread-out variant where in step k each rank receives from rank − k and sends to rank + k, preserving the one-pair-per-round property.

**The bisection bound.** All-to-all is the first operation where the *network*, not the endpoint, sets the floor. Split the p ranks into two halves. Every left-half rank sends s bytes to every right-half rank: p²s/4 bytes cross the bisection. The senders' aggregate NIC bandwidth is (p/2)·B, so the operation cannot finish faster than (p²s/4)/((p/2)B) = (n/2)·β, with n ≈ p·s the per-rank send volume. Pairwise exchange achieves n·β — within a factor of two of the bound, with full-duplex links and perfect scheduling narrowing it further. Note what happened: the per-endpoint cost model gave way to an *aggregate topology* argument. Module 5 (DIST-5.8 bisection bandwidth) generalizes this; for now, hold the conclusion: all-to-all performance is a property of your fabric's fattest cut, which is why fat-tree/Clos designs (DIST-8.5) and adaptive routing (DIST-8.6) matter most exactly here.

**In between.** For medium blocks (≈256 B to ≈32 KB per block in MPICH's measurements), the winner is neither: it is the plain isend/irecv schedule with rotated destinations — few enough messages that latency is manageable, large enough blocks that store-and-forward overhead hurts. Three regimes, three algorithms, one operation.

### 1.3 Barrier (DIST-4.9)

**The problem.** Sometimes no data needs to move — ranks simply must not proceed until every rank has arrived at a known point. `MPI_Barrier(comm)` provides it. The MPI standard's own taxonomy notes barrier is the odd one out: it moves no data, so it fits none of the one-to-all / all-to-one / all-to-all classes.

Why it exists: to make earlier communication *observable*. After a non-blocking send completes locally (DIST-2.3), the sender knows the library accepted the data, not that the receiver consumed it. A barrier — like any collective — creates ordering: once all ranks have passed it, every pre-barrier communication is guaranteed complete. Applications use it to separate timing phases, to safely reuse buffers across timesteps, and to enforce read-after-write between phases of a bulk-synchronous structure (a pattern DIST-14.7 formalizes).

**The cost of a barrier is the skew it exposes.** A barrier returns when the *slowest* rank arrives. Every other rank sits idle for exactly its distance from the slowest. The barrier is thus less a cost source than a *measurement instrument* for load imbalance: it converts invisible skew into visible idle time (DIST-1.8). This is why performance engineers treat barrier-heavy code as a symptom: the barrier is rarely the problem; the imbalance it synchronizes is. Iterative solvers feel this acutely — HPCG's conjugate-gradient iterations contain global dot products (all-reduces), each an implicit synchronization point, which is a large part of why HPCG efficiency falls as rank count grows while HPL's mostly-overlapped broadcasts do not.

**Algorithms.** The two classical designs are from Hensgen, Finkel, and Manber's 1988 paper "Two algorithms for barrier synchronization" (written for shared memory, adopted everywhere):

- **Dissemination barrier.** ⌈lg p⌉ rounds; in round k (k = 0, 1, …) rank i notifies rank (i + 2^k) mod p and waits for a notification from (i − 2^k) mod p. After ⌈lg p⌉ rounds, the fact that "everyone arrived" has disseminated to everyone — the same information-spreading pattern as Bruck's allgather/all-to-all, which is *why* those algorithms are called dissemination-style. Cost ≈ ⌈lg p⌉·α and p·⌈lg p⌉ total messages.
- **Tournament barrier.** Ranks pair off; the loser of each pair spins while the winner advances to the next round; the final champion releases everyone (directly, or by reversing the tree). Total work is just 2(p−1) notifications with depth 2·lg p — fewer messages than dissemination, at the price of an asymmetric arrival/release structure.

Both need re-initialization before reuse — the paper's solutions, *double buffering* and *sense reversal* (flip the polarity of the flag each episode instead of resetting it), are still how production barriers avoid a race between "released" and "reset".

**What libraries ship.** Open MPI's tuned component offers linear (gather-to-root + broadcast of nothing), double_ring (arrival wave and release wave travel a ring in opposite directions), recursive_doubling, bruck (= dissemination), two_proc, and tree — the same skeleton catalog as the data-moving collectives, minus the data. For barrier the choice is nearly pure α-optimization: dissemination/recursive-doubling win at scale, linear at small p.

**One semantic trap.** MPI defines barrier completion as *all processes having entered the call*. A rank that returns early is not guaranteed that every other rank has already *returned* — only that they have called it. Timing code that measures "after the barrier, everyone starts together" is therefore measuring an entry-synchronization, not an exit-synchronization. In practice ranks leave within one notification of each other, but code that *requires* exit-synchronization (for example, a rank writing a file another rank will immediately read) needs a real handshake, not a barrier.

### 1.4 Collective algorithms — the catalog (DIST-4.10)

Strip away the operation names and the last two volumes have used the same handful of communication skeletons over and over. This is the level at which libraries are actually built.

| Skeleton | Steps | Per-step bytes (per rank) | Best regime | Seen in |
|---|---|---|---|---|
| Linear / pipeline | p − 1 | n/p … | tiny p, or as a component | naive bcast, old reduce-scatter, linear barrier |
| Binomial tree | ⌈lg p⌉ | n | small messages | bcast, reduce |
| Ring | p − 1 | n/p | large messages | allgather, reduce-scatter, allreduce (ring), double-ring barrier |
| Recursive doubling / halving | lg p | n/2, n/4, … or doubling | short–medium; power-of-two p | allgather, allreduce (short), reduce-scatter, barrier |
| Bruck / dissemination | ⌈lg p⌉ | grows or shrinks by construction | tiny messages, any p | allgather, all-to-all, barrier |
| Pairwise exchange | p − 1 | 2·(n/p) | large messages | all-to-all, reduce-scatter |
| Hierarchical (two-level) | local + global + local | varies | multi-rail / multi-node reality | SMP-aware collectives, NCCL intra/inter-node |

Four cross-cutting lessons fall out of the catalog:

**The same skeleton serves many operations.** Recursive doubling appears as allgather, short-message allreduce, the barrier, and non-commutative reduce-scatter. The ring appears as long-message allgather, reduce-scatter, allreduce, and barrier. A library implements each skeleton once as a pattern of point-to-point exchanges plus per-operation "reduce here / copy here" hooks, then mixes components — which is how composition algorithms (scatter + ring-roll for bcast; reduce-scatter + allgather for allreduce) arise naturally.

**Power-of-two assumptions are everywhere, and patched the same way.** Doubling/halving schedules need p = 2^k. The universal patch — fold extra ranks into neighbors, run the clean schedule on the power-of-two subset, unfold — costs about one extra round. Bruck-style algorithms alone escape, handling any p in exactly ⌈lg p⌉ rounds at the price of a final local reordering.

**Commutativity is an algorithm license.** Recursive halving for reduce-scatter and ring allreduce both fold operands in arrival order; they are only legal because the operator commutes. A non-commutative op forces the library onto a different skeleton or a heavier one — a clean example of algebraic properties of the *application* constraining *system* choices.

**Real systems are hierarchical, so algorithms compose over hierarchy.** On a node of 8 GPUs with NVLink connected by N NICs to other nodes, "the ring" becomes: ring inside the node, ring across nodes (one hop per node), ring inside again. That two-level (or n-level) structure is what "hierarchical strategies" in this topic means, and what NCCL's intra-node/inter-node engine, Open MPI's `han` component, and MPICH's SMP-aware collectives all implement. Rank placement decides which physical ring you get — the subject of Module 12.

**Selection is a real mechanism, not a detail.** MPICH ships measured cutoffs per operation (e.g. Bruck all-to-all below 256 B/block; pairwise above 32 KB). Open MPI's `tuned` component makes this explicit and *user-controllable*: fixed decision rules, per-collective forced algorithms (choose by numeric algorithm id — barrier alone has six), or a dynamic decision file mapping (collective, communicator size, message size) → algorithm, which you can regenerate for your own fabric with benchmarking scripts. The 2007 "Tuned" paper by Fagg, Bosilca, Pješivac-Grbović, Angskun, and Dongarra is the reference for this design. NCCL exposes the same idea as `NCCL_ALGO` for overriding its automatic choice among ring/tree/NVLS-style algorithms. One operation, many algorithms, and a decision procedure — that is the architecture of every modern collective stack.

### 1.5 Collective cost models (DIST-4.11)

The catalog only answers "what exists". The cost model answers "which one, here, now". The workhorse is the α-β-γ model (Hockney-style, as used by Thakur et al.):

```
T(collective) = steps · α  +  (bytes on the critical path) · β  +  (reduction arithmetic) · γ
```

with assumptions that must be remembered because they are also the model's failure modes: any pair of ranks communicates at equal cost; links are bidirectional; each NIC can inject one message and receive one at a time (single-ported); and all ranks move in lockstep rounds. Two refinements from the MPICH work matter in practice: unidirectional costs α^uni, β^uni with ratios to bidirectional ones between 0.5 (simplex) and 1.0 (full duplex), and the treatment of γ as a per-byte cost that can be nonzero (a reduction is real arithmetic, and on GPUs it runs on the same hardware you wanted for math).

**Closed forms.** Collecting the formulas derived across this volume (n per rank unless noted):

| Collective / algorithm | Cost |
|---|---|
| Bcast, binomial tree | ⌈lg p⌉·(α + nβ) |
| Reduce, binomial tree | ⌈lg p⌉·(α + nβ + nγ) |
| Reduce, Rabenseifner (RS + gather) | 2·lg p·α + 2((p−1)/p)·nβ + ((p−1)/p)·nγ |
| Allreduce, recursive doubling (short) | lg p·α + n·lg p·β + n·lg p·γ |
| Allreduce, Rabenseifner / ring | 2·lg p·α (ring: 2(p−1)·α) + 2((p−1)/p)·nβ + ((p−1)/p)·nγ |
| Reduce-scatter, recursive halving | lg p·α + ((p−1)/p)·(nβ + nγ) |
| Reduce-scatter, pairwise/ring | (p−1)·α + ((p−1)/p)·(nβ + nγ) |
| Allgather, recursive doubling / Bruck | lg p·α + ((p−1)/p)·nβ |
| Allgather, ring | (p−1)·α + ((p−1)/p)·nβ |
| All-to-all, Bruck | lg p·α + (n/2)·lg p·β |
| All-to-all, pairwise | (p−1)·α + n·β |
| Barrier, dissemination / rec. doubling | ⌈lg p⌉·α |
| Barrier, linear | 2(p−1)·α |

**Volume lower bounds.** Several of these β-coefficients are provably minimal: rank i's reduce-scatter segment needs the other p−1 ranks' copies of that segment, so (p−1)/p·n received bytes is a floor; allgather is the same floor; allreduce is both, hence 2(p−1)/p·n. This gives the cost model a second career as a *sanity checker*: any implementation whose measured time falls below its volume bound is measuring the wrong thing.

**Crossovers are the actionable output.** Set two formulas equal and solve for n. Concretely, for all-to-all with p = 64, α = 2 μs, B = 12.5 GB/s (β = 80 ps/byte): Bruck gives 6α + 3nβ, pairwise gives 63α + nβ; equating yields n* ≈ 700 KB of per-rank volume, i.e. ~11 KB per block. MPICH's *measured* cutoffs put Bruck's ceiling near 256 B per block, with the isend/irecv schedule owning the middle. Same order, different constant — because the model's α and β are not constants: small messages pay protocol and copy overheads (an effective β several times worse), and store-and-forward touches memory twice. This is precisely why libraries ship *measured* decision functions rather than analytic ones, and why re-tuning them per fabric (Open MPI's decision files) can pay off.

**Where the model lies.** The sharpest example is already on the table: for allgather at power-of-two p, recursive doubling and ring have *identical* bandwidth terms, and doubling has lg p vs p−1 latency terms — the model says doubling always wins. Measurement on Myrinet and IBM SP clusters says the ring wins for long messages. The violated assumption is "any pair at equal cost": in a switched fabric, nearest-neighbor patterns (ring) sustain more than twice the bandwidth of distant-partner patterns (doubling), as Thakur et al. confirmed with the b_eff pattern benchmark. Distance, contention, and topology — the exact terms Module 5 adds (hop count, injection bandwidth, contention, bisection) — are first-order effects the flat model ignores. A modern corollary: NCCL's cost model includes topology-aware terms for exactly this reason.

**γ and the hardware underneath.** The γ-term quietly reshapes algorithm choice on accelerators. On CPUs, reduce arithmetic and data movement overlap poorly, so γ shows up in the critical path; on GPUs, reduction kernels are fast relative to interconnects, and on NVSwitch-based systems reductions can execute *inside the fabric* (in-network collectives), effectively removing part of both β and γ from the endpoint's critical path. That changes which skeleton wins — Module 8 (network offload) and Module 9 (NCCL) develop this.

**From cost model to benchmark column.** The cost model is not just a library internal — it is baked into the most-watched numbers in GPU communication. nccl-tests reports, alongside time and "algorithm bandwidth" (S/t), a *bus bandwidth* computed by multiplying algbw by exactly the volume coefficients above: 2(n−1)/n for allreduce, (n−1)/n for reduce-scatter and allgather. The definition exists so the number can be compared against hardware peak *regardless of rank count* — algorithm bandwidth of an allreduce falls as p grows simply because the operation moves 2(p−1)/p·n bytes per rank; bus bandwidth factors that out. When you read "NCCL allreduce at 90% of peak", the "peak" is this cost-model-normalized quantity. Reading benchmark output correctly *requires* today's topic.

## 2. Key Developments / News

### 2.1 NCCL 2.32.3 ships a new collective cost model — and a textbook demonstration of why one is needed

**What happened.** NVIDIA released NCCL v2.32.3-1 on September 17, 2026. Among its collectives-and-runtime changes: "improves Blackwell symmetric AllGather performance, resource overhead modeling and kernel selection with a new cost model," and adds "a ring-based hierarchical copy-engine AllGather implementation" selectable through `NCCL_HIER_CE_COLL_AG_RAIL_RING_ENABLE`. The same release adds initial support for the Vera Rubin platform (sm107), including rail- and plane-detection for its next-generation fabric — and states explicitly that performance-model tuning for Rubin is deferred to the next release.

**What technically changed.** Map the release onto today's topics and almost every line lands: a *cost model* (DIST-4.11) now drives Blackwell AllGather *kernel selection* — algorithm choice, in production, decided per call by a model that includes resource overhead, not just message size; a *ring-based hierarchical* AllGather on copy engines is a DIST-4.10 hierarchical skeleton running on DMA engines rather than SMs (continuing the 2.30/2.31 direction covered September 29); and rail-optimized rings (choosing the ring mapping to match multiple NIC "rails") acknowledge that the flat any-pair-at-equal-cost assumption is false on multi-rail GPU nodes — the same assumption failure the ring-vs-doubling allgather result exposed in 2005. The diagnostics additions belong to the same story: GPU-resident progress counters and a watchdog DMA mirror for diagnosing stalled collective kernels (a *progress* problem, DIST-2.7, made observable in product), plus a startup warning when the NVLink fabric's *measured* bandwidth is degraded — literally reporting a worse-than-model β at communicator initialization. The companion nccl4py 0.6.0 release adds CuTe DSL device-side reduce/copy operations over symmetric windows, extending device-initiated reduction toward the one-sided model of Module 10.

**Why it matters and what to watch.** The release is a live demonstration of this module's central claim — collective performance is an algorithm-selection problem solved by cost models, re-solved for every new fabric. Rubin arriving *without* its tuned performance model, with tuning promised next release, is the cleanest possible statement that hardware ships first and the model makes it fast. Watch: the next release's Rubin model tuning, and whether the new AllGather cost model propagates to the other collectives.

### 2.2 Träff (2024): reduce-scatter can be round-optimal *and* volume-optimal at once

**What happened.** Jesper Larsson Träff's paper "Optimal, Non-pipelined Reduce-scatter and Allreduce Algorithms" (arXiv:2410.14234, October 2024) presents an algorithm for reduce-scatter over commutative operators that finishes in ⌈log₂ p⌉ communication rounds with each processor sending, receiving, and reducing *exactly* p − 1 blocks — the minimum possible round count and the minimum possible per-processor volume, achieved simultaneously. The communication pattern is a simple ⌈log₂ p⌉-regular circulant graph, the same pattern family Bruck-style algorithms use. Combined with a standard allgather, it yields a volume-optimal allreduce; the paper also notes the construction serves as a template for round-optimal all-to-all, and maps directly onto `MPI_Reduce_scatter_block`, `MPI_Reduce_scatter`, and `MPI_Allreduce`.

**What it means, precisely.** Recursive halving (Section 1.1) already achieves the optimal volume (p−1)/p·n, but its rounds are *unbalanced*: the first round moves n/2, the last n/2^lg p, so the schedule's time is shaped by its heaviest round, and the p−1-block total is spread very unevenly. Träff's point is that a schedule exists in which every round moves the same amount and the total is still minimal — closing a gap that had simply been tolerated. Note the honest framing: this is a *research claim* of optimality within a stated model (non-pipelined, commutative operator, equal-cost links — the same assumptions as Section 1.5), not yet a measured production win; libraries adopt new algorithms only after benchmarks on real fabrics, as the MPICH and Open MPI histories show.

**Why it connects.** The paper is the cost model of DIST-4.11 doing what it is for: making a deficiency in classic algorithms *provable* and stating the target a replacement must hit. Twenty years after the MPICH collective rewrite, the α-β model is still the discovery instrument — and reduce-scatter, today's first topic, is still where the frontier is.
